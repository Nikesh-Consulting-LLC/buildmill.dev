Template Cards

A template gets a name, a short markdown description and a cover image. Admins edit them in a form; a person creating a project chooses from cards. This page shows how each surface would look and behave, and the decisions behind it.

Rendered in a system font — the app uses Geist. Colours are the app's own tokens, and the page follows your light/dark theme. Everything below is clickable where the real thing would be.

On the dev project the catalog holds Default, Generic Web App and Python + Next.JS Web App — and all three carry the same boilerplate description, because it was never shown anywhere a person would notice. Specifically:

  • The picker fetches id, name, is_default only; description is never loaded.
  • category exists on the catalog but is write-only — set at create, rendered nowhere.
  • Org copies (org_project_templates) have no category at all.
  • The org's “New custom template” is a window.prompt for the name; no description field exists on that path.
  • Neither table has an image column, and no bucket holds template images.

Mockup A — New project, choosing from cards

The same dialog, widened. Templates come first because they answer “what kind of thing is this?”; the org's default is preselected so someone who doesn't care types a name and moves on. The cards sit in a single row you slide through — three in view and the edge of a fourth — so the dialog is the same height whether the org has three templates or thirty. Real vs illustrative. The first three cards are the templates that exist on the dev catalog today, with example descriptions written the way a good short description should read (today they're identical). FastAPI service, Static marketing site and Mobile app are illustrative — they exist only to show how the grid, categories and the no-image cover behave once the catalog grows. The picker lists the org's copies, and an org sets its own default — here that's Python + Next.JS, even though the catalog's default is Default.

Default is preselected

The choice never blocks. Name gets focus on open; a person can ignore templates entirely and get what they get today.

One row, whatever the count

Three cards and the edge of a fourth — the peek says there's more. Arrows step a screenful, the wheel, a trackpad swipe or a drag slide freely, and each card snaps into place. Height is fixed, so Name and Repository never move.

Chips only when useful

Category chips appear when there are two or more categories and narrow the row; a filter box appears past six templates. With three General templates it's just the row.

No image still looks designed

A template without a cover gets a generated one — initials on a tint derived from the name — so day one, when no template has an image, the row isn't a line of broken icons.

Keyboard is a radio group

Cards are role="radio" inside a labelled group: arrow keys move the selection and slide it into view, Space picks, focus ring is the app's. Cover images are decorative (alt=""); the name is the label.

Description clamps at three lines

Inline markdown only on a card — bold, italic, code; links render as text (a link inside a radio is a trap). The full text lives on the settings page.

Copy fixed

The helper text still says “guidelines”; a project now inherits Agent Instructions plus worker instructions. Same fix in the same change.

Generated coverUp to two initials from the name (“PN”, “GW”, “D”) on one of a few tints picked by a stable hash of the name, in both themes. Pure CSS — no image is stored, so it never breaks and costs nothing.
MarkdownThe description renders through the existing MarkdownView. On cards, an inline-only variant: paragraphs collapse, headings/lists/images render as text, links become plain text; clamped to three lines. Full render on the settings/admin header and in Copy from catalog.
Image guidanceShown as a 2:1 banner with object-fit: cover; recommend 800×400. Wide-and-short reads as a banner in a row and leaves most of the card to the words. Illustrations or logos in a consistent style read better side by side than photos — the admin form says so in the hint.

Native scroll with scroll-snap per card, so wheel, trackpad, touch and drag all work without a library; prev/next buttons step one screenful and hide at the ends; a fade at each edge and page dots say where you are. Selecting a card slides it fully into view. Chips at ≥ 2 categories filter the row; a filter box appears past 6 templates. Height never depends on the count.

Assumptions carried into the story

  • A wider single-step dialog, with the row on top — not a separate page or a two-step wizard.
  • Public bucket for covers. A template cover is decorative content, not org data, so it lives in a public bucket like avatars. Keeping org-uploaded covers private would cost a signed URL per card at render (cached, like attachments).
  • An org may override the catalog's image and description on its copy — the same way every other part of a copy is editable.
  • Description stays at 2,000 with a live preview and counter rather than a hard short cap.
  • 2:1 covers. With a single row, 16:9 would fit too; 2:1 gives the words more of the card.
