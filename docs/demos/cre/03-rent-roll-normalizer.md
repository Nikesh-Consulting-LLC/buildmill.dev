# 03 · Broker rent roll & T-12 normalizer — **the live demo**

## 1. Pitch

**Tier 1 — the data platform work they're already paying for, and the one that never ends.** Every broker sends a different Excel layout. Every property-management export is a little different. Every acquisitions analyst has spent an evening re-keying a rent roll into the underwriting template. Here, a rent roll format is a **parser** — one Python module, one fixture workbook, one golden CSV — and a new deal arriving in a new format is a **story**, written in the time it takes to attach the file. This is a genuine acquisitions pain point that never stops, which makes it the argument for *standing capacity* rather than a project.

**Demo moment:** the visitor's own rent roll, attached to a work item written live in the room; a plan that comes back, gets rejected once for a real reason, comes back fixed; a PR whose tests prove the parsed totals tie to the sheet's own total row; and the cost of that one run on the screen.

## 2. Template card

- **name:** `CRE · Rent roll & T-12 normalizer (parser per format)`
- **description:** A Python package that turns any broker or PM-system rent roll (and T-12) workbook into one canonical schema, one parser per format, each pinned by a fixture and a golden CSV; a new format is a story. No credentials, no network — a workbook in, a table out.
- **category:** `Data platform`

Canonical rent-roll schema (`schema.py`): `property_name, unit_id, unit_type, tenant_name (nullable → vacant), sf, lease_start, lease_end (nullable → mtm), base_rent_monthly, rent_psf_annual (derived), escalation_pct, escalation_next_on, recovery_type, security_deposit, status (occupied|vacant|mtm|future|notice), source_row`. T-12 schema: `property_name, account, category (revenue|opex|noi|below_line), period, amount, source_cell`.

Pre-built before the meeting: everything above with the three parsers merged (each through the factory, so they have runs and PRs behind them). Backlog otherwise **empty** — this is where the visitor's artifact goes. Size ≈ 2 MB.

Each **story** adds: `rentroll/parsers/<format>.py`, registers it in `registry.py`, `fixtures/<format>/<file>.xlsx` (the attached document, copied in), `expected/<format>/<file>.csv` (the agent produces it *and the totals-tie test proves it*), and `docs/formats/<format>.md`.

## 4. Agent Instructions (paste-ready)

```markdown
## Project overview
A Python package that normalizes commercial-real-estate rent rolls and T-12 operating statements from many Excel layouts (brokers, Yardi/MRI/RealPage exports, Argus) into one canonical schema. Each layout is a parser under `rentroll/parsers/`, pinned by a fixture workbook and a golden CSV. Work items are almost always "add a parser for this workbook" — the workbook is attached to the work item as a document; copy it into `fixtures/<format>/` unchanged.

## Tech stack
Python 3.12; `openpyxl` (read cells, merged ranges, formulas as values), `pandas` for shaping, `pydantic` v2 for the canonical schema, `typer` CLI; tests with `pytest` + `hypothesis`. No network, no database, no credentials.

## Commands
- `pip install -e .[dev]`
- `python -m pytest -q` — whole suite (< 20 s)
- `rentroll parse fixtures/<format>/<file>.xlsx --format <name> --out /tmp/out.csv`
- `rentroll validate /tmp/out.csv` — schema + tie-out checks on any canonical CSV
- `python tools/make_fixtures.py` — regenerate the synthetic fixtures (only if a story says so)

## Run commands
Before you submit: `python -m pytest -q` green, including the new (fixture, expected) pair your parser adds — the golden test and the totals-tie test are parametrized over whatever is on disk, so a new fixture with no expected CSV fails loudly. Produce the golden CSV with your parser, then *read the workbook's own total row and confirm the tie by hand* before committing it. Report command, exit code and counts through the pre-submit gate.

## Testing expectations
A parser is done when: (1) its golden CSV matches exactly on identifiers and text and within 0.005 on money; (2) `sum(base_rent_monthly)` equals the sheet's stated total (and per-floor/per-building subtotals where the sheet has them); (3) required columns are non-null for occupied units, vacant units are rows with `tenant_name = null, status = vacant`, month-to-month leases have `lease_end = null, status = mtm`; (4) an unknown or missing column raises `ParseError` naming the header — never silently mis-map. Match columns by **header text** (normalized: lowercase, stripped, synonyms in `base.py`), never by position. Annual rents are converted to monthly and the decision is recorded in `docs/formats/<format>.md`.

## Environment setup
None. There are no environment variables and there must be no `.env` file.

## Things to avoid
- Don't match columns by index or by letter — layouts drift; headers are the contract.
- Don't hardcode sheet names; find the sheet by a header signature (`base.py` has helpers).
- Don't "clean" a fixture workbook — it must stay exactly as received; the parser adapts to it.
- Don't reuse an existing parser by copy-paste when a subclass with overridden `header_map` will do; but don't force a subclass when the layout is genuinely different either.
- Don't compute rent PSF from `sf` when the sheet gives it — parse it and let `validate.py` cross-check.
- Don't drop rows you don't understand. Raise, or emit them with `status = unknown` and a note, and say which in the PR.

## Permissions or boundaries
Add files under `rentroll/parsers/`, `fixtures/<new format>/`, `expected/<new format>/`, `docs/formats/`; edit `registry.py` to register. Ask via clarification before changing `schema.py`, `base.py` or `normalize.py` — those are shared by every parser. Never modify an existing fixture or golden CSV unless the story is about that format.
```

## 5. Project settings

- **Pre-submit gate command:** `python -m pytest -q`
- **Project environment:** none.
- **Automated suite:** none (the suite is the pre-submit gate; nothing needs a server).
- **Deployment:** none.
- **Gates:** `auto_approve_*` **off** — this is the project where the rejection is the show.
- **Documents:** the visitor's workbook is attached to the live work item (Documents panel on the issue) so the run context lists it and the agent reads it with `get_document`. Attach it as `.xlsx`; keep it under 25 MB.
- **Learnings pre-seeded:** "Broker OM rent rolls often merge header cells across two rows; read both rows and join with a space before matching headers." (Came out of the OM appendix parser — a real learning to point at.)

## 7. Live demo script — the reference script

*Before the meeting: pool empty; runner connected with Claude Code enabled; three parsers merged; the project's Costs and Audit already have the three stories' history.*

1. **Ask for the artifact.** "Send me one rent roll — the uglier the better." Save it as `<Property>_rent_roll.xlsx`.
2. **Create the work item, live.** Type `story`, title *Parser for the attached rent roll — `<Property>`*, paste the acceptance criterion from row 4 above and edit the format name with them. Attach the workbook in the Documents panel. Say out loud what you typed: "the totals must tie to your own total row."
3. **Dispatch the plan run.** Show it enter the pool and get claimed by the runner. Note the time. Switch to another project (#1 or #2) while it thinks — 3–6 minutes.
4. **The plan is back.** Open the review page. Read the plan aloud. It will very likely map columns by inspecting the sheet. Find the real flaw — there is always one — and **reject once**, e.g.: *"You matched columns by position (B, D, F). Match by header text with the synonym table in `base.py`, and fail loudly on any header you don't recognize — brokers move columns."* If the plan already does that, reject on the tie-out: *"Also assert the per-floor subtotals, not just the grand total."*
5. **The retry carries your comment verbatim.** Open the retry run's context and show the rejection feedback inside it. This is the moment: "every reviewer note becomes part of the next run's brief; nothing is retyped, nothing is lost."
6. **Approve the re-plan; dispatch code.** While it runs (5–10 minutes): open the Audit tab — two plan decisions already there with your name and the second; open the Costs room and show the three merged parsers' cost per story.
7. **The PR is up.** Open it: the parser, the fixture copied in unchanged, the golden CSV, the docs page. Open the review page: the pre-submit strip — `pytest`, N passed, 0 failed — including *their* file's totals-tie test. Say the total the PR states and ask them if it matches their sheet.
8. **Approve → merge.** Then the run page: tokens in/out, cost to four decimals. "That is what a new broker format costs you. Every future deal in this format is free."

If the code run fails the gate: do not hide it. Open the evidence, read the failure, send it back with a comment. A visible failure caught by the gate is a better demo than a green run.

## 8. Security / credentials answer

The project has no credentials, no network calls and no database — a workbook goes in and a CSV comes out, on the operator's own machine. The visitor's file is stored as a work-item document in the factory's private bucket, readable only by the claimed run, and it lands in the repo only because the story says to copy it in as a fixture; if they'd rather it didn't, the story says "don't commit the fixture" and the golden test is skipped for that format.

## 9. Prep & risks

- Runner box: Python 3.12, `pip install -e .[dev]` from a fresh clone, `pytest` green in < 20 s.
- Rehearse the live story **three times** with three different real-world rent rolls (find ugly ones: merged cells, totals mid-sheet, two tables on one sheet, notes rows). Note where plans go wrong; that's your rejection comment library.
- Have a fallback artifact of your own (`fixtures/samples/ugly_broker_rent_roll.xlsx`, *not* registered) in case the visitor's file is a PDF, a scan or is too big — say "we'd add a document-extraction story for PDFs; that's a second-meeting item" and use yours.
- If the workbook contains real tenant names and the room is sensitive, ask before attaching; the story can say "anonymize tenant names in the fixture."
- Time-box: if the plan run hasn't returned in 8 minutes, move to the release demo (#4) and come back — never stare at a spinner.
- The rejection must be **true**. If the plan is genuinely right, reject on a real preference and say that's what you're doing ("this is fine; I want subtotals asserted too") — the audience should see a manager exercising judgement, not theatre.
