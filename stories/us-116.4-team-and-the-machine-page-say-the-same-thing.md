# US-116.4 — Team and the machine page say the same thing

**Status:** Testing
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.2 (`worker_idle_reason` gains `no-roles` and `no-model` —
this story puts presence in front of it and makes the result the only status
anyone renders), US-10.12 (`runner_sessions` presence on the roster), US-26.7
(the SSH probe and `agent_slots.service_state`), US-27.9 ("presence is not
permission"), US-35.1 (one idle reason for Team and the fleet page)

## Story

As the manager, I want every page that shows an agent — the Team roster, the
agent's runner page, the machine page, the superadmin Machines list — to show
the **same one word** for the same agent at the same moment, and I want
"online" to mean the agent is actually there, so that "Team says online but
superadmin says stopped" cannot happen and I do not have to open a second page
to find out which one is lying.

## Design

### Two things are wrong today, and they compound

**Different questions, overlapping words.** Each surface answers its own
question with its own vocabulary:

| surface | what it shows | reads |
|---|---|---|
| Team roster (`team/page.tsx:72,146-154`; `team-view.tsx:660-696`) | `online`/`offline` pill + a health pill from incident count + the State column's idle reason | `runner_sessions.disconnected_at is null`; `runner_incidents` in the last hour; `worker_idle_reason` |
| agent runner page (`[principalId]/runner/page.tsx:145-147, 318-324`) | `online`/`offline` + `paused`/`enabled` | same session predicate; `runner_config.paused` |
| machine page slot card (`servers/[id]/host-detail.tsx:643-678`) | `Paused`/`Enabled`, `Connected`/`Not connected`, `service <state>`, `Token revoked`, `Auto-repair gave up` | `desired_state`, same session predicate, `service_state` (SSH probe, ≤5 min stale), `worker.status` |
| superadmin Machines card (`admin/machines/page.tsx:117-122`) | "N enabled agents are not running" | `desired_state = enabled and service_state in (failed, inactive)` |

None of these is false. An agent the wizard just created is **connected and
paused** — that is its designed landing state (`agent_provision.py:1906`) — so
Team says `online` (green) while the machine page says `Paused` and, until the
next probe, possibly `service inactive`. The manager reads the second as
"stopped", goes there to fix it, and concludes the two pages disagree. They do
not; they were never asked the same question.

**Presence has no expiry.** Every surface above defines "online" as
`disconnected_at is null`. That column is written in exactly two places: the
socket handler's `finally` (`runner_socket.py:310-313`, `close_runner_session`)
and supersede-on-reconnect (`db.py:1855-1862`). `last_seen_at` is heartbeated
every 30 s (`connection.py:25`, `touch_runner_session`) **and read by nothing**.
There is no sweep — migration `099_runner_sessions.sql:24-25` justifies its
partial index by "the reaper's job" and the reaper was never written; the
liveness loop (`main.py:135-198`) reaps deploy runs, suite runs, provider runs,
jobs, release preps and idle CLI sessions, and not this. So a hard stop of the
API — kill, OOM, VM reset — leaves every connected agent reading `online` on all
six surfaces until *that same agent* reconnects; if the agent is down too, the
ghost is permanent.

Prod has not hit this yet: checked 2026-08-17, no `runner_sessions` row has ever
been closed more than three minutes after its last heartbeat, because every
restart so far has been uvicorn shutting down gracefully. It is a latent fault,
and it is the reason "online" cannot be trusted as a matter of design rather
than of luck.

### One status, one resolver, every surface

`worker_idle_reason` (us-116.2's version) already answers "why is this agent not
working" for the roster and the console. This story puts **presence in front
of it** and makes the combined answer the one thing anyone renders:

```
agent_status(worker) -> { state, detail, since }
```

with `state` one of, in precedence order:

| state | when |
|---|---|
| `offline` | no live socket, or the live socket's `last_seen_at` is older than 90 s |
| `revoked` | `workers.status <> 'active'` |
| `stopped` | `runner_config.paused` — the manager (or the wizard default) paused it |
| `no-roles` | us-116.2 |
| `no-model` | us-116.2 |
| `no-grants` | as today |
| `queue-held` | as today |
| `working` | holds a running run |
| `ready` | connected, allowed, nothing to do (today's `idle`) |

`offline` sits first because nothing below it is actionable while the agent is
not there. `stopped` replaces the word `paused` in the manager's vocabulary:
"paused" read as a transient the system would lift; it is a state the manager
put the agent in and only the manager lifts (us-116.5's Stop/Start). The
machine page's `Paused`/`Enabled` badge goes; the state says it.

90 s is three missed heartbeats and the same window `requeue_stale_heartbeats`
already uses for claims (`db.py:7715`). Presence therefore becomes:

```
disconnected_at is null and last_seen_at > now() - interval '90 seconds'
```

in one place — a `live_runner_sessions` view every reader uses (the six web
sites listed above, `_wait_for_connect`, `worker_session_declares_auth`) — and
the liveness loop gains the reaper migration 099 promised: rows past the window
get `disconnected_at = now()`, so realtime subscribers see the row change and
the row itself agrees with the view. The in-process `_LIVE` map keeps gating
sockets and console attach (`is_worker_live`); it is a cache of the same fact,
never a second definition.

Batch reads: `GET /agents/idle-reasons` (org, by principal) and
`/agent-servers/{id}/slots/idle-reasons` (host, by slot) return `state` in the
same shape from the same function; nothing computes status in the browser.

### What each surface renders

One label map and one tone map, exported once (`IDLE_LABELS` grows into it):

| state | label | tone |
|---|---|---|
| offline | Offline | muted |
| revoked | Token revoked | red |
| stopped | Stopped | muted |
| no-roles | No roles checked | amber |
| no-model | No model configured | amber |
| no-grants | No project grants | amber |
| queue-held | Queue held | amber |
| working | Working | green |
| ready | Ready | green |

- **Team roster:** the `online`/`offline` pill and the State column collapse
  into one cell showing the label (and the existing detail line under it — the
  run it holds, "last seen 4 min ago", or the fix link). The health pill stays
  and keeps meaning incidents, per us-116.2.
- **Runner page header:** the same label replaces `online · paused`.
- **Machine page slot card:** the same label as the first badge. Machine-only
  facts stay as secondary badges because they are *why* — `service inactive`,
  `Auto-repair gave up`, `Not connected` when the state is Offline — but the
  first word is the same one Team shows.
- **Superadmin Machines card (and `/servers`):** "N agents not ready
  (2 stopped, 1 offline)" from the same status — a small client component on
  the card asks the host-scoped status route, the same call the slot cards
  make — instead of the probe-only "not running" count.
- **Wizard Done step:** the new agent's state, from the same call, instead of
  its own `runner_sessions` poll.

The State column's tone for `stopped` is muted, not amber: it is a choice, not
a fault.

## Acceptance criteria

1. For any agent, at any moment, the Team roster State cell, the runner page
   header, the machine page slot card's first badge and the superadmin
   Machines card's count agree — same state, same label. Verified by loading
   all four for one agent in each of `stopped`, `ready`, `working`, `offline`.
2. Presence expires: with an agent's socket left open but its heartbeats
   stopped (or the API killed with `SIGKILL` and restarted), every surface
   reads **Offline** within two minutes, and `runner_sessions.disconnected_at`
   is set by the sweep. When the agent reconnects it reads Ready without a
   page reload.
3. A paused agent reads **Stopped** everywhere — never `online` on one page and
   `Paused` on another. Its tone is muted.
4. Precedence holds as tabled: an offline revoked agent reads Offline; a
   revoked stopped agent reads Token revoked; a stopped agent with no model
   reads Stopped.
5. There is exactly one presence predicate (`live_runner_sessions`) and one
   status function; a grep for `disconnected_at` in `apps/web/src` finds no
   direct reads. The API suite pins the 90 s window and that the sweep closes
   a stale row and leaves a fresh one alone.
6. `GET /agents/idle-reasons` and the host-scoped twin return `state` for every
   agent from the same function; the web label/tone maps are covered by
   `npm run test:web` for every state.
7. The superadmin Machines card says "N agents not ready" with the breakdown,
   from the same status — the probe-only "not running" count is gone (the
   probe's `service_state` still shows on the slot card as a secondary badge).
8. `cd apps/api && python -m pytest` and `npm run test:web` cover the above.

## Out of scope

- **Starting or stopping anything.** This story only makes the pages agree
  about what is; us-116.5 is the button.
- **A second presence channel** (HTTP `workers.last_seen_at`, used by the
  Workbench's 5-minute "online" filter). It stays as it is; the socket window
  is the one this story fixes. Folding the two is a later, separate decision.
- **The health pill.** Incidents stay incidents (us-116.2's reasoning).
- **Deploys bouncing every socket** (~20 prod deploys on 2026-08-16/17, each
  reconnecting within 30 s). Expected, under the 90 s window, and not worth a
  zero-downtime deploy's complexity for now.
