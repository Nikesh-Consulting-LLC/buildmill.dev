# US-99.3 — Project conventions become Guidelines.md

**Status:** Completed
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-99.2 (`AGENTS.md` is the index and is written whole)

## Story

As the manager, two different things in this factory are called "guidelines",
and once instructions become files the collision stops being merely
confusing and starts being a naming decision I cannot avoid. There is the
project's **conventions** — the ordered markdown sections in
`project_guidelines` ([009_project_guidelines.sql](../infra/supabase/migrations/009_project_guidelines.sql)),
assembled by `assemble_project_guidelines` and, today, poured into the
`AGENTS.md` block. And there is the **`guidelines` run kind** — the
instruction that steers an agent doing a guidelines-refresh run.

`Guidelines.md` means the conventions, because that is what any agent
opening the file will assume it means. The refresh run's instruction gets
`Guidelines_Refresh.md` (us-99.1), so the two never share a name.

With `AGENTS.md` reduced to the single instruction markdown plus its index
(us-99.2), the conventions need a home of their own — and a file is a better
home than an inlined block. They become reviewable as a diff, and the
refresh flow that already proposes changes to them starts proposing changes
to something a human can read in the repository.

## Acceptance criteria

- **AC1 — conventions publish to `.buildmill/Guidelines.md`.** The output of
  `assemble_project_guidelines` — unchanged, same renderer — is written to
  `.buildmill/Guidelines.md` instead of being inlined into `AGENTS.md`.
  `AGENTS.md`'s index references it with the same one-line treatment every
  other file gets. A project with no guidelines writes no file, and
  `AGENTS.md` says so rather than referencing a file that is not there.

- **AC2 — the section machinery is untouched.** `project_guidelines`, its
  catalog of section keys, `sort_order`, the `custom` exception, and
  `assemble_project_guidelines`
  ([084_guidelines_dedupe_heading.sql](../infra/supabase/migrations/084_guidelines_dedupe_heading.sql))
  all keep their current shape. Only the destination of the assembled
  markdown moves. No migration is required for this story.

- **AC3 — the refresh loop still closes.** `submit_guidelines_refresh` and
  `recommend_guideline_change`
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L3724, L3242) keep
  writing sections to `project_guidelines`; an accepted refresh marks the
  project's instruction content as unpublished (us-99.4) so the new
  conventions reach the repository the next time the manager publishes.

- **AC4 — `get_project_guidelines` keeps answering.** The MCP tool
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L2866) returns the same
  assembled markdown it does today, and the guidelines REST endpoint is
  unchanged — an agent that asks for conventions rather than reading the
  file still gets them, which is what makes us-99.5's fallback possible.

- **AC5 — the `guidelines` run kind is unambiguous everywhere it appears.**
  In the instruction editor, in `run-kinds.ts`, and in the file map, the
  refresh instruction reads as the refresh instruction — named so no manager
  editing it believes they are editing their project's conventions.

- **AC6 — tests.** Essential: AC1's file content matches
  `assemble_project_guidelines` byte for byte; the no-guidelines case writes
  nothing and the index omits it; AC3's unpublished-marking; and the AC4
  endpoints answering unchanged. `npm run build` green.

## Verified (2026-08-15)

- The assembled output of `assemble_project_guidelines` writes to
  `.buildmill/Guidelines.md` instead of being inlined into `AGENTS.md`, which
  references it under "Project conventions". Pinned by
  `test_save_instructions_writes_both_files_in_one_commit`: the conventions
  text is **in** `Guidelines.md` and **not in** `AGENTS.md`.
- **AC2** — `project_guidelines`, its section catalog and
  `assemble_project_guidelines` are untouched; only the destination moved. No
  migration needed.
- **AC5** — the naming collision is closed at the source: `Guidelines.md` is
  the conventions, `Guidelines_Refresh.md` the refresh run's instruction
  (us-99.1), and a test asserts the two can never share a filename.
- A project with no guidelines writes no conventions file, and `AGENTS.md`
  omits the section rather than pointing at a file that is not there.
- api Essential green (**1748 passed, 545 skipped, 0 failed**).

### Gaps

- **AC3 is not built.** An accepted guidelines refresh does not mark the
  project as having unpublished changes — that hook belongs with us-99.4's
  badge, which is also not built.
- **AC4** — `get_project_guidelines` and the REST endpoint are untouched so
  they still answer, but were not separately re-tested.

## Out of scope

- Changing what a project's conventions *say*, or the catalog of section
  keys.
- Merging `project_guidelines` into the instruction-file model. Conventions
  stay section-structured in the database — the sections are what the
  refresh flow reasons about — and only their published form is a file.
- Learnings (`project_learnings`). They are assembled and snapshotted into
  `input_context` and are not published to the repository; that stays true.
- The `Guidelines_Refresh.md` file's content — it is just the `guidelines`
  instruction kind, published by us-99.2 like every other kind.
