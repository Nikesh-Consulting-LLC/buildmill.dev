# US-86.1 — Routing is two checkboxes; execution is always serial

**Status:** Testing
**Phase:** 86 — Routing, simplified
**Depends on:** migrations 230/234/235 (sequential_only, build_mode, issue_hold_reason), migration 129 (batch dispatch + serial drain), migration 139 (feature-owned code run), us-85.2 (ordered batch dispatch)

## Story

As the manager, a project's Task processing card offers exactly two
switches, and neither of them is about concurrency:

1. **"Follow the build order (Epic → Feature → Story)"** — checked (the
   default), items dispatch in hierarchy order: an item whose predecessors
   in the sequence aren't done yet waits, exactly as feature/epic ordering
   holds work today. Unchecked, routing is free: I may dispatch any story,
   any feature, in any epic, in any order I choose — the switch frees the
   ORDER only, never the serial law below.
2. **"Route the feature as one"** — checked, a feature's stories travel
   together: one action plans them all (queued at once, worked one at a
   time), one action codes them all (the existing feature-owned single run
   → one PR), and the per-story route buttons disappear — the feature's
   header carries the only route actions. Unchecked, stories carry their
   own buttons and route individually.

The **Concurrency section is gone**. `sequential_only`'s project-wide
dispatch freeze — where one story sitting at `planned` blocked every other
item in the project from even *dispatching* (the 2026-08-12 bottleneck) —
is deleted, not defaulted off. In its place, one law that is not a setting:
**a project works one item at a time, start to merge.** The routing unit —
a story, or the whole feature when switch 2 is on — owns the project from
its first claimed run until its work merges: no other item starts while it
is being planned, while its plan awaits my approval, while it is being
built, or while its PR sits unmerged. I dispatch and queue freely at any
time; everything queued behind the item in progress waits visibly, wearing
an hourglass with the reason, never a refused button or one that has
vanished. Seriality moves from dispatch time (where it stalled queueing
and hid why) to claim time (where it protects the shared workspace and
unpinned branch bases, and can be *seen*).

## Semantics pinned

- **Serial is per project, not per org.** Two projects still run in
  parallel across the fleet; within one project the law holds. The
  existing same-feature rule (c) is subsumed by this wider rule.
- **The unit is exclusive, start to merge.** A run is claimable only when
  no *other* unit of the project is in progress — where "in progress"
  spans the unit's whole journey: a run claimed or running, a plan sitting
  in review, an unmerged PR (`in-review`/`needs-fixes`). The unit in
  progress frees the project only at `merged` (or by failing/being
  abandoned). Its OWN follow-up runs are always claimable — the re-plan
  after a send-back, the code run after plan approval ARE the item in
  progress, and holding them would deadlock it.
- **Within a feature unit, stories are one journey.** With switch 2 on,
  the feature is the unit: its sibling stories' plan runs drain one at a
  time (one run executes at once, always) but never gate on each other's
  approvals — plan review inside the unit happens in parallel with the
  next sibling's plan run, exactly as the batch pipeline behaves today —
  and the code phase is the one feature-owned run and one PR. My own
  actions (approving plans, reviewing the PR, merging) are never blocked
  by anything.
- **Queue order.** With switch 1 on, the executable order is the build
  order (epic → item → sub number, nulls last — us-85.2's key). With
  switch 1 off, it is dispatch order (run `created_at`). The pool offers
  the project's runs one at a time in that order; everything else in the
  project shows a hold reason naming what it is waiting on.
- **Switch 2 changes the unit, never the engine.** Feature-at-once uses the
  existing `dispatch_feature_batch` (plans) and feature-owned code run
  (one PR, migration 139). Off = today's story-mode shape. The old
  three-way `build_mode` and its epic variant retire; an epic is ordering
  (switch 1), not a routing unit.
- **Free routing is the manager's risk, said out loud.** With switch 1 off,
  coding item B before item A merges can conflict at merge (bases aren't
  pinned). The card says so under the unchecked box; the system does not
  forbid it.

## Acceptance criteria

- **AC1 — the card.** The Task processing card shows the two checkboxes
  with the copy above and nothing else about ordering or concurrency; the
  build-mode radio and the "Sequential (one story at a time)" checkbox are
  gone. Both new switches default ON for new projects.
- **AC2 — dispatch freedom.** With any item of the project in flight
  (`planning` → `in-review`), other items still dispatch successfully in
  every legal state — the `must reach merged` refusal no longer exists
  anywhere (SQL, API, UI copy).
- **AC3 — one item, start to merge.** Queue three items in one project:
  only the first is offered to agents. While it is being planned, sitting
  in plan review, being built, or holding an unmerged PR, the other two
  stay held — and become claimable only after it merges (or fails / is
  abandoned). The item's own follow-up runs flow throughout. My own
  actions — approving a plan, reviewing, merging — are never held. A
  second project's items are offered concurrently the whole time.
- **AC4 — order under switch 1.** Switch 1 decides only WHICH queued unit
  goes next: on = build order (an item whose predecessor feature/epic
  isn't `done` also shows the existing "waiting on an earlier …" hold);
  off = dispatch order, hierarchy holds dropped. The exclusivity law of
  AC3 applies identically in both positions.
- **AC5 — feature-at-once.** Switch 2 on: story rows show no route buttons
  anywhere (work-item page, hub, dashboard Dispatch group); the feature
  header carries Plan all / Code all, wired to the existing batch endpoints.
  The feature is the unit AC3 serializes — its sibling plan runs drain one
  at a time internally without gating on each other's approvals, and the
  code phase is the one feature-owned run and one PR. Switch 2 off: story
  buttons return; the feature-owned code run is not forced. Flipping the
  switch mid-feature never strands work: whatever is already queued or
  running finishes under the rules it started with.
- **AC5b — one git write per batch, not per story.** A feature-at-once
  batch action performs the project-repo writes (docs/factory tree +
  instruction-file sync) once for the whole batch — one commit — instead
  of once per story. Same for batch plan approval. The tree's content is
  identical to what N per-story syncs would have left.
- **AC5c — the hourglass, everywhere.** Every held item on every surface —
  dashboard Waiting-on-you rows, the Work items hub, and the story/feature
  page's own route buttons — shows the US-74.5 hourglass with the hold
  reason in words ("waiting: <ITEM> is being built", "… awaiting plan
  approval", "… PR not merged yet"). A hold never hides a button (only
  switch 2 does that) and never lets a click reach a server refusal.
- **AC6 — migration of existing projects.** `build_mode` feature/epic →
  both switches on; `build_mode` story → switch 1 on, switch 2 off;
  `sequential_only` is dropped without replacement (its projects get the
  serial-execution rule like everyone else). The mapping is recorded in the
  migration header; `issue_hold_reason` / `issue_dispatch_refusal` /
  `feature_dispatch_phase` and the pool predicates are rewritten to the
  two-switch model in the same migration, so SQL, API, and UI can never
  disagree mid-deploy.
- **AC7 — the trouble rule survives.** A sibling in trouble
  (`issue_in_trouble`) still pauses healthy work under switch 1 and still
  exempts its own remediation run, as today.

## Out of scope

- Concurrent execution within a project (pinned bases / stacked branches) —
  explicitly rejected: the system is serial, no matter what.
- Changing what a feature-owned code run produces (still one branch, one
  PR).
- Org-wide or agent-count-aware scheduling changes.
- Backfilling or re-ordering runs already queued at deploy time.
