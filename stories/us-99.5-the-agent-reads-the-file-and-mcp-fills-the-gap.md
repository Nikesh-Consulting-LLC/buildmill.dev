# US-99.5 — The agent reads the file, and MCP fills the gap

**Status:** New
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-99.2, us-99.4 (files are published, and can be behind)

## Story

As an agent, my instructions arrive twice once this phase lands: as prose
inside `get_work_context`, and as a file in the workspace I already hold.
Two copies of the same text is not redundancy, it is a question — which one
governs when they differ, and they *will* differ, because a manager can save
an instruction and not publish it (us-99.4).

The file governs. That is the point of moving them there: the repository is
what an agent works in, what a human reads, and what carries the instruction
alongside the code it describes. So `get_work_context` stops carrying the
prose and starts naming the file — a pointer, not a payload, which also
takes a large block of text out of every context payload the factory sends.

But a pointer to a file that is not there is worse than the prose was. A
project whose manager has never published, a repository where somebody
deleted `.buildmill/`, a workspace fetched before the publish landed — in
each case the agent must still be able to get its instruction. So MCP keeps
serving the content, as the fallback rather than the default: ask for it by
kind, get the current text from the database, and carry on.

## Acceptance criteria

- **AC1 — the context names the file.** `get_work_context` renders, in place
  of the instruction prose, the path of the `.buildmill/` file for the run's
  resolved kind — resolved through `instruction_kind_for` exactly as today
  ([db.py](../apps/api/app/db.py) L9052-9080), so type differentiation is
  unchanged — together with the instruction to read it first, and the name
  of the fallback tool for when it is missing. The structured mirror carries
  the path as data.

- **AC2 — a tool serves the content.** A new MCP tool returns the current
  resolved content for an instruction kind, given a claimed run (kind
  implied) or a project and a kind. It answers from the database — the same
  four-level resolution chain that ends at `baked_worker_instruction` — so
  it is correct whether or not anything was ever published, and whether or
  not the published copy is current. It is read-only, needs no claim beyond
  what the caller already holds, and is added to `test_all_tools_listed`
  and `_READ_ONLY_TOOLS`
  ([test_factory_mcp.py](../apps/api/tests/test_factory_mcp.py) L82, L117).

- **AC3 — the per-item instruction set survives, and layers on top.**
  `get_instructions(run_id)` keeps returning `issues.instruction_set`
  ([053_instruction_set.sql](../infra/supabase/migrations/053_instruction_set.sql))
  verbatim, with no claim required, exactly as today. A work item whose
  instruction set a manager has edited still governs that item — the file is
  the project's default, the instruction set is this item's contract, and
  the context says which is which so an agent holding both knows the order.

- **AC4 — the fallback is instructed, not inferred.** The `merge`-and-every-
  other-kind default text and the server `instructions` blob
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L95-183) both state the
  rule: read `.buildmill/<File>.md` from the workspace; if it is absent, call
  the fallback tool; never proceed on neither.

- **AC5 — nothing is silently instruction-less.** A run whose file is
  missing and whose fallback returns blank is a named condition the agent
  reports, not something it works around. Blank-content → factory-default
  semantics in `worker_instruction_for` are untouched, so "blank" here means
  the whole chain resolved to nothing.

- **AC6 — the payload gets smaller, measurably.** The instruction prose
  leaving `get_work_context` is a real reduction in every dispatched
  context; the story records the before and after for one representative run
  of each kind.

- **AC7 — documented and pinned.**
  [interface-catalog.md](../docs/application/interface-catalog.md) gains the
  new tool and corrects its standing drift: it claims `factory_mcp.py`
  defines **36** tools when it defines **51**, still lists the removed
  `submit_release_run`, and omits `get_environment`, `submit_elaboration`,
  `submit_guidelines_refresh`, `report_spec_map`, `report_test_evidence`,
  `acknowledge_stop`, `record_trace`, `claim_release_prep_work`,
  `list_factory_queue`, `get_project_tree`, `read_project_file` and
  `get_project_workspace`.

- **AC8 — tests.** Essential: AC1's pointer replacing prose for each kind;
  AC2's resolution including the never-published project; AC3's layering;
  and AC5's named blank condition. Runner suite green — `cli_base.py`
  deliberately contributes no task prose and must keep contributing none.

## Out of scope

- Retiring `issues.instruction_set` (AC3 keeps it deliberately).
- Reading instruction files from anywhere but the default branch's published
  state — us-99.4 fixed the branch, and this story does not widen it.
- Verifying that the file in the workspace matches the database. The agent
  is told to prefer the file; the factory does not police the difference.
- Changing `get_project_guidelines` or `get_project_learnings`, which keep
  serving conventions and learnings as they do today.
