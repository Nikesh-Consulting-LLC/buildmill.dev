# US-116.8 — The fleet says when it goes dark, and says a standing fault once

**Status:** Testing
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.4 (presence with an expiry — "live" is defined once),
US-26.7 (`raise_service_incident`, once per hour), US-27.9 (the revoked-token
alarm), US-79.8 (Agent failures / System issues consoles), US-9.12 / US-91.15
(`notify_org_managers` and the per-type notification renderer)

## Story

As the manager, I want to be told, once, when **all** my agents go dark at the
same time — and to be told a standing fault once per episode rather than once
an hour — so that a fleet-wide outage is a message in my inbox instead of a
grey roster I happen to look at, and so that the one alarm that matters is not
buried under four hundred copies of a fact I already know.

## Design

### An outage nobody was told about

On 2026-08-17, from 11:49 to 12:57 UTC, every agent on Pod-001 was offline —
migration 279 had dropped a column that `get_worker_by_token` still selected,
so every socket hello and every pool poll failed (`app_issues`: 8,023
`UndefinedColumn` occurrences across two fingerprints in those 68 minutes;
fixed by `cd24e18`). During that time:

- the Team roster showed six grey `offline` pills to anyone who opened it;
- the machine page showed six `Not connected` badges to anyone who opened it;
- nobody was notified. `notifications` has no row for it. The System issues
  console had two rows with occurrence counts in the thousands, which is the
  crash-report view of the same fact, not the fleet view.

The signal was unambiguous — six agents that had been live for hours dropped
inside the same second and none came back — and no code looks for it.

### The alarm that fires every hour

`raise_service_incident` (`agent_provision.py:1436-1459`) is documented as
"once per transition, not once per probe" and is implemented as **once per
hour** per worker and kind. A revoked worker left bound to its slot is
re-alarmed on the hour, every hour, and `notify_org_managers` fires with it
(`:2375-2386`). Fourteen days of prod: **429** `agent-token` incidents; one
agent (Sandy's Claude Releaser, revoked, slot kept) accounts for 118 over five
days, i.e. 118 identical notifications for one condition nobody had changed.
Meanwhile the roster's State column already says *Token revoked* continuously
(us-116.4 keeps that), so the repetition carries no information.

### Two rules

**Fleet-dark.** On the liveness loop, per org and per machine: if the set of
live agents (us-116.4's presence) was non-empty and has been **empty for more
than two minutes**, raise once — a notification to the org's managers
(*"All 6 agents went offline at 11:49 UTC and have not reconnected"*) and one
System issue for the platform admin naming the org(s) and machine(s) — and
record when the fleet came back on the same issue. Two minutes is above any
deploy bounce (measured ≤ 30 s reconnect, 20 deploys on 2026-08-16/17) and the
90 s presence window, so a release never pages anyone. Partial loss (some
agents down) is not this alarm — those agents read Offline on the roster and
their own service incidents cover them.

**A standing fault, once per episode.** `raise_service_incident` dedupes on the
*episode*, not the hour: an incident of a kind is raised for a worker only if
the most recent incident of that kind for it has been **cleared** — by a probe
that found the condition gone (`service_state = active` for `agent-service`,
`workers.status = active` for `agent-token`) — or there is none. The clear is
recorded on the incident row (`cleared_at`), so the console can show
open-since / cleared-at instead of a list of duplicates. Notifications follow
the same rule. Nothing is lost: the state (us-116.4) shows the fault for as
long as it lasts; the incident marks when it started and when it stopped.

## Acceptance criteria

1. With every agent in an org held offline for three minutes (stop their
   heartbeats or their services), the org's managers receive **exactly one**
   notification naming the count and time, and exactly one System issue exists
   for it. When the agents reconnect, the issue records the return time and no
   second notification is sent.
2. Every agent offline for 60 s and back (a deploy bounce) produces nothing.
3. Some agents offline, others live, produces no fleet-dark alarm.
4. A revoked agent left bound to its slot for 24 h produces one `agent-token`
   incident and one notification. Re-issue its token and let the probe see it
   active: the incident gains `cleared_at`. Revoke it again: a new incident.
5. The same for `agent-service`: a unit that stays `failed` across six probes
   is one incident with one notification, cleared when a probe finds it active.
6. The Agent failures / runner incidents console shows open-since and cleared
   for these kinds instead of repeated rows.
7. `cd apps/api && python -m pytest --full` (the sweep talks to Postgres)
   covers: fleet-dark after the window, not before, not on partial loss, not
   twice; episode dedupe with clear and re-raise. Essential covers the pure
   decision functions.

## Out of scope

- **A generic alerting framework** (thresholds, channels, escalation). Two
  rules, in the loop that already runs.
- **Alerting on a single agent going offline.** The roster says Offline; the
  auto-repair ladder acts; a manager who wants a page per agent is asking for
  a different product.
- **Zero-downtime deploys.** The two-minute window makes them unnecessary for
  this story's purpose.
