# US-87.10 — A page load has a budget

**Status:** New
**Phase:** 87 — The app gets fast
**Depends on:** us-87.1 … us-87.9 (this measures what they fix)

## Story

As the operator, this phase exists because performance decayed invisibly for
months. Every regression in it was introduced by a reasonable change: a
badge that needed a count, a filter that needed a body, a subscription that
needed to be live. Nothing failed. It just got slower, and nobody was
holding a number.

The instrumentation already exists — `api_request_log` (US-62.8) records
route, duration and database time per request, and `client_perf_events`
records web vitals per page load. Nothing reads them as a gate.

Without a budget, Phase 87 is a one-time cleanup that decays the same way.

## Acceptance criteria

- **AC1 — a seeded scale fixture exists.** A repeatable script seeds a dev
  workspace with **100 projects, 5,000 work items, 500 runs** and
  proportional epics, comments and events. It is the standard against which
  "fast" is claimed, and it is committed, not improvised per-measurement.
- **AC2 — the numbers are published.** A performance page (admin-only, or a
  documented query set) reports p50/p95 server render time and database time
  for the app's main surfaces — Things to Do, Work Items, a work-item
  detail, Factory Queue, Projects — read from `api_request_log` and
  `client_perf_events` rather than from a synthetic benchmark.
- **AC3 — budgets are stated per surface.** Each surface carries a target
  the manager approves (a starting proposal: p95 server render under 800 ms
  and under 12 database round trips at the AC1 fixture size). The targets
  live in `APPLICATION.md` beside the surfaces they govern.
- **AC4 — breaching is visible.** A surface over its budget shows up
  somewhere the manager already looks — a Things to Do card or an admin
  banner — naming the surface and its measured number. Silent decay is the
  thing this story exists to prevent.
- **AC5 — the round-trip count is checkable in a test.** A test asserts the
  database round-trip count for the app shell and for `/issues` at fixture
  size, so a future change that reintroduces a per-navigation `loadWaiting`
  fails rather than merely slows. This is the regression guard for us-87.1.
- **AC6 — the phase reports its result.** The story records the measured
  before (from this analysis, [docs/performance-analysis-2026-08-12.md](../docs/performance-analysis-2026-08-12.md))
  and after for each headline number: Realtime's share of database time,
  shell round trips per navigation, `/issues` payload size, API connection
  churn, worker heartbeat writes.

## Out of scope

- A CI performance gate — testing is local by decision in this project, and
  there is no CI test workflow to hang it on.
- Third-party APM.
- Load testing concurrent users; this story measures a single manager's
  experience at scale of *data*, which is the reported problem.
