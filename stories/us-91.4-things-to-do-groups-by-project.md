# US-91.4 — Dispatch groups by project, and a project folds away

**Status:** Completed
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** [us-91.2](us-91.2-dispatch-opens-with-what-is-already-running.md) (groups both of that tab's sections)

## Story

As the manager, I run several projects at once, and the Dispatch tab is a
flat list across all of them. So a morning's work — "clear everything
waiting on Build Mill, then look at the other two" — means reading a project
name on every row and mentally filtering, on a list that can be forty rows
long.

Group both sections of the tab by project, and let me collapse a project I
am not working on. The global project filter already decides *which*
projects are in play; this decides how much of each one I want on screen
right now.

## Acceptance criteria

- **AC1 — both sections group.** In Progress (us-91.2) and the action rows
  below it each render under project headers. The two sections keep
  independent collapse state — folding a project in one does not fold it in
  the other, because they answer different questions.
- **AC2 — the header names the project and counts its rows.** Project name,
  the number of rows inside, and a chevron that rotates on expand, matching
  the disclosure pattern the factory table already uses for agent notes.
- **AC3 — collapse hides rows, never facts.** A collapsed project still
  shows its count in the header, and its items are still counted in the
  section heading and the tab badge. Collapsing is a view state, not a
  filter — the numbers must not move when I fold something away.
- **AC4 — expanded by default, and it remembers.** Every project starts
  expanded. What I collapse survives a page refresh and the dashboard's own
  `router.refresh()` after a dispatch, stored per section in `localStorage`
  beside the existing dashboard preferences.
- **AC5 — one project renders flat.** When every row in a section belongs
  to the same project, no grouping chrome is drawn at all — the same rule
  `nestAgentItems` already applies to a feature owning a single row. A
  single-project workspace must not pay for a feature it cannot use.
- **AC6 — grouping composes with feature nesting.** Inside a project group,
  the existing feature header nesting (us-24.1/24.2) still applies to the
  action rows, and a feature-owned build is still one row (us-86.2). Project
  → feature → story, and every item still appears exactly once.
- **AC7 — the factory rows learn their project's name.**
  [data.ts](../apps/web/src/app/(app)/dashboard/data.ts)'s `AgentItem`
  carries `projectId` only; add the name from the projects the page already
  loads — no extra query (us-87.1).
- **AC8 — projects appear in a stable order.** The same order the global
  project filter lists them in, so the tab does not reshuffle between loads.

## Out of scope

- Grouping the **In the factory**, **Completed** or **Releases** tabs.
- A "collapse all / expand all" control.
- Any change to the global project filter, or to which projects are in
  scope.
- Sorting rows within a project — they keep their current order (build
  order / age as each group defines it today).

## Verified (2026-08-14, localhost against build-mill-dev)

- Both sections group by project: `Build Mill (4)` and `Demo (7)` as the outer
  level, with the existing action groups (Triage, Reviews, Fix & retry) nested
  inside them.
- Collapsing `Build Mill` removed its five rows (header + four items) and
  flipped `aria-expanded`; **the Dispatch tab count stayed 11** — collapsing is
  a view state, never a filter.
- The choice persisted to `localStorage` under
  `dashboard.dispatch.collapsedProjects` (In Progress keeps its own key).
