# US-85.1 — Prepare Agent Workspace on demand

**Status:** Completed
**Phase:** 85 — Agent readiness
**Depends on:** worker_capabilities (Project access, migration 199), agent_server_jobs (machine job pattern), Phase 57 platform machines, Phase 83 session engine

## Story

As the manager, on an agent's **Project access** list, each granted project row
offers a **Prepare Agent Workspace** action. Clicking it opens a popup and starts
a background job on the agent's runner that makes the agent's working directory
for that project fully ready for work — so that when I later dispatch a task to
this agent, the workspace already exists, holds the latest code, and every
configured tool works, instead of the first run burning its session discovering
a broken environment (US-2.8.1: 26 minutes and $3.92 spent probing a missing
shell and unreachable MCP before a single planning token was useful).

## The job's steps

The popup shows the steps as a checklist, each moving pending → running → ok /
failed, streamed live while the runner works:

1. **Invoke agent** — reach the agent's runner over the control socket; confirm
   the slot is connected and idle enough to prepare.
2. **Prepare working directory** — create (or reuse) the per-project workspace
   directory for this agent.
3. **Fetch latest code** — clone or update the project to the current default
   branch head through the factory git remote; record the commit it landed on.
4. **Configure agent settings** — write the workspace-level agent config
   (working directory, factory MCP endpoint + fresh worker token, module
   config files).
5. **Install / configure MCP servers** — materialize the MCP server
   configuration the agent's module will load.
6. **Register tool servers** — take the org's enabled Tool servers
   (Settings → Tool servers) that this agent's presets grant, and register
   them in the agent's tool configuration; report each server registered.
7. **Check configuration** — verify the pieces just written actually work from
   inside the agent's environment: shell executes, git answers, factory MCP
   answers an authenticated call, each registered tool server answers its
   handshake/validation.
8. **Check agent settings** — resolve the agent's run settings (model/LLM
   route, effort, max_turns, billing) exactly as a run would, and report what
   resolved — including any setting the module cannot accept (undeliverable
   knobs are listed, not silently dropped).

## Acceptance criteria

- **AC1 — the button.** Every project row in an agent's Project access section
  (Team roster expanded row, agents only) shows a "Prepare workspace" action.
  It is disabled with an explanatory tooltip when the agent has no connected
  runner session.
- **AC2 — the popup.** Clicking opens a dialog titled with the agent and
  project names, listing the eight steps above by name. Each step shows a
  status icon (pending / spinner / check / cross) and a one-line detail once
  it has run (e.g. the commit fetched, the count of tool servers registered).
  Steps display as a vertical checklist, not a log dump; each step's detail
  line carries the specifics.
- **AC3 — background, not modal-blocking.** The job runs server-side
  (a `workspace_prep_jobs` row, migration 246); closing the popup does
  not cancel it, and reopening (button shows "Preparing…" while a job is
  queued/running) reattaches to the live job. Progress arrives by realtime on
  the job row — no manual refresh.
- **AC4 — honest outcome.** The job ends `succeeded` only when every step
  passed. A failed step marks the job `failed`, later steps stay `pending`
  (not run), and the failing step's detail names the actual error (e.g.
  "bash not found at /usr/bin/bash"). The popup's terminal state says
  "Workspace ready" or "Preparation failed at step N — <reason>".
- **AC5 — durable result.** The prepared state is recorded on the
  worker/project pair (prepared commit, finished_at, job id), and the Project
  access row shows a small "Prepared <relative time>" caption when the last
  preparation succeeded; a failed last attempt shows "Preparation failed".
- **AC6 — one at a time.** A second click while a prepare job for the same
  (agent, project) is queued/running answers 409 and the UI reattaches to the
  running job instead of starting another. Preparing must not disturb a run
  in progress on that agent: dispatch answers 409 `agent busy` semantics in
  reverse — a busy agent refuses prepare.
- **AC7 — org scoping.** The endpoint requires manager capability on the org;
  the job row, its log, and the prepared-state record are org-scoped under
  RLS like every other table.

## Out of scope

- Automatic preparation (on grant, on schedule, or before dispatch) — this
  story is the manual button only; auto-warm is a follow-up.
- Preparing human (non-agent) principals' environments.
- Changing what a run does at claim time — runs still prepare their own
  workspace if needed; a prepared directory only makes that a fast no-op.
- Per-project tool-server overrides (grants remain preset-scoped).
- Fixing the fleet defects US-2.8.1 exposed (broken shell path, stale MCP
  token, undeliverable knobs) — those are separate fixes; this story's step 7
  merely *detects* them.

**Design note:** token-bearing config files (`.factory-mcp.json`,
`.grok/config.toml`) are written, verified, and then removed — the
mcpconfig security rule (a worker token never outlives the work that needed

run-scoped grants anyway. "Directory ready" = clone + workspace state +
proven-working environment.
