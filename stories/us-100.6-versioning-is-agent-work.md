# US-100.6 — Versioning is agent work

**Status:** New
**Phase:** 100 — One document, not twenty-two sections
**Depends on:** us-100.1 (the versioning instructions live in the document)

## Story

As the manager, versioning is currently something the factory does *to* a
release rather than something an agent does. The scheme is computed —
`YYYY.MM.DD.N`, the date plus a same-day counter — and
[CLAUDE.md](../CLAUDE.md) states the rule flatly: *"The factory computes the
version — you never hand-pick one mid-flight."* An agent reads the version
off the release; it never decides one.

That was the right call when versioning was arithmetic. It stops being the
right call once the versioning rules live in the Agent Instructions
(us-100.1), because then the project has *written down* how it wants to be
versioned — and the one participant who reads that document is not allowed
to act on it. A project that wants semantic versioning, or a train, or a
different counter, can now say so in a place every agent reads, and nothing
will honour it.

So versioning becomes agent work: an agent reads the project's Agent
Instructions, proposes the version and the reasoning, and the manager
approves it at the gate that already exists.

## Acceptance criteria

- **AC1 — an agent proposes the version.** At release cut, an agent reads the
  project's Agent Instructions and proposes a version string with its
  reasoning — which rules it applied and why this is the next version. The
  proposal is data on the release, not a fait accompli.

- **AC2 — the manager still decides.** The existing manager override at cut
  stands: the proposal is a default that can be replaced, and once cut the
  version is fixed and read-only, exactly as
  [CLAUDE.md](../CLAUDE.md) already requires. Nothing here lets a version
  change mid-flight.

- **AC3 — `YYYY.MM.DD.N` remains the fallback.** A project whose Agent
  Instructions say nothing about versioning gets today's computed scheme, and
  a proposal that is unparseable or collides with an existing version is
  refused with the computed one offered instead. **The factory never ships a
  release with no version because an agent had an opinion.**

- **AC4 — the run kind.** This work needs a home: either the existing
  `release` kind gains the proposal step, or a new kind is created for it.
  **Recommendation: extend `release`.** It already reads the commit range,
  writes the notes and deploys to UAT — versioning is the same job at the
  same moment, and a separate kind would mean a second dispatch, a second
  claim and a second lease for one string. If a new kind is created instead,
  it must go through the full us-98.1 checklist (`runs_kind_check`,
  `HANDBACK_SHAPE`, `ROUTE_KINDS`, `run-kinds.ts`, the file map, the editor)
  — a kind the runner has never heard of sits `queued` forever, which has
  shipped three times.

- **AC5 — the reasoning is kept.** The version's rationale is recorded on the
  release beside the version, so "why is this 2026.08.15.2 and not 2.1.0" has
  an answer six months later without reading a run trace.

- **AC6 — CLAUDE.md is corrected.** Its Versioning & Release section states
  the never-hand-pick rule as absolute. If this story changes that, the
  document says so — a rule left standing that the code no longer follows is
  worse than no rule.

- **AC7 — tests.** Essential: the fallback when the document is silent; the
  refusal on an unparseable or colliding proposal; the manager override still
  winning; and the recorded rationale.

## Out of scope

- Changing the release lifecycle itself — cut, UAT, sign-off, promote all
  stay as they are, and promotion still never re-versions.
- Letting an agent cut, sign off, or promote a release. Only the version
  *proposal* moves; every gate stays the manager's.
- Retiring `YYYY.MM.DD.N` as the default. It remains what most projects get.
