# US-100.6 — Versioning is agent work

**Status:** Testing
**Phase:** 100 — One document, not twenty-two sections
**Depends on:** us-100.1 (the versioning instructions live in the document)

## Story

As the manager, versioning is currently something the factory does *to* a
release rather than something an agent does. The scheme is computed —
`YYYY.MM.DD.N`, the date plus a same-day counter — and
[CLAUDE.md](../CLAUDE.md) states the rule flatly: *"The factory computes the
version — you never hand-pick one mid-flight."* An agent reads the version
off the release; it never decides one.

That was the right call when versioning was arithmetic. It stops being the
right call once the versioning rules live in the Agent Instructions
(us-100.1), because then the project has *written down* how it wants to be
versioned — and the one participant who reads that document is not allowed
to act on it. A project that wants semantic versioning, or a train, or a
different counter, can now say so in a place every agent reads, and nothing
will honour it.

So versioning becomes agent work: an agent reads the project's Agent
Instructions, proposes the version and the reasoning, and the manager
approves it at the gate that already exists.

## Acceptance criteria

- **AC1 — an agent proposes the version.** At release cut, an agent reads the
  project's Agent Instructions and proposes a version string with its
  reasoning — which rules it applied and why this is the next version. The
  proposal is data on the release, not a fait accompli.

- **AC2 — the manager still decides.** The existing manager override at cut
  stands: the proposal is a default that can be replaced, and once cut the
  version is fixed and read-only, exactly as
  [CLAUDE.md](../CLAUDE.md) already requires. Nothing here lets a version
  change mid-flight.

- **AC3 — `YYYY.MM.DD.N` remains the fallback.** A project whose Agent
  Instructions say nothing about versioning gets today's computed scheme, and
  a proposal that is unparseable or collides with an existing version is
  refused with the computed one offered instead. **The factory never ships a
  release with no version because an agent had an opinion.**

- **AC4 — the existing `release` kind gains the step. No new kind.**
  Decided by the manager, 2026-08-15. `release` already reads the commit
  range, writes the notes and deploys to UAT; versioning is the same job at
  the same moment, and a separate kind would have meant a second dispatch, a
  second claim and a second lease for one string.

  Concretely: no change to `runs_kind_check`, `HANDBACK_SHAPE`,
  `ROUTE_KINDS`, `run-kinds.ts` or the us-99.1 file map — the whole us-98.1
  new-kind checklist is **not** triggered, which is most of why this is the
  cheaper shape. What changes is `submit_release_notes`, which gains the
  proposed version and its rationale, and `Release_Prep.md`, whose default
  text gains the instruction to read the project's Agent Instructions for
  the versioning rules and propose accordingly.

  The one thing to watch: `release` already carries several
  responsibilities, and this adds a fourth. If the hand-back starts refusing
  for reasons that have nothing to do with each other, that is the signal the
  split was wrong after all — worth naming now so it is recognised then
  rather than absorbed.

- **AC5 — the reasoning is kept.** The version's rationale is recorded on the
  release beside the version, so "why is this 2026.08.15.2 and not 2.1.0" has
  an answer six months later without reading a run trace.

- **AC6 — CLAUDE.md is corrected.** Its Versioning & Release section states
  the never-hand-pick rule as absolute. If this story changes that, the
  document says so — a rule left standing that the code no longer follows is
  worse than no rule.

- **AC7 — tests.** Essential: the fallback when the document is silent; the
  refusal on an unparseable or colliding proposal; the manager override still
  winning; and the recorded rationale.

## Verified (2026-08-15)

- **AC1/AC5** — `submit_release_notes` gains `proposed_version` and
  `version_rationale`; migration 264 adds the two nullable columns to
  `releases` (applied to **both** databases). `releases.version` is untouched
  — a proposal is an input to the cut, never the cut.
- **AC2** — nothing writes `version`, so the manager's override at cut and
  the immutability after it are unchanged by construction.
- **AC3 — the factory never ships a release with no version.** The proposal
  is validated *before* the notes land, so a bad one never half-completes the
  job, and omitting it entirely stays the normal path.
- **The validator deliberately does NOT check the format.** Validating
  against `YYYY.MM.DD.N` would re-impose exactly the constraint this story
  removes — a project may now define semantic versioning, a train, or
  anything else. What is checked is what is true of a version in *any*
  scheme: it exists, it is one token, it is ≤64 chars, it could be a git tag,
  it does not collide, and it comes with a reason.
- **13 tests**, Essential and pure. They pin that six unrelated schemes are
  all accepted (`2.1.0`, `v3`, `2026.3`, `release-42`, `1.0.0-rc.1`,
  `24w33a`), every character git refuses in a tag is rejected, a collision is
  rejected, and a proposal with no rationale is rejected — the number is read
  months later to explain itself.
- **AC4** — no new run kind, exactly as decided: `runs_kind_check`,
  `HANDBACK_SHAPE`, `ROUTE_KINDS`, `run-kinds.ts` and the file map are all
  untouched.
- **AC6 — CLAUDE.md corrected.** Its never-hand-pick rule was absolute and is
  now false for the proposal; the section says what changed and what still
  holds. A rule left standing that the code no longer follows is worse than
  no rule.
- Types regenerated; api Essential green (**1797 passed, 545 skipped, 0
  failed**); `npm run build` green.

### Gaps

- ~~**`Release_Prep.md`'s default instruction text is unchanged**~~ — closed
  by migration 269 (with us-100.5): the `release` default now tells the
  agent to read the versioning rules in the Agent Instructions and propose
  `proposed_version` with a `version_rationale`, or propose nothing when the
  rules say nothing. Backfilled into every untouched project row (10/10 on
  prod) and template section.
- **No UI** shows the proposal or its rationale at the cut, so a manager
  cannot see it yet.
- `release_versions_for_prep` is untested against a real database
  (`DATABASE_URL` unset); only the validator it feeds is covered.

## Out of scope

- Changing the release lifecycle itself — cut, UAT, sign-off, promote all
  stay as they are, and promotion still never re-versions.
- Letting an agent cut, sign off, or promote a release. Only the version
  *proposal* moves; every gate stays the manager's.
- Retiring `YYYY.MM.DD.N` as the default. It remains what most projects get.
