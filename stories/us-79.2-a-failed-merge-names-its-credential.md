# US-79.2 — A failed merge names its credential and its cure

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-2 (`409: GitHub merge failed: Bad credentials`, issue `cc35b06c-e00d-45a3-8887-0fc4ec5bae9b`) and BUG-3 (`409: GitHub merge failed: Not Found`, issue `ec717022-61f3-4fa0-a869-585bf29a7dc9`)

## Story

As a manager approving a run, I want a merge that GitHub refuses to tell me
**which credential was used and what to do about it**, so that a dead PAT or a
missing grant is a two-minute reconnect instead of an opaque 409 relayed from
GitHub.

## Context

Both prod bugs are one approve flow on the Demo project's PR #31.
`github.merge_pull_request` collapses every upstream refusal into
`GitHubError("GitHub merge failed: <GitHub's message>")` with no status code,
so `_merge_pr` (apps/api/app/routers/reviews.py) can only relay the words:

- **"Bad credentials"** is GitHub's 401 — the credential `github_tokens`
  picked (a PAT explicitly listing the repo beats the App, per US-3.15) was
  revoked or rotated. The manager was told the *merge* failed; the truth is
  the *credential* failed.
- **"Not Found"** is GitHub's 404 — the credential cannot see the repo (GitHub
  404s unauthorized reads) or the PR is gone (merged or closed by hand, which
  is exactly what happened on Demo during the FEAT-2.4 hand-repair).

Separately, `_merge_pr`'s catch around `token_for_user` answers **"No GitHub
connection and GITHUB_TOKEN not configured"** for *every* `GitHubError`,
including "connection exists but its Vault secret is missing" and "App token
mint failed" — a message that sends the manager to create a connection they
already have.

## Acceptance criteria

1. `GitHubError` raised by `merge_pull_request` (and `get_pull` /
   `list_pull_files` on this path) carries the upstream HTTP status, so
   callers branch on the number, not on GitHub's prose.
2. On a 401: the 409 detail names the method and identity used — "the App
   installation for this org" or "the stored PAT (…last4)" — and directs to
   Settings → GitHub to reconnect. Token material never appears in the
   detail, the log, or the self-report context (method + identity only).
3. On a 404: the approve flow re-reads the PR with the same credential and
   answers by state —
   - PR already **merged**: approve reconciles as success (the run records the
     real merge SHA, the work item completes) and the UI says "already merged
     on GitHub" instead of erroring;
   - PR **closed** unmerged: 409 "the PR was closed on GitHub — reopen it or
     reject the run";
   - PR **invisible** to the credential: 409 naming the credential and saying
     the repo is outside its grant.
4. Credential-resolution failure distinguishes its three causes in the detail:
   no connection at all (current message stays), Vault secret missing, App
   token mint refused — each with the action that fixes it.
5. Every one of these remains self-reported as today (they are dependency
   failures, US-76.1), with the diagnosis in the report context.
6. Tests cover the 401 branch, each 404 sub-state, and the three
   credential-resolution messages (fakes at the `github` module boundary, in
   the pattern of the existing reviews tests).

## Out of scope

- Changing the US-3.15 credential preference order, or retrying the merge
  with the next credential in that order — resolution stays deterministic.
- GitHub App grant management UI.
- Fixing the Demo org's dead PAT — that is configuration, verified during UAT
  by reconnecting and re-approving a real PR.

## Proof required to reach Testing

Unit tests green for every branch above, plus a captured 409 body for the 401
case showing the named credential, from a dev-org run with a deliberately
broken PAT.

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `04fc450`).
`GitHubError` carries `upstream_status` from merge/get_pull/list_pull_files
(AC1). `github_tokens.resolve_for_user` returns the token **and** its
description — App installation id or PAT last-4, never the secret (the
report scrubber redacts credential-named keys, so the context key is
`connection`). The merge path branches: 401 names the credential and
Settings → GitHub; 404 probes the PR — merged-by-hand reconciles as success
with the real SHA recorded and an "Already merged on GitHub" toast at both
approve surfaces, closed-unmerged answers "reopen or reject", invisible
names the credential and the repository grant (AC2/AC3). The
credential-resolution catch distinguishes no-connection / Vault-secret-gone /
mint-refused by relaying the US-5.24 taxonomy's own messages (AC4). All the
dependency-failure branches still self-report with the diagnosis attached
(AC5). The dirty-conflict flow is byte-for-byte the old behavior.

**Verified:** `test_merge_diagnosis.py` (7 tests, one per branch incl.
secret-never-leaks assertions) plus the existing reviews/operational suites
(44 tests) green. Web build clean for the two toast call sites.

**Not verified:** the captured 409 from a live dev-org run with a
deliberately broken PAT — needs a real GitHub connection to break, which is
a UAT step; the branch logic is fully covered by fakes at the `github`
module boundary. Reconnecting the Demo org's dead PAT is configuration, not
code, and remains the manager's step.
