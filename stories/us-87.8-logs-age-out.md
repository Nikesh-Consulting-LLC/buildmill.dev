# US-87.8 — Logs age out, diffs live outside the row

**Status:** New
**Phase:** 87 — The app gets fast
**Depends on:** nothing

## Story

As the operator, nothing in this database is ever deleted. There is no
retention logic in the API and **no `pg_cron` schedule in any migration**.
Measured on prod:

| Table | Rows | Size |
|---|---|---|
| `api_request_log` | 584,934 | **106 MB** |
| `content_audit` | 31,260 | 36 MB |
| `runs` | 185 | **33 MB** |
| `agent_server_jobs` | 9,125 | 3.6 MB |
| `run_trace` | 6,968 | 2.1 MB |
| `runner_command_audit` | 1,645 | 3.0 MB |

`api_request_log` is a diagnostic table (US-62.8) growing at ~585 k rows per
six weeks. `client_perf_events` takes a browser-side insert on every page
load and has the same shape.

And `runs` is 33 MB for 185 rows because `runs.diff` holds 29 MB of text —
with a single row at **30,098,163 bytes**. No query does `select *` on
`runs` today, so this is not yet a hot path; it is a 30 MB landmine under
the next one, and it bloats every backup.

## Acceptance criteria

- **AC1 — a retention policy exists and is written down.** Each high-volume
  table gets a stated retention window in `APPLICATION.md`:
  `api_request_log` and `client_perf_events` (diagnostics — days),
  `content_audit`, `run_trace`, `runner_command_audit`,
  `agent_server_jobs`, `deployment_run_events` (operational history —
  longer). The manager approves the windows; nothing is guessed.
- **AC2 — something enforces it.** A `pg_cron` job (or an equivalent
  scheduled path) deletes past the window, in bounded batches that do not
  hold a long transaction. The job's own failures are visible, not silent.
- **AC3 — audit that must be kept, is kept.** Anything the audit trail or a
  compliance claim depends on — approvals, gate decisions, `issue_events` —
  is explicitly out of the deletion set. The story names what is exempt and
  why. Deleting evidence to save disk is the failure mode here.
- **AC4 — a big diff does not live in the row.** `runs.diff` above a
  threshold (default 1 MB) is stored in the private `data` Storage bucket
  and the column holds a pointer; the review surfaces that read a diff
  follow the pointer transparently. Existing oversized rows are migrated.
- **AC5 — no query pulls a diff it does not need.** A test asserts that no
  `select *` reaches `runs`, so a fat column can never be fetched by
  accident.
- **AC6 — applied to both projects.** Migrations land in
  `infra/supabase/migrations/`, applied to **prod and dev**, types
  regenerated.
- **AC7 — proof.** Table sizes before and after the first retention pass,
  recorded in the story.

## Out of scope

- Archiving deleted rows to cold storage — if the manager wants history
  beyond the window, that is a separate story.
- `llm_usage` — spend records are financial history and stay.
