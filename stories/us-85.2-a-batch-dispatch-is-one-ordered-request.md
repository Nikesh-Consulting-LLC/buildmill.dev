# US-85.2 — A batch dispatch is one ordered request

**Status:** Testing
**Phase:** 85 — Agent readiness
**Depends on:** us-6.2 (Waiting on you list), us-68.4 (mobile Dispatch all), us-36.2 (manual dispatch resets attempts), migration 169 (build-order batch precedent)

## Story

As the manager, when I select work items on the dashboard's Waiting-on-you
list and press **Dispatch selected** (or the mobile **Dispatch all**), the
whole batch is one request the server executes in build order, with a
per-item outcome — instead of the browser looping one POST per checkbox in
the order I happened to click them.

The failure this closes was observed live on 2026-08-12 (FEAT-2.8, eleven
stories): the client-side loop dispatched sub-stories **2, 3, then 9** —
checkbox-click order, one POST every ~11 seconds — then a second manual
round sent 4 and 5, and five stories were never dispatched at all. Story 9's
plan ran ahead of 4–8 because the claim-side ordering rule can only serialize
runs that exist; an out-of-order *dispatch* becomes an out-of-order *plan*.
Nothing failed loudly anywhere.

## Acceptance criteria

- **AC1 — one request.** The Dispatch selected / Dispatch all buttons issue
  exactly one `POST /api/v1/issues/batch-dispatch` carrying every selected
  issue id. A closed tab or mid-flight refresh no longer truncates the batch
  — the server finishes what was asked.
- **AC2 — build order, server-decided.** The server sorts the ids by the
  canonical build order (epic number → item number → sub number, nulls last,
  then created_at) before dispatching, regardless of click order or request
  order. The dashboard never orders a batch again.
- **AC3 — per-item outcome.** The response lists `dispatched`
  (`{id, run_id}`) and `skipped` (`{id, reason}`) with the dispatcher's own
  refusal text verbatim. The UI toast says "N dispatched" or
  "N dispatched, M skipped" and names the first skipped reason; skipped items
  stay in the list after refresh.
- **AC4 — a refusal never aborts the batch.** One item refusing (sequential
  mode, missing plan, feature-owned build, attempts cap) is recorded in
  `skipped` and the loop continues; every remaining item still gets its
  attempt.
- **AC5 — same rules as single dispatch.** Each item goes through the exact
  single-dispatch path (attempt reset, `dispatch_issue` RPC under the
  caller's JWT, repo-docs sync per touched project) — the batch adds
  ordering and reporting, never a bypass. No schema change.

## Out of scope

- The feature-header batch (us-84.1) — already server-side and ordered via
  `dispatch_feature_batch`; unchanged.
- Changing claim-side ordering (rule c) or hold semantics.
- Selecting items the list did not load — selection stays what the manager
  checked.
- Remediating the out-of-order sub-9 plan itself (a plan run is a document;
  reviewing it later is harmless).
