# US-81.2 — The suite pipeline runs a pinned build's tests

**Status:** Testing
**Phase:** 81 — Automated release testing
**Dependencies:** us-81.1

## Story

As a manager, I want the factory itself to run a declared suite against a
deployed instance — deterministically, with no LLM anywhere in the path — and
capture per-test results, so "the tests passed" is something the factory
observed, not something somebody reports.

## Context

This is the center of gravity of the phase. The pipeline is a sibling of
`apps/api/app/deploy.py` and reuses its building blocks directly
(`connect_to_server`, the GitHub tarball fetch at a pinned SHA, SFTP upload,
`_exec`, secret masking, the fire-and-forget task registry, streamed events).
Authoring specs is LLM work that goes through review; running them is
plumbing. pytest and Playwright both emit JUnit XML natively — that is the
whole interface.

## Acceptance criteria

1. New tables in the `deployment_runs`/`deployment_run_events` mold (api-only
   writes via service role, member SELECT, realtime):
   - `suite_runs`: suite, project, `deployment_id` (target under test),
     `release_id` (nullable), `trigger` in `uat-deploy|prod-promote|manual`,
     `commit_sha`, `base_url`, `status` in
     `queued|running|succeeded|failed|error|timed-out|cancelled`, totals
     (total/passed/failed/skipped), `log`, `error`, waiver columns
     (`waived_at/by`, `waive_reason`), timestamps. A partial unique index
     allows one queued-or-running run per suite.
   - `suite_run_tests`: `spec_ref`, `status` in `pass|fail|skipped|error`,
     `duration_ms`, `message`, `test_case_id` (nullable).
   - `suite_run_events`: the `deployment_run_events` shape (phase, message,
     data), realtime-published.
2. New module `apps/api/app/suites.py` runs the pipeline over SSH on the
   suite's server (default: the target deployment's server, which is the one
   machine guaranteed to reach `website_url` — the `health_check_once`
   precedent): **preflight** (reachable, tools, disk) → **fetch** the GitHub
   tarball at the pinned `commit_sha` → **transfer/extract** into a fresh
   per-run dir, with a persistent per-suite cache dir exported as
   `SF_CACHE_DIR` (the factory stays dumb about package managers) →
   **script**: `run_command` under `/bin/sh -e` with `project_build_config`
   values injected as env plus `SF_BASE_URL` (the deployment's
   `website_url`), `SF_COMMIT_SHA`, `SF_RELEASE_VERSION`, `SF_RESULTS_PATH`,
   wall-clocked by `timeout_minutes` → **collect**: SFTP-read `results_path`,
   parse JUnit XML (defusedxml; new `apps/api/app/junit.py`) → write
   `suite_run_tests` and totals → **cleanup** the run dir, keep the cache.
   Output lines are masked and streamed as events.
3. Terminal semantics are honest and distinct: `succeeded` = JUnit parsed,
   zero failures/errors; `failed` = JUnit parsed with failures (**JUnit is
   truth; the script's exit code is informative only**); `error` = could not
   test (SSH, preflight, missing results file, parse failure) — which is not
   the same thing as tests failing; `timed-out` on wall clock.
4. Manual trigger: `POST /api/v1/suites/{suite_id}/run` against a chosen
   deployment (`trigger='manual'`, `release_id` null). A second trigger while
   one is in flight answers 409 off the partial index.
5. A live run view shows the phase stream, the log, and the per-test table as
   they happen (reuse the deployment-run event components).
6. A `failed`/`error`/`timed-out` run notifies through the project's existing
   notification endpoints.

## Out of scope

- Release triggers (us-81.3) and the sign-off gate (us-81.4).
- Installing toolchains: the pipeline demands `tar`/`curl` etc. at preflight
  and fails legibly, like deploy preflight does. Browser provisioning for
  Playwright (system deps on the chosen server) is the operator's setup, and
  the preflight error must say exactly what is missing.
- Parallel suite execution: suites on one server run sequentially in v1.

## Outcome

Built 2026-08-11. Migration `240_suite_runs.sql` (both DBs): `suite_runs` /
`suite_run_tests` / `suite_run_events`, member-read-only (no write policies —
a browser cannot forge results), single-flight partial index, realtime on runs
+ events. `apps/api/app/junit.py` (defusedxml with stdlib fallback;
`defusedxml` added to requirements). `apps/api/app/suites.py` reuses
deploy.py's SSH pieces: preflight (tar/curl/timeout) → pinned-SHA tarball →
extract with persistent `SF_CACHE_DIR` → `run_command` under
`timeout N /bin/sh -e -s` with build-config env + `SF_BASE_URL` /
`SF_COMMIT_SHA` / `SF_RELEASE_VERSION` / `SF_RESULTS_PATH` → SFTP-collect +
parse → per-test rows → cleanup. JUnit is truth (exit code informative);
`error` is not `failed`; exit 124 means `timed-out`. Suites sharing a server
run sequentially via a per-server asyncio lock. Manual trigger
`POST /api/v1/suites/{id}/run` (branch-head commit); live run view at
`/tests/suites/[runId]` (realtime feed + per-test table). Orphan reaper wired
into API startup. Failures notify via the deployment channel's new
`suite-failed` event — enable it per deployment in Notifications.

**Verified:** 8 JUnit parser tests + 12 endpoint tests green; full Essential
suite green; web build clean.
**Not verified:** an end-to-end run against a real server — the first live
suite run on UAT is the proof this story still owes.
