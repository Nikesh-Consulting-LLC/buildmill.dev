# US-118.2 — An org's copy can change its face

**Status:** Testing
**Phase:** 118 — A template shows its face
**Depends on:** US-118.1 (columns, bucket, `TemplateDetailsDialog`,
`TemplateCard`, `TemplateThumb`, inline markdown), migration 227 (org copies,
`manage_project` RLS on `org_project_templates`), 267
(`copy_project_template_into_org`), US-114.1 (the org page's two-pane shape,
Export/Import)

Design reference: [docs/design/template-cards.html](../docs/design/template-cards.html)
— Mockup B (with `scope="org"`: no Key field) and Mockup C's org-settings
header.

## Story

As an org owner or admin, I want my org's template copies to arrive with the
catalog's description and cover and let me change them — and my own custom
templates to be created through a real form — so that the cards my members
choose from say what *our* templates are for, in our words and with our
picture, and a custom template is not a `window.prompt` for a name and
nothing else.

## Design

### What exists today

- `/settings/project-templates` (`project-templates-client.tsx`) fetches the
  catalog's `description` and `category` (`page.tsx:19-22`) and renders
  **neither** in the *Copy from catalog* dialog (lines 669–706: name, mono
  key, Default badge, Copy).
- The org's header shows name, key, badges and the description as plain text
  (`:641-645`); rename is inline (`:255-266`).
- **New custom template** is `window.prompt("Name for the new template?")`
  (`:280-292`) — no description, no category, no cover.
- After US-118.1, `copy_project_template_into_org` already carries
  `category` and `image_path`, so a fresh copy *has* a face; nothing on the
  org page shows or edits it yet.

### Copy from catalog shows what it is copying

Each catalog row in the dialog becomes a `TemplateCard variant="row"`: thumb
(the catalog cover or generated), name, mono key, Default badge, the
description in inline markdown clamped to one line, and the existing Copy
button as the row's action. Nothing new is fetched — the fields were already
selected and dropped on the floor.

### The org header and list wear the face

Same treatment as the admin page: `TemplateThumb` before the name in the
header and in every list row; the description rendered through
`MarkdownView` (full) under the header; badges (`Default`, `Hidden`,
`Archived`) unchanged. Inline rename is replaced by **Edit details**
(`canManage` only — non-managers see the header read-only, as today).

### Edit details, org scope

`TemplateDetailsDialog` with `scope="org"`: **Name**, **Category**,
**Description**, **Cover** — no Key (org copies have `template_key` from
the catalog or nothing; it is not theirs to write). Category is editable
here because US-118.3's chips group by it and a custom template needs one.

Writes go **browser → Supabase under RLS**, no API:

- the row: `update org_project_templates set name, category, description,
  image_path` — `manage_project` policy (227:141-146);
- the object: upload to `<org_id>/<org_template_id>/cover` under the
  `template_image_writable` policy from US-118.1 (folder is a uuid →
  `has_org_capability(folder, 'manage_project')`);
- `image_path` becomes the org's own path; the CHECK constraint accepts it
  and refuses any other org's folder.

A copy that still points at `catalog/<id>/cover` shows the catalog's cover.
**Replace** uploads to the org's own path and repoints the row; **Remove**
nulls `image_path` and, only if the path is the org's own, deletes the object
— it never tries to delete a catalog object (RLS would refuse anyway, and a
refused delete must not surface as an error to the manager). After Remove
the copy shows the generated cover, not the catalog's — "remove" means
"no image", the same as everywhere else.

### New custom template is the same form

`createCustom` opens the dialog in `mode="create"`, `scope="org"`: Name
required; Category, Description, Cover optional. Insert the row, then — if
a cover was picked — upload to `<org_id>/<new id>/cover` and update
`image_path`. The `window.prompt` goes.

### Delete

`deleteTemplate` removes the org's own cover object best-effort before the
row (never a catalog object), so a deleted custom template leaves nothing
in the bucket.

### Docs

`interface-catalog.md`'s `/settings/project-templates` row gains Edit
details, the create form and the org's cover path.

## Acceptance criteria

1. **Copy from catalog** lists each catalog template as a row with its
   thumb (or generated cover), name, key, Default badge and one line of
   description in inline markdown; Copy behaves as before, and the new copy
   shows the catalog's cover and description immediately.
2. The org header reads: thumb · name · key · Default / Hidden / Archived ·
   **Edit details** (managers only) · Export · Import; the description below
   renders as markdown. List rows show the thumb. Inline rename is gone.
3. **Edit details** for a manager offers Name, Category, Description
   (Write/Preview, counter, hint), Cover (Upload / Replace / Remove, hint)
   and the live card preview — and **no Key field**. Save writes the row
   directly under RLS; a member without `manage_project` sees no Edit
   details button and any direct write is refused by RLS.
4. **Replace** on a copy still pointing at the catalog's cover uploads to
   `<org>/<template>/cover`, repoints `image_path`, and the header, list and
   preview show the new image without a hard reload. **Remove** on the same
   copy nulls `image_path` without attempting to delete the catalog object,
   and the copy renders the generated cover.
5. **Remove** on a copy with its own upload deletes the object and nulls the
   path; **Delete template** on a custom template removes its cover object
   before the row.
6. **New custom template** opens the create form (Name required); a picked
   cover is uploaded after insert and the new template appears in the list
   with it. There is no `window.prompt` left on the page.
7. Storage RLS (SQL test): a member with `manage_project` can insert, update
   and delete under their own org's folder; is refused under another org's
   folder and under `catalog/`; a member without the capability is refused
   under their own org's folder. The CHECK constraint refuses an
   `image_path` in another org's folder or with a stray extension.
8. `npm run build` clean; `cd apps/api && python -m pytest --full` includes
   the new `*_sql.py` cases (skipped without `DATABASE_URL`, as the suite
   already does).
9. `interface-catalog.md`'s `/settings/project-templates` row is updated.

## Out of scope

- **Pulling the catalog's later edits into an org copy** (a "refresh from
  catalog" for description or cover). A copy is a copy, as it is for files.
- **Editing the key** on an org copy — `template_key` is provenance, not a
  field.
- **The picker surfaces** — US-118.3 and US-118.4.
- **Per-member visibility of covers** — the bucket is public by design
  (US-118.1).
