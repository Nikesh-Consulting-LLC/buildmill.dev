# US-98.5 — An unresolved branch fails the whole merge

**Status:** New
**Phase:** 98 — Many branches, one landing
**Depends on:** us-98.4 (there is a hand-back to constrain)

## Story

As the manager, a merge either happened or it did not. If I ask for six
branches to land and five of them do, what I am handed is not a merge — it
is a new state nobody asked for, that I now have to reason about branch by
branch, and that quietly redefines what the pull request in front of me
means. A partial merge is the kind of result that looks like progress and
costs more than starting over.

So the rule is all-or-nothing, and it is enforced at the point of
submission rather than trusted to the agent's judgement. Every branch the
run declared must be accounted for as merged, or nothing is written: no
factory branch, no pull request, no commit. The run fails with a reason
naming the branch it could not land and the paths that defeated it, and that
reason is what I read.

This is deliberately stricter than `submit_changeset`'s existing
`allow_partial` flag, which exists for a different problem — a batch run
covering several work items, where landing four of six is genuinely useful.
A merge is one indivisible act.

## Acceptance criteria

- **AC1 — the declared set must be complete.** A merge submission whose
  per-branch declaration (us-98.4 AC2) does not cover **every** branch in
  the run's list is refused, before any GitHub write, with a message naming
  the missing branches. A declaration covering a branch that is not in the
  run's list is refused the same way.

- **AC2 — `allow_partial` is not available to a merge.** Whatever transport
  a merge run submits through, the partial-acceptance path is refused by
  name for `merge`, so the flag cannot be used to smuggle a partial merge
  past AC1.

- **AC3 — failing is a first-class answer, not an error.** An agent that
  cannot resolve a branch reports the failure through the run's normal
  hand-back path with: the branch it could not land, the paths that
  conflicted, and what it tried. The run ends `failed` with that reason
  attached, the chore returns to a state the manager can redispatch from,
  and the reason rides the retry run's feedback the way a rejection does —
  the same mechanism `reject-conflict`
  ([reviews.py](../apps/api/app/routers/reviews.py) L596-675) already uses
  to put a conflict in front of an agent.

- **AC4 — nothing partial survives a failure.** After a failed merge run
  there is no factory merge branch, no open pull request, and no commit
  attributable to the run. Verified by a test that fails a merge mid-way and
  asserts the repository is untouched.

- **AC5 — the failure is not the machine's fault.** A merge that fails
  because the code genuinely conflicts is work-classed, not
  infrastructure-classed, so it does not pollute runner health. The
  `fault_class` this produces is stated explicitly and pinned by a test.

- **AC6 — the instruction says so.** The `merge` default instruction text
  from us-98.1 states the all-or-nothing rule plainly, so an agent learns it
  from its instructions rather than from a refusal.

- **AC7 — tests.** Essential, faked GitHub: the AC1 refusals in both
  directions (missing branch, extra branch); the AC2 refusal; the AC3 failure
  shape and its feedback carry-through; and AC4's no-residue assertion.

## Verified (2026-08-15)

- **AC1** — a merge submission whose declaration does not cover every branch
  in the run's list is refused, naming **all** the missing ones; a
  declaration covering a branch outside the list is refused the same way.
- **AC2** — `allow_partial` is refused outright on a merge. The check runs
  **before** the completeness check on purpose: were the order reversed, a
  complete declaration plus `allow_partial` would sail through and the flag
  would be silently meaningless rather than refused. Pinned by its own test.
- **AC4** — the whole gate runs before a single blob is written, so a refused
  merge creates no branch, no commit and no PR. That is what makes "nothing
  partial survives" true rather than merely intended.
- **AC6** — the `merge` instruction default (us-98.1) states the rule, so an
  agent learns it from its instructions rather than from a refusal.
- **14 tests in `test_merge_submission_gate.py`**, pure-function and
  therefore **Essential** — `test_factory_mcp.py` is `needs_db` and skips, so
  this rule would otherwise have had no coverage in the suite anyone runs.
  They pin: complete declaration passes; every missing branch named; extra
  branch refused; `allow_partial` refused both when the declaration is
  incomplete *and* when it is complete; no declaration refused with the
  asked-for set in the hint; blank and missing `outcome` refused ("clean" is
  a fine answer, silence is not); non-merge runs untouched; `merged_branches`
  on a code run refused rather than ignored; and **malformed entries do not
  satisfy the check** — a list of junk must not count as having declared
  anything.

### Not built in this story — an honest gap

- **AC3 (failing is a first-class answer) and AC5 (fault classing) are NOT
  implemented.** The *enforcement* half of this story — a partial merge
  cannot be submitted — is done and tested. The *reporting* half is not: an
  agent that cannot resolve a branch currently falls through to the generic
  run-failure path, and I have **not** verified that such a failure is
  work-classed rather than infrastructure-classed, nor that the reason rides
  the retry run's feedback the way `reject-conflict` does. Refusing to
  accept a bad merge is the safety property and it holds; making the failure
  articulate does not, and should be finished before this phase is called
  complete.

## Out of scope

- Splitting the failures into new merge chores, or any other auto-creation
  of work items from a failed run.
- Retrying automatically. A failed merge is redispatched by the manager,
  like every other failed run.
- Changing `allow_partial` for the run kinds that legitimately use it —
  AC2 refuses it for `merge` only.
- Any attempt to resolve conflicts server-side, or to pre-check
  mergeability at dispatch. The agent finds out by trying, which is also how
  it learns enough to explain the failure.
