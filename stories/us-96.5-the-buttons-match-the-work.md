# US-96.5 — The buttons match the work

**Status:** Completed
**Phase:** 96 — The type shapes the path
**Depends on:** us-96.1, us-96.2, us-96.4 (this story renders the flows they create)

## Story

As the manager, the UI still dresses all four types in the same clothes:
the same stage tracker, the same "Planning / Plan review / Planned" labels,
the same dispatch buttons — even where us-96.1 made planning impossible for
a chore, us-96.2 turned a bug's plan into an RCA, and us-96.4 took the
wheel away from feature children. A surface that offers actions the API
refuses, or names a bug's diagnosis "Plan review", makes the manager
translate on every glance.

Every type gets rendered as what it is: its own stage shape, its own
labels, its own action set — on the work item page, on workbench rows, and
in the help that explains the factory to new eyes. The database vocabulary
does not change; only what the manager reads does.

## Acceptance criteria

- **AC1 — per-type stage shapes.** The stage tracker
  ([stage-tracker.ts](../apps/web/src/lib/stage-tracker.ts),
  [stage-tracker.tsx](../apps/web/src/components/stage-tracker.tsx)) renders:
  story (standalone and feature child): Plan → Plan review → Build → Code
  review → Merged; bug: Analyze → RCA review → Fix → Code review → Merged;
  chore: Build → Code review → Merged; feature: PRD → Break down → Plan →
  Build → Done. A feature child's tracker also names the feature that
  carries it.
- **AC2 — per-type actions on the work item page.** On
  [issues/[id]/page.tsx](../apps/web/src/app/(app)/issues/%5Bid%5D/page.tsx):
  a chore offers Dispatch (build) only; a bug offers Dispatch RCA, then the
  review link, then Dispatch fix; a standalone story keeps today's trio; a
  feature child offers **no** dispatch actions — a line names its feature
  ("flows with FEAT-2.3", linked) — except in trouble
  (`failed`/`needs-fixes`), where the exemption's individual dispatch
  appears; a feature shows the us-96.4 controls.
- **AC3 — labels speak the type.** Where a story reads "Planning / Plan
  review / Planned", a bug reads "Analyzing / RCA review / Fix ready" —
  one mapping (type + status → label) used by the work item page, the
  Work Items list ([issue-views.tsx](../apps/web/src/app/(app)/issues/issue-views.tsx)),
  and workbench rows, rendered through the shared `StatusBadge`, no new
  badge pattern. The database status values are untouched.
- **AC4 — the help matches the product.** The lifecycle flowchart and help
  text ([lifecycle-flowchart.tsx](../apps/web/src/components/help/lifecycle-flowchart.tsx),
  [help-content.ts](../apps/web/src/components/help/help-content.ts)) show
  the four paths as built, including the feature-as-steering-wheel rule.
- **AC5 — nothing dead, nothing missing.** No surface offers an action the
  API refuses for that type and state, and every action the API accepts is
  reachable — verified before Testing by a click-through of all four types
  on dev, recorded in this file.
- **AC6 — tests.** Web tests pin the pure parts: the per-type stage shapes
  and the type + status → label mapping.

## Verified (2026-08-15, on the phase branch; this machine has no web env)

- **Stage shapes (AC1)**: `stage-tracker.ts` — a new `choreRail` (Draft →
  Build, no plan stage, review inside Build's waiting state) and a
  bug-voiced `dispatchableRail` (stage labels RCA/Fix; contexts
  "diagnosing the cause", "the analysis awaits your review", "RCA
  approved; dispatch the fix run"). `deriveCompact` routes by type, so
  every list row's stage dots inherit the shapes for free. A feature
  child's tracker already named its owning feature (US-22.10) and now
  defers the *plan* too: a never-planned child's "Dispatch planning" is
  disabled with `featureOwnsPlanReason` and a link to the feature —
  lifted by any existing plan artifact (revision) exactly like the
  server rule (`hasAnyPlan` rides `TrackerInput` from the page's
  artifact read).
- **Actions per type (AC2)**: the per-type views already existed
  (US-15.20) — what changed is what they say and offer. The chore view
  drops its Plan tab (`tabsForType`) and its rail's one action is
  "Dispatch build"; the bug view's plan tab is labeled "RCA"
  (`tabLabel`) and `PlanPanel` heads it "Root cause analysis"; the
  review surface got its RCA words in us-96.2.
- **Labels (AC3)**: `StatusBadge` gains `issueType` and a pure exported
  `issueStatusLabel` — a bug reads "Analyzing / RCA review / Fix ready"
  where a story reads "Planning / Plan review / Planned" — wired on the
  work item page header and the Work Items board cards; the Workbench's
  review rows say "Root cause analysis ready for your review · Approve
  RCA" for bugs (data.ts). No new badge pattern; tones unchanged.
- **Help (AC4)**: the lifecycle flowchart is a hand-laid SVG, so the
  type paths ride as annotations rather than re-laid rails: the Plan
  node reads "plans · a bug's RCA" and the story/bug edge reads
  "story · bug (a chore skips to Build)".
  - **UAT rework (2026-08-15, "show how items get routed")**: the
    annotations were not enough — the help now has a dedicated **How
    each type is routed** section (`routing-map.tsx`) under Work items:
    four drawn lanes (feature-with-stories, standalone story, bug,
    chore) in the stage tracker's own visual language, each with the one
    sentence that explains its shape, plus the four routing rules
    (feature owns its stories, one item at a time, build order picks
    who is next, where to set it). The **Build order** topic's default
    prose was rewritten from the retired build-mode radio / concurrency
    checkbox to US-86.1's two switches and serial law, and to Phase
    96's feature-ownership refusals and one-row feature triage; the
    pipeline walkthrough's intro/draft/plan text now says which types
    vary and how. Structural (code), so it changes only when routing
    does. Build green.
- **Tests (AC6)**: six tracker tests added (chore shape, chore review
  link, chore fix retry, bug labels, plan deferral, revision lift); one
  US-22.10-era test that pinned per-story planning was corrected to the
  us-96.4 rule in place. Web suite 168/168; `npm run build` green.
- **AC5 deviation — for UAT**: no `apps/web/.env.local` on this machine,
  so the four-type click-through could not run in a browser here; it is
  the UAT script (create one of each type on dev → confirm each page's
  actions, tracker, and labels; confirm no dead buttons). Every rule the
  buttons mirror is server-enforced and was live-verified in
  us-96.1/96.2/96.4.

## Out of scope

- Any `issues.status` or `runs.kind` vocabulary change — labels only.
- Mobile-specific layouts beyond what the shared components inherit
  (Phase 92 owns the phone).
- New colors, badge variants, or icons — existing tokens and components.
- The feature page's own controls — built in us-96.4, only *consumed* here.
