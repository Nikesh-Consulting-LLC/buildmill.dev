# US-96.5 — The buttons match the work

**Status:** New
**Phase:** 96 — The type shapes the path
**Depends on:** us-96.1, us-96.2, us-96.4 (this story renders the flows they create)

## Story

As the manager, the UI still dresses all four types in the same clothes:
the same stage tracker, the same "Planning / Plan review / Planned" labels,
the same dispatch buttons — even where us-96.1 made planning impossible for
a chore, us-96.2 turned a bug's plan into an RCA, and us-96.4 took the
wheel away from feature children. A surface that offers actions the API
refuses, or names a bug's diagnosis "Plan review", makes the manager
translate on every glance.

Every type gets rendered as what it is: its own stage shape, its own
labels, its own action set — on the work item page, on workbench rows, and
in the help that explains the factory to new eyes. The database vocabulary
does not change; only what the manager reads does.

## Acceptance criteria

- **AC1 — per-type stage shapes.** The stage tracker
  ([stage-tracker.ts](../apps/web/src/lib/stage-tracker.ts),
  [stage-tracker.tsx](../apps/web/src/components/stage-tracker.tsx)) renders:
  story (standalone and feature child): Plan → Plan review → Build → Code
  review → Merged; bug: Analyze → RCA review → Fix → Code review → Merged;
  chore: Build → Code review → Merged; feature: PRD → Break down → Plan →
  Build → Done. A feature child's tracker also names the feature that
  carries it.
- **AC2 — per-type actions on the work item page.** On
  [issues/[id]/page.tsx](../apps/web/src/app/(app)/issues/%5Bid%5D/page.tsx):
  a chore offers Dispatch (build) only; a bug offers Dispatch RCA, then the
  review link, then Dispatch fix; a standalone story keeps today's trio; a
  feature child offers **no** dispatch actions — a line names its feature
  ("flows with FEAT-2.3", linked) — except in trouble
  (`failed`/`needs-fixes`), where the exemption's individual dispatch
  appears; a feature shows the us-96.4 controls.
- **AC3 — labels speak the type.** Where a story reads "Planning / Plan
  review / Planned", a bug reads "Analyzing / RCA review / Fix ready" —
  one mapping (type + status → label) used by the work item page, the
  Work Items list ([issue-views.tsx](../apps/web/src/app/(app)/issues/issue-views.tsx)),
  and workbench rows, rendered through the shared `StatusBadge`, no new
  badge pattern. The database status values are untouched.
- **AC4 — the help matches the product.** The lifecycle flowchart and help
  text ([lifecycle-flowchart.tsx](../apps/web/src/components/help/lifecycle-flowchart.tsx),
  [help-content.ts](../apps/web/src/components/help/help-content.ts)) show
  the four paths as built, including the feature-as-steering-wheel rule.
- **AC5 — nothing dead, nothing missing.** No surface offers an action the
  API refuses for that type and state, and every action the API accepts is
  reachable — verified before Testing by a click-through of all four types
  on dev, recorded in this file.
- **AC6 — tests.** Web tests pin the pure parts: the per-type stage shapes
  and the type + status → label mapping.

## Out of scope

- Any `issues.status` or `runs.kind` vocabulary change — labels only.
- Mobile-specific layouts beyond what the shared components inherit
  (Phase 92 owns the phone).
- New colors, badge variants, or icons — existing tokens and components.
- The feature page's own controls — built in us-96.4, only *consumed* here.
