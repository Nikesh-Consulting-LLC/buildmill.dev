# US-101.5 — The release page is the plan a tester follows

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** us-101.2 (sections, ordering, criticality), us-101.4 (the declaration)

## Story

As the manager, I open a release to do one thing: work through it and sign it
off. The page should open with the facts I check first — which commit is
deployed, which migrations ran, how many checks there are and how many of
those I cannot skip — and then be a numbered list I work down, ticking as I
go, with the pass/fail I record *being* the tick.

Today the page opens with two blocks of markdown and then a flat list of case
rows ordered by UUID.

The good news is that every number a masthead needs is **already fetched by
this page**. The deploy result and duration are in the deployment-attempt rows
it renders at the bottom; the automated test counts are in the suite-run rows
it already reads; the pinned commit is on the release; the story range is
`included_items`; the checklist counts are the case rows themselves. The
masthead is a rendering problem, not a data problem — which is also why it
belongs to the app rather than to the agent, since half of those facts do not
exist until after the agent has finished (us-101.4).

## Acceptance criteria

- **AC1 — the page opens with facts, not prose.** A masthead carrying: the
  pinned commit, the migrations in the range, the work-item range, the number
  of checks and how many are critical, and — once they exist — the UAT deploy
  result with its duration and the automated suite's passed/failed counts. All
  server-rendered from data the page already loads.

- **AC2 — a fact that does not exist yet says so.** Before the UAT deploy
  finishes, the deploy fact reads as pending, not as absent and not as zero. A
  masthead that shows "0 failed" for a suite that has not run is worse than
  one that shows nothing.

- **AC3 — the checklist is sectioned and in order.** Cases are grouped by
  section in the canonical order and sorted within it, each section carrying
  its note from the declaration. The ordering query changes from `issue_id,
  title` to section order, then `sort`, then title.

- **AC4 — a check reads as an instruction and an observation.** Each row shows
  its step and, distinctly labelled, its expected result. The distinction is
  visual and consistent — a tester scanning the page can see what to *do*
  separately from what to *see*.

- **AC5 — a critical check is visibly different.** Marked in a way that
  survives a phone screen, and explained: these are the checks the test suite
  cannot make for you.

- **AC6 — the story chip stays on every check that has one.** Both inherited
  cases and, now, agent-authored ones (us-101.2), linking back to the work
  item.

- **AC7 — ticking is recording.** The pass/fail/blocked controls and their
  write path are unchanged; there is no second set of checkboxes anywhere on
  the page. `release_signoff_blocker` is untouched, so sign-off still opens
  only when every active case has a verdict and none failed or blocked.

- **AC8 — the sections do not make sign-off a chore.** With a genuinely
  sectioned checklist the case count goes up, and every case needs a verdict.
  The existing "pass all" affordance — which only touches cases with no result
  yet — remains, and is reachable per section as well as for the whole
  release.

- **AC9 — an old release is not broken by the new page.** A release with no
  declaration and unsectioned cases renders as it does today: the markdown
  notes, the flat list, the same buttons.

- **AC10 — it works on a phone.** Phase 92 put releases and test cases on the
  phone deliberately; a sectioned checklist that only works on a laptop
  undoes that.

## Out of scope

- Editing the checklist in the UI, re-sorting it, or adding a case by hand to
  a release. The library's own creation surface is unchanged.
- Printing or exporting the page as a standalone file.
- Changing what sign-off means, or giving `critical` any gating power.
- The releases *list* page, which selects no notes columns and stays that way.
