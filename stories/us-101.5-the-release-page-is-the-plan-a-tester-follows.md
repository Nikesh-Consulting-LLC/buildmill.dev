# US-101.5 — The release page is the plan a tester follows

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** us-101.2 (sections, ordering, criticality), us-101.4 (the declaration)

## Story

As the manager, I open a release to do one thing: work through it and sign it
off. The page should open with the facts I check first — which commit is
deployed, which migrations ran, how many checks there are and how many of
those I cannot skip — and then be a numbered list I work down, ticking as I
go, with the pass/fail I record *being* the tick.

Today the page opens with two blocks of markdown
([page.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/page.tsx)
L301–327) and then a flat list of case rows ordered by `issue_id` then
`title` (L65–71).

The good news is that every number a masthead needs is **already fetched by
this page**:

| Fact | Already loaded at |
|---|---|
| deployment attempts — status, `created_at`, `finished_at` | L177–186 |
| suite runs — `tests_total`, `tests_passed`, `tests_failed` | L93–99 |
| the included work items | L101–104 |
| the checks themselves | L65–71 |
| the sign-off blocker | L161–167 |

The pinned commit is on the release row. So the masthead is a rendering
problem, not a data problem — which is also why it belongs to the app rather
than to the agent, since half of those facts do not exist until after the
agent has finished (us-101.4).

Two of them are loaded and then effectively hidden: the deployment attempts
render only inside an Attempts card gated on there having been a *failure*
(L424–461), so on a clean release the deploy result — the single fact a tester
checks first — is fetched and never shown.

## Acceptance criteria

- **AC1 — the page opens with facts, not prose.** A masthead carrying: the
  pinned commit, the migrations in the range, the work-item range, the number
  of checks and how many are critical, and — once they exist — the UAT deploy
  result with its duration and the automated suites' passed/failed counts. All
  server-rendered from data the page already loads. The deploy fact appears on
  a **successful** release too, not only on a failed one.

- **AC2 — a fact that does not exist yet says so.** Before the UAT deploy
  finishes, the deploy fact reads as pending, not as absent and not as zero. A
  masthead that shows "0 failed" for a suite that has not run is worse than
  one that shows nothing.

- **AC3 — the checklist is sectioned and in order.** Cases are grouped by
  section in the canonical order and sorted within it, each section carrying
  its note from the declaration. The ordering changes from `issue_id, title`
  to section order, then `sort`, then title.

- **AC4 — a check reads as an instruction and an observation.** Each row shows
  its step and, distinctly labelled, its expected result. The distinction is
  visual and consistent — a tester scanning the page can see what to *do*
  separately from what to *see*. Today both live only inside the expanded body
  (L239–275), so a collapsed checklist shows titles alone; a tester working
  top to bottom must be able to read the checks without opening each one.

- **AC5 — a critical check is visibly different.** Marked in a way that
  survives a phone screen, and explained: these are the checks the test suite
  cannot make for you.

- **AC6 — every check says where it came from.** Both inherited cases and,
  now, agent-authored ones (us-101.2) name the work item they test and link to
  it. Today that provenance line sits inside the expanded body (L241–257) and
  agent-authored cases can only ever say "Regression case for this release";
  after us-101.2 they have a story, and it must be visible where the tester is
  looking.

- **AC7 — ticking is recording.** The pass/fail/blocked controls and their
  write path are unchanged; there is no second set of checkboxes anywhere on
  the page. `release_signoff_blocker`
  ([241_suite_results_gate.sql](../infra/supabase/migrations/241_suite_results_gate.sql)
  L22–121) is untouched, so sign-off still opens only when the UAT build is
  this release's, every active case has a verdict, none failed or blocked, and
  every gating suite has passed or been waived.

- **AC8 — the sections do not make sign-off a chore.** With a genuinely
  sectioned checklist the case count goes up, and every case needs a verdict.
  The existing "Pass all · N" affordance — which only touches cases with no
  result yet, so a recorded fail or blocked is never overwritten (L109,
  L159–175) — remains, and is reachable per section as well as for the whole
  release.

- **AC9 — an old release is not broken by the new page.** A release with no
  declaration and unsectioned cases renders as it does today: the markdown
  notes, the flat list, the same buttons.

- **AC10 — it works on a phone.** Phase 92 put releases and test cases on the
  phone deliberately; a sectioned checklist that only works on a laptop
  undoes that.

## Out of scope

- Editing the checklist in the UI, re-sorting it, or adding a case by hand to
  a release. The library's own creation surface is unchanged.
- Printing or exporting the page as a standalone file.
- Changing what sign-off means, or giving `critical` any gating power.
- The releases *list* page, which selects no notes columns and stays that way.
- Showing us-100.6's version proposal and its rationale. No UI reads those
  columns yet; closing that is us-100.6's recorded gap, not this story's.
