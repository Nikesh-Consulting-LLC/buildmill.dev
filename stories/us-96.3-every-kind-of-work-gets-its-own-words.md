# US-96.3 — Every kind of work gets its own words

**Status:** New
**Phase:** 96 — The type shapes the path
**Depends on:** us-96.1, us-96.2 (their instruction kinds exist; this story completes the family and the editor)

## Story

As the manager, a standalone story — one with no parent feature — is planned
by instructions written for a feature child: they lean on "the PRD context
when present" and assume a breakdown decided the story's shape. A standalone
story has neither. Its planner walks in with the story and acceptance
criteria as the entire contract, and the words it receives should say so
instead of gesturing at documents that don't exist.

With us-96.1 and us-96.2, `worker_instructions` grows from a
one-size-per-run-kind table into a family: the feature-child pair
(`plan`/`code`), the bug pair (`bug_rca`/`bug_fix`), the chore single-shot
(`chore`) — and now the standalone pair. The Settings editor that presents
this family has to name each member for what it steers, or the manager
editing "code" won't know which workers it reaches anymore.

## Acceptance criteria

- **AC1 — the standalone pair exists.** The migration widens the
  `worker_instructions.run_kind` check with `standalone_plan` and
  `standalone_code`, with factory defaults in `default_worker_instruction`:
  derived from today's `plan`/`code` text, minus the PRD/breakdown framing,
  plus the honest premise — there is no PRD; the story and its acceptance
  criteria are the whole contract; doubt narrows scope rather than
  inventing it. Seeding trigger updated, every project backfilled.
- **AC2 — resolution by parentage.** A story with `parent_id null` resolves
  `standalone_plan`/`standalone_code`; a feature child keeps `plan`/`code`.
  Same two call sites as us-96.1/96.2 (`get_worker_instruction`,
  `seed_issue_instructions`), and the mapping lives in **one** place both
  read — type + parentage in, instruction kind out — so they cannot
  disagree.
- **AC3 — the editor names the family.** The worker-instructions Settings
  surface lists every kind with a human name and a one-line "who receives
  this": Story (in a feature) — plan / build; Story (standalone) — plan /
  build; Bug — root cause analysis; Bug — fix; Chore — single-shot build;
  plus the existing prd/breakdown/test/release/deploy and thinking-prompt
  entries unchanged. Reset-to-default works per kind through the existing
  RPC; edits keep landing in `content_audit` (verified, no change
  expected).
- **AC4 — blank falls back, old projects stay whole.**
  `worker_instruction_for`'s blank-content → factory-default semantics are
  untouched; a project that never edits anything behaves identically before
  and after, pinned by a test.
- **AC5 — templates still copy clean.** `copy_project_template_into_org`
  ([227_project_templates.sql](../infra/supabase/migrations/227_project_templates.sql))
  keeps working against the widened kind set — verified by test or by
  reading the copy path, recorded either way.
- **AC6 — both projects, types, sweep, tests.** Migration applied to prod
  and dev, types regenerated, embed sweep run. The mapping function is
  pure — unit-tested; the new defaults and constraint pinned by SQL tests.

## Out of scope

- Changing the per-issue `instruction_set` machinery (migration 053) — it
  seeds from whatever kind resolves and needs no new behavior here.
- Rewording the existing `plan`/`code`/`prd`/`breakdown` defaults — only
  the new kinds get new text.
- Per-type UI beyond the Settings editor — us-96.5.
- Org-level (project-independent) instruction overrides — the table stays
  per-project as it is.
