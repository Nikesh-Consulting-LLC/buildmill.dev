# US-100.1 — Agent Instructions is one document

**Status:** New
**Phase:** 100 — One document, not twenty-two sections
**Depends on:** nothing (revises us-99.3, shipped 2026-08-15)

## Story

As the manager, a project's conventions are twenty-two catalog sections —
Tech stack, Commands, Run commands, Code style, Things to avoid, Project
overview, Architecture notes, File structure, Testing expectations,
Environment setup, Git/PR conventions, Monorepo notes, Links, Known issues,
Permissions, Preferred libraries, Good patterns, Subagent notes, Versioning &
Release, and more
([project-guidelines-catalog.ts](../apps/web/src/lib/project-guidelines-catalog.ts)).
Every one is a card I fill in separately, and the agent receives them
concatenated back into a single document anyway.

The structure buys nothing. It costs a form with twenty-two boxes where a
person wants one editor, it makes "where does this note go?" a question with
no good answer, and it means the thing an agent actually reads exists in no
single place a human can edit.

So it becomes what it always was at the point of use: **one markdown
document, called Agent Instructions**. The manager writes it; the agent reads
it; nothing assembles it from parts.

## Acceptance criteria

- **AC1 — one field replaces the catalog.** A migration adds a single
  markdown column for the project's Agent Instructions. The twenty-two-key
  catalog, its unique-per-key index
  ([009_project_guidelines.sql](../infra/supabase/migrations/009_project_guidelines.sql)),
  and `project-guidelines-catalog.ts` retire.

- **AC2 — nothing already written is lost.** The migration concatenates each
  project's existing sections, **in `sort_order`**, into the new field with
  their titles as headings — the same output `assemble_project_guidelines`
  produces today, so what an agent reads is byte-identical on the day of the
  change. Verified per project on both databases before the old table is
  dropped, and the drop is a **separate later migration**, not this one.

- **AC3 — one editor.** Project Settings shows a single markdown editor for
  Agent Instructions, not a wall of section cards. Edits keep landing in
  `content_audit` as they do now.

- **AC4 — the run context is unchanged in shape.** `dispatch_issue` keeps
  putting the assembled text into `input_context.guidelines` under that key,
  so no run, no MCP tool and no runner path has to change in this story.
  `assemble_project_guidelines` becomes a thin read of the new field.

- **AC5 — Versioning & Release moves into the document.** That section is
  served separately today as reference material to release runs
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L1848), addressed by its
  section key. **Its content becomes part of the Agent Instructions**, which
  every agent already reads — so the separate reference path retires rather
  than being re-pointed at a key that no longer exists. The migration
  concatenates it like any other section (AC2), and the tool that served it
  is removed in the same change, not left answering an empty string. How a
  version actually gets *decided* is us-100.6.

- **AC6 — both projects, types, tests.** Migration applied to prod and dev,
  `database.types.ts` regenerated, embed sweep run. A test pins AC2's
  concatenation against real multi-section fixtures.

- **AC7 — the Guidelines section is decommissioned, on a schedule.** Nothing
  reads `project_guidelines` after this story: not `dispatch_issue`, not the
  MCP tools, not the UI. The table survives one release **only** as a
  rollback for AC2's backfill, and its drop is written as the next migration
  in the same change so it cannot be forgotten. A test asserts no code path
  reads the table, so "decommissioned" is a checked fact rather than an
  intention.

## Out of scope

- Publishing (us-100.2), the tab names (us-100.3), templates (us-100.4), the
  refresh run (us-100.5).
- `project_learnings`, which is a separate table with a separate purpose and
  is **not** decommissioned.
