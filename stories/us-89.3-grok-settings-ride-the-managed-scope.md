# US-89.3 — The agent's Grok settings ride the managed scope

**Status:** New
**Phase:** 89 — The zero-secret workspace
**Depends on:** us-89.1 (loopback broker — the MCP entry this writes), us-83.1 (pinned CLI, config doors closed), us-78.5 (model config write), docs.x.ai/build/settings (the authority)

## Story

As the operator, the factory configures the interactive agent's CLI the
way its vendor documents, not through ad-hoc files: everything the
factory ENFORCES — the model block (gateway `base_url`,
`env_key = "BUILDMILL_GATEWAY_KEY"`, `api_backend`), the factory MCP
server (the us-89.1 loopback broker entry), timeouts and hardening —
is written to the **managed scope** (`$GROK_HOME/.grok/managed_config.toml`,
per docs.x.ai/build/settings), with hard constraints expressed in
**requirements.toml** where the CLI supports them. The user scope stays
the agent's own; the **project scope** (`.grok/config.toml` inside the
workspace repo) is never written by the factory again — the layer us-83.1
had to harden against injection, and the file that carried a token into a
project repo on 2026-08-13, simply stops being ours.

`grok inspect` — the vendor's own "what configuration loaded" command —
becomes the verification: Prepare Workspace step 7 and the session doctor
run it and report which scopes answered, so a config that silently failed
to load is a named failure, not a mystery mid-run.

## Acceptance criteria

- **AC1 — managed scope carries the enforcement, per work unit.** On
  every session open and interactive-run claim, the factory REGENERATES
  `managed_config.toml` under the slot's own `$GROK_HOME` from the
  CURRENT project's resolution — that project's model route, that
  project's granted tool servers, the `mcp_servers.factory` loopback
  entry (us-89.1 shape; legacy only when the broker is down). There are
  no global Grok settings anywhere: `$GROK_HOME` is per-slot (own OS
  user), the content is per-work-unit, and the serial law (us-32.3 /
  Phase 86) guarantees one project's config is all a slot ever needs at
  once. A slot claiming a different project next gets that project's
  config on the same rewrite. The user-scope `config.toml` write is
  retired for factory-owned keys.
- **AC2 — the workspace is config-silent.** The factory never writes
  `.grok/config.toml` (or any `.grok/` file) inside the workspace. The
  grok module's `mcp_argv` translation targets the managed scope instead.
  FACTORY_SCRATCH keeps refusing `.grok/` as the belt.
- **AC3 — requirements where supported.** Constraints the CLI honors via
  `requirements.toml` (per the docs) are expressed there rather than
  re-implemented as wrapper checks; unsupported constraints keep their
  current enforcement, named in a code comment.
- **AC4 — inspect is the probe.** Prepare Workspace step 7 (and the
  full-prepare checks) run `grok inspect` when the grok/interactive module
  is enabled and record which config scopes loaded; a managed config that
  did not load fails the step with the CLI's own words.
- **AC5 — precedence proven.** A test pins that a workspace
  `.grok/config.toml` (attacker- or agent-written) cannot override the
  managed model/MCP entries — the vendor's documented precedence, verified
  from our side.

## Out of scope

- `/etc/grok/`-level machine-wide config (per-slot `$GROK_HOME` isolation
  is the fleet's model; machine-wide would leak across slots).
- UI-section settings (`ui.*`) — the agent's cosmetics are its own.
- Claude/opencode module config layouts (their own vendors' conventions;
  separate story if wanted).
