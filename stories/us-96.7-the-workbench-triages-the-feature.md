# US-96.7 — The workbench triages the feature, not its stories

**Status:** Completed
**Phase:** 96 — The type shapes the path
**Depends on:** us-96.4 (the feature-level actions and per-child approval surface the rolled-up row points at)

## Story

As the manager, the Workbench and the Factory queue still triage a feature
one story at a time. US-24.1 and US-24.2 nested the children under a
feature *header*, but that is presentation only — every child story still
lands as its own row in the waiting list, its own row in the queue, its own
unit in the pending count. A five-story feature reads as five decisions
when, after us-96.4, there is exactly one steering wheel: the feature.

A feature with children becomes **one triage item** everywhere work is
listed for action. Its row summarizes where the batch stands, carries the
feature-level actions, and names — without expanding into rows — anything
inside that needs me. Standalone stories, bugs, and chores are untouched:
they are their own steering wheels.

## Acceptance criteria

- **AC1 — one row on the Workbench.** In the waiting list
  ([waiting-list.tsx](../apps/web/src/app/(app)/workbench/waiting-list.tsx)),
  a feature with non-abandoned children renders as a single row; its
  children never render rows of their own in any waiting group. The row
  shows the batch's position in one line — e.g. "3 of 5 plans approved ·
  2 await review", "building 2 of 5 · 1 in review" — plus the oldest
  child's wait age in the existing age pill. The US-24.1 header
  interleaving retires for these rows.
- **AC2 — the row acts at feature level.** The row's actions are us-96.4's:
  dispatch the phase, or go to the feature page for the per-child approval
  walk. A child in trouble (`failed`/`needs-fixes`) does not get its own
  row — the feature row carries a named attention badge ("US-2.3.4 needs
  attention") linking to the feature page, where the trouble exemption's
  individual dispatch lives.
- **AC3 — the count agrees with the list.** `org_pending_count`
  (migration 249) counts a feature with one or more waiting children as
  **one** pending item, in the same migration that ships the UI — the
  sidebar badge, the tab title, and the page can never disagree
  ([data.ts](../apps/web/src/app/(app)/workbench/data.ts) pins this pact;
  `getPendingCount` and `loadWaiting` change in step).
- **AC4 — one item in the Factory queue.** On the Factory queue
  ([queue-view.tsx](../apps/web/src/app/(app)/factory-queue/queue-view.tsx),
  [data.ts](../apps/web/src/app/(app)/factory-queue/data.ts)), a feature's
  child runs collapse into one feature row: state rolls up (running if any
  child runs, else blocked-on-you / held / queued), the active child's
  worker and activity phrase show on the row, and a held batch shows the
  blocker `issue_hold_reason` already names ("waiting: US-2.3.2 ahead of
  this one is still running"). The US-24.2 parent nesting retires for
  these rows.
- **AC5 — the feature is the reorder unit.** Dragging reorders the feature
  as a block — its children's `queue_rank`s move together and never
  interleave with another item's runs. Pause acts on the feature's queued
  runs as one unit. Runs of standalone items are untouched.
- **AC6 — in progress stays honest.** The In Progress section
  ([in-progress-section.tsx](../apps/web/src/app/(app)/workbench/in-progress-section.tsx))
  keeps one row per working agent — the manager must still see what an
  agent is actually doing, and reach its CLI window (us-91.3) — but the row
  names the batch: "FEAT-2.3 › US-2.3.4".
- **AC7 — no orphaned entry points.** Everything a child row used to offer
  is reachable through the feature row or the feature page — verified by a
  click-through on dev covering: plans awaiting review, a build in review,
  a child in trouble, a held batch, and a running batch; recorded in this
  file before Testing.
- **AC8 — both projects, tests.** The `org_pending_count` migration applied
  to prod and dev, types regenerated, embed sweep run. A SQL test pins the
  new count definition; web tests pin the rollup summarizer where it is
  pure (child states in → row line + attention badges out).

## Verified (2026-08-15, on the phase branch; this machine has no web env)

- **Workbench**: `feature-rollup.ts` collapses parented items across every
  actionable group into one synthesized feature row — batch position in
  the reason line ("2 stories waiting — 1 awaits your review · 1 needs
  attention"), the worst wait on the age pill, trouble named in chips that
  link to the feature page, and the US-84.1 batch gate rendered on the row
  in both the card and table layouts. The US-24.1 header interleaving
  degrades to identity (children never reach it). The stranded group keeps
  per-run rows deliberately.
- **Count**: migration `259_pending_count_counts_the_feature_once.sql`
  applied to **both** projects; the four issue groups collapse to
  `count(distinct coalesce(parent_id, id))` with 249's predicates carried
  byte-for-byte, and the web computes `pendingCount` after the rollup so
  the two definitions stay one. Function executes clean on live dev (the
  zeros returned to a service-role caller are the `is_org_member` gate).
- **Factory queue**: `queue-rollup.ts` + `queue-view.tsx` — one row per
  feature with precedence-rolled state, the active member's worker and
  activity on the row, the batch's hold reason otherwise, "N of M paused"
  when mixed. The feature row is the drag unit (members ride as a
  contiguous block through the same `reorder_factory_queue` RPC; a claimed
  member pins the block) and the pause unit (`set_run_paused` per queued
  member). Members stay reachable through the row's expander with per-run
  pause/cancel intact — nothing a child row offered is lost.
- **In Progress**: a per-story run row names its batch
  ("FEAT-2.3 › US-2.3.4"); feature-owned builds were already one row.
- Nine unit tests on the two pure rollups (web suite green, 162 tests);
  `npm run build` green.
- **AC7 deviation — for UAT**: this machine has no `apps/web/.env.local`,
  so no dev server and no browser click-through was possible here. The
  five-state click-through (plans awaiting review, a build in review, a
  child in trouble, a held batch, a running batch) is the UAT script for
  this story rather than a pre-verified fact. Everything mechanically
  provable without a browser was proven above.

## Out of scope

- Standalone stories, bugs, and chores — one item each already; unchanged.
- The Work Items list and the feature page itself — they enumerate children
  by design; rollup is for the action surfaces (Workbench, Factory queue).
- Collapsing In Progress to one row per feature — an agent's live work
  stays visible per run (AC6 labels it, nothing more).
- Any dispatch/refusal rule — us-96.4 owns the rules; this story only makes
  the surfaces tell the same story.
