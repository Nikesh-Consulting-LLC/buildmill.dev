# US-101.4 — The notes are a declaration, not a wall of markdown

**Status:** Testing
**Phase:** 101 — A release explains itself
**Depends on:** nothing hard — buildable in parallel with us-101.2 and us-101.3

## Story

As the manager, I want the release page to read like a document someone wrote
for me: a standfirst that says how to work through it, numbered sections with
a line explaining what each one is for, and a closing note on what to do if
the happy path fails. What I get is `notes_summary` and `notes_detail` —
two `text` columns rendered as undivided markdown
([page.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/page.tsx)
L301–327) — with exactly one rule enforced on either of them: the version must
appear in the first line.

The obvious answer is to let the agent write the whole page as HTML. It is the
wrong answer here, for two reasons that are facts about this system rather
than matters of taste:

**The facts a masthead needs do not exist when the agent writes.**
`release_prep.submit` fires the UAT deploy *after* the notes are stored
([release_prep.py](../apps/api/app/release_prep.py) L139–172). At the moment
the agent writes, the deploy has not run, `uat_deployed_at` is null, and no
`suite_runs` row exists for the release. An agent-authored masthead saying
"deploy: success, 1m00s · api suite 1735 passed" is not a quality problem to
be prompted away — it is a fabrication, because those numbers do not yet exist
anywhere.

**A sandboxed page cannot carry the checkboxes.** The only safe way to render
agent-authored HTML here is the wireframe precedent — `<iframe srcDoc
sandbox="allow-scripts">` *without* `allow-same-origin`
([wireframe-panel.tsx](../apps/web/src/app/\(app\)/issues/[id]/wireframe-panel.tsx)
L263–268). That frame has an opaque origin: it cannot reach the session,
cannot resolve a relative URL, and cannot record a verdict. So its checklist
would be decorative and the real pass/fail buttons would sit below it — two
checklists, which is precisely the thing this phase exists to prevent.
Dropping the sandbox means handing agent-authored script the app's origin and
session, which is not on offer.

So the agent authors every word and every section of the page, and hands it
back as a declaration the app renders — the same call this repository already
made for wireframes, where migration 185 records the reasoning: store the
declaration, not the rendered output, because that is what lets a restyle
reach every page ever written. Release notes are read for years. Freezing each
one in the CSS of the day it was cut is a decision you make once and regret
slowly.

## Acceptance criteria

- **AC1 — a release stores a declaration.** `releases` gains `notes_doc`
  (jsonb, default empty) in the next free migration, beside the
  `proposed_version` / `version_rationale` columns us-100.6 added. Not
  `artifacts`: that table's `issue_id` is still `NOT NULL` with a composite
  foreign key to `issues` ([031_issues.sql](../infra/supabase/migrations/031_issues.sql)
  L171–187), and a release has no issue.

- **AC2 — the vocabulary is small and written down.** A single pure module
  owns the block types and the section names. It carries a *brief* — a
  description of the vocabulary generated from the vocabulary itself — so the
  instruction that tells an agent what to write and the renderer that draws it
  cannot drift apart. This is the `vocabulary_brief()` pattern from
  [wireframes.py](../apps/api/app/wireframes.py) L677, and it exists because
  the alternative is prose describing a renderer that has since changed.

- **AC3 — one block type is free-form prose.** A `prose` block carrying
  markdown, rendered through the existing `MarkdownView` the notes already use.
  A fixed vocabulary will be the wrong shape for some release; this recovers
  nearly all of the expressive range of raw HTML at none of the cost, and
  means a bespoke need is a *paragraph*, not a bespoke page.

- **AC4 — a malformed declaration is coerced, never refused.** Unknown keys
  are dropped, missing ones defaulted, and what was changed is reported back
  to the agent as advice — the `_as_declaration` pattern
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L3821) and the US-42.1
  doctrine behind it (L3570): fifteen consecutive hand-backs were once refused
  over a field typed as the wrong shape, and each refusal cost a full re-run.
  Coerce the shape; never reject the payload over it.

- **AC5 — the agent does not write the facts it cannot know.** The
  declaration has no slot for deploy result, deploy duration, or automated
  test counts, and the instruction says why. Those are rendered by the app
  from data it already has (us-101.5).

- **AC6 — the flat notes survive, and stay true.** `notes_summary` and
  `notes_detail` continue to exist and continue to satisfy the
  version-in-the-first-line rule — the release list, the retry path and the
  document export all read them. Where they are derived from the declaration,
  they are derived *before* validation, not after.

- **AC7 — the exported document is regenerated, and stops failing silently.**
  The `release-notes-<version>` project document
  ([release_prep.py](../apps/api/app/release_prep.py) L113–131) is written
  from the declaration. A second artifact that diverges from the page is worse
  than no artifact. That block is currently wrapped in a bare `except
  Exception` that swallows any failure and leaves `doc_id = ""`, so a release
  can complete with no exported notes and nothing said about it; the export
  staying non-fatal is right, staying silent is not.

- **AC8 — every existing release still renders.** A release whose `notes_doc`
  is empty renders today's markdown view unchanged. No backfill, no migration
  of prose.

## Verified (2026-08-15)

- **AC1** — migration **272**, applied to **both** databases:
  `releases.notes_doc jsonb not null default '{}'`.
- **AC2** — `apps/api/app/release_notes.py` owns `SECTIONS` and `BLOCKS`, and
  `vocabulary_brief()` is generated from them. It reaches the agent on the
  claim (`notes_vocabulary`) and is inlined by the runner prompt, so the text
  telling an agent what it may write and the renderer drawing it are the same
  source. A test asserts the brief names every section and block key.
- **AC3** — `prose` carries markdown, rendered through the existing
  `MarkdownView`.
- **AC4** — `as_declaration` coerces: a whole document sent as a string
  becomes one prose block, `sections` sent as a list is keyed, an unknown
  block is kept as prose, a bad callout tone becomes `info`. Every one reports
  a finding and none is a rejection; the findings ride back on a **successful**
  submit.
- **AC5** — the vocabulary has no slot for deploy result, duration or suite
  counts, and `vocabulary_brief()` says why in the same breath.
- **AC6** — `notes_summary`/`notes_detail` untouched, version-in-first-line
  rule unchanged.
- **AC7** — the export is rendered by `render_markdown` from the declaration
  and the checks, so the file and the page cannot diverge. The bare
  `except Exception` that swallowed a failed write now records
  `document_error`, which the tool reports back — non-fatal, no longer silent.
- **AC8** — `hasNotesDoc` gates the new rendering; an empty declaration falls
  through to today's markdown view. No backfill.
- Covered by the 34 tests in `test_release_notes_vocabulary.py`;
  `npm run build` green.

### Not verified

No declaration has been rendered from a real agent's hand-back — see us-101.5,
which could not be opened in a browser here.

## Out of scope

- The rendering itself — us-101.5.
- A `release_kit/` directory. The wireframe kit is ~2,850 lines because it
  draws arbitrary UI; a release page is a masthead, some sections, a checklist
  and some prose. That is a React component and one Python module, and cloning
  the kit here would be copying the precedent instead of applying it.
- Committing the page into the project's repository the way wireframes are
  committed.
- Versioning or diffing declarations across release attempts.
  `release_prep_runs.notes_summary` / `.notes_detail` remain declared and
  unwritten ([215_release_system_job.sql](../infra/supabase/migrations/215_release_system_job.sql)
  L88); this story does not adopt them.
- Surfacing us-100.6's `proposed_version` / `version_rationale`, which no UI
  reads yet. That is us-100.6's own recorded gap, not this story's.
