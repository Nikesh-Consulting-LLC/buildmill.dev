# US-101.4 — The notes are a declaration, not a wall of markdown

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** nothing hard — buildable in parallel with us-101.2 and us-101.3

## Story

As the manager, I want the release page to read like a document someone wrote
for me: a standfirst that says how to work through it, numbered sections with
a line explaining what each one is for, and a closing note on what to do if
the happy path fails. What I get is `notes_summary` and `notes_detail` —
two `text` columns rendered as undivided markdown
([page.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/page.tsx) L301) —
with exactly one rule enforced on either of them: the version must appear in
the first line.

The obvious answer is to let the agent write the whole page as HTML. It is the
wrong answer here, for two reasons that are facts about this system rather
than matters of taste:

**The facts a masthead needs do not exist when the agent writes.**
`release_prep.submit` fires the UAT deploy *after* the notes are stored
([release_prep.py](../apps/api/app/release_prep.py) L123). At the moment the
agent writes, the deploy has not run, `uat_deployed_at` is null, and no
`suite_runs` row exists. An agent-authored masthead saying "deploy: success,
1m00s · api suite 1735 passed" is not a quality problem to be prompted away —
it is a fabrication, because those numbers do not yet exist anywhere.

**A sandboxed page cannot carry the checkboxes.** The only safe way to render
agent-authored HTML here is the wireframe precedent — `<iframe srcDoc
sandbox="allow-scripts">` *without* `allow-same-origin`
([wireframe-panel.tsx](../apps/web/src/app/\(app\)/issues/[id]/wireframe-panel.tsx)
L262). That frame has an opaque origin: it cannot reach the session, cannot
resolve a relative URL, and cannot record a verdict. So its checklist would be
decorative and the real pass/fail buttons would sit below it — two checklists,
which is precisely the thing this phase exists to prevent. Dropping the
sandbox means handing agent-authored script the app's origin and session,
which is not on offer.

So the agent authors every word and every section of the page, and hands it
back as a declaration the app renders — the same call this repository already
made for wireframes, where migration 185 records the reasoning: store the
declaration, not the rendered output, because that is what lets a restyle
reach every page ever written. Release notes are read for years. Freezing each
one in the CSS of the day it was cut is a decision you make once and regret
slowly.

## Acceptance criteria

- **AC1 — a release stores a declaration.** `releases` gains `notes_doc`
  (jsonb, default empty). Not `artifacts`: that table's `issue_id` is `NOT
  NULL` with a composite foreign key to `issues`, and a release has no issue.

- **AC2 — the vocabulary is small and written down.** A single pure module
  owns the block types and the section names. It carries a *brief* — a
  description of the vocabulary generated from the vocabulary itself — so the
  instruction that tells an agent what to write and the renderer that draws it
  cannot drift apart. This is the `vocabulary_brief()` pattern from
  [wireframes.py](../apps/api/app/wireframes.py) L677, and it exists because
  the alternative is prose describing a renderer that has since changed.

- **AC3 — one block type is free-form prose.** A `prose` block carrying
  markdown, rendered through the existing `MarkdownView`. A fixed vocabulary
  will be the wrong shape for some release; this recovers nearly all of the
  expressive range of raw HTML at none of the cost, and means a bespoke need
  is a *paragraph*, not a bespoke page.

- **AC4 — a malformed declaration is coerced, never refused.** Unknown keys
  are dropped, missing ones defaulted, and what was changed is reported back
  to the agent as advice — the `elaborate` coercion pattern
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L3777). A shape quibble
  must not cost a re-run.

- **AC5 — the agent does not write the facts it cannot know.** The
  declaration has no slot for deploy result, deploy duration, or automated
  test counts, and the instruction says why. Those are rendered by the app
  from data it already has (us-101.5).

- **AC6 — the flat notes survive, and stay true.** `notes_summary` and
  `notes_detail` continue to exist and continue to satisfy the version-in-the-
  first-line rule — the release list, the retry path and the document export
  all read them. Where they are derived from the declaration, they are derived
  *before* validation, not after.

- **AC7 — the exported document is regenerated, not orphaned.** The
  `release-notes-<version>` project document ([release_prep.py](../apps/api/app/release_prep.py)
  L101) is written from the declaration. A second artifact that diverges from
  the page is worse than no artifact.

- **AC8 — every existing release still renders.** A release whose `notes_doc`
  is empty renders today's markdown view unchanged. No backfill, no migration
  of prose.

## Out of scope

- The rendering itself — us-101.5.
- A `release_kit/` directory. The wireframe kit is ~2,850 lines because it
  draws arbitrary UI; a release page is a masthead, some sections, a checklist
  and some prose. That is a React component and one Python module, and cloning
  the kit here would be copying the precedent instead of applying it.
- Committing the page into the project's repository the way wireframes are
  committed.
- Versioning or diffing declarations across release attempts.
  `release_prep_runs.notes_summary` / `.notes_detail` remain declared and
  unwritten ([215_release_system_job.sql](../infra/supabase/migrations/215_release_system_job.sql)
  L88); this story does not adopt them.
