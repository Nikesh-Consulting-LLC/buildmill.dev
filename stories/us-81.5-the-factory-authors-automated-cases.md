# US-81.5 — The factory authors automated cases

**Status:** Testing
**Phase:** 81 — Automated release testing
**Dependencies:** us-81.1

## Story

As a manager, I want a story's plan to mark which test cases will be
automated, and the coding agent to deliver the spec files as part of the
change, so automated coverage grows with every story instead of being a
separate project someone has to run.

## Context

Authoring is LLM work; it rides the existing artifact/review path. The plan
run already writes a test plan whose approval materializes `test_cases` rows;
this story widens that contract. Specs are code: they land in the project
repo through the same reviewed changeset as the feature, and pin with the
release commit for free.

## Acceptance criteria

1. The test-plan JSON contract gains optional `execution`
   (`manual|automated`) and `layer` (`api|browser`) per case. The parser
   (`artifacts_sim._normalize_case`), the approval materialization
   (`workflow._materialize_test_plan`), and its service-role mirror
   (`db.materialize_test_cases`) carry them. A case that omits them is
   `manual` — every existing plan parses unchanged.
2. The baked `plan` instruction says when to mark a case automated (the
   acceptance is machine-checkable against a deployed instance) and which
   layer it belongs to. The baked `code` instruction says an
   automated-marked case means the spec file is part of the change, written
   under the suite's convention.
3. A new MCP tool `report_spec_map(run_id, [{test_case_id, suite_id,
   spec_ref}])` — a sibling of `report_test_results` — records the linkage at
   code-run submit. When the work item merges, the mapped cases flip to
   `execution='automated'` with their `suite_id` and `spec_ref`.
4. The code run's dispatch context carries the project's declared suites
   (names, layers, `results_path` conventions) so the agent writes specs
   where the pipeline will find them.
5. `attach_release_inherited_cases` is re-created to carry the new columns
   (`execution`, `suite_id`, `spec_ref`, `always_on_uat`) onto release
   copies, **and** to additionally attach active `always_on_uat` cases even
   when they belong to no included work item — the person-flagged
   always-on-UAT suite, delivered for manual and automated cases alike.

## Out of scope

- Converting existing prose cases to specs (us-82.2 — this story is about
  new cases at plan time).
- Any change to how manual cases are marked at release time.

## Outcome

Built 2026-08-11. Migration `242_inherit_automated_cases.sql` (both DBs):
inheritance carries execution/suite_id/spec_ref/always_on_uat and attaches
always-on cases without an issue (`is not distinct from` dedup + the now
load-bearing project filter). The parser accepts `execution`/`layer` (valid
vocabulary only — invented values are dropped, pinned by
`test_automated_case_authoring.py`); both materialization paths store
`execution`. `layer` is accepted in plans but not a column — the suite chosen
at spec time carries the layer. New MCP `report_spec_map` (held on
`runs.spec_map`, **project**-scoped so conversion chores can map other
stories' cases); applied on merge in both paths (manual approve +
auto-approve), never on rejection. The rendered run context carries the
project's suites + the authoring contract — deliberately rendering-side, so
project-level instruction overrides can never shadow it (the
worker-instruction precedence trap).

**Verified:** parser tests, Essential green. **Not verified:** an agent
actually authoring an automated case end-to-end.
