# US-96.11 — A key never rides the trace

**Status:** Completed
**Phase:** 96 — The type shapes the path
**Depends on:** nothing (extends the us-89.1 zero-secret-workspace line to
the telemetry the runner emits)

## Story

As the manager, the run trace showed me a credential. During run
`22b807a5`'s zombie retry (2026-08-14, see us-96.9), the agent probed the
loopback MCP broker with curl, and the tool summaries streamed to
`run_trace` carried the `X-Factory-Local-Key` value **verbatim, twice** —
on a table the dashboard renders to anyone who can open the run. The blast
radius happened to be small: the broker key is machine-local, minted fresh
at supervisor start
([mcp_broker.py](../apps/runner/supervisor/mcp_broker.py)), worthless off
the box. But nothing about the path that leaked it knows that. The same
emit pipeline would have shipped the worker token or the gateway key just
as faithfully — long-lived credentials this time — and the agent got
partway there in the same run, echoing `TOKEN_PREFIX` from its environment.

The us-89.1 rule is "files travel; secrets must not ride them". Telemetry
travels further than files — into the database, the dashboard, and
`content_audit`. Same rule, same rigor: the supervisor knows every secret
it holds, so nothing it emits off the box may contain one.

## Acceptance criteria

- **AC1 — one choke point on the runner.** Every string the supervisor
  sends off the box — run trace content, run activity lines,
  permission/decision summaries, module stdout destined for `runs.stdout`,
  incident payloads — passes one redaction step
  (in [session_host.py](../apps/runner/supervisor/session_host.py)'s emit
  path or the posting layer beneath it, not per call site) that replaces
  every live secret value the supervisor holds — the broker local key, the
  worker token, the gateway key, any SSH or provider credential in its
  environment — with a mask naming the kind:
  `[redacted:factory-local-key]`, `[redacted:worker-token]`. Values are
  matched exactly (and base64/URL-encoded forms of them), so ordinary prose
  about keys is untouched.
- **AC2 — the API assumes the runner failed.** `record_run_trace`
  ([db.py](../apps/api/app/db.py)) — or the route in front of it — scrubs
  pattern-shaped credentials it can recognize without knowing values:
  `X-Factory-Local-Key: <value>`, `X-Worker-Token: <value>`,
  `Authorization: Bearer <value>`. The scrubbed form is what is stored;
  the original is nowhere, including `content_audit`.
- **AC3 — the stored row is the clean row.** Redaction is at write time,
  not render time: reading `run_trace`/`runs.stdout` with service role
  shows the mask. No web-side masking is added or needed.
- **AC4 — the incident is replayed as a test.** A runner test feeds the
  2026-08-14 shape — a tool summary containing a curl command with the
  live broker key — and asserts the persisted content carries the mask and
  not the key; a sibling case does the same for a worker token in an
  env-echo line. An api Essential test pins AC2's header patterns.
- **AC5 — the ledger is swept once.** A one-off sweep over existing
  `run_trace` and `runs.stdout` rows for the AC2 patterns scrubs any hit
  in place and records what was found in this story's Verified section.
  (Expected: the two known 2026-08-14 rows, whose key dies with the next
  supervisor restart — noted, restarted, confirmed dead.)

## Verified (2026-08-15)

- **AC1**: `supervisor/redact.py` is the registry+scrubber (exact value,
  base64 and URL-encoded forms; masks name the kind; values under 8 chars
  never register). The choke points are the two posting layers — the
  control socket's `connection.notify()` (run traces, session narration,
  incidents) and `WorkerClient.submit()` (module stdout/error destined
  for `runs.stdout`) — never per call site. Registrations: the broker's
  local key at mint (`mcp_broker.py`), the worker token at startup
  (`__main__.py`), the gateway key at env mint (`model_env`), the
  subscription token at `subscription_env`. One honest scoping note: SSH
  and provider credentials never enter the supervisor's environment (they
  live server-side in Vault/Storage); what reaches the box is the minted
  gateway key, which is registered.
- **AC2/AC3**: `db.scrub_credential_patterns` masks the three header
  shapes (`X-Factory-Local-Key`, `X-Worker-Token`,
  `Authorization: Bearer`, case/quote/separator-tolerant) at write time
  in `record_run_trace` AND on `runs.stdout`/`error` in `complete_run` —
  the stored row is the clean row; no render-time masking exists.
- **AC4**: the incident replayed as tests — the runner side
  (`test_redact.py`, 6 tests: the curl shape, the env echo, the base64
  form, prose untouched, short values, params walk) and the api side
  (`test_trace_redaction.py`, 4 tests pinning the header patterns).
  Runner suite 323 passed; api Essential 1680 passed.
- **AC5 — the sweep found more than the two known rows.** Prod
  `run_trace` held **119** credential-shaped rows: 100
  `X-Factory-Local-Key` (broker keys — machine-local, dead on supervisor
  restart), **11 `X-Worker-Token`**, 8 `Authorization: Bearer`. Dev had
  zero; `runs.stdout` was clean on both. All swept in place with the
  same patterns the write path now enforces; a negative-lookahead
  re-scan confirms **zero raw values remain**. ⚠️ For UAT: the 11
  worker-token rows carried a **long-lived** credential — rotate the
  worker token(s) on Settings → Workers, since the values sat readable
  in the dashboard until today.

## Out of scope

- Restricting what an agent may *run* — probing its own loopback broker
  with curl is legitimate debugging; the sin was persisting the credential,
  not executing the command.
- Entropy-based secret *guessing* (flagging any high-entropy string) — too
  many false positives on hashes and shas, which traces legitimately carry.
  Known values and known header shapes only.
- The Vault/Storage write-only story for provider and server credentials —
  already the rule; nothing here touches it.
- Rewriting `content_audit` history beyond what AC5's sweep finds.
