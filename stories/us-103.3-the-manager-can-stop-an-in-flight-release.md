# US-103.3 — The manager can stop an in-flight release

**Status:** New
**Phase:** 103 — A release cannot get stuck
**Depends on:** us-103.1 (the reaper), US-23.1/US-63.3 (`/releases/{id}/cancel`), US-90.1 (`/releases/{id}/retry`), migration 215 (in-flight uniqueness index), US-26.7 / US-145 (run cancel — the shape this follows)

## Story

As the manager, when a release is in flight and I can see it is not going
anywhere, I want one button that stops it, so I am never reduced to editing the
production database — which is exactly what 2026.08.16.3 cost me.

Today the release lifecycle has a hole in the middle. `/cancel` refuses
anything but `queued` ([releases.py:225](../apps/api/app/routers/releases.py:225)).
`/retry` refuses anything but `failed` / `uat-deploy-failed`
([releases.py:293](../apps/api/app/routers/releases.py:293)). `running` sits
between them, reachable by neither, and the Actions cell renders empty because
the UI mirrors those rules exactly
([releases/page.tsx:266](../apps/web/src/app/(app)/releases/page.tsx:266)).
Meanwhile `releases_one_in_flight_per_project` counts `running` as in flight,
so the release I cannot touch is also blocking every future cut.

us-103.1 reaps this — after the two-hour lease expires. This story is the
manager not having to wait for it.

## Design

### Stop is cancel, grown up

`/cancel`'s original restriction was principled and is now wrong in one
respect. US-23.1 reasoned that once a worker holds the prep it is "doing real
work — writing notes, the UAT deploy about to fire", so the honest routes are
to stop the run or let it reach UAT and reject it. But release prep is not a
`runs` row: there is no Stop-work button pointed at it anywhere, and rejecting
a release stuck at `running` leaves the prep row live. The escape hatch it
pointed at does not exist.

So `/cancel` widens to accept `queued`, `running`, `notes-ready` and
`uat-deploy-failed`, and the widened path does what the narrow one did not
have to: **stop the job as well as the release.**

- Any `release_prep_runs` row for this release that is `queued` is deleted, as
  today (US-23.1's reasoning holds — a job that never began should not
  fabricate a failure in the activity feed).
- Any row that is `running` is moved to `cancelled` — the status
  `release_prep_runs` has carried since migration 215 and nothing has ever
  written — with the manager and their reason stamped on it. Not deleted: it
  *did* happen, it cost a session, and the release detail page's attempt list
  should say so.
- The release lands on `cancelled`, out of the in-flight index, so the next cut
  is immediately possible.

### The stopped agent cannot come back

This is the half that makes Stop safe, and the half a naive implementation
misses. `release_prep.submit` gates on `prep["status"] != "running"`
([release_prep.py:84](../apps/api/app/release_prep.py:84)), so a prep moved to
`cancelled` is refused — but the message must say *stopped by the manager*,
not the generic status line, because the agent's transcript is where that
answer gets read. The runner's own supervision (`release_prep_status`,
[workloop.py:945](../apps/runner/supervisor/workloop.py:945)) already polls
status and reports; a `cancelled` result stops it reporting the agent as
failed for a job the manager took away.

The same rule us-103.2 states applies from this side: nothing resurrects a
stopped prep. Re-adoption skips it, heartbeat refuses it, submit refuses it.

### Reject stays the UAT verdict

`/reject` already accepts `running` and this story does not narrow it — but the
two say different things and the UI should stop blurring them. **Reject** is a
verdict on the build: UAT found it bad, it is superseded, the version name is
burned forever. **Stop** is a verdict on the *attempt*: the agent died, the
job hung, I changed my mind, and nothing was learned about the build. A
release cut ten minutes ago whose runner crashed should not enter the record
as a rejected build.

One correctness follow-on: reject at `running` must stop the prep row too, by
the same path, or a zombie agent can write notes onto a rejected release and
fire a UAT deploy. That is a real hole in `/reject` today and it closes here.

## Acceptance criteria

- **AC1 — Stop accepts the states that need it.** `POST /releases/{id}/cancel`
  accepts `queued`, `running`, `notes-ready` and `uat-deploy-failed`, and
  refuses `deploying`, `uat-deployed`, `uat-signed-off`, `promoting`,
  `released`, `rejected`, `rolled-back`, `cancelled` — each with a sentence
  naming the state and the action that does apply (sign-off, reject, or
  rollback).
- **AC2 — the job stops with the release.** Queued prep rows are deleted;
  running prep rows move to `cancelled` with `finished_at`, the manager id and
  the reason. The release lands `cancelled` with `cancelled_at`,
  `cancelled_by`, and the reason. No prep row for the release is left
  `queued` or `running`.
- **AC3 — the stopped agent is refused, in words.** `submit` and `heartbeat`
  against a cancelled prep are refused with a message naming that the manager
  stopped the release, and write nothing — no notes, no test cases, no
  document, no UAT deploy. Pinned by a test that submits a full valid payload
  after a stop and asserts the release row is untouched.
- **AC4 — the project is unblocked.** After a Stop, no in-flight release
  exists for the project: `build_preview` reports no in-flight blocker and a
  fresh cut succeeds.
- **AC5 — reject closes the same hole.** `/reject` on a `running` release
  stops its prep row by the same path, so a late submit is refused there too.
- **AC6 — the button is where the state is.** The releases list and the
  release detail page show **Stop** for every state AC1 accepts, with a
  confirmation naming the version and taking an optional reason (`ConfirmDialog`,
  not a new pattern). Stop and Reject are visibly different actions with
  one-line help distinguishing "the attempt failed" from "the build is bad".
  A stopped release shows its reason and stopper wherever `rejected_reason`
  surfaces today.
- **AC7 — tests.** API: each accepted state stops cleanly; each refused state
  returns 409 with the right sentence; submit/heartbeat after stop are refused
  and write nothing; reject-at-running stops the prep; a cut succeeds
  immediately after a stop. Web: the button renders for exactly AC1's states.

## Out of scope

- Killing the agent's *process* on the machine. Stop is a factory-side state
  change; the runner notices through the status it already polls. Reaching
  into a session to kill it is US-26.7's territory and a separate story.
- Stopping a release at `deploying` — the deploy pipeline owns its own
  terminal branches, and interrupting it mid-flight is a different problem
  with different failure modes.
- Refunding or accounting for the tokens a stopped session spent.
- Any change to `/retry` — a stopped release is not retried, it is superseded
  by a new cut. (A stopped release deliberately does **not** offer Retry: the
  manager chose to end this attempt.)
- Auto-stopping on any signal. Automatic ending is us-103.1's reaper, on lease
  expiry, and nothing else.
- The Workbench surface for all of this — us-103.4.
