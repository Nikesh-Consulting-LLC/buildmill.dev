# US-91.3 — An agent at work has a door to its CLI

**Status:** Completed
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** [us-91.2](us-91.2-dispatch-opens-with-what-is-already-running.md) (the section this button lives in)

## Story

As the manager, when I see an agent has been on a story for forty minutes,
the next thing I want is to watch it — the CLI window. Today the only doors
to it are the Team roster (us-78.11) and a run page. From In Progress I have
to leave the dashboard, find the agent in the roster, and click the terminal
icon there, having already read the agent's name on the row I was looking at.

Put the same button on the In Progress row. Same icon, same destination,
same glow while the agent is working — one affordance the manager learns
once.

## Acceptance criteria

- **AC1 — the button is the roster's button.** A `TerminalSquare` icon
  button, `variant="outline" size="sm"`, titled `Open CLI window — working
  now`, navigating to `/team/{principalId}/console` — matching
  [team-view.tsx](../apps/web/src/app/(app)/team/team-view.tsx)'s agent row
  so the two cannot drift into looking like different features.
- **AC2 — only where there is a CLI to open.** The button renders only when
  the claiming agent's `enabled_modules` include `interactive` — the same
  condition the roster uses. An agent without that module gets no button,
  not a button that lands on an empty page.
- **AC3 — it glows, because the row is by definition working.** Every In
  Progress row has a live claim, so the button always carries the roster's
  working-now emerald ring. It is a state indicator that agrees with the row
  it sits on.
- **AC4 — one query, not one per row.** The modules lookup is a single
  `runner_config` read for the principals actually on screen, resolved in
  [data.ts](../apps/web/src/app/(app)/dashboard/data.ts) alongside the claims
  it already loads — not a fetch per row and not a full roster load
  (us-87.1).
- **AC5 — a row without a principal is unaffected.** Where the claim has no
  `workerPrincipalId`, the row renders exactly as it did without the button.

## Out of scope

- Adding the button to the **In the factory** tab or the Completed tab.
- The Claude Terminal / runner console actions from the roster — this is the
  CLI window only.
- Any change to the console page itself.

## Verified (2026-08-14, localhost against build-mill-dev)

- With the claiming agent's `enabled_modules` including `interactive`, the row
  rendered the button with `title="Open CLI window — working now"` and the
  roster's emerald ring, linking to `/team/{principalId}/console`.
- With the same agent's modules empty, no button rendered — verified before and
  after flipping the module on and back.
- `interactiveByPrincipal` is resolved server-side in **one** `runner_config`
  read for the claiming workers only, and is `{}` when nobody holds a claim.
