# US-98.2 — A merge names the branches it will land

**Status:** Testing
**Phase:** 98 — Many branches, one landing
**Depends on:** us-98.1 (the `merge` run kind and its instruction exist)

## Story

As the manager, a merge run is meaningless without its subject. Every other
run kind derives what to work on from the work item — the story, the plan,
the release. A merge derives nothing: the branches to land are a decision I
make, and nothing in the database can currently hold it.

So a chore gains a branch list, and a chore that carries one is what a merge
run is dispatched against. The list is the contract: us-98.3 lets the agent
read exactly these branches and no others, us-98.5 fails the run if any one
of them is left unmerged, and us-98.6 shows the manager the same list beside
the diff. Everything downstream reads this one field, so it has to be
validated at the point it is set rather than discovered to be wrong forty
minutes into a run.

The rich branch-picking UX is the manager's own later decision. This story
delivers the data, the dispatch path, the refusals, and a minimal way to set
the list — enough for a merge to be created and run.

## Acceptance criteria

- **AC1 — a chore can carry branches.** A migration adds a branch list to
  `public.issues` (a `text[]`/`jsonb` array of branch names, default empty),
  org-scoped by the table's existing RLS with no new policy. A comment on
  the column says what it is for and which run kind reads it.

- **AC2 — the list is validated where it is written, not where it is read.**
  Setting the list refuses, with a named message: an empty list on an item
  being dispatched as a merge; a duplicate branch; the project's default
  branch appearing in the list; and a branch that does not exist on the
  repository at the time it is set. A non-chore work item cannot carry a
  branch list at all.

- **AC3 — dispatch routes it.** `dispatch_kind_for` answers `merge` for a
  chore that carries a non-empty branch list, and the existing chore rule
  still holds — there is no planning phase, so a named `plan` dispatch keeps
  refusing with the message
  [255_chore_is_one_shot.sql](../infra/supabase/migrations/255_chore_is_one_shot.sql)
  already gives it. A merge run's `input_context` carries the branch list
  and each branch's head sha **as resolved at dispatch**, plus the default
  branch and its head, so the run has a frozen record of what it was asked
  to land.

- **AC4 — refusals are named, never silent.** `issue_dispatch_refusal`
  answers in prose for: a merge dispatch on an item with an empty list; a
  merge dispatch on a non-chore; and a branch in the list that has since
  been deleted from the repository. Each says which branch and what to do.

- **AC5 — a minimal way to set it.** The chore's work-item page can add and
  remove branches, showing each one's head sha short form, and dispatches
  the merge from there. The branches are visible on the item after dispatch
  as a read-only record of what was asked for.

- **AC6 — both projects, types, sweep, tests.** Migration applied to prod
  and dev, `database.types.ts` regenerated, embed sweep run. SQL tests pin
  every AC2 refusal and the AC3 routing; a route test pins that
  `input_context` freezes the head shas rather than re-reading them.
  `npm run build` green; api Essential green.

## Verified (2026-08-15, live against build-mill-dev and Software-Factory prod)

- Migration `262_a_merge_names_its_branches.sql` applied to **both**
  projects; `issues.merge_branches text[] not null default '{}'` exists on
  each. No new table, so no new RLS — the column rides `issues`' existing
  org-scoped policies.
- **A 15-assertion probe on dev, which rolls itself back**, covering every
  AC2/AC3/AC4 rule in one transaction: `non-chore-refused`,
  `dupes-refused`, `default-branch-refused`, `blank-refused`,
  `whitespace-refused`, `plain-chore-infers-code`, `merge-needs-branches`,
  `infers-merge`, `code-refused-on-merge-chore`, `merge-on-story-refused`,
  `mismatched-heads-refused`, `blank-sha-refused`; then the happy path —
  `run_kind=merge`, `ctx_branches=2`, `ctx_base=base999`,
  `issue_status=queued`, `instruction_seeded=yes`. Residue afterwards
  confirmed **zero** (probe issues 0, merge runs 0, issues with branches 0).
- The `code`-on-a-merge-chore prose refusal reads, live: *"this chore
  carries 2 branch(es) to merge — dispatch merges them, it does not build"*.
  `issue_dispatch_refusal(chore,'merge')` correctly returns null.
- **No regression to the hot path.** Surveyed all **53** prod issues through
  `dispatch_kind_for`: 12 resolve, 41 refused on pre-existing status rules,
  **0** merge. Every existing issue has an empty list, so `v_is_merge` is
  false throughout and behavior is unchanged by construction — confirmed
  empirically rather than argued.
- **Two defects of mine, caught before they could ship:**
  - `dispatch_merge` was first written `security definer`. Every sibling
    dispatcher (`dispatch_issue`, `dispatch_breakdown`, `dispatch_wireframe`)
    is `security invoker` with RLS as the authorization; definer would have
    read and mutated **any issue in any org by id**. Found by checking the
    siblings' `prosecdef` before wiring the endpoint. Corrected on both
    databases — now `prosecdef=false`, `proconfig=null`, granted to
    `authenticated`+`service_role`, identical body hash `731c5b3b…` on each.
  - Dropping `p_kind text default null` from `dispatch_kind_for` failed with
    `42P13` — Postgres refusing to break every one-argument caller. Noted in
    the migration. Also learned and recorded: `apply_migration` is
    transactional, so that failure rolled back with **nothing** partially
    applied (verified by checking for the column and functions afterwards).
- API: `POST /api/v1/issues/{id}/dispatch-merge` resolves the base and every
  named branch from GitHub, refuses by name — **naming all missing branches
  at once** — and passes `[{branch, head_sha, base_head}]` to the RPC.
  The `issues→projects` embed uses the hinted
  `projects!issues_project_id_org_id_fkey(...)`; constraint name confirmed
  against the live catalog, and the embed sweep passes (11).
- **11 route tests**, Essential, no network: head freezing with exact payload
  equality, manager's branch **order** preserved, empty list refused without
  touching GitHub *or* minting a token, a deleted branch named, *all* missing
  branches named at once, unresolvable base, RPC refusal → 409, unknown issue
  → 404, repo-less project → 409, token scoped to the issue's org (US-76.4),
  and auth required. **Confirmed non-vacuous by mutation**: dropping
  `base_head` from the payload turned the freezing test red, and it went
  green again on restore.
- UI: a `Branches to merge` section on the chore Overview offers the
  repository's real branches (so an unenterable name cannot be entered),
  shows each head's short sha, writes through the Supabase SDK under RLS with
  an optimistic toggle that **reverts and surfaces the trigger's message** on
  refusal, warns about selected-but-since-deleted branches, and dispatches.
  The default branch is filtered out of the offer rather than refused later.
- `database.types.ts` regenerated: 13 hunks — `merge_branches` in
  Row/Insert/Update and `dispatch_merge` in Functions. The web build was
  re-run **against the regenerated types**, because the first pass compiled
  on stale ones and proved less than it appeared to.
- api Essential green (**1697 passed, 545 skipped, 0 failed**);
  `npm run build` green; embed sweep green.
- **Not verified here, for UAT**: the section rendered in a browser, a real
  branch actually resolving against a live repository, and an end-to-end
  dispatch producing a queued merge run an agent claims. The SQL tests in
  `test_merge_run_kind_sql.py` still **skip** (`DATABASE_URL` unset); their
  assertions were executed directly against both databases instead.

## Out of scope

- The fuller branch-picker surface — which branches to offer, how to group
  them by work item, whether to suggest a set. The manager is deciding that
  UX separately; AC5 is deliberately the minimum that works.
- Deleting the source branches after a successful merge. Nothing is cleaned
  up in this phase; the branches stay exactly where they are.
- Changing the status of the work items those branches belong to. Landing a
  branch is not approving its work item, and this phase keeps them separate.
- Auto-creating merge chores from merged-but-unreleased work — a merge chore
  is created by the manager.
