# US-98.4 — A merge hands back a branch and a pull request

**Status:** New
**Phase:** 98 — Many branches, one landing
**Depends on:** us-98.3 (the agent can read every branch it was given)

## Story

As the manager, the result of a merge run must arrive the way every other
piece of work arrives: as a diff I can read, on a branch I can inspect, in a
pull request my CI can run against. Not as a commit that has already landed.

That last point is the whole design. It would be simpler for the agent to
submit a merged tree and for the server to write it to the default branch on
success — but conflict resolution is precisely the work where an agent is
most likely to silently drop somebody's change, and "the merge succeeded" is
not evidence that it kept everything. A merged file that compiles and reads
cleanly can still have lost a whole function. So the merge lands on a
factory branch, a pull request carries it into the default branch, GitHub
runs the checks, and the manager approves (us-98.6).

The commit itself is built the way every factory commit is built —
`apply_changeset` — which means a single-parent commit of the merged tree.
The source branches will therefore still read as unmerged on GitHub, and
their own pull requests will not auto-close. That is a known and accepted
consequence for this phase, recorded here so nobody later reads it as a bug.

## Acceptance criteria

- **AC1 — the merge has its own branch.** `resolve_working_branch` gives a
  merge run a factory branch of its own, named for the chore
  (`factory/merge-<display-id>`), branched from the base recorded at
  dispatch. The branch is created by the hand-back, not at dispatch, so a
  merge that never submits leaves nothing behind.

- **AC2 — the hand-back declares what it merged.** The merge run's
  submission carries the changeset (base sha, message, files) **plus** a
  summary and, for each branch in the run's declared list, the head sha the
  agent merged and a short account of what it did — clean, or resolved with
  a named decision. The declared set is checked against the run's list;
  us-98.5 owns what happens when they disagree. The submission runs through
  the same gate every changeset does: `split_scratch`,
  `validate_changeset`'s caps and path rules, the project-SECRET sweep, and
  the repo's real `.gitignore`.

- **AC3 — the pull request is opened by the factory.** On a valid
  submission the factory applies the changeset to the merge branch and opens
  a pull request into the project's default branch, reusing the existing
  open-PR-if-head-matches path in
  [worker.py](../apps/api/app/routers/worker.py) L1204-1234. The PR body
  names every source branch with the head sha that was merged and carries
  the agent's summary; the title names the chore. A merge run never uses
  `direct` submit mode — the pull request is the point, so a project
  configured for direct submission is refused by name rather than silently
  bypassing review.

- **AC4 — a moved base is a retry, not a corruption.** `apply_changeset`
  already refuses when the branch head has moved from the declared
  `base_sha`, answering `{stale, current_head}`. A merge run gets the same
  answer with a merge-shaped hint — refetch the branches, redo the merge
  against the new base, resubmit — and nothing is written.

- **AC5 — the runner knows the shape.** The `merge` row in `HANDBACK_SHAPE`
  ([cli_base.py](../apps/runner/supervisor/modules/cli_base.py) L62-73)
  added by us-98.1 matches what AC2 actually requires, and the runner's
  hand-back tests cover it. `MCP_REQUIRED_KINDS`
  ([workloop.py](../apps/runner/supervisor/workloop.py) L265) is considered
  and the decision recorded.

- **AC6 — the surface is pinned and documented.** New or changed tools go
  into `test_all_tools_listed` / `_READ_ONLY_TOOLS`, the server
  `instructions` blob, and
  [interface-catalog.md](../docs/application/interface-catalog.md).

- **AC7 — tests.** Essential, faked GitHub: branch naming; PR opened with
  the branch list in its body; the direct-submit-mode refusal; the stale
  base answer; and the validation gate rejecting an oversized or
  path-escaping merge changeset. Runner suite green.

## Out of scope

- **A real multi-parent merge commit.** `github.create_commit` accepts
  multiple parents and the factory could build one, which would make GitHub
  show the source branches as genuinely merged and auto-close their PRs.
  This phase does not: it reuses `apply_changeset` unchanged. The
  consequence — source branches still reading as unmerged, `git log
  --merges` showing nothing — is accepted, and is the natural first
  candidate if this phase's merges prove useful.
- Deleting source branches, or touching the status of the work items they
  belong to (us-98.2's out-of-scope list, restated because this is where
  someone would be tempted).
- Approving or merging the pull request — us-98.6.
- The all-or-nothing rule and its failure path — us-98.5.
