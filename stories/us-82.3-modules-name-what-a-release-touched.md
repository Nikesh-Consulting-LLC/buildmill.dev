# US-82.3 — Modules name what a release touched

**Status:** Testing
**Phase:** 82 — Smoke, conversion, selection
**Dependencies:** us-81.4

## Story

As a manager, I want to name my project's modules once — a label and the
paths that belong to it — and have each release tell me which modules it
touched and which manual regression cases that suggests, so scarce human
testing time goes where the change actually was.

## Context

Automated suites run whole every release — machine time is cheap, and
selective execution is an optimization with a correctness cost. Module
selection earns its keep where time is scarce: the *manual* cases a person
runs at release time. This story is a suggestion engine, not a gate.

## Acceptance criteria

1. New `project_modules` table (org/project-scoped, member RLS): `name`
   (unique per project), `path_globs` (list of pathspec globs). Managed in
   project settings via plain RLS CRUD.
2. `test_cases` gains a nullable `module_id`; the case dialog and the plan
   contract can set it.
3. At release cut, the factory computes the touched modules from the release
   commit range's changed files matched against the globs, and records them
   on the release.
4. The release page shows the touched modules, and suggests active manual
   cases tagged with a touched module that are **not** already attached to
   the release — with a one-click attach per case (attached cases then gate
   sign-off exactly like inherited ones).
5. Automated suites are unaffected: they keep running whole. Nothing in this
   story selects or skips automated tests.
6. A project with no modules defined behaves exactly as today.

## Out of scope

- Selective execution of automated suites by module.
- Auto-attaching suggested cases — the manager clicks, deliberately.
- Deriving modules automatically from the tree.

## Outcome

Built 2026-08-11. Migration `243_project_modules.sql` (both DBs):
`project_modules` (name + path_globs), `test_cases.module_id`,
`releases.touched_modules` (names, not ids — the snapshot survives renames).
Modules card in the Suites tab; module select in the case dialog. The cut
endpoint computes touched modules from the real commit range (GitHub compare
files matched by pathspec gitwildmatch — git's own glob semantics),
best-effort and never fatal; needs a previous released version (a first
release records none). The release page suggests active manual cases tagged
with a touched module and not already in the set, one-click Attach (a copy,
so it gates sign-off like any inherited case). Automated suites are
untouched — they run whole.

**Verified:** build + Essential green; schema pins. **Not verified:** a cut
computing touched modules against a real repo.
