# US-114.2 — A project edits its files like a template

**Status:** Testing
**Phase:** 114 — A template travels as a zip
**Depends on:** US-100.3 (the project's two instruction tabs), US-100.4 (the
template pages' shared tree + editor, `template-files-editor.tsx`), US-99.4
(the publish bar and its unpublished-files badge), US-7.4/US-7.5 (the two
mark-ready stamps), US-20.1 (Task processing lives with the instructions),
US-114.1 (the shared Export/Import buttons)

## Story

As a manager, I want a project's instruction files presented exactly the way
the template pages present them — one grouped file tree on the left, one
editor on the right — so that what I see on a template and what I see on a
project are the same thing in the same shape, instead of two tabs with two
different layouts for what is, on disk, one folder.

## Design

### Two tabs, two layouts, one folder

Today `/projects/<id>` has an **Agent Instructions** tab (one big document
editor with mark-ready, publish, history and the refresh dialog above it) and
a **Task Instructions** tab (a section nav on the left, one card per kind
stacked on the right, each card its own editor with Save / Reset to default).
The templates pages (us-100.4) show the same seventeen files as a single tree
— *Agent instructions* first, then the seven phase groups — with exactly one
editor open at a time. A manager who has just authored a template and opens
the project it seeded sees a different shape for the same content.

### One **Instructions** tab, the templates' shape

The two tabs become one, **Instructions**, built from the same
`TemplateFileTree` + `TemplateFileEditor` the templates render:

- **Left**: *Task processing* (the routing/auto-approve card US-20.1 put first
  — it is settings, not a file, so it sits above the tree as its own row),
  then the file tree exactly as the templates draw it, filled files dark and
  empty files muted, `?file=<key>` selecting one.
- **Right**: the selected file's editor — title, path, description, Save —
  plus what a project knows that a template does not: who last edited it and
  when (or *factory default* when nobody has), and the template-drift line
  us-114.3 adds.
- **Above both**: the two mark-ready controls (Agent Instructions, Task
  Instructions — they are two stamps on the project row and the readiness
  card links to each), the publish bar (which already counts *all* files;
  it only ever hung on the document tab), one History link that follows the
  active file's audit surface, and the refresh dialog.

Saving is unchanged underneath: the document to `projects.agent_instructions`,
a task file to its `worker_instructions` row, both straight to Supabase under
RLS. Blanking a task file stores an empty string (a project row, unlike a
template section, is the value an agent reads — there is no fallback to
clear to). *Reset to default* keeps working from the editor header
(us-114.3 makes it template-aware).

### Nothing else moves

`?tab=guidelines` and `?tab=worker-instructions` keep resolving — both land on
Instructions (the first with `AGENTS.md` selected) so old deep links from the
readiness card, deployment dialog and refresh review still work; those links
are updated to the new tab name too.

## Acceptance criteria

1. `/projects/<id>` shows one **Instructions** tab in place of *Agent
   Instructions* and *Task Instructions*; the tab has a *Task processing* row
   above the same grouped file tree the template pages show (same seventeen
   files, same groups, same order, same names), and one editor on the right.
2. Selecting a file in the tree opens it in the editor with its title, path
   and description; editing and saving writes the project's copy (the
   document to `projects.agent_instructions`, a task file to its
   `worker_instructions` row) and the tree's filled/empty style follows.
3. The editor header says who last edited the file and when, or *factory
   default* when it has never been edited.
4. Mark-ready for both stamps, the publish bar with its unpublished-files
   count, History, and Refresh instructions all sit above the tree/editor
   and behave as before; History opens the audit surface of the active file.
5. *Task processing* opens the routing/auto-approve card in the editor pane
   and its switches still save.
6. `?tab=guidelines` and `?tab=worker-instructions` open the Instructions tab
   (`guidelines` with `AGENTS.md` selected).

## Out of scope

- **Template provenance, drift, Reset to template, Change template,
  Export/Import** on this tab — us-114.3.
- **A publish-per-file affordance.** The publish bar publishes the whole set;
  per-file publish is not asked for.
- **Retiring `worker-instructions-tab.tsx` / `agent-instructions-tab.tsx`
  callers elsewhere** beyond this page — nothing else renders them.

## Verification (2026-08-17)

Built on branch `us-114.1-template-zip`. `npm run build` (type-check) and
`npm run test:web` (257 pass) clean; the deleted `agent-instructions-tab.tsx`,
`agent-instructions-editor.tsx` and `worker-instructions-tab.tsx` have no
remaining importers.

The Demo project's `/projects/<id>?tab=instructions` was fetched from the dev
server and its streamed HTML parsed: the tab strip reads *Overview,
Instructions, Deployments, Suites, Environment, Documents, Learnings, GitHub*
(the two old tabs gone), the tree carries **17** file rows plus *Task
processing*, and the header holds Export / Import / Change template / Reset to
template / Save (AC1). `?tab=guidelines` and `?tab=worker-instructions` map to
`instructions` in `page.tsx` (AC6).

**Not verified live:** clicking through save (AC2), the last-edited note
(AC3), mark-ready / publish / History behaviour (AC4) and Task processing
switches (AC5). The project page reveals its Suspense boundary with a React
view transition, which waits on `requestAnimationFrame`, and the embedded
Browser pane was hidden during this session so the client never painted the
content the server had already sent. UAT walks those in a visible browser.
