# US-103.5 — A release in flight freezes dispatch, and says so

**Status:** New
**Phase:** 103 — A release cannot get stuck
**Depends on:** migration 235 (`issue_dispatch_refusal` / `issue_hold_reason` / `org_issue_dispatch_blocks`, US-74.5), us-103.3 (Stop — the way out of the freeze), us-103.4 (the Workbench release card)

## Story

As the manager, while a release for a project is in flight, I want the factory
to refuse to route new work to agents on that project — and to tell me, in
the place I clicked, exactly why and what would unblock it. I can still write
stories, bugs and chores all day; I just cannot send them to an agent until the
release is finished, stopped or rejected.

The reason is the release's own promise. A release is **pinned to one commit**,
and everything downstream — the notes, the UAT deploy, the promotion — reads
that SHA. Work merged while it is in flight is not in the build being tested,
but it *is* on the default branch, so it silently belongs to the next release
while the manager watches it merge during this one. The tested build and the
branch drift apart in the one window where the manager is meant to be reading
UAT results rather than reasoning about which commits are in what.

## Design

### The rule goes where the rules already are

Migration 235 built exactly the mechanism for this and its opening comment
states the discipline: a surface may ask "can this be dispatched right now,
and if not, why?" and gets the answer **from the same code the factory
enforces, never a re-derivation**. `issue_dispatch_refusal(p_issue, p_kind)`
returns the message; `dispatch_issue` raises what it returns;
`org_issue_dispatch_blocks` hands the identical string to the UI, which
renders it through `heldReason` ([dispatch-block.ts:22](../apps/web/src/lib/dispatch-block.ts:22)).

So this story adds one refusal branch to `issue_dispatch_refusal` and gets
enforcement, the Workbench explanation, and the issue-page explanation from a
single place. No new endpoint, no UI-side rule, and no possibility of the
button and the RPC disagreeing.

### A hard refusal, not a soft hold

Migration 235 distinguishes a **hard** refusal (the button would error) from a
**soft** hold (the run is created and immediately parked, draining by itself
when the condition clears). A soft hold is tempting here — queue everything
during the release, let it drain on promotion — and it is the wrong choice for
this rule. A parked run holds a claim slot and reads to the manager as work in
progress; the whole point is that nothing is in progress on this project until
the release lands. And the freeze can end in three different ways (released,
stopped, rejected), one of which means "this build was bad" — draining a
queue automatically into a rejected build's aftermath is not a decision to
make silently. Hard refusal, manager re-dispatches, one click.

### What is frozen, and what is not

Frozen: `plan` and `code` — the kinds that put a worker on the project's
repository and end in a merge.

Not frozen: authoring and grooming work that never touches the repo —
`breakdown`, `elaborate`, `draw`, and `guidelines` (already exempt as
"not delivery work", US-43.5). This is the manager's stated line: writing
stories, bugs and chores stays open, routing them does not. Creating and
editing work items is plain CRUD under RLS and is untouched by this story in
any case.

Also not frozen: work already in flight. A run claimed before the cut keeps
going, and its PR can still be reviewed and merged — stopping a worker
mid-story to protect a release would trade one stranded thing for another.
The freeze is on **starting** new work, which is the manager's own action and
the one the message can explain.

Scope is the release's project. Other projects in the org dispatch normally.

### The words

The refusal names the release, its version, its state, and the way out —
because the manager reading it on the Workbench needs to know whether they are
waiting on themselves:

> Release 2026.08.16.3 is in flight (on UAT — waiting on test results and
> sign-off). New work can be written but not dispatched on this project until
> it is released, stopped or rejected.

The lifecycle phrase reuses `FLIGHT_WORDS` from us-103.4 so the Workbench card
and the refusal cannot describe the same release differently.

## Acceptance criteria

- **AC1 — one rule, in the enforced place.** A migration (applied to **both**
  Supabase projects) adds the release-in-flight branch to
  `issue_dispatch_refusal(p_issue, p_kind)` for kinds `plan` and `code`, when
  the issue's project has a release in a state the in-flight uniqueness index
  counts. `dispatch_issue` therefore refuses it with the identical message;
  `database.types.ts` is regenerated and the embed sweep passes.
- **AC2 — the message says why and what unblocks it.** The refusal names the
  version, the lifecycle phrase, and the three exits (released, stopped,
  rejected), in the wording above.
- **AC3 — the UI explains before the click.** On the Workbench and the issue
  page, dispatch-shaped actions on a frozen project render held with that
  reason — the existing `org_issue_dispatch_blocks` → `heldReason` path, no
  new client-side rule. The Workbench release card states that dispatch is
  frozen while it is in flight, so the explanation is present even when no
  work item is on screen.
- **AC4 — authoring is untouched.** Creating, editing, splitting and
  prioritising stories, bugs, chores and features works normally on a frozen
  project, as do `breakdown`, `elaborate`, `draw` and `guidelines` dispatches.
  Pinned by tests, because this is the half the manager asked for by name.
- **AC5 — in-flight work continues.** Runs claimed before the cut are not
  cancelled, parked or held; their submit, review and merge paths are
  unchanged.
- **AC6 — the freeze lifts by itself.** When the release reaches `released`,
  `cancelled` or `rejected`, dispatch succeeds again with no manual step and
  no stale cached block on either surface.
- **AC7 — scoped to the project.** A release in flight on project A never
  blocks dispatch on project B, in the same org or another.
- **AC8 — tests.** API/SQL: the refusal fires for `plan`/`code` on a frozen
  project and not for the exempt kinds; `dispatch_issue` raises it;
  `org_issue_dispatch_blocks` reports it as hard; it clears on each of the
  three exits; another project is unaffected. Web: the held reason renders on
  both surfaces.

## Out of scope

- Blocking **merges** of already-open PRs during a release. The manager's
  approve-and-merge stays available; if merging during a release proves to be
  the sharper edge, that is its own story with its own evidence.
- A soft/parked hold or an auto-draining queue (considered and rejected
  above).
- An override switch for the freeze. If it needs one, that is a decision worth
  its own story rather than a flag added in passing.
- Freezing anything at org level, or across projects.
- Changing what counts as in flight — `releases_one_in_flight_per_project`
  (migration 215) is the single definition and this story reads it rather than
  restating it.
