# US-91.2 — Dispatch opens with what is already running

**Status:** Completed
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** [us-91.1](us-91.1-the-tab-is-named-for-what-you-do-there.md) (the tab this sits on)

## Story

As the manager, before I dispatch anything I want to know what is *already*
being worked on. Today that answer lives one tab away, on **In the factory**,
mixed in with queued and held rows that nobody has picked up. So the decision
"should I send three more stories in?" is made on the wrong tab, or on
memory.

Put a section called **In Progress** at the top of Dispatch, above the
action rows, showing only the work an agent has actually claimed and is
running right now — with the same row shape the factory table uses, because
a manager should not have to learn two layouts for the same fact.

The factory tab stays exactly as it is. It answers a different question
("what is the factory holding, claimed or not"), and it owns the queue
details, the hold reasons and the requeue affordance. In Progress is the
short answer to "who is busy", printed where the dispatch decision is made.

## Acceptance criteria

- **AC1 — the section is on top of Dispatch.** Above the waiting groups
  rendered by
  [waiting-list.tsx](../apps/web/src/app/(app)/dashboard/waiting-list.tsx),
  under a heading reading `In Progress` with a count, matching the section
  heading style already used by the Releases tab ("In flight (N)").
- **AC2 — claimed and running only.** A row appears only when a worker
  holds a live claim on the run — the same claim rows that give the factory
  table its `workerName`/`runId`. Queued rows, held rows ("Nobody can take
  this", `holdReason`), and rows with no live worker do **not** appear.
  "In progress" means an agent has it, not "the factory knows about it".
- **AC3 — a feature-owned build is one row.** Per us-86.2, a run whose
  issue is a feature shows once, as the feature, with the run's agent,
  elapsed and heard on it — not as one row per story it carries. The story
  count rides the row (`one run, N stories`), and its stories do not appear
  separately.
- **AC4 — the row looks like a factory row.** Type badge, display id, title
  linking to `/issues/{id}?from=dashboard`, the stage/status badge, the
  agent name linking to `/team/{principalId}/runner`, elapsed, and heard —
  with the silence colouring and the `title` explanation the factory table
  already carries, and the `RequeueButton` on a silent row. Columns hidden
  below `lg` fall back to the same subline the factory table uses.
- **AC5 — empty says so plainly.** With nothing claimed, the section
  renders the shared `EmptyState` (never a bare heading with a zero) titled
  **"Nothing is being worked on"**, with a line telling the manager what to
  do about it — dispatch something from the list below. The action rows
  below it still render normally.
- **AC6 — the tab badge does not change.** The Dispatch tab's count still
  counts the action items only (`waitingCount`). In Progress carries its own
  count in its heading. Two numbers, each of one thing.
- **AC7 — no new per-row query.** The section is built from data the
  dashboard already loads for the factory tab (`agentItems`, `featureRuns`
  in [data.ts](../apps/web/src/app/(app)/dashboard/data.ts)). Rendering it
  adds no round trips to the page load (us-87.1, us-87.10).

## Out of scope

- Removing, renaming or thinning the **In the factory** tab. It keeps every
  row it shows today, including the ones In Progress deliberately omits, plus
  Queue details and the feature nesting.
- Any per-row action beyond what the factory table already offers (requeue
  on silence) — the CLI window button is [us-91.3](us-91.3-an-agent-at-work-has-a-door-to-its-cli.md).
- Grouping the section by project — that is [us-91.4](us-91.4-things-to-do-groups-by-project.md).
- Live push updates for the section; it refreshes with the page like the
  rest of the dashboard.

## Verified (2026-08-14, localhost against build-mill-dev)

- **Empty**: with nothing claimed, the section reads `In Progress (0)` above
  the action rows, with the shared `EmptyState` titled **"Factory's idle"**
  over "Dispatch something below." The rows below still render. (Shortened
  after the manager's UAT, along with the tab's "Inbox zero" state.)
- **Populated**: exercised with a temporary synthetic running claim on dev
  (inserted, observed, then deleted — dev is back to its prior state). The row
  showed the type badge, `US-2.1.20`, the title, the `38m elapsed · heard 1m`
  sub-line, the agent linking to `/team/{id}/runner`, and the Elapsed/Heard
  columns — the factory's row shape.
- The Dispatch tab badge stayed `11` while In Progress carried its own count:
  two numbers, each of one thing.

**Changed during implementation — the Stage column reads the RUN, not the
issue.** The first cut echoed `issues.status`, which put a **Queued** pill on a
row inside a section called In Progress whenever the status write lags the
claim. Every row here has a live claim by construction, so the stage is
`Running` (or `Building N` for a feature-owned build) — the same correction
us-86.2 made on the factory tab.

**Not exercised**: the feature-owned build as one row (AC3). No feature build
was live on dev. The code path is the `featureRuns` map the factory tab already
uses.
