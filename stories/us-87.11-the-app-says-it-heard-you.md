# US-87.11 — The app says it heard you

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** us-87.1 … us-87.7 (this exists because those landed)

## Story

As the manager, the app got fast enough that I can no longer tell it is
working. A click lands, the content swaps instantly, and my eye never
registers that anything happened — so I am left wondering whether the click
took. The slowness used to be the feedback; removing it removed the signal
with it.

The mechanism was already built (US-62.8's `GlobalProgressBar` and
`router-with-progress`) and is not broken so much as calibrated for the app
that existed last week. `--animate-global-progress` is a **1.1-second sweep
starting fully off-screen left**, behind a 150 ms opacity fade. A navigation
that now finishes in ~150 ms shows the bar reaching full opacity at roughly
14% of its travel — still mostly off-screen — and then fading out. There is
nothing to see. And with **zero `loading.tsx` files** anywhere in the app,
nothing at all renders between the old page and the new one.

## Acceptance criteria

- **AC1 — the bar reads at any speed.** The progress indicator is
  perceptible on a navigation that completes in ~120 ms *and* on one that
  takes five seconds. It appears with **no delay** (the usual "wait 200 ms
  to avoid a flash" advice is exactly what produces the complaint here) and
  stays a minimum of ~400 ms once shown, so a fast operation still leaves a
  readable signal rather than a flicker.
- **AC2 — a background refresh still stays quiet.** `refreshSilently()`
  keeps its exemption. A page fed by realtime must not strobe "working…",
  or the bar stops meaning "your click landed" — the reason the exemption
  exists. Live updates get their own signal in us-87.12.
- **AC3 — a slow route shows its shape, not a blank.** The six routes with
  real server work — Things to Do, Work Items, a work item, a project, a
  review, the factory queue — each have a `loading.tsx` built from the
  existing `Skeleton` component, laid out to mirror the page beneath so the
  handoff moves as little as possible.
- **AC4 — content arrives, it does not pop.** The skeleton→content handoff
  and route→route changes animate via React's `<ViewTransition>`
  (`experimental.viewTransition`), using the exit-fast / enter-gently timing
  the Next guide prescribes. Changing a filter on the Work Items hub
  crossfades in place rather than snapping — a filter change is "same place,
  different content", not a navigation.
- **AC5 — motion is optional.** Every animation added here stands down under
  `prefers-reduced-motion`, following the `motion-safe:` precedent already
  set in `buildmill-loader.tsx`.
- **AC6 — nothing regresses.** `npm run build` clean, `npm run lint` at 0
  errors, `npm run test:web` green, with the bar's minimum-visible timing
  covered by a unit test (it is pure logic and the one part of this that can
  be tested without a browser).
- **AC7 — proof is visual.** Verified in a browser, in light and dark, with
  reduced motion on and off. A screenshot or page dump is the evidence; a
  passing type-check proves nothing about whether this feels right.

## Out of scope

- Highlighting rows that changed from a live update — us-87.12.
- `unstable_instant` / Cache Components. The `loading.js` doc points at it,
  but it requires `cacheComponents` and `use cache` over the data, and every
  page here reads per-user Supabase data under RLS. Caching that per route
  would be a correctness and security problem, not a speed win.
- Shared-element morphs between routes (thumbnail → hero). A real View
  Transitions capability, but no surface here has that relationship.
- Any change to what the pages fetch. This story is purely how the app
  *reports* what it is doing.

## Verification record

Built 2026-08-13 on `us-87.11-feedback`. No migration.

**Verified:** `npm run build` type-checks clean and accepts
`experimental.viewTransition` on next 16.2.10; `npm run lint` 0 errors;
`npm run test:web` 107/107, with 8 new cases in `lib/progress-timing.test.ts`
covering the minimum-visible arithmetic (AC6).

Verified in a running build (`next start`, port 3100) rather than by
inspection:

- **View transitions actually fire.** `document.startViewTransition` was
  wrapped and counted across a client-side navigation: **3 calls**. The API is
  supported in this browser and so is `view-transition-class`, which is what
  React's `enter`/`exit` props compile to.
- **The CSS is live, not merely written.** All four `::view-transition-*`
  rules are present in the parsed stylesheet. Worth recording how this was
  nearly missed: the browser serializes them as
  `::view-transition-old(*.skeleton-out)` — with the universal name — so a
  substring search for the authored selector returns nothing and the rules
  look absent. The first check produced exactly that false negative.
- The `global-progress` keyframe now animates `width`, and the old
  `translateX` sweep is gone from the compiled CSS.
- No console errors on load.

**A boundary found while verifying, not a defect:** the progress bar lights
only for navigation driven through `useRouter` in
`lib/router-with-progress.ts` — its original US-62.8 purpose was the
post-dialog `router.refresh()`, where "did my click land?" had no answer. A
plain `<Link>` click (the sidebar, a row) does **not** light it, and never
has. Those navigations are covered instead by the `loading.tsx` skeleton and
the crossfade, which is the right feedback for a route load — a bar and a
skeleton both firing would be two signals for one event. Recorded because it
is invisible from the code: the bar's absence on a Link click reads as broken
until you know it is by design. **If the manager wants the bar on Link clicks
too, that is a small follow-up** (wrap navigation in the global transition at
the Link layer).

**Not verified (UAT):**

- **No screenshot.** The Browser pane was not compositing frames in this
  session, so every visual claim above rests on the DOM, the parsed CSS and
  the instrumented transition count — not on having seen it. The manager has
  since looked at it in their own dev server and confirmed it reads well,
  which is the evidence this story actually turns on.
- Light/dark and `prefers-reduced-motion` were not toggled. The reduced-motion
  guard is present in the compiled CSS (`prefers-reduced-motion` matched), but
  its effect was not observed.
- The skeletons were never seen. At current speed the routes rarely suspend
  long enough to render one, which is correct — but it means the six
  `loading.tsx` files and their exit transition are unobserved. Throttling the
  network is the way to force them.
