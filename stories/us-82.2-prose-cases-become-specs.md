# US-82.2 — Prose cases become specs

**Status:** Testing
**Phase:** 82 — Smoke, conversion, selection
**Dependencies:** us-81.5

## Story

As a manager, I want to write a test in words, click **Automate**, and have
an agent turn it into a Playwright or pytest spec through a normal reviewed
change, so my judgment about what to test compounds into the automated suite
without me writing code.

## Acceptance criteria

1. The `/tests` library allows selecting manual cases and clicking
   **Automate**. The factory creates a work item ("Automate tests: N cases")
   carrying the selected case ids — visible in the pool like any other work
   item.
2. The work item dispatches as a **standard `code` run** — no new run kind.
   Its dispatch context carries the conversion brief: the full case bodies
   (title, steps, expected result), the target suite and its conventions,
   and the instruction to write one spec per case.
3. The agent writes the specs, submits the changeset through the normal
   review path, and reports the `case → spec_ref` map via `report_spec_map`.
4. On merge, the cases flip to `execution='automated'` with `suite_id` and
   `spec_ref`; from the next release on, the pipeline answers them instead
   of a human.
5. Send-back works as for any code run: the retry carries the feedback, the
   cases stay manual until a conversion actually merges.

## Out of scope

- A new run kind, job table, or role — a spec is a reviewed code change, and
  the `code` machinery (workspace, changeset, review, retries, merge)
  already exists for exactly this.
- Bulk-converting the entire library in one item — the manager selects; the
  factory doesn't volunteer.

## Outcome

Built 2026-08-11. `/tests` multi-select gained **Automate N cases** (manual +
active only): one click creates a `chore` work item ("Automate tests: N
cases") whose body carries the conversion brief — full case bodies with ids,
the declared suites with their suite_ids, the report_spec_map contract, and
"do not edit the cases" — plus two acceptance criteria. It rides the ordinary
plan-then-code pipeline; `store_spec_map` is project-scoped precisely so this
chore can map cases belonging to other stories; the flip to automated happens
only on merge.
