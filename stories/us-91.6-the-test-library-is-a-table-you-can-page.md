# US-91.6 — The test library is a table you can page through

**Status:** Testing
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** nothing

## Story

As the manager, the Tests page renders every case as a bordered card about
90px tall. Twenty cases is a page and a half of scrolling; a project with a
few hundred is unusable — I cannot see the shape of the library, cannot
compare two cases without scrolling between them, and the browser renders
all of them whether or not I look (the same problem us-87.4 fixed for long
lists elsewhere).

Make it a table: one row per case, the facts in columns, the prose behind a
disclosure. Then page it, so the number of rows on screen is bounded no
matter how large the library grows.

## Acceptance criteria

- **AC1 — one row per case.** The card list in
  [test-library.tsx](../apps/web/src/app/(app)/tests/test-library.tsx)
  becomes the shared `Table`, with columns: select checkbox, title, source
  (human/agent icon), execution (with the suite name on an automated case,
  `spec_ref` as its tooltip), type and environment badges, linked work item,
  status, and the actions cell (edit dialog, abandon/restore). The `every
  UAT` badge keeps its place and its tooltip.
- **AC2 — the prose is one click away.** Steps and expected result move to
  a row that expands underneath, replacing the per-card `<details>`. Nothing
  that was readable before becomes unreachable.
- **AC3 — the table pages.** Client-side paging over the filtered set, page
  size **10** (50 after the first cut; the manager's UAT called it — the point
  was a window you step through, and fifty rows is still a scroll), with a pager reading `N–M of T` and previous/next — matching the
  pattern in [admin/orgs](../apps/web/src/app/(app)/admin/orgs/page.tsx).
  Under one page, the pager does not render.
- **AC4 — filters own the set, paging owns the window.** Changing any
  filter pill resets to page 1 and the count reflects the filtered total,
  never the page.
- **AC5 — selection is honest about its scope.** "Select all" selects the
  cases on the **current page** and says so; the bulk bar's count, the
  Automate button's count, and the delete confirmation all describe exactly
  the rows selected. A selection must never silently include rows the
  manager never saw — this bar deletes test cases and their run history.
- **AC6 — a selection survives paging.** Rows selected on page 1 stay
  selected after paging to page 2 and back, and the bulk bar keeps counting
  them.
- **AC7 — empty and no-match still read well.** The existing `EmptyState`
  ("No test cases match") still renders when the filters exclude everything,
  and the pager is absent.
- **AC8 — the other panels on the page are untouched.** Recent runs, the
  Run tests dialog, and the project picker keep their current layout.

## Out of scope

- Server-side paging, or dropping `steps`/`expected_result` from the list
  query (us-87.3's rule). Today's per-project case counts are small enough
  that the payload is not the complaint; revisit if it becomes one.
- Sorting by column, or search over cases.
- The test **run** pages (`/tests/runs/[id]`, `/tests/suites/[runId]`), which
  have their own checklists.
- Any change to what a case is, or to the automate flow.

## Verified (2026-08-14, localhost against build-mill-dev)

- The library renders as a table: `Test case · Source · Execution · Type &
  environment · Work item`, plus the select and disclosure columns.
- 10 rows on screen with the pager reading **`1–10 of 230`** (UAT round 2;
  it was 50).
- Select-all is page-scoped and says so: **"Select all on this page (10)"**.
- Steps and expected result open in a row beneath, replacing the per-card
  `<details>`.
