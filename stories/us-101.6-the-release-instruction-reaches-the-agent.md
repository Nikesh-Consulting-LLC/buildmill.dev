# US-101.6 — The instruction the release agent reads is the one the manager edits

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** us-101.2, us-101.3, us-101.4 — the vocabulary must exist before the text can describe it

## Story

As the manager, I have a Worker instructions tab with a **Release** box in it.
I can edit that text, it is stored per project, it overrides the factory
default, and since us-99.1 it publishes to `.buildmill/Release_Prep.md`.

It reaches no one.

Instruction delivery is keyed on a `runs` row
([worker.py](../apps/api/app/routers/worker.py) L377). A release-prep job has
no `runs` row — it lives in `release_prep_runs`, a table Phase 63 introduced
precisely to keep it out of the run pool. The runner builds its context as
`{prep_id, version, project_id}`
([workloop.py](../apps/runner/supervisor/workloop.py) L900) and hands it to
`_release_prep_prompt` ([cli_base.py](../apps/runner/supervisor/modules/cli_base.py)
L266), a pure function of those three fields. The queue tool returns five
scalars. At no point does anything read `worker_instructions`.

So the only text steering a release agent is a Python string in the runner —
not per-project, not visible to a manager, not editable without a deploy. And
the text that *is* editable has drifted somewhere worse than stale: it
instructs the agent to call `trigger_deployment`, `get_deployment_run_status`
and `get_deployment_health` and to finish with `submit_release_run`. The last
of those no longer exists. The other three do — but all three resolve a `runs`
row of kind `deploy`, so from a release-prep job they are **structurally
uncallable**. It also does not mention `submit_release_notes`, which is the
actual hand-back, and it describes deploying to UAT as the agent's job when
the system fires that deploy itself the moment the agent submits.

This story makes the editable text the operative text, and makes it true.

## Acceptance criteria

- **AC1 — the release instruction reaches the release agent.** A release-prep
  job resolves the project's `release` instruction — project override, then
  template, then factory default — and the agent reads it before writing
  anything. `project_id` is already in the runner's context, and
  `get_instruction_file` already gates on project authorization, so this is a
  delivery fix rather than a new payload; the us-99.5 doctrine that the file
  is authoritative and MCP is the fallback door applies here unchanged.

- **AC2 — editing the box changes the output.** A manager who edits Release in
  Worker instructions, publishes, and cuts a release gets notes shaped by what
  they wrote. Demonstrated end to end, because this has never once been true.

- **AC3 — the default text describes the job that exists.** Rewritten to name
  `get_release_changes` and `submit_release_notes`, the section vocabulary and
  the step-and-expectation rule from us-101.3, the story tagging from
  us-101.2, and the declaration from us-101.4 — the vocabulary quoted from the
  renderer's own brief rather than restated.

- **AC4 — it forbids the fabrication it currently invites.** The text states
  plainly that the UAT deploy has not happened, that no automated suite has
  run, and that the agent must not describe either. This is the single
  highest-risk sentence in the instruction, because the current text tells the
  agent to deploy and verify — and an agent that believes it deployed will
  write that it did.

- **AC5 — the runner prompt shrinks to mechanics.** `_release_prep_prompt`
  keeps what is true of every release-prep job regardless of project — you
  already hold the claim, there is no repository checkout, a refused call is
  not a finished job — and stops being the place where release-note quality is
  decided.

- **AC6 — the migration is surgery, not a retype.** The `release` branch of
  `baked_worker_instruction` is replaced by reading `pg_proc.prosrc`,
  substituting that one branch, and re-creating the function — the pattern of
  [174_plan_says_what_changes.sql](../infra/supabase/migrations/174_plan_says_what_changes.sql).
  Never retype the function body: that lesson cost migrations 095, 105 and 106
  and is restated at [131_release_run_contract.sql](../infra/supabase/migrations/131_release_run_contract.sql)
  L10. A drift guard asserts the old text is still there and no-ops if it is
  not, so a re-run is safe.

- **AC7 — existing projects are backfilled.** Every project's stored `release`
  instruction that the manager has never edited is updated to the new default.
  Without this the migration changes the factory default and nothing else,
  because every project already carries a seeded row — and the projects that
  most need the fix are the ones that have been running longest.

- **AC8 — a manager's own edit is never overwritten.** The backfill touches
  only untouched rows, using the `updated_by` stamp us-99.7 relies on for the
  same distinction.

- **AC9 — the published file follows.** `.buildmill/Release_Prep.md` reflects
  the new text on the next publish, and what the file says is what the agent
  reads.

## Out of scope

- Making `release_prep` a `runs` row. It was deliberately separated; this
  story delivers an instruction to it, not a re-merge.
- The `deploy` instruction and the deployment run kind.
- Any other kind's default text.
- Per-project *tuning* of the vocabulary itself — the section names and block
  types stay factory-owned (us-101.4), or the renderer and the instruction
  drift apart again.
