# US-101.6 — The instruction the release agent reads is the one the manager edits

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** us-101.2, us-101.3, us-101.4 — the vocabulary must exist before the text can describe it

## Story

As the manager, I have a per-task instruction for **Release**. I can edit it,
it is stored per project, it overrides the factory default, and since us-99.1
it publishes to `.buildmill/Release_Prep.md`
([instruction_files.py](../apps/api/app/instruction_files.py) L41).

It reaches no one.

Instruction delivery is keyed on a `runs` row. There are three delivery sites
— the worker context route ([worker.py](../apps/api/app/routers/worker.py)
L379), `get_work_context`
([factory_mcp.py](../apps/api/app/factory_mcp.py) L727), and the explicit
`get_instruction_file` fallback — and every one of them starts by resolving a
run. A release-prep job has no `runs` row: it lives in `release_prep_runs`, a
table migration 215 introduced with "not another `runs.kind`" written into its
header. The runner builds its context as `{prep_id, version, project_id}`
([workloop.py](../apps/runner/supervisor/workloop.py) L901–909) under the kind
`release_prep` — not `release`, so nothing keyed on the instruction kind could
fire even if it were looked up — and hands it to `_release_prep_prompt`
([cli_base.py](../apps/runner/supervisor/modules/cli_base.py) L266–303), a
pure function of those three fields. The queue and claim tools return five
scalars between them. At no point does anything read `worker_instructions`.

So the only text steering a release agent is a Python string in the runner:
not per-project, not visible to a manager, not editable without a deploy.

Phase 100 made this worse rather than better, and that is the reason this
story exists in the shape it does. Migration 269 **rewrote** the baked
`release` default on 2026-08-15 and backfilled it into every untouched project
row. The new text:

- still instructs the agent to `trigger_deployment`,
  `get_deployment_run_status` and `get_deployment_health`. Those tools exist —
  but each resolves a `runs` row of kind `deploy`, so from a release-prep job
  they are structurally uncallable;
- still ends "Finish with `submit_release_run`", which is not an MCP tool at
  all: the name survives only inside prompt strings. The real hand-back is
  `submit_release_notes`;
- and now says the versioning rules are in the project's Agent Instructions,
  "**your context carries them**". They are not carried. Nothing on this path
  delivers that document.

The consequence is us-100.6's feature landing in a place no agent can reach:
`_release_prep_prompt` still documents the four-argument
`submit_release_notes(prep_id, notes_summary, notes_detail, test_cases)` and
never mentions `proposed_version` or `version_rationale`. The one prompt an
agent actually reads does not know the parameters exist, and the instruction
that does know is the one that never arrives.

This story makes the editable text the operative text, and makes it true.

## Acceptance criteria

- **AC1 — the release instruction reaches the release agent.** A release-prep
  job resolves the project's `release` instruction — project override, then
  template, then factory default — and the agent reads it before writing
  anything. The prep row already carries `project_id`, so this is a delivery
  fix, not a new dispatch payload.

- **AC2 — and so does the Agent Instructions document, because the
  instruction promises it.** Migration 269's text tells the agent to read the
  project's versioning rules from `projects.agent_instructions`. Either the
  document is delivered or that sentence is removed; a default instruction
  that points at something absent is how an agent ends up inventing the
  answer. Reuse `db.get_project_instruction_files` — the us-100.5 builder that
  reads the document and every resolved per-task instruction **live at context
  time rather than from a dispatch snapshot** — the same way the `guidelines`
  run branch of `get_work_context` already does.

- **AC3 — editing the box changes the output.** A manager who edits Release,
  publishes, and cuts a release gets notes shaped by what they wrote.
  Demonstrated end to end, because this has never once been true.

- **AC4 — the default text describes the job that exists.** Rewritten to name
  `get_release_changes` and `submit_release_notes` with its real signature —
  including `proposed_version` and `version_rationale` — the section
  vocabulary and the step-and-expectation rule from us-101.3, the story
  tagging from us-101.2, and the declaration from us-101.4, with the
  vocabulary quoted from the renderer's own brief rather than restated. The
  three deploy tools and `submit_release_run` come out.

- **AC5 — it forbids the fabrication it currently invites.** The text states
  plainly that the UAT deploy has not happened, that no automated suite has
  run, and that the agent must not describe either. This is the single
  highest-risk sentence in the instruction, because the current text tells the
  agent to deploy and verify — and an agent that believes it deployed will
  write that it did.

- **AC6 — the runner prompt shrinks to mechanics.** `_release_prep_prompt`
  keeps what is true of every release-prep job regardless of project — you
  already hold the claim, there is no repository checkout, a refused call is
  not a finished job — and stops being the place where release-note quality
  and the hand-back signature are decided.

- **AC7 — the migration is surgery, not a retype.** The `release` branch of
  `baked_worker_instruction` is replaced by reading `pg_proc.prosrc`, splicing
  that one `when` branch, and re-creating the function — the pattern of
  [269_the_refresh_and_release_defaults_speak_files.sql](../infra/supabase/migrations/269_the_refresh_and_release_defaults_speak_files.sql),
  which is now the closest precedent and the one to copy: it hashes every
  *other* kind before and after and rolls back if any moved, and it no-ops on
  a re-run by testing for a marker from the new text. Never retype the
  function body — that lesson cost migrations 095, 105 and 106 and is restated
  at [131_release_run_contract.sql](../infra/supabase/migrations/131_release_run_contract.sql)
  L10.

- **AC8 — existing projects and templates are backfilled; edited rows are
  not.** Every project row and template section still holding the *old*
  default verbatim takes the new one; a row a manager has touched is left
  exactly as it is. 269 did this for 10/10 projects on prod, and it is
  mandatory here for the same reason: without it the migration changes the
  factory default and nothing else, because every project already carries a
  seeded row.

- **AC9 — the published file follows.** `.buildmill/Release_Prep.md` reflects
  the new text on the next publish, and what the file says is what the agent
  reads.

- **AC10 — the catalog stops documenting a tool that does not exist.**
  [interface-catalog.md](../docs/application/interface-catalog.md) L403 still
  lists `submit_release_run` as the release hand-back and never mentions
  `submit_release_notes` — three phases after it replaced it. Corrected with
  this change, since a reference that names the wrong tool is how the wrong
  tool ends up in the next instruction.

## Out of scope

- Making `release_prep` a `runs` row. It was deliberately separated; this
  story delivers an instruction to it, not a re-merge.
- Deleting the dead `release` branch of `get_work_context`
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) ~L1090–1165). It is
  unreachable twice over — nothing inserts a `runs` row of kind `release`, and
  the `submit_release_run` it ends with is not a tool — but removing it is a
  separate, purely subtractive change.
- **The `release_versions_for_prep` bug, which this story's instruction will
  start triggering.** `db.release_versions_for_prep` queries
  `public.release_preps`; no such table exists anywhere in `infra/` — the
  table is `public.release_prep_runs`. Any hand-back carrying a
  `proposed_version` reaches that query through us-100.6's validation gate and
  raises `UndefinedTable`. So today the version proposal is unreachable
  (nothing tells the agent the parameters exist) and would crash if it were
  reached; AC4 makes it reachable. **This must be fixed before or with AC4**,
  and it is us-100.6's defect, not this phase's — it is named here so it is
  not discovered by a release.
- The `deploy` instruction and the deployment run kind.
- Any other kind's default text.
- Per-project *tuning* of the vocabulary itself — the section names and block
  types stay factory-owned (us-101.4), or the renderer and the instruction
  drift apart again.
