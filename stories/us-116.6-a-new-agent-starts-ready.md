# US-116.6 — A new agent starts ready

**Status:** Testing
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.4 (one status — the Done step renders it), US-116.5
(Start — the Done step's fallback button), US-116.7 (the org's default model —
what a wizard-created agent resolves to when nobody pinned one), US-26.5
(slots come up paused), US-55.1 (project access rows), US-57.3 (pool
placement), US-57.6 (platform-owned config fields), US-61.2 (the wizard offers
no preset choice)

## Story

As the manager, I want an agent I finish creating in the wizard to be
**Ready** on the Team page without a second click on any other page, and I
want the wizard to fail on nothing that the settings page can save, so that
"create an agent" is one action with one outcome and not the start of a
scavenger hunt.

## Design

### Where a new agent lands today

The wizard runs four steps (`add-agent-wizard.tsx:310-502`): `create_worker`,
the access rows, one config PATCH, then placement. What comes out:

| fact | value | where |
|---|---|---|
| `agent_slots.desired_state` | `'paused'`, literal in the INSERT | `agent_provision.py:1906` |
| `runner_config.paused` | `true` | `create_slot_identity` (`:1161`); the adoption path re-keys through `reissue_worker_token(pause=True)` (`:1221-1228`) |
| the systemd unit | `enable --now` — running, connected | `:1928-1937`; log line `[slot N connected — paused, claiming nothing until you enable it]` (`:1944`) |
| model | none — `run_routes: {}` (`:302-308`, US-61.2), no `model_overrides`, `model_routes` seeded from the empty `platform_run_config` | us-116.1's table: five of six live agents |

So the agent connects (Team: `online`) and sits paused (machine page:
`Paused`) — the exact disagreement us-116.4 removes — and the only thing that
enables it is the Done step's **Enable the agent** button, which renders only
once the runner has said hello *and* the slot row has appeared
(`add-agent-wizard.tsx:1336-1361`). Close the wizard during those 20–90 s and
the agent is benched, with nothing on its Team row to lift it (until
us-116.5). "It starts paused, so a fresh install claims nothing by accident"
(`:1345`) protected against a claim the manager did not intend — but the wizard
has just asked, explicitly, which projects it may work on and which roles it
does. Grants and roles are the fail-closed gate (US-31.3, US-53.4); a second
gate that requires a second click buys nothing and costs the manager a trip.

**And the config PATCH 403s for anyone but the platform admin.** The body
names `run_routes` (`:398`, always `{}`), and the platform-owned-field guard
fires on *presence*, not value (`runner_socket.py:1001` —
`getattr(body, f) is not None`; `{}` is not `None`). The settings page knows
this and deliberately omits the field (`settings/page.tsx:301-306`); the
wizard does not. Result for a tenant org owner: *"The agent identity … was
created, but configuring it failed"* — a principal with a token and no config,
which the wizard's Undo then has to clean up. It works today only because the
manager creating agents is a platform admin.

### Ready when the wizard closes

1. **Placement carries the intent.** `POST /agent-servers/{id}/slots` and
   `POST /agent-pools/{id}/place` accept `desired_state: "enabled"`; the wizard
   sends it. The add-slot job creates the slot and its `runner_config` in that
   state *before* `systemctl enable --now`, so the first hello can claim. The
   queued pool path (`upsert_pool_placement_request`, 202) carries the same
   flag through to `pool_placement_sweep`. The machine page's bare **Add
   agent** (no grants, no roles chosen) keeps today's paused default — it has
   nothing to claim anyway — and its help text stays true. Migration 142's
   "slots come up paused" comment is amended: paused is the *bare* default;
   the wizard asks for enabled because it just collected the intent.
2. **The config PATCH omits `run_routes`**, as the settings page does. Nothing
   in the wizard sends a platform-owned field. (`_require_platform_admin_for_
   platform_fields` itself is left alone: presence-based is the documented
   rule and the settings page depends on it.)
3. **The Done step shows the agent's real state**, from us-116.4's status —
   the same call the roster makes — instead of its own `runner_sessions` poll:
   *Ready — it can claim work now.* / *No model configured — set one under
   Model per role, or give the org a default model (Settings → LLM providers).*
   / *Offline — the runner has not said hello yet.* Each non-ready state
   carries the roster's fix link. The Enable button becomes us-116.5's Start
   and appears only when the state is `stopped` (something paused it after
   placement).
4. **The wizard warns before it creates when no model will resolve.** With
   us-116.7 in place, "no model" means the org has no default model and the
   manager pinned none — the Roles step can say so up front (*"No model will
   resolve for these roles — this agent will not run until one is set"*),
   using the same resolver, so the manager is told once, before the agent
   exists, rather than by a failed run.

## Acceptance criteria

1. Run the wizard for an interactive agent with at least one project and one
   role, on a pool, and close it as soon as it says Done. Within 90 s the
   agent reads **Ready** on `/team` with no further click on any page. Its
   `desired_state` is `enabled` and `runner_config.paused` is `false` from the
   moment the slot row exists.
2. The same, on a machine placement (`/agent-servers/{id}/slots` with
   `adopt_worker_id`), reads Ready the same way. The machine page's bare Add
   agent still creates a paused slot.
3. A member of a tenant org who is **not** a platform admin completes the
   wizard without a 403; the request body contains no `run_routes`. Pinned by
   an API test that PATCHes the wizard's exact body as a non-admin and gets
   200, and a web test on the body builder.
4. The Done step's status line is the roster's status for that agent (same
   label, same fix link) — Ready, No model configured, Offline, Stopped —
   and Enable appears only for Stopped, calling us-116.5's Start.
5. When no model would resolve for the chosen roles, the wizard says so on the
   Roles step before creation, in one sentence naming both places a model can
   be set; it does not block creation.
6. A queued pool placement (202) lands enabled once the sweep places it.
7. `cd apps/api && python -m pytest` covers the `desired_state` parameter on
   both placement endpoints, its default when absent, the queued path, and the
   non-admin PATCH; `npm run test:web` covers the wizard body and the Done
   step's state rendering.

## Out of scope

- **Offering a model or preset in the wizard.** US-61.2 removed it on purpose;
  us-116.7 gives a blank agent a real answer, and the settings page keeps the
  per-role control.
- **Changing the bare Add agent's default.** Paused stays right for a slot with
  no grants; nothing is lost.
- **Loosening the platform-owned-field guard.** The wizard stops tripping it;
  the rule stands.
