# US-114.1 — A template travels as a zip

**Status:** Testing
**Phase:** 114 — A template travels as a zip
**Depends on:** US-100.4 (a template is the files a project publishes: the
`AGENTS.md` body plus one `.buildmill/*.md` per task kind, on both the
superadmin catalog and the org's copies), US-99.1 (`KIND_FILES`, the kind →
file-name map the export names files by), US-67.3 (Owner/Admin write the org's
templates under RLS via `manage_project`)

## Story

As a superadmin or a workspace Owner/Admin, I want to export a project
template's instruction files as a zip and import a zip back over a template,
so that a set of instructions I have tuned in one place — an org, a laptop, a
text editor — can be carried to another without pasting seventeen files one at
a time.

## Design

### The zip is the published layout

A template already has a canonical on-disk shape: it is what a project
publishes to its repository (us-99.1, us-100.4) — `AGENTS.md` at the root and
`.buildmill/<File>.md` per task kind, named by `KIND_FILES` (`Plan.md`,
`Plan_Standalone.md`, `RCA.md`, `Code.md`, `Code_Standalone.md`, `Fix.md`,
`Chore.md`, `Merge.md`, `Test.md`, `Deploy.md`, `Release_Prep.md`,
`Guidelines_Refresh.md`, `PRD.md`, `Breakdown.md`, `Elaborate.md`,
`Wireframe.md`). The export **is** that tree, zipped. There is no manifest and
no second format to learn: unzip it and you are looking at exactly what a new
project would receive; zip up such a folder and it imports.

Only files with content are exported — an empty file is not "a file" anywhere
else in this feature either (`filledFileCount`, and a blank publishes as a
delete, us-99.4). The archive is named `<key>-template.zip` on the catalog
(`default-template.zip`) and `<name-slug>-template.zip` on an org copy.

### Import overwrites in place; it never creates

The manager picks a template first, then imports into it. What the zip carries
replaces what that template holds, file by file:

| in the zip | effect on the template |
|---|---|
| a known file with content | that file is overwritten (or created if it was empty) |
| a known file that is empty | that file is **cleared** — the section row is deleted, exactly as blanking it in the editor does (us-100.4: a stored empty string would beat the factory default at project creation) |
| a known file absent from the zip | left untouched |
| anything else (`Guidelines.md`, `README.md`, `__MACOSX/…`, `.DS_Store`) | ignored, and named in the confirmation |

A single common top-level folder is stripped, because that is what zipping a
folder on macOS or Windows produces. Files are matched by their name inside
`.buildmill/` (or `AGENTS.md` at the root); a `Plan.md` sitting at the root is
accepted too, so a hand-made zip of loose files works. A zip with **no**
recognisable file is refused before anything is written.

### Nothing is written until the manager sees the plan

Import is destructive to the selected template, so the confirm dialog says
what will happen *before* the first write, per file: **N overwritten**, **M
cleared**, **K unchanged** (identical text — listed so "nothing happened" is
never a surprise), and what was ignored. Confirm applies the whole set; cancel
writes nothing.

On the catalog the writes go through the existing admin api endpoints (PATCH
`agent_instructions`, PUT/DELETE a `worker_instruction` section) — one call per
changed file, so a failure part-way names the file it stopped on and the
template is reloaded to show what actually landed. On the org page the
document update and the section upserts/deletes go straight to Supabase under
RLS, as every other write on that page does; the upsert is one statement for
all changed sections.

The admin api caps a per-task file at 20,000 characters and the document at
200,000; an oversize file in the zip is refused **before** the first write,
naming the file, rather than failing half-way.

### Who

The two buttons — **Export** and **Import** — sit beside Rename/Delete on the
selected template's header, on both pages. On `/admin/project-templates` the
page is already superadmin-only. On `/settings/project-templates` they render
only for `manage_project` (Owner/Admin); every other role sees neither, and the
database's RLS on `org_project_templates` / `org_project_template_sections` is
the real boundary for the import — a hidden button is a courtesy.

### Where the code sits

The zip is built and read in the browser (`fflate`, ~8 KB, no dependencies —
the web app has no zip library today, and neither page needs the api to touch
files it can already read and write itself: "build less API"). The pure part —
which paths a template exports to, which zip entries map back to which key,
and the overwrite/clear/unchanged/ignored plan — is one module with a
round-trip test beside it; the two pages share one buttons component and each
supplies its own `applyImport`, the same split `template-files-editor.tsx`
already makes for `onSave`.

## Acceptance criteria

1. On `/admin/project-templates`, with a template selected, **Export**
   downloads `<key>-template.zip` containing `AGENTS.md` (when the document
   has content) and `.buildmill/<File>.md` for every per-task file that has
   content, each file's text byte-for-byte what the editor shows; empty files
   are not in the archive.
2. On `/settings/project-templates`, an Owner/Admin sees the same **Export**
   and **Import** buttons on the selected template and Export produces
   `<name-slug>-template.zip` in the same layout; a Member/Viewer sees neither
   button.
3. **Import** on either page opens a file picker; choosing a zip shows a
   confirmation listing, per file, whether it will be overwritten, cleared,
   or is unchanged, plus any ignored entries — and writes nothing until
   confirmed. Cancel leaves the template exactly as it was.
4. After confirming, the selected template's files read exactly what the zip
   carried: an overwritten file shows the new text in the editor, a cleared
   file shows empty (and its section row is gone), an untouched file keeps its
   old text, and the file count in the list updates. No new template is
   created.
5. A zip exported from one template imports into another (on either page)
   with the same result — round-trip is lossless, including a zip whose
   entries sit under one top-level folder.
6. A zip with no recognisable file is refused with a message and no write; a
   zip carrying a per-task file over 20,000 characters is refused on the
   catalog before the first write, naming the file.
7. `npm run test:web` carries a round-trip test for the zip module: export →
   import yields the same contents, unknown entries are ignored, a common
   folder prefix is stripped, and an empty file plans as *cleared*.

## Out of scope

- **Creating a template from a zip.** Import targets the template the manager
  has selected — the user was explicit. "New template from zip" is a
  one-liner on top of this if wanted later.
- **A manifest in the zip** (name, description, version, exported-at). The
  archive is the files and nothing else, so it doubles as "what a project gets".
  Provenance can ride a manifest in a later story without breaking this one.
- **Exporting a project's live `.buildmill/` from its repository.** That is
  GitHub, not a template; the publish path (us-99.4) already owns it.
- **Import from a folder or drag-and-drop.** A zip via the file picker.
- **A server-side endpoint for either direction.** Both pages can already read
  and write everything the zip holds; a new api route would only re-wrap CRUD.

## Verification (2026-08-17)

Built on branch `us-114.1-template-zip`, no migration. Verified on the local
dev server against `/settings/project-templates` with a scratch org template
("Zip UAT us-114.1", created and deleted for the test):

- **Import** — a zip built with `my-template/AGENTS.md`,
  `my-template/.buildmill/Plan.md`, `my-template/.buildmill/Release_Prep.md`,
  `my-template/README.md` and `__MACOSX/…` junk opened the confirmation
  *"OVERWRITTEN (3) AGENTS.md, .buildmill/Plan.md, .buildmill/Release_Prep.md ·
  IGNORED (1) README.md"* (folder prefix stripped, junk dropped); confirming
  took the count from 0 to 3 of 17 and the editor showed the imported text.
- **Export** — downloaded `zip-uat-us-114-1-template.zip`; decoded with fflate
  it held exactly the three files with byte-identical text (AC1/AC5).
- **Clear / root file / unchanged** — a second zip with an empty
  `.buildmill/Plan.md`, the same `Release_Prep.md` and a bare `Code.md` planned
  *"OVERWRITTEN (1) Code.md · CLEARED (1) Plan.md · UNCHANGED (1)
  Release_Prep.md"*; after confirm the export held `AGENTS.md`, `Code.md`,
  `Release_Prep.md` — Plan gone, Code added (AC3/AC4).
- `npm run test:web`: 257 pass, including the nine `template-zip.test.ts`
  cases (round trip, folder prefix, ignored entries, every kind, plan,
  oversize, filename, not-a-zip) (AC7). `npm run build` and `npm run lint`
  clean for the touched files.

**Not verified in a browser:** `/admin/project-templates` (AC1 on the catalog,
AC6's 20,000-character refusal). The active dev org is not the platform-admin
org, so the page redirects; it renders the same `TemplateZipButtons` and its
`applyImport` makes the same PATCH/PUT/DELETE calls `saveFile` already makes,
and the oversize check runs client-side before any call. Superadmin UAT
should confirm one export and one import there.
