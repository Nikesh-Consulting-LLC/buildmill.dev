# US-115.1 — The interactive agent's tools come from its own config

**Status:** Testing
**Phase:** 115 — The interactive agent's tools come from its own config
**Depends on:** US-78.3 (the Buildmill Interactive Agent — a fork of
`xai-org/grok-build` driven over ACP), US-78.4 (the `session/new` `mcpServers`
hand-off this replaces), US-83.1 (`$GROK_HOME/config.toml` is rewritten every
run; auto-update and `[compat.*]` scanning off), US-89.1 (the loopback broker —
the entry this writes), US-31.9 (`mcpconfig.build()` — the one description of a
run's tool surface), US-34.2 (granted tool servers ride beside the factory's)

Revives **us-89.3**, retired unbuilt on 2026-08-17 with the note *"still the
right shape if the Grok interactive agent comes back into use"* — the manager
brought it back on 2026-08-17. It is re-scoped to what CLI 1.0.0 actually
reads; see *Out of scope* for what of us-89.3 is deliberately not taken.

## Story

As the operator, I want the interactive agent to receive the factory's MCP
server through the CLI's own `config.toml` — the file its vendor documents —
and to not start reasoning until that server has answered, so that an agent
either has the factory's tools or the run says so, instead of the agent
quietly deciding to reach the factory with `curl` and nobody finding out.

## Design

### What is wrong today, measured

The module hands its servers to the CLI as a parameter of `session/new`
(us-78.4), which is a real capability and works. What does not work is *when*:
the CLI resolves `startupHints.nonInteractive` → absent → `McpInitStrategy`
**Progressive** ("start immediately, advertise tools as they become
available"), so the first LLM turn begins while the factory server is still
handshaking. The agent's own `search_tool` answers `status: "partial"`.

Every interactive run in `run_trace` shows the empty first search, 7–23 s after
the handshake line. Twelve runs between 2026-08-12 20:16 and 2026-08-13
recovered — the model narrated *"the MCP server is still connecting"*, retried,
and `factory__*` calls started landing at 24–90 s. The six runs since
2026-08-15 23:55 did not: one search, then the model read
`.factory-mcp.json` out of its own checkout and drove the factory over raw HTTP
for the rest of the run (15–44 `curl` invocations each, zero `factory__*`
calls). Both endings are the same defect. The second is worse only because we
left a working workaround inside the workspace.

Nothing reported it. The trace's `agent handshake — … mcp stdio, http, sse`
line says what the CLI *declared*, not what connected, and the CLI's MCP status
updates arrive as `sessionUpdate` variants `describe_update` drops.

### Where the CLI reads configuration

| layer | file | what it may carry |
|---|---|---|
| 1 | `/etc/grok/managed_config.toml` | everything (machine-wide) |
| 2 | `$GROK_HOME/managed_config.toml` | everything |
| **3** | **`$GROK_HOME/config.toml`** | **everything — this is the file the factory already writes** |
| 4–5 | `requirements.toml` (`$GROK_HOME`, `/etc/grok`) | constraints; may fail startup closed |
| — | `<cwd>/.grok/config.toml` | `[mcp_servers]`, `[plugins]`, `[permission]` only |

Later layers win. The factory already owns layer 3 — us-78.5 puts the model
block there and us-83.1 the hardening — and `$GROK_HOME` is per-slot, 0600,
rewritten on **every** run. So the servers go in the file we already write, on
the machine's own terms, and a stale entry from an earlier run is overwritten
out of existence by the same mechanism that already retires a stale
`[model.*]` block.

### The entry

`mcpconfig.build()` stays the single description of what a run's tool surface
is — factory server plus whatever us-34.2 granted. This story adds a second
rendering of that same dict, as `[mcp_servers.*]` TOML:

```toml
[mcp_servers.factory]
url = "http://127.0.0.1:41983/factory"
bearer_token_env_var = "FACTORY_MCP_KEY"
enabled = true
startup_timeout_sec = 60
tool_timeout_sec = 900
```

The keys are the vendor's (`url`, `headers`, `bearer_token_env_var`,
`enabled`, `startup_timeout_sec`, `tool_timeout_sec`, `tool_timeouts`); the
loader rejects unknown ones. `startup_timeout_sec` is raised from the CLI's
default 30 s because a cold API behind Cloudflare has been slower than that,
and `tool_timeout_sec` is bounded by the run's own remaining lease rather than
the CLI's 6000 s default, so a hung tool cannot outlive the work it belongs to.

### No secret lands in the file

`bearer_token_env_var` names an environment variable; the CLI reads it at load
time and sets `Authorization: Bearer <value>`. The value reaches the child
through its environment, never through a file — the same rule us-89.1 set for
the workspace, now applied to the CLI's own home. (Header values also expand
`${VAR}`, which is what the granted servers use.)

For that to be an honest credential rather than a decoration, **both ends
accept a bearer token**: the loopback broker takes `Authorization: Bearer
<local key>` as equivalent to `X-Factory-Local-Key`, and the factory MCP mount
takes `Authorization: Bearer <worker token>` as equivalent to `X-Worker-Token`.
Both are additive — every existing header keeps working, and the MCP standard's
own auth shape starts working.

It also buys the thing that makes this reliable: the CLI skips OAuth discovery
entirely for a server that already carries an `Authorization` header. Without
one it spends up to 5 s probing four `.well-known` URLs before the handshake
even starts.

### Blocking, and deliberately not "non-interactive"

`MCP_INIT_STRATEGY=blocking` in the child's environment is checked **first** by
the CLI's own resolver, ahead of every hint, and is the whole fix for the
timing: no LLM call until MCP init finishes.

The other route to Blocking — `_meta.startupHints.nonInteractive: true` — is
**refused**. It also flips the CLI's OAuth handling to `NonInteractive`, which
fails *closed*: a discovery probe that times out or that finds any OAuth
metadata returns `NeedsInteractiveLogin` and the server never starts. Our
servers do not speak OAuth, so that trade buys nothing and puts every granted
tool server one slow network hop away from silently not existing. The env var
gives the same strategy with none of that.

### One source of truth, and no workaround left in the tree

With the servers in `config.toml`, `session/new` is handed an **empty** list.
The CLI merges by normalized URL and client entries win, so sending the same
server twice would work — but two descriptions that can disagree is how this
kind of bug is born, and the point of the story is that the config is the
source.

`.factory-mcp.json` stops being written into the checkout for this module. It
was only ever the hand-off to `servers_from_config_file`; the CLI never read
it. What it did do was sit in the agent's working tree with a URL and a key in
it, which is exactly what the last six runs used. The file is still built (one
`mcpconfig.build()`), just written beside the workspace instead of inside it,
and still removed in a `finally`. `changesets.py` keeps ignoring the name.

### Proof before the model is paid to discover it

The engine's existing guard — *"the factory's MCP tools could not be given to
this agent"* — keys on the ACP list, which is now empty by design. Its
replacement is stronger: before the CLI is spawned, the module speaks MCP to
the configured URL itself — `initialize`, `notifications/initialized`,
`tools/list` — and refuses the run if that fails, naming the transport error
and spending nothing. A run that starts is a run whose factory server answered
with a tool count, and that count goes in the trace.

This does not prove the CLI connected; `MCP_INIT_STRATEGY=blocking` covers the
window where it could fail to. Together they replace a silent degradation with
either a working tool surface or a named failure.

### Where the code sits

- `mcpconfig.to_grok_toml(config, …)` renders `build()`'s dict as
  `[mcp_servers.*]`, returning the TOML text and the environment mapping its
  placeholders need — pure, and tested as such.
- `mcpconfig.probe(url, headers, …)` is the preflight.
- `interactive.write_model_config()` gains the rendered block (it already
  composes `[model.*]` + hardening; this is a third section, same file, same
  0600, same every-run rewrite).
- `CLIModule.mcp_config_dir(workdir)` decides where the per-run JSON lands —
  the workspace by default, overridden by the interactive module — so the
  other five modules are untouched.
- `acp.engine.open_session(..., env=…)` passes the child environment through to
  `prim.run_session`, which already accepts one.
- `mcp_broker` and `factory_mcp.build_mcp_asgi` accept the bearer form.

## Acceptance criteria

1. `$GROK_HOME/config.toml` written for an interactive run contains a
   `[mcp_servers.factory]` entry whose `url` is the loopback broker's (or the
   factory MCP URL when the broker is down), with `bearer_token_env_var`,
   `enabled = true`, `startup_timeout_sec` and `tool_timeout_sec`, plus one
   `[mcp_servers.<slug>]` per granted tool server — alongside the `[model.*]`
   block and the us-83.1 hardening, which are unchanged.
2. That file contains **no** credential: neither the worker token, the broker's
   local key, nor any granted server's key appears in its text. The values
   reach the CLI only through the child process's environment.
3. The CLI is spawned with `MCP_INIT_STRATEGY=blocking`; no
   `startupHints.nonInteractive` is sent on `initialize` or `session/new`.
4. `session/new` carries an empty `mcpServers` list for this module, and no
   `.factory-mcp.json` is written inside the workspace checkout during an
   interactive run (it is written beside it and removed afterwards). The other
   five modules keep writing it into the workspace exactly as before.
5. Before the CLI is spawned, the module completes `initialize` →
   `tools/list` against the configured MCP URL; the tool count is emitted to
   the run trace. A failure fails the run with the transport's own words, no
   CLI is started, and the trace says nothing was spent.
6. The loopback broker accepts `Authorization: Bearer <local key>` and
   `X-Factory-Local-Key` equally, and refuses a wrong or missing credential in
   both forms; the factory MCP mount accepts `Authorization: Bearer <worker
   token>` and `X-Worker-Token` equally, and still answers 401 to a revoked or
   absent token in both forms.
7. `cd apps/runner && python -m pytest` and `cd apps/api && python -m pytest`
   pass, carrying: the TOML rendering (factory entry, granted entry, stdio
   entry, no-secret assertion, timeouts), the config-dir override, the empty
   ACP list, the env the child is spawned with, the preflight refusal, and the
   two bearer-acceptance tests.
8. On a live interactive run, the first `search_tool` of the run returns
   `factory__*` tools (not `status: "partial"`), and the run's trace carries
   **zero** `curl`/`run_terminal_command` calls against the MCP endpoint.

## Out of scope

- **`managed_config.toml` and `requirements.toml`** (us-89.3's original
  target). `managed_config.toml` sits *below* `config.toml` in the merge, so it
  is the weaker place to write what the factory enforces, and the fail-closed
  `requirements.toml` layers want an Ed25519-signed policy. `$GROK_HOME` is
  already per-slot and factory-owned; the extra layer buys precedence we do not
  need against an attacker we do not have. Worth revisiting if the agent ever
  runs where the slot's home is not ours.
- **`grok inspect` as a Prepare Workspace probe** (us-89.3 AC4). The preflight
  here proves the *server*, which is what fails; proving the CLI's *view* of
  its config is a provisioning-time check and belongs with the provisioner.
- **`[permission]` rules in the config.** Our ACP handler answers every
  permission request with `allow_once` on purpose (us-83.4 — never
  `allow_always`), and each decision lands in the trace. Pre-approving in the
  config would delete that record to save a round trip.
- **`[features] tool_search = false`** (listing all ~53 factory tools directly
  instead of behind `search_tool`/`use_tool`). It may well be the right call
  for this tool surface, but it changes how every prompt is built and wants its
  own measurement.
- **The other five CLI modules.** They keep the workspace `.factory-mcp.json`
  and their existing argv; only `mcp_config_dir` becomes overridable.
- **`.grok/config.toml` inside the workspace.** The factory does not write it
  and does not start now; `[compat.*]` scanning is already off (us-83.1).

## Verification record (2026-08-17)

Built on branch `phase-115-agent-reads-its-own-config`, no migration. Verified
against the **real** FastAPI app (only `db.get_worker_by_token` faked, so the
real `/mcp` mount, the real auth shim and the real MCP server answered) with the
**real** loopback broker in front of it, driven by the official Python MCP SDK
client.

- **AC1/AC2 — the file.** `$GROK_HOME/config.toml` came out as
  `[model."grok-4.5"]` + `[mcp_servers."factory"]` + `[cli]`/`[compat.*]`, parsed
  by `tomllib` to `['cli', 'compat', 'mcp_servers', 'model']`; the factory entry
  read exactly `{url, bearer_token_env_var: "FACTORY_MCP_KEY", enabled: true,
  startup_timeout_sec: 60, tool_timeout_sec: 900}`. Neither the worker token nor
  the broker's local key appears anywhere in the text; both were in the env
  mapping handed to the child. `auto_update = false` and `compat.claude.mcps =
  false` survived the new section — the bug where the model block *replaced* the
  body instead of joining it was found and fixed by this check.
- **AC6 — both credentials, both legs.** A real MCP client authenticating with
  **nothing but `Authorization: Bearer`** listed **53 tools** through the broker
  and 53 direct to the API — identical to the legacy header. Refusals, by status:

  | | bearer ok | header ok | bearer wrong | none | `Basic` |
  |---|---|---|---|---|---|
  | broker | 200 | 200 | 403 | 403 | — |
  | api | 200 | 200 | 401 | 401 | 401 |

- **AC5 — the preflight.** `mcpconfig.probe` returned 53 tool names
  (`list_available_work`, `list_factory_queue`, …) through the broker; against a
  bad credential it raised `initialize answered HTTP 401: {"error": "invalid or
  revoked worker token"}`, which is what the run's refusal quotes.
- **AC3/AC4 — unit-level.** `session/new` carries `mcpServers: []`, the child is
  spawned with `MCP_INIT_STRATEGY=blocking` and `FACTORY_MCP_KEY`, no
  `startupHints` is sent, `InteractiveModule.mcp_config_dir` resolves beside the
  workspace while `claude`'s still resolves to it, and a probe failure returns
  exit 1 with `prim.sessions == []` — the CLI is never spawned.
- **Litter.** The holder directory is removed with the file (guarded by its
  suffix, so a caller passing a real checkout — every other module — cannot lose
  one); otherwise an empty `project-x.mcp` would sit in the workspace root and be
  reported as a workspace by `workspace.usage()` and aged out by `reclaim()`.
- **AC7 — suites.** `apps/runner`: **348 passed** (~80 s). `apps/api` Essential:
  **1960 passed, 591 skipped** (~68 s). Note the api suite needs `SUPABASE_URL` /
  `SUPABASE_PUBLISHABLE_KEY`; without `apps/api/.env` it cannot import at all —
  pre-existing on this machine, confirmed against a stash of these changes.

**Not verified: AC8, and everything that needs the CLI itself.** No
`buildmill-agent-cli` runs on this machine, so what is proven is that the file
the CLI reads is well-formed, complete and secret-free, and that the server it
points at answers. What is *not* proven is the CLI's own parse of it, that
`MCP_INIT_STRATEGY=blocking` changes its behaviour as its source says, or that a
live run's first `search_tool` now returns `factory__*`. That needs one
interactive run on a pool machine — the manager's UAT. Read from the trace:
the run should carry `factory MCP ready — 53 tools` before the handshake line,
`factory__*` calls with no "still connecting" retry, and zero
`run_terminal_command` calls against `127.0.0.1`.

**Also unproven: the fallback shape.** Every check above ran with the broker up.
The no-broker path (`X-Worker-Token` direct to the API) is covered by unit tests
and by the "api direct" leg above, but not by a real run.
