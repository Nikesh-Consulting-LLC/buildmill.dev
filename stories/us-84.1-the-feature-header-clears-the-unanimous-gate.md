# US-84.1 — The feature header clears the unanimous gate

**Status:** Testing
**Phase:** 84 — Dashboard batch ergonomics
**Dependencies:** none (every mechanism it projects already shipped: us-20.6,
us-25.2, us-27.11, us-41.1, us-41.2)

## Story

As the manager working Things to Do, when every story under a feature sits at
the same gate, I want the feature's header row to carry the one-click batch
action for that gate — Curate all N stories, Plan all N stories, Code all N
stories, Approve all N plans — so I clear the whole batch from the dashboard
instead of clicking through N story rows or opening the feature page to find
the button that already exists there.

## Context

us-24.1's rule is that a feature header row in Waiting on you carries **no
action** — it must not compete with the story rows below it. us-25.2 carved
exactly one exception: when EVERY non-abandoned child sits at `plan-review`
(and there is more than one), the header renders `ApproveAllPlansButton`,
because clearing the whole gate is something no single row can do. That
reasoning is not specific to the plan gate, but the implementation is:
`ParentFeatureRef.planGateCount` (`dashboard/data.ts`) knows only one stage.

Meanwhile the work-item page's stage tracker already speaks the full batch
vocabulary, each with its server-side mechanism proven in production:

- **Curate all** (us-41.2) — `curate_feature_stories` RPC, org-scoped CRUD
  under RLS, one transaction, called straight from the browser.
- **Plan all / Code all** (us-20.6, us-27.11, us-41.1) —
  `POST /api/v1/issues/{id}/batch-dispatch`, preceded by a phase-stating
  confirm fed by the preview endpoint (`same_stage`, child count, and — in
  feature/epic mode — that the code phase is one feature-owned run).
- **Approve all plans** (us-20.6/us-25.2) —
  `POST /api/v1/issues/{id}/plans/approve-all`, partial results reported via
  the approved/skipped toast.

So a feature fresh out of breakdown shows eight draft stories in Triage, each
"Open draft", and the dashboard offers no way to say "I've read the breakdown,
release them all" — the manager either opens the feature page or clicks eight
times. Worse, in feature/epic build mode a set of `planned` stories lands in
"No action available" ("its feature owns the build, dispatch from there") —
the dashboard names the action and makes the manager leave the page to take
it. This story is a projection, not a mechanism: put the button where the
work already is.

## Acceptance criteria

1. `ParentFeatureRef.planGateCount` generalizes to a batch-gate summary
   (e.g. `batchGate: { kind, count } | null`) computed in `loadWaiting` from
   ALL non-abandoned children of the feature (the existing sibling tally —
   never only the children this dashboard happened to load):
   - all `draft` → `curate`
   - all `ready` → `plan`
   - all `planned` → `code`
   - all `plan-review` → `approve` (behavior unchanged from us-25.2)
   - any mix, or any other unanimous status → `null` (a partial batch invites
     acting on work the manager has not seen; the per-story rows are still
     right there — us-25.2's rule, kept).
2. Unanimous **and more than one**: `total > 1` stays, for every gate — a
   batch of one is the row's own action wearing a hat.
3. The header row renders the matching action in BOTH dashboard variants
   (desktop table rows and the below-`md` cards — the two render sites that
   exist today):
   - `curate` → "Curate all N stories", calling the same
     `curate_feature_stories` RPC the stage tracker calls.
   - `plan` / `code` → "Plan all N stories" / "Code all N stories", going
     through the same phase-stating confirm as the stage tracker (us-27.11 —
     a batch that spends money states its phase first; in feature/epic mode
     the dialog says the code phase is one feature-owned run) and posting the
     same `/batch-dispatch` endpoint.
   - `approve` → `ApproveAllPlansButton`, unchanged.
4. Same endpoints, same server-side checks — one action, two entry points
   (us-25.2's own words). No new API surface, and no client-side
   re-derivation of dispatch legality: if the factory refuses or holds some
   children (build-order blocks, hold rules), the server's answer surfaces
   through the existing partial-result reporting, the way approve-all
   already toasts approved/skipped.
5. Display semantics, pinned so UAT is confirm-only:
   - A feature whose 8 stories all sit in `draft` shows **"Curate all 8
     stories"** on its header row in Triage; one click moves all 8 to
     `ready` and the group re-renders without a page change.
   - A feature whose stories all sit at `planned` in a feature/epic-mode
     project shows **"Code all N stories"** on its header — the rows
     themselves may sit in "No action available", and that is exactly the
     dead-end this removes.
   - A feature with mixed child statuses shows a plain header, as today.
6. The unanimity/kind derivation is pure logic with a `.test.ts` beside it
   (mixed statuses, unanimous-of-one, each gate mapping, abandoned children
   excluded). `npm run build` and `npm run test:web` pass.

## Verification (2026-08-12, local dev + dev Supabase)

Built as: `lib/batch-gate.ts` (pure derivation + labels, 5 unit tests),
`components/batch-phase-dialog.tsx` (the us-27.11 confirm EXTRACTED from the
stage tracker so both entry points render one dialog), `components/
feature-batch-action.tsx` (the header button; approve delegates to
`ApproveAllPlansButton` unchanged), `data.ts` `planGateCount` → `batchGate`,
`orgId` threaded page → tabs → WaitingList. `npm run test:web` 84/84,
`npm run build` clean, lint 0 errors.

Verified in the browser against a scratch feature (3 stories, Demo project,
story mode, dev DB — created, walked through the gates, deleted):

- All 3 `draft` → header in Triage shows **"Curate all 3 stories"**; ONE
  CLICK moved all three to `ready` (real `curate_feature_stories` RPC) and
  the group re-rendered without a page change — rows moved to Dispatch, the
  header advancing to **"Plan all 3 stories"** (AC5 scenario 1, live).
- Clicking "Plan all 3 stories" opened the shared phase confirm: "Plan 3
  stories? · 3 of 3 stories have no approved plan yet — one planning run per
  story, drained one at a time." Cancelled with "Not now" (no runs queued).
- All 3 `planned` → header shows **"Code all 3 stories"** in Dispatch.
- All 3 `plan-review` → header shows **"Approve all 3 plans"** in Reviews —
  us-25.2's path, unchanged through the new derivation. Beside it, a feature
  with 40+ mixed-status children showed a plain header throughout.
- Mixed (2 plan-review + 1 ready) → the header action disappeared (AC5
  scenario 3).

NOT verified: the confirmed `/batch-dispatch` POST and the approve-all POST
from this entry point (both cancelled/not clicked — same endpoints the stage
tracker and us-25.2 already exercise in production); the below-`md` mobile
card variant (same component, same props, not observed); the feature/epic-
mode "as one run" dialog shape and its instruction preview (Demo is story
mode — the dialog is the extracted stage-tracker code that already renders
it there).

## Out of scope

- Batch actions over mixed gates, partial batches, or "select these five"
  on the header — the checkbox batch in the Dispatch group already covers
  cross-feature multi-select and is untouched.
- A code-review "approve all diffs" gate. Approving N diffs is N distinct
  decisions about code; in-review stays per-story (the same judgement that
  keeps send-back per-story in us-20.6).
- Any new endpoint, RPC, or migration.
- Changes to the stage tracker or the work-item page — the feature page's
  own batch actions are the source this story projects, not a target.
