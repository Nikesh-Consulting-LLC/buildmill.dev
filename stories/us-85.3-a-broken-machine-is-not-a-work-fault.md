# US-85.3 — A broken machine is not a work fault

**Status:** New
**Phase:** 85 — Agent readiness
**Depends on:** us-85.1 (workspace verification checks), migration 161 (`runs.fault_class` + escalation gate, US-33.4), US-10.11 (fault classing at hand-back), US-68.3 (auto-repair ladder), us-79.8 (agent failure reports)

## Story

As the manager, when a run fails because the machine it landed on is broken —
no usable shell, an unreachable or token-rejecting factory MCP, a corrupt
workspace — I want the failure recorded as a **machine fault**, so the
escalation ladder does not answer a broken box by thinking harder, the box is
flagged for the auto-repair sweep that already knows how to fix it, and a
story's failure history blames the story only when the story deserves it.

The defining incident: the US-2.8.1 plan run of 2026-08-12 (run
`dcba94f5-1b86-4c55-b079-d6b1db0212ba`, pool machine 9) spent its whole
session on a machine with no bash and no factory MCP in session — a pure
environment failure, later proven by us-85.1's own checks and fixed by a
machine Update (`e4e749e` provisions bash) — yet `runs.fault_class` recorded
**work-fault**. Every consumer of that label then drew the wrong conclusion:

- **Escalation** (US-33.4, migration 161) escalates the preset only on
  work-fault, precisely because "a broken box is not answered by thinking
  harder." The mislabel is what arms it: a retry would have climbed the
  ladder and spent a costlier preset against the same broken machine.
- **Runner incidents** (US-10.11) are raised only on runner-fault, so no
  incident was recorded and no manager was pinged; machine 9 kept a clean
  record while burning 26 minutes of a paid session.
- **The auto-repair sweep** (US-68.3) only sees a slot whose *process* is
  down (`slots_due_for_repair` requires `service_state in
  ('failed','inactive')`). Machine 9's supervisor was up and healthy — a
  running slot with a broken bench is invisible to the ladder, even though
  the ladder's last rung (Update) is exactly what fixed it, by hand, later.

## Design

### Check the bench before blaming the work

Text needles cannot carry this alone. The US-2.8.1 run did not end with
"bash not found" in its final error — it burned its turn budget fighting the
environment and ended on the turn ceiling, which `repair.classify` maps to
`unrecoverable` and `classify_fault` defaults to work-fault. And US-54.2
already taught this codebase that grepping an agent's transcript for
environment words is how narration gets mistaken for failure.

So the authoritative signal is a **probe, not a grep**. us-85.1 built exactly
the right checks (`apps/runner/supervisor/workspace_prepare.py`, step 7:
shell executes, bash on PATH and at `/usr/bin/bash`, git answers, factory MCP
answers an authenticated initialize — distinguishing unreachable / token
rejected / wrong status). This story factors those checks into a helper both
callers share, and the workloop runs them **after any module failure that is
about to be labelled work-fault**. A failing check flips the label to
`machine-fault` and puts the check's own finding at the head of the hand-back
error ("bash not found on PATH (agent CLIs invoke it)"), ahead of the
module's error — evidence outranking diagnosis, per US-27.12. All checks
passing means work-fault stands, now with proof. The probe needs the run
context (workspace path, MCP endpoint, worker token), so it runs where the
hand-back payload is assembled in `workloop.py`, not inside
`repair.classify_fault` — the needle classifier stays a pure, testable
function.

### The taxonomy

`fault_class` grows a third value:

| value | meaning | the fix |
|---|---|---|
| `work-fault` | the work failed on a proven-good bench | the story / the plan |
| `machine-fault` *(new)* | the machine's environment is broken: missing shell/tooling or agent CLI, unreachable or token-rejecting factory MCP, broken workspace/checkout, missing dependencies | the box |
| `runner-fault` | supervisor/resource conditions that are not the box's environment: a transient that never cleared (wait budget exhausted), the subscription usage cap, no module for the kind, no gateway credentials | config, or time |

Existing needle mappings move accordingly: `reclone` (broken checkout) and
`reinstall` (missing dep/CLI) failures that survive repair are machine-faults.
`wait` exhaustion, the usage cap, and the workloop's hard-coded supervisor
refusals stay runner-fault. A turn-ceiling failure stays work-fault **unless**
the probe fails — US-2.8.1's exact shape.

Why a third value instead of folding these into runner-fault: auto-repair
must be able to trust the label. A wait-exhausted transient (the class a
factory-api deploy produces) is a runner-fault that no machine Update can or
should answer; keying the sweep on runner-fault would have it reimaging boxes
over network blips. `machine-fault` is the one label that means "this box,
specifically, is broken" — which is what makes it actionable.

### What the API does with it

A machine-fault hand-back does everything a runner-fault one does — runner
incident recorded, org managers notified — and additionally marks the slot
that ran it as environment-suspect, which makes it due for the existing
auto-repair sweep even though its process state is `active`. The ladder
itself is untouched (restart → reissue token → update, one rung per 15-minute
cooldown); Update is the rung that provisions bash. The flag clears when a
repair job for that slot completes ok, or when a later run from the slot
succeeds.

## Acceptance criteria

- **AC1 — the taxonomy exists.** One migration (applied to **both** Supabase
  projects) widens migration 161's check constraint so `runs.fault_class`
  accepts `machine-fault`, and adds the environment-suspect marker to
  `agent_slots`; the column comment states the three-way semantics.
  `db.record_run_fault_class` accepts the new value; `database.types.ts` is
  regenerated and the embed-ambiguity sweep passes.
- **AC2 — the probe outranks the default.** On a failed module result headed
  for work-fault, the runner runs the environment checks — a helper shared
  with `workspace_prepare.py`, not a copy. Any failing check ⇒
  `machine-fault`, with the check's finding leading the hand-back error
  text. All checks passing ⇒ work-fault stands. Probes are time-bounded
  (the existing 15s MCP check ceiling; the whole probe well under a minute)
  and never run on succeeded results.
- **AC3 — needles reclassify.** `reclone`/`reinstall` failures that survive
  repair report machine-fault. Wait-exhausted and usage-cap failures keep
  runner-fault. A turn-ceiling failure reports work-fault when the probe
  passes and machine-fault when it fails.
- **AC4 — the sweep sees a running-but-broken slot.** A machine-fault
  hand-back records a runner incident naming the failed checks and flags the
  slot; `slots_due_for_repair` includes flagged slots regardless of
  `service_state`; the ladder proceeds unchanged from its cheapest rung. The
  flag clears on a completed repair job for that slot or a subsequent
  succeeded run from it.
- **AC5 — escalation stays cold.** After a machine-fault run, the next
  dispatch of the same item does not climb the preset ladder — the
  `fault_class != 'work-fault'` gate in `db.py` covers the new value, pinned
  by a test.
- **AC6 — the report names the machine.** The runner-incident message and
  the us-79.8 agent-failure report carry the fault class and the failed-check
  findings verbatim (e.g. "bash not found on PATH"), so the manager reads a
  machine diagnosis, not a story diagnosis. No new UI: wherever
  `fault_class` surfaces today, the new value displays as-is.
- **AC7 — tests.** Runner: unit tests per branch (probe-fail ⇒ machine-fault
  even on turn-ceiling; probe-pass ⇒ work-fault; the needle moves in AC3).
  API: constraint accepts the value, `record_run_fault_class` stores it, the
  hand-back flags the slot, the sweep picks up a flagged `active` slot, and
  the escalation gate holds.

## Out of scope

- Auto-redispatching the failed run after a repair — the issue still returns
  to `failed` and the manager re-dispatches.
- Steering dispatch away from a flagged machine (pool claim stays
  first-come-first-served) — a follow-up once the flag proves reliable.
- Reclassifying historical runs — `dcba94f5` stays work-fault in the record;
  this story is prospective.
- New UI surfaces for fault statistics.
- Fixing any particular machine — machine 9 is already repaired; this story
  is the labelling and the wiring, not a repair.
- Changing wait/usage-cap/turn-limit retry semantics (US-52.4, US-54.1,
  US-63.x stand as shipped).
- The gitproxy 500-on-GitHub-connect-timeout guard (open from the Phase 85
  postmortem; separate fix).
