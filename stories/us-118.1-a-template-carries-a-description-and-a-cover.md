# US-118.1 — A template carries a description and a cover

**Status:** New
**Phase:** 118 — A template shows its face
**Depends on:** migration 227 (`project_templates` / `org_project_templates`,
`copy_project_template_into_org`), 229 (`is_disabled`), 265–267 (a template
carries `agent_instructions`, the copy carries it too), US-114.1 (the admin
page's current two-pane shape, Export/Import), migration 014 (`avatars` — the
public-bucket + `getPublicUrl` + fixed-path-upsert pattern this story copies),
`markdown-view.tsx` (the one markdown renderer), migrations 086/087/253
(`is_platform_admin()`, `has_org_capability(org, cap)`)

Design reference: [docs/design/template-cards.html](../docs/design/template-cards.html)
— Mockup B (the details form with its live card preview) and the "Decisions
and spec" table. Open it in a browser; it is interactive.

## Story

As the platform admin, I want every catalog template to carry a short
markdown description and a cover image, edited in a plain form that shows me
the card a project creator will see, so that the three templates on the
catalog stop being three names with the same boilerplate sentence and start
telling people what each one is for.

## Design

### What exists today

- `project_templates.description text not null default ''` (≤ 2000 in the
  API) is shown as **plain text** in exactly one admin place
  (`admin/project-templates/page.tsx:538-542`) and never rendered as
  markdown. On the dev catalog all three templates — *Default*, *Generic Web
  App*, *Python + Next.JS Web App* — carry the identical sentence, because a
  field nobody sees is a field nobody writes.
- `category` is **write-only**: set in the admin create form
  (`page.tsx:647-657`), stored, rendered nowhere. `org_project_templates`
  has no `category` at all.
- Neither table has an image column; no bucket holds template images
  (three buckets exist: `avatars` public, `project-docs` and `attachments`
  private — `014`, `037`, `056`).
- The admin header edits name and key through an inline "Rename"
  (`page.tsx:470-515`); description and category cannot be edited after
  create at all.

### Data — migration `284_a_template_carries_a_cover.sql`

Both template tables gain the same face; the org copy also gains the
category it was missing so a later picker can group by it:

```sql
alter table public.project_templates
  add column image_path text
    check (image_path is null or image_path ~ '^catalog/[0-9a-f-]{36}/cover$');

alter table public.org_project_templates
  add column category text not null default '',
  add column image_path text;
alter table public.org_project_templates
  add constraint org_project_templates_image_path_check check (
    image_path is null
    or image_path ~ '^catalog/[0-9a-f-]{36}/cover$'          -- inherited from the catalog
    or image_path = org_id::text || '/' || id::text || '/cover'  -- the org's own upload
  );
```

`copy_project_template_into_org` carries `category` and `image_path` (the
catalog path — an org copy shows the catalog's cover until the org replaces
it, US-118.2). `image_path` is null when there is no image; **null is a real,
good state** — it renders the generated cover below, not a broken image.

**Bucket `template-images` — public.** A cover is decorative content, not
org data, which is what makes public acceptable here where it is not for
`attachments`: a row of twenty cards is twenty plain `<img>` tags with no
signed-URL round trips. 2 MB, allow-list `image/png, image/jpeg, image/webp,
image/gif, image/svg+xml`. Object paths are fixed and extension-less, like
avatars, so replace is an upsert and nothing is orphaned:

| who | path | write policy |
|---|---|---|
| platform admin | `catalog/<template_id>/cover` | `is_platform_admin()` |
| org manager (US-118.2) | `<org_id>/<org_template_id>/cover` | `has_org_capability(<org_id>, 'manage_project')` |

One `stable` helper, `public.template_image_writable(name text)`, decides
both rows (folder `catalog` → admin; folder that is a uuid → capability;
anything else → false, without a cast error), and the three
`storage.objects` policies (insert / update / delete, `to authenticated`) are
one line each. Select is public for the bucket, as `014` did for avatars.
**No policy ever returns anything but the image** — there is nothing secret
in this bucket by construction.

Applied with `python scripts/migrate.py apply 284_…sql` (both projects,
types regenerated, embed sweep run).

### API — the catalog row is written through `admin.py`

`project_templates` has no client write policy (writes go through the
service role), so the catalog's `image_path` is set by the existing routes:

- `ProjectTemplatePatchBody` gains `image_path: str | None` — accepted only
  as `None` or exactly `catalog/<this template's id>/cover`; anything else is
  422 naming the field. The API does not touch Storage on PATCH; the browser
  already uploaded under RLS.
- `DELETE /admin/project-templates/{id}` deletes `catalog/<id>/cover`
  best-effort through `storage.py` (`delete_object`; a missing object is not
  an error — `_is_not_found` already knows Storage says 400/"404" for that).
- `POST` is unchanged: a template is created without an image, and the form
  uploads once the row exists (below). `GET` already returns the row.

### Web — the shared pieces every later story reuses

- `apps/web/src/lib/template-cover.ts` (pure, tested):
  `templateInitials(name)` — first letter of the first two words, upper-case;
  one word gives one letter; `templateTint(name)` — one of three tint
  classes, chosen by a stable hash of the name; `templateCoverUrl(path,
  updatedAt)` — `getPublicUrl` + `?v=<updated_at>` so a replaced image shows
  without a hard reload; the bucket name, byte limit and MIME allow-list as
  constants.
- `apps/web/src/components/template-card.tsx`: **`TemplateCover`** (the
  `<img>` when `image_path` is set, `alt=""` because the name is the label;
  otherwise the generated cover — initials on the tint, both themes);
  **`TemplateCard`** with `variant="card"` (2:1 cover, name + Default badge,
  description clamped to three lines) and `variant="row"` (72px thumb, name,
  one line, a `meta` slot) — both take `selected` / `disabled` / radio
  attributes so US-118.3/118.4 only compose them; **`TemplateThumb`** (28px,
  for list rows and headers).
- `MarkdownView` gains an **inline** mode (`inline` prop or a `MarkdownInline`
  export): paragraphs collapse, headings/lists render as text, links render
  as their text, images render nothing — the subset a card can hold. Full
  rendering stays the default and is what headers use.
- **`TemplateDetailsDialog`** (`components/template-details-dialog.tsx`) —
  one form, three uses across the phase (`scope: "catalog" | "org"`,
  `mode: "create" | "edit"`):
  - Name (both scopes); **Key** (catalog only, mono, ≤ 64); **Category**
    (both scopes, `<datalist>` of the categories already in use, ≤ 100);
  - **Description** — the existing `MarkdownEditor` (Write / Preview), a
    counter `n / 2000` that turns amber past 300, and the hint *"Markdown.
    Keep it short — the card shows about the first three lines."* The 2000
    cap stays; the preview does the teaching;
  - **Cover** — the current cover (or the generated one), *Upload image* /
    *Replace* / *Remove*, and the hint *"PNG, JPEG, WebP, GIF or SVG up to
    2 MB. Shown as a 2:1 banner — 800×400 works well; taller images are
    cropped to the middle."* Type and size are checked client-side before
    any upload, with a message naming the limit;
  - a **live `TemplateCard` preview** to the right, captioned *How it
    appears to project creators*, re-rendered on every keystroke and image
    change, so a 1,500-character description looks wrong before it is saved;
  - Save writes everything in one go (upload/remove first, then the row);
    Cancel discards, including a picked-but-unsaved file.

### The admin page

- The header's inline **Rename** becomes **Edit details** and opens the
  dialog with `scope="catalog"` (name and key move into it — one place to
  edit the face). The header shows a `TemplateThumb` before the name; the
  description renders through `MarkdownView` (full) instead of as plain text.
- List rows in the left pane show the thumb before the name.
- The **New project template** dialog is the same form in `mode="create"`
  (Key and Name required; Category, Description, Cover optional). A cover
  picked here is uploaded to `catalog/<new id>/cover` after the POST returns
  the id, then `PATCH image_path` — the new template shows it without a
  reload.
- Upload, replace and remove go **browser → Storage under RLS** with the
  admin's own session (the admin is an authenticated user;
  `is_platform_admin()` holds), then `PATCH image_path` through `apiCall`.
- **Duplicate** copies description and category and leaves `image_path`
  null — a duplicate starts with the generated cover, because sharing one
  object between two catalog rows would make Remove on one break the other.

### Docs

`docs/application/domain-objects.md` has **no entry** for
`project_templates` / `org_project_templates` today (the list at lines 68–80
jumps past them). This story adds one — what a template is, the two tables,
the face fields, the bucket, who writes what — and updates the
`/admin/project-templates` row in `interface-catalog.md`.

## Acceptance criteria

1. Migration 284 is applied to **both** Supabase projects: `image_path` on
   both tables with the CHECK shapes above, `category` on
   `org_project_templates`, `copy_project_template_into_org` carrying both,
   bucket `template-images` (public, 2 MB, the five MIME types), the
   `template_image_writable` helper and its three write policies plus public
   select. `database.types.ts` is regenerated and
   `test_embed_ambiguity.py` passes.
2. Storage RLS (SQL test): a platform admin can insert, update and delete
   `catalog/<uuid>/cover`; a non-admin authenticated user is refused for any
   `catalog/…` path; a folder name that is neither `catalog` nor a uuid is
   refused without an error; anyone can read an object by its public URL.
3. `PATCH /admin/project-templates/{id}` accepts `image_path` as `null` or
   `catalog/<id>/cover`; any other value — another template's id, an org
   path, a URL — is **422** naming `image_path`. `DELETE` removes
   `catalog/<id>/cover` best-effort: a missing object does not fail the
   delete. `POST …/duplicate` copies description and category and leaves
   `image_path` null.
4. On `/admin/project-templates` the header reads: thumb · name · mono key ·
   `vN` · Default (or *Make default*) · **Edit details** · Export · Import ·
   Delete. The description below it renders markdown — `**bold**` is bold,
   `` `code` `` is mono, a link is a link — not the raw text. There is no
   inline Rename any more.
5. **Edit details** opens a dialog with Name, Key, Category, Description
   (Write/Preview, `n / 2000` counter, the three-lines hint), Cover (current
   or generated cover; Upload / Replace / Remove; the format-and-size hint)
   and a live card preview on the right that changes as the description is
   typed and when the image is replaced or removed. Save persists name, key,
   category, description and image in one action; Cancel leaves the row and
   its object untouched even if a file was picked.
6. Picking a 3 MB PNG, or a PDF, is refused before any upload with a message
   that names the 2 MB limit or the accepted types.
7. **Remove** deletes the object, sets `image_path` null, and the header
   thumb, list thumb and preview show the generated cover at once. Replacing
   the image shows the new one without a hard reload (`?v=updated_at`).
8. A template with `image_path` null renders the generated cover: initials
   *PN* for "Python + Next.JS Web App", *GW* for "Generic Web App", *D* for
   "Default", on a tint that is the same for the same name on every render
   and legible in both light and dark.
9. **New project template** has the same fields; Key and Name are required,
   the rest optional; a cover picked before Create is uploaded to
   `catalog/<new id>/cover` and patched onto the row, and the new template
   opens showing it.
10. `MarkdownView`'s inline mode renders bold, italic, code and link *text*,
    and drops images and block structure — verified by rendering the
    mockup's example descriptions in the preview card.
11. Tests: `template-cover.test.ts` covers initials (one word, two words,
    punctuation between), tint stability, and the cache-busted URL; API tests
    cover the `image_path` shapes on PATCH and the best-effort delete;
    `*_sql.py` covers the storage policies (AC2), the CHECK constraints
    (catalog shape, own-org shape, another org's path refused) and the copy
    RPC carrying category and image_path. `cd apps/api && python -m pytest`,
    `npm run test:web` and `npm run build` are clean.
12. `docs/application/domain-objects.md` gains the templates entry;
    `interface-catalog.md`'s `/admin/project-templates` row names Edit
    details, description, cover and the bucket.

## Out of scope

- **The org's copies** — inheriting the catalog's face and changing it is
  US-118.2; **choosing from cards** is US-118.3; **Change template** is
  US-118.4. This story ships the components they compose.
- **Cropping or editing the image in the browser.** `object-fit: cover`
  crops to the middle; the hint says so.
- **An icon-and-colour picker instead of images.** The generated cover is
  the no-image state, not an alternative authoring path.
- **Restricting who can read a cover.** Public by design; if org covers ever
  need to be private the cost is a signed URL per card, cached like
  attachments — a different story.
- **Rewriting the three catalog descriptions.** Content, not code: once the
  form exists the admin writes them, and the preview shows whether they
  read.
- **Reordering templates by drag**, and **a `/projects/new` page** — the
  escape hatch if the catalog outgrows a dialog, noted in US-118.3.
