# US-100.4 — A template defines the Agent Instructions

**Status:** Completed
**Phase:** 100 — One document, not twenty-two sections
**Depends on:** us-100.1 (the document), us-100.3 (its name)

## Story

As the superadmin, a project template carries three kinds of section today —
`guideline`, `worker_instruction` and `prompt`
([227_project_templates.sql](../infra/supabase/migrations/227_project_templates.sql)).
Two of them stop making sense.

`guideline` sections are the twenty-two-key catalog, which us-100.1 retires;
a template that seeds them is seeding a shape that no longer exists.
`prompt` sections carry the server-side LLM prompts (`test_case_elaborate`,
`deploy_script_generate`) — the ones us-99.1 already excluded from the
published file set because no agent ever reads them and they are
platform-global rather than per-project. A template is how a *project* is
started; platform machinery does not belong in it.

So a template holds exactly two things: **the Agent Instructions document**,
and **the per-task instructions**. That is also the whole of what a project
has, which is the point — the template editor and the project editor become
the same two surfaces, so a superadmin authoring a template can see what a
manager will get.

## Acceptance criteria

- **AC1 — the template holds the document.** A template carries an Agent
  Instructions markdown document, seeded into a project at creation exactly
  as instruction sections are today, and editable per project afterwards.

- **AC2 — `guideline` and `prompt` sections retire from templates.** The
  `section_type` guard ([admin.py](../apps/api/app/routers/admin.py) L1021)
  accepts neither. Existing rows of those types are migrated — `guideline`
  rows concatenated into the template's new document the way us-100.1 does
  for projects, `prompt` rows dropped — and the migration reports what it
  moved and what it discarded rather than doing it silently.

- **AC3 — the copy path still copies everything.**
  `copy_project_template_into_org` keeps working across the narrowed set, and
  `seed_worker_instructions` seeds the document alongside the per-task
  instructions. A project created from a template that carries no document
  gets an empty one, not a missing row.

- **AC4 — the template editor is REBUILT to edit file contents.** Decided by
  the manager, 2026-08-15, in preference to patching a third nav entry onto
  the existing section-row component.

  A template no longer holds "sections". It holds **the contents of the files
  a project will publish**: the `AGENTS.md` body, and one editor per
  `.buildmill/*.md`. What a superadmin edits is therefore literally what
  lands in a repository — the same two surfaces a project has (us-100.3), in
  the same order, with the same names.

  This is a rebuild of `admin/project-templates/page.tsx` and
  `settings/project-templates/project-templates-client.tsx`, both ~600-line
  master-detail components with **no test coverage**. Worth its own session:
  the risk is not data loss but a page that renders and silently does not
  save, which a passing build does not catch.

- **AC5 — platform prompts keep their home.** Retiring `prompt` sections from
  *templates* must not remove the ability to set those prompts at all — they
  still live in `llm_prompt_templates` and the superadmin prompt-templates
  surface. The story records where they now live so nothing is lost with the
  section type.

- **AC6 — both projects, types, tests.** Migration applied to prod and dev,
  types regenerated, embed sweep run. Essential tests: AC2's migration on
  fixtures containing all three section types; AC3's seeding; AC4's
  set-equality.

## Partially built (2026-08-15) — the storage, not the surface

- **AC1 — the template holds the document.** Migration 265 adds
  `agent_instructions` to both `project_templates` and
  `org_project_templates`, backfilled from each template's guideline sections
  rendered as `## Title` blocks in `sort_order` — the same shape migration
  263 used project-side. Verified on prod: **1 platform** and **8 org**
  templates now carry a document, rendering correctly.
- Verify-or-rollback, like 263: the migration counts the templates that *had*
  guideline content and aborts if fewer ended up with a document.

### AC2 is deliberately NOT implemented as written

The story said `prompt` rows are "dropped". **Before writing that migration I
counted, and production holds 18 prompt sections — 16 org, 2 platform — every
one with content.** `llm_prompt_templates` does not hold the same thing: a
template's prompt section is that template's own customization. Deleting them
is real data loss with no recovery.

Retiring them from the **editor** requires no deletion at all. Migration 265
is therefore purely additive and **deletes nothing** — all 18 prompt sections
and all 18 guideline sections are still in place, confirmed on prod after the
apply. The narrowing belongs in the UI, where it is reversible by reverting a
commit rather than by restoring a backup.

Two tests pin this so it is not "corrected" later: the migration contains no
`drop column`, `drop table` or `delete from`, and it verifies its own
backfill.

### Also built

- **AC2's editor half.** Both template editors now offer **no** prompt
  sections (`PROMPT_KINDS` is empty in each), with the reason in a comment at
  the point of change. The rows stay in the database, so this is reversible
  by reverting the commit.
- **AC3 — seeding.** Migration 266 extends `seed_worker_instructions` to copy
  the template's document into a new project, guarded so a create that
  supplies its own document is never overwritten. Verified live on dev by a
  self-rolling-back probe: `doc_seeded=t`, 18 instruction kinds, document
  copied verbatim. Applied to both databases.
- api Essential green (**1802 passed, 545 skipped, 0 failed**); `npm run
  build` green.

## Built (2026-08-15, second pass) — the surface

**AC4 — both editors rebuilt to edit file contents.** A template now
presents exactly what a project publishes: **Agent Instructions**
(`AGENTS.md`) first, then one row per `.buildmill/*.md`, grouped
Requirements → Planning → Coding → Integration → Testing → Release → Refresh
with the project's own titles ("Stories in a feature — build", not `code`).
Selecting a row opens that one file in the Write/Preview editor; the row
shows its file name and reads muted when blank. The list shows *N of 17
files*.

- One shared component renders the tree and the editor for both pages —
  [template-files-editor.tsx](../apps/web/src/components/template-files-editor.tsx)
  — and one pure module defines the file set —
  [template-files.ts](../apps/web/src/lib/template-files.ts) — derived from
  `KIND_FILES` plus the document. The project's Task Instructions tab now
  reads its titles and groups from the same
  [instruction-kinds.ts](../apps/web/src/lib/instruction-kinds.ts), so the
  three surfaces cannot drift: they are the same list.
- Storage is unchanged: the document is the `agent_instructions` column
  (265), each per-task file is a `worker_instruction` section keyed by kind.
  Saving a blank per-task file **deletes** the section rather than storing
  `''` — because `seed_worker_instructions` coalesces on the section, a
  stored empty string would beat the factory default at project creation.
- Guideline sections and prompt sections are **not offered** anywhere in
  either editor (no "Add guideline section", no Prompts group). Their rows
  remain in the database untouched.

**AC5 — where the platform prompts live.** `test_case_elaborate` and
`deploy_script_generate` are set at **/admin/prompt-templates**
(`llm_prompt_templates`) and, per project, on the project's Task
Instructions tab under "Other". A template no longer carries them; the
server's refusal (below) says so in words.

**AC6 — the guard.** `_TEMPLATE_SECTION_TYPES = ("worker_instruction",)`.
`PUT …/sections/guideline/*` and `…/prompt/*` answer **422** with a reason
naming where the content now lives. `PATCH /admin/project-templates/{id}`
accepts `agent_instructions`; duplicate copies the document and only the
`worker_instruction` sections. The list endpoint returns `file_count`
(filled files, document included) instead of `section_count`.

**AC3 completed — the copy path.** Migration **267** makes
`copy_project_template_into_org` carry `agent_instructions` and copy only
`worker_instruction` sections. Applied to **both** databases (function-only
change; no type regeneration needed). Between 265 and this, a freshly copied
org template arrived with an empty document even when the catalog original
had one.

**Also fixed in passing (Phase 98 gap found by the web suite):** `merge`
had no entry in `AGENT_ROLES`, so no agent could be configured to claim a
merge run. It now sits under Programming.

### UAT (one sitting)

1. `/admin/project-templates` → expand a template: first row **Agent
   Instructions · AGENTS.md**, then groups Requirements…Refresh with
   per-task titles; no "Guideline sections", no "Prompts". List shows
   "N of 17 files".
2. Click a per-task row → editor header shows the title, `.buildmill/<file>`,
   the description; edit, Save → toast names the path; row un-mutes.
3. Blank a per-task file and Save → count drops by one; reload → still blank.
4. `/settings/project-templates` → same tree, same names, same order;
   non-manager sees it read-only.
5. Copy from Catalog a template whose document is non-empty → the copy's
   Agent Instructions row is filled.
6. Agent settings → Programming role now lists Merge.

## Out of scope

- Re-applying a changed template to existing projects — us-99.7 owns that,
  and its accept/decline half is still unbuilt.
- Changing who may write templates: platform stays superadmin, org copies
  stay gated on `manage_project`.
- `llm_prompt_templates` itself, which is a separate system and unchanged.
