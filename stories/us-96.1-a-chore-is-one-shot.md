# US-96.1 — A chore is one shot

**Status:** New
**Phase:** 96 — The type shapes the path
**Depends on:** nothing (us-96.2 builds on the type branch this story cuts)

## Story

As the manager, every work item type rides the same pipe today: plan run →
plan review → code run → code review. For a chore — rename a label, bump a
dependency, delete a dead flag — that is two runs and two gates for work
whose whole description fits in the title. The plan gate protects nothing
there; it just doubles the cost and the waiting.

A chore becomes single-shot: dispatch builds it. No plan run, no plan
review — the item goes straight to a `code`-kind run and comes back as a
PR. The one gate that has teeth stays: code review. The state machine does
not change — `planning`/`plan-review`/`planned` simply never occur for a
chore, the way `prd-review` never occurs for a story today.

## Acceptance criteria

- **AC1 — dispatch builds it.** `dispatch_kind_for`
  ([209_dispatch_kind_for_failed_is_buildable.sql](../infra/supabase/migrations/209_dispatch_kind_for_failed_is_buildable.sql))
  gains a type branch: for a `chore`, the inferred kind is always `code`,
  legal from `draft`/`ready`/`failed`/`needs-fixes`, with **no**
  approved-plan requirement — the `code run requires an approved plan`
  guards exempt the type. An explicit `p_kind = 'plan'` on a chore is
  refused in plain words: "a chore has no planning phase — dispatch builds
  it".
- **AC2 — the context carries the work, not a plan.** `dispatch_issue`
  composes a chore's `input_context` without `plan`/`test_plan` keys
  (absent, not null); title, body, acceptance criteria, guidelines,
  learnings, documents and rejection feedback ride exactly as they do for a
  code run today. The event written is `dispatched`, never
  `plan-dispatched`.
- **AC3 — retry never re-plans.** A chore at `needs-fixes` or `failed`
  redispatches as another `code` run carrying the latest `code-review`
  rejection comment as feedback — the "failed always re-plans" rule in
  `dispatch_issue` branches by type. Pinned by a test.
- **AC4 — the one gate stays.** Submit still opens the PR and moves the
  chore to `in-review`; approve merges, reject → `needs-fixes` — the
  code-review path is byte-identical to today's, pinned by a route test.
- **AC5 — a chore speaks its own instructions.** The migration widens the
  `worker_instructions.run_kind` check (last widened in
  [227_project_templates.sql](../infra/supabase/migrations/227_project_templates.sql))
  with `chore`, adds a factory default in `default_worker_instruction`
  (single-shot wording: implement directly from the item itself, keep the
  diff small, say how to verify in the hand-back notes), updates the
  seeding trigger and backfills every project. Both call sites resolve it:
  context-serve (`get_worker_instruction`,
  [db.py](../apps/api/app/db.py)) and dispatch-time
  (`seed_issue_instructions` inside `dispatch_issue`).
- **AC6 — hold rules don't wait on plans a chore will never have.**
  `issue_hold_reason`'s sibling counts that wait on approved plan
  artifacts ([235_issue_dispatch_blocks.sql](../infra/supabase/migrations/235_issue_dispatch_blocks.sql))
  exclude chore siblings.
- **AC7 — the reference stays true.**
  [docs/application/lifecycles.md](../docs/application/lifecycles.md)'s
  Issue status table gains the type-aware dispatch rows in the same commit.
- **AC8 — the migration goes to both projects.** Written in
  `infra/supabase/migrations/`, applied to prod and dev, types regenerated,
  embed sweep run (`python scripts/migrate.py apply`).
- **AC9 — tests.** SQL tests (Full QA) pin the `dispatch_kind_for` type
  branch and both refusals; an Essential route test (faked reads) pins that
  dispatching a chore creates a `code`-kind run.

## Out of scope

- Chore-specific buttons, stage tracker, and status labels — us-96.5.
- Chores as children of features. A chore is standalone work; batch
  dispatch of a feature whose children include a chore is unchanged (AC6
  only keeps such a child from wedging its siblings).
- Test-case materialization for chores — with no plan gate there is no
  test plan to materialize; the worker's hand-back notes carry
  verification, as they do for any code run.
- Bugs (us-96.2) and instruction kinds beyond `chore` (us-96.2, us-96.3).
