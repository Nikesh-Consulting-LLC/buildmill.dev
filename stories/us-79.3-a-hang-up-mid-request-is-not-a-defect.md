# US-79.3 — A caller that hangs up mid-request is not a defect

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-4 (`ClientDisconnect`, issue `ce2f3aad-f9b8-4a52-8629-898b8c8239a9`)

## Story

As the superadmin reading the System issues inbox, I want a client that
disconnected mid-request to leave nothing behind, so that the inbox holds only
failures the factory caused.

## Context

An agent (or its tunnel) dropped the connection while POSTing to
`/api/v1/llm-gateway/v1/chat/completions`. `await request.body()`
(apps/api/app/routers/llm_gateway.py:351) raised `starlette.requests.ClientDisconnect`,
which climbed through the `BaseHTTPMiddleware` stack — wrapped in an
`ExceptionGroup` by Starlette's collapsing task group along the way — reached
the catch-all `@app.exception_handler(Exception)` and was filed as a system
error. Nothing failed on our side; the caller left. There is nobody to answer,
so any status code we "return" is theater — the only real effects are the log
line and the report row, and the report row is wrong.

## Acceptance criteria

1. `ClientDisconnect` never produces an `app_issues` row, whether it arrives
   bare or as the sole member of an `ExceptionGroup` (both shapes appear in
   the prod trace). Single-member groups are unwrapped before the
   should-report decision; multi-member groups still report.
2. The request ends quietly: a debug-level log line (path + "client
   disconnected"), no error-level noise, no 500 counted in request timing as
   if the app failed — the timing row records the disconnect distinctly if
   the timing middleware sees these at all.
3. The gateway's body read is guarded at the source as well (defense in the
   route, policy in the handler), so a future middleware reshuffle cannot
   silently reopen the reporting path.
4. Regression tests: invoking the unhandled-exception path with a bare
   `ClientDisconnect` and with `ExceptionGroup([ClientDisconnect()])` files
   nothing; an unrelated `ExceptionGroup` with two members still files.

## Out of scope

- Retrying or buffering gateway requests for flaky clients — the runner
  already owns retry behavior.
- Any change to gateway auth, provider resolution, or metering.
- WebSocket hang-ups (us-79.6 owns those).

## Proof required to reach Testing

The regression tests above green; a grep of the test run's log output showing
the debug line, not a traceback.

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `6003e5b`).
`unwrap()` / `is_client_disconnect()` in errors.py peel single-member
ExceptionGroups; the catch-all answers a hang-up with 204 and no report; the
gateway guards its own `request.body()` (defense at the source, AC3); request
timing records 499 instead of blaming the app with a 500 (AC2).

**Verified:** `test_client_disconnect.py` — bare and group-wrapped hang-ups
file nothing and answer 204; a multi-member group holding a real crash still
files exactly one report; unwrap stops at multi-member groups. Gateway suite
(27 tests) green.

**Not verified:** a literal socket drop mid-upload against a running server —
simulated at the exception layer, which is where the defect lived.
