# US-97.1 — A moved repo relinks itself, or asks

**Status:** New
**Phase:** 97 — GitHub linkage stays true
**Depends on:** nothing

## Story

As the manager, when a GitHub repository is renamed or transferred, the
factory must either follow it or say so — never limp. On 2026-08-15 the Demo
project's repo moved (`Nikesh-Consulting-LLC/demo` → `kaushlesh-nikesh/demo`)
and run `ff9ef2be` finished its coding work, then spent forty minutes unable
to hand back: `get_workspace` answered `'sha'`, `submit_changeset` answered
`'commit'`, `submit_code_work` answered `'str' object has no attribute
'get'`, and `get_repo_tree` answered an **empty tree** — while the git proxy
push sailed through, because git follows redirects and our REST client does
not. The worker diagnosed the move itself and parked on a clarification; the
project row was fixed by hand.

Three defects compounded, and each gets closed here:

1. **The client mistakes a redirect for data.** GitHub answers requests to a
   moved repo with `301 Moved Permanently`. `get_commit`
   ([github.py](../apps/api/app/github.py) L264) builds its client without
   `follow_redirects` and only treats `>= 400` as an error, so it parses the
   redirect body as a commit — 35 of the 38 `httpx.AsyncClient(...)`
   constructions in that module share the gap (only the diff/tarball/zipball
   helpers opt in).
2. **Broken payloads leak as riddles.** `commit["sha"]`
   ([factory_mcp.py](../apps/api/app/factory_mcp.py) L2399) and
   `base_commit["commit"]["tree"]["sha"]`
   ([changesets.py](../apps/api/app/changesets.py) L321) raise bare
   `KeyError`s that the MCP layer stringifies to `'sha'` / `'commit'` — an
   error that tells the worker nothing and cost this run its forty minutes.
3. **Nothing reconciles the link.** The project row kept the dead path
   silently. The Edit-project dialog could not even express the new one: its
   select only offers repos from the org installation's list, which no longer
   contains a repo that moved out — so the UI had no way to repair the very
   state it was in.

After this story: a repo move is **detected the moment any factory GitHub
call meets it**, and the factory either relinks automatically (when its App
can see the repo at the new path) or tells the manager exactly what to do
(when it can't). Inconsistency is never a durable state.

## Acceptance criteria

- **AC1 — one client, redirect-aware.** GitHub REST calls go through a
  shared client/request helper in `github.py`. For safe reads (GET) it
  follows redirects; for everything it treats a `301` on `/repos/...` as a
  **named condition**, raising `GitHubError` carrying the new
  `owner/repo` parsed from the `Location` header — never returning the
  redirect body as payload. No call site constructs a bare
  `httpx.AsyncClient` for the REST API anymore; pinned by a test that scans
  the module the way `test_suite_split.py` pins the suite guard.
- **AC2 — payload shape is checked, not assumed.** `get_commit`,
  `get_ref`, `get_content`, `get_tree`, `compare_commits` and the git-data
  writers validate the fields they index before indexing; a response missing
  them raises `GitHubError("unexpected GitHub answer for <op> (<status>)")`.
  No worker-facing tool error may consist solely of a stringified
  `KeyError`/`AttributeError` — the MCP tool wrappers catch unexpected
  exceptions and answer `<tool>: <type>: <message>`. Pinned by route tests
  that fake a 301 body for `get_workspace`, `submit_changeset` and
  `submit_code_work` and assert the answer names the move (today they answer
  `'sha'` / `'commit'` / `'str' object has no attribute 'get'`).
- **AC3 — a detected move reconciles automatically when it can.** When any
  factory operation hits the repo-moved condition, the api resolves the new
  full name (following the redirect once), verifies its GitHub App
  installation can access the repo there, and — only then — updates
  `projects.repo_full_name` in place, writes the change to the project's
  audit surface (the same trail the Edit dialog writes), and notifies the
  org ("Demo's repository moved to kaushlesh-nikesh/demo — the factory
  followed it"). The operation that tripped the detection then proceeds (or
  the worker's retry succeeds) against the new path.
- **AC4 — and asks when it can't.** If the App cannot access the repo at
  its new location, nothing is written: the project page shows a named
  broken-link state ("GitHub reports this repository moved to X and the
  factory cannot see it there — grant the GitHub App access, then relink"),
  a notification says the same, and every factory GitHub tool on that
  project answers that message rather than a low-level error. The prompt
  clears itself once reconciliation succeeds.
- **AC5 — the Edit dialog names the stale state.** When a project's stored
  `repo_full_name` is not among the repos the installation offers, the
  Edit-project dialog says so next to the select ("current: X — not in the
  installation's list") instead of displaying the stale value as if it were
  selectable. Saving without touching the select never rewrites the repo.
- **AC6 — tests.** Essential (faked reads, no network): the 301-condition
  tests of AC2; reconciler tests — moved + accessible ⇒ row updated +
  audited + notified, moved + inaccessible ⇒ no write + prompt state; and
  the client-construction scan of AC1. The runner is untouched.

## Out of scope

- Repo **deletion**, installation revocation, and permission downgrades —
  only the rename/transfer (301) condition is handled here; other GitHub
  failures keep their current error paths.
- Following redirects on the factory **git proxy** — git already does.
- Back-classifying run `ff9ef2be` or altering `fault_class` semantics
  (us-85.3 owns fault classing).
- Migrating historical audit rows; the trail starts at this change.
- Any change to how the org's GitHub App installation list is fetched or
  cached; AC5 only makes the dialog honest about it.
