# US-98.6 — The manager reviews the merge summary

**Status:** New
**Phase:** 98 — Many branches, one landing
**Depends on:** us-98.4 (a merge branch and a pull request exist to review)

## Story

As the manager, reviewing a merge is not reviewing a feature. A feature's
diff answers "is this good code"; a merge's diff answers a narrower and
harder question — "did anything get lost". The only way to answer it is to
see which branches were folded in, which files had to be reconciled, and
what the agent decided in each case. A plain diff hides exactly that: a
conflict resolved by silently taking one side looks identical to a clean
merge.

So the review surface for a merge leads with the account, not the diff. Each
source branch, the head sha that was landed, and what happened to it — clean,
or reconciled with a stated decision. The diff is there underneath, and
GitHub's checks run against the pull request the way they do for any branch.

Approving merges the pull request. And it merges it with a **merge commit**,
not a squash: squashing would collapse every source branch's history into
one new commit and destroy the only record of where those changes came from
— which is the same reason release PRs to `prod` are never squashed.

## Acceptance criteria

- **AC1 — the review leads with the account.** A merge run in review shows,
  above the diff: the base branch and head it merged into, then one row per
  source branch — branch name, head sha short form, and the agent's
  per-branch account (clean, or the reconciliation it made). The summary and
  the pull-request link sit alongside.

- **AC2 — the diff and the checks are both reachable.** The merged diff
  renders through the existing review surface, and the pull request's GitHub
  check status is visible, so a merge whose CI is red is obvious before it
  is approved.

- **AC3 — approve merges with a merge commit.** Approving a merge run calls
  the existing `_merge_pr` path ([reviews.py](../apps/api/app/routers/reviews.py)
  L50) with `merge_method="merge"` rather than the default squash. A test
  pins the method for `merge` runs specifically, and pins that no other run
  kind's merge method changes.

- **AC4 — send back works, and carries the reason.** Sending a merge back
  returns it with the manager's comment, which rides the retry run's
  feedback like any other rejection. The merge branch and its pull request
  are left standing so the next run can build on them or replace them —
  whichever it does, it is not starting from a repository the factory has
  half-changed.

- **AC5 — a conflicted merge PR routes like any other.** If the merge pull
  request itself becomes unmergeable — the base moved while it sat in review
  — the existing `MergeConflict` detection and the `reject-conflict` path
  ([reviews.py](../apps/api/app/routers/reviews.py) L36, L596-675) handle it
  unchanged, and the message it composes names the merge run for what it is.

- **AC6 — the chore completes on merge.** A merge chore whose pull request
  merges reaches its terminal state the way a chore's build does; the work
  items owning the *source* branches are not touched.

- **AC7 — tests.** Essential, faked GitHub: the AC3 merge-method assertion
  and its negative; the AC1 review payload shape; AC4's feedback
  carry-through; and AC6's chore transition. `npm run build` green.

## Out of scope

- Deleting the source branches after the merge lands, and transitioning the
  work items they belong to — stated as out of scope in us-98.2 and us-98.4
  and restated here because this is the surface where it would be added.
- Blocking approval on a red CI check. The check status is shown (AC2); the
  manager decides. Gating is a separate decision affecting every run kind.
- Any change to how non-merge runs are reviewed or merged.
- Releasing what the merge landed. A merge puts commits on the default
  branch; cutting a release from them is the existing release path.
