# US-117.3 — A release prep resolves its model like a run does

**Status:** Testing
**Phase:** 117 — A transient fault reads as transient
**Depends on:** us-116.7 (the org default provider's model, the resolver's
floor), us-116.1 (one resolver, server-side), US-63.x (the follow-up this
narrows), US-78.5 (the no-model refusal)

## Story

As the manager, I want a release prep to resolve its model through the same
chain a run uses, so that a model I set on the org is a model the release
agent can actually use.

## Design

### The failure

A release cut on 2026-08-18 03:00 refused:

```
the interactive CLI exited 1 after 7s. Its last output:
this agent has no model to reason with. Set one on its settings page under
Model per role, give the org's default preset a model, or set a default model
on the org's default LLM provider (Settings → LLM providers) — nothing was spent.
```

The manager had already done the third thing. The org's default provider
(*Grok XAI*) named `grok-4.6` throughout. The refusal was advising a fix that
was already in place.

### Why the floor could not be reached

The prep's model was chosen in the **runner**, from the agent's own overrides
and nothing else ([workloop.py:948](../apps/runner/supervisor/workloop.py:948)):

```python
overrides = config.get("model_overrides") or {}
model = (overrides.get("release_prep") or overrides.get("release")
         or overrides.get("code") or next(iter(overrides.values()), None))
```

`DevOps` has `model_overrides = {}` — so `model` was `None`, the gateway was
minted with no model (`mint_gateway_key` stores `(model or "").strip() or
None`, no fallback), `GROK_MODEL` was empty, no `[model.*]` block was written,
and `interactive` raised its refusal.

**The exclusion was deliberate, and overreached.** US-63.x fixed a real bug —
release prep is not a `ROUTE_KINDS` member, so empty resolved settings let the
env provider fall through to "whatever the org default happened to be" rather
than the agent's own pin. The fix kept the agent's pin winning by reading
*only* `model_overrides`. That also cut off every fallback beneath it, and
us-116.7 later added one the runner cannot see: the org default provider's
model, which lives in `model_resolution` on the server.

Net effect: **an agent with no per-role pin could never run a release prep**,
whatever the org configured. DevOps failed identically on 16, 17 and 18 August.

### The fix

The **claim** resolves the model, through `model_resolution.resolve_for_kind`
— the same resolver a run's claim uses — and returns it. The runner prefers
that answer.

Release prep has no route of its own, so it borrows the agent's **`release`**
resolution: the closest analog, and the role an agent must hold to be offered
the work at all. That inherits the whole precedence chain, so US-63.x's intent
survives as its first step — the agent's own pin still wins — and the preset
and the floor follow beneath it.

The runner keeps its local chain as a fallback for an API that predates the
field, so a deploy-skewed runner keeps working rather than refusing every prep.

## Acceptance criteria

- **AC1 — the floor is reachable.** An agent that pins nothing, whose default
  preset names nothing, and whose org default provider names `grok-4.6`,
  resolves `grok-4.6`. Pinned by a test with exactly that arrangement.
- **AC2 — the agent's own pin still wins** over the org's (US-63.x's intent).
- **AC3 — nobody chose anywhere is still a refusal.** `None` resolves to
  `None`, the runner still refuses, and the refusal still says nothing was
  spent — this story removes a false refusal, not the true one.
- **AC4 — the claim carries it.** `POST /worker/release-prep/{id}/claim`
  answers a `model` field; the runner prefers it over its local overrides.
- **AC5 — deploy skew is survivable.** A claim without the field falls back to
  the runner's existing chain.
- **AC6 — Essential.** The API tests fake their reads; the runner tests pin
  the fallback chain. No database, no network.

## Verification (2026-08-18)

api **2037 passed** / 591 skipped (+3); runner **368 passed** (+4).

**Not verified end to end.** No release was cut against the changed code — the
prep path needs a live agent on a pool machine, which this workstation is not.
What is proven is the resolution (three cases, faked reads) and the runner's
selection chain.

**The prod symptom is separately unblocked:** `DevOps` was given
`{"test","release","deploy"} → grok-4.6` directly, matching the org's provider
default, so the next cut runs without waiting for this story to ship.

## Out of scope

- **Whether release prep should be a `ROUTE_KINDS` member** with a route of
  its own. Borrowing `release` is the smaller change and matches how the work
  is authorized; making it a first-class kind is a bigger question about the
  routing table.
- **The refusal's wording** (US-78.5/us-116.3) — it was accurate about the
  three places, just unreachable from this path.
- **`mint_gateway_key` gaining a fallback.** The model belongs to the
  resolver, not the mint; a second fallback there is the "two implementations
  that disagree" us-116.1 warns about.
