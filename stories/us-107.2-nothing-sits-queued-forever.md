# US-107.2 — Nothing sits queued forever

**Status:** Testing
**Phase:** 107 — Fixed is an outcome, and nothing waits forever
**Depends on:** US-3.2 (`requeue_expired_claims`), US-31.2 (stale-heartbeat sweep), us-103.1 (the same hole, one layer up), the Workbench "Factory stalled" banner

## Story

As the manager, I want a run that no worker ever claims to be surfaced and aged
out, so that a queued job cannot sit for six days while the Workbench cheerfully
reports that an agent is working on it.

**This is not hypothetical — it is why the story exists.** On 2026-08-16 an
Instructions Refresh card on the Buildmill App workbench read *"An agent is
reading the repository · 6d ago"*. Run `f483ee01` had been `queued` since
2026-08-10 15:00 and was **never claimed**: `worker_id`, `claimed_at` and
`claim_expires_at` all null, zero recommendations produced, its
`guideline_refreshes` row still `pending`. A second run, `9f41a332` (a `plan` on
Boondock Edge Portal), had been queued 6d 11h the same way. Both were cleared by
hand.

## Design

### Why nothing caught it

`requeue_expired_claims` (`apps/api/app/db.py:7828`) is the factory's only
reaper, and its `where` clause is:

```
r.status = 'running' and r.worker_id is not null and r.claim_expires_at < now()
```

Every one of those is false for a never-claimed run. **A lease can only expire
if it was ever taken.** A run that no worker picks up has no lease, so it is
invisible to the sweep — permanently. This is precisely the shape of us-103.1
(release prep had no reaper at all), one layer down, and the same lesson:
*the failure mode is not the claim going stale, it is the claim never happening.*

### The card lied, which is what made it survive

A `pending` refresh with no recommendations renders as "An agent is reading the
repository". That reads as progress, so it is not a thing to investigate — it is
a thing to wait for. Six days of waiting looked exactly like six seconds of
waiting. Whatever is built here, **the card must distinguish "queued, nobody has
picked this up" from "claimed, an agent is working"**, because the wrong words
are why nobody looked.

### What was chosen: say it truthfully, offer a way out, never auto-cancel

Three options were on the table — flag only, auto-cancel after a threshold, or
auto-cancel only when no capable worker was online for the whole window. **This
story does the first, plus a manual cancel, and deliberately does not
auto-cancel anything.**

The reason is the incident itself. The run did not need killing by a machine;
it needed *not to be described as progress*. "An agent is reading the
repository" is a thing you wait for, so six days of it looked exactly like six
seconds of it. Had the card said "nothing has picked this up", it would have
been dealt with on day one.

Auto-cancel is also the one option that destroys legitimate work: a run queued
overnight while the operator's runner is off is indistinguishable, at the
database level, from this one. Binning it would turn a visibility bug into a
data-loss bug. If the honest label proves insufficient in practice, the sweep
is still available — but it should be earned by evidence, not assumed.

### The three states

`refreshState` splits what was one boolean:

| state | when | reads as |
|---|---|---|
| `ready` | the agent handed back sections | *N files proposed — one decision* |
| `working` | `claimed_at` is set, no sections yet | *An agent is reading the repository* |
| `waiting` | unclaimed, under 1h | *Queued — waiting for a worker to pick it up* |
| `stalled` | unclaimed, 1h or more | *No worker has picked this up* + amber + **Cancel it** |

`claimed_at` is the only honest test. A run sits `queued` with every claim
column null from creation until a worker takes it — which may be never.

**A slow agent is not a stalled queue.** A `claimed` refresh stays `working`
however long it runs; that is the lease reaper's job, and it already has one.

## Acceptance criteria

- **AC1 — an unclaimed refresh never claims an agent is working.** A `pending`
  refresh whose run has no `claimed_at` reads *"Queued — waiting for a worker
  to pick it up"*, and past an hour *"No worker has picked this up"*. It never
  reads "An agent is reading the repository".
- **AC2 — a stalled card looks different.** Past the threshold the card takes
  amber styling and a warning icon instead of the calm spinner, and states that
  nothing reaps an unclaimed run so it will wait indefinitely.
- **AC3 — there is a way out.** A stalled card offers **Cancel it**, which
  confirms and then calls the existing `POST /api/v1/runs/{id}/cancel`. No new
  endpoint.
- **AC4 — a working agent is left alone.** A refresh whose run *is* claimed
  reads as an agent working however long it takes, with no amber and no cancel.
- **AC5 — the regression is pinned.** A test asserts that an unclaimed refresh
  at 6 days — the `f483ee01` case — is `stalled`, and a sweep over several
  durations asserts no unclaimed state ever produces the "agent is reading"
  label.

## Out of scope

- **Auto-cancelling anything.** See Design — chosen against, with reasons.
- The general never-claimed-run sweep across *all* run kinds. This story fixes
  the surface that lied; a `plan` run queued forever is still only visible
  through the existing "Factory stalled" banner. **That gap is real and still
  open** — see below.
- Changing why a worker did not claim the run — capability matching and pool
  routing are their own subject.
- The two runs from the incident; both were dealt with by hand on 2026-08-16.

## Built (2026-08-16)

Web only; no migration, no API change.

- `refresh-state.ts` + `.test.ts` **(new)** — the four states and their labels,
  7 tests, including the incident case and the sweep in AC5.
- `cancel-stalled-refresh.tsx` **(new)** — a client island so the card stays a
  server component; confirms, then calls the existing cancel endpoint. It sets
  `Content-Type: application/json` explicitly, because `apiFetch` adds the
  bearer token but not the content type and the endpoint's body is a Pydantic
  model — without it FastAPI answers 422.
- `data.ts` — the run rides along on the refresh query, FK-named
  (`runs!guideline_refreshes_run_id_fkey`) because `guideline_refreshes` holds
  FKs to both `runs` and `issues` and an un-hinted embed is how PGRST201 starts.
  `GuidelineRefresh` gains `runId`, `claimed`, `hoursWaiting`.
- `guideline-refresh-group.tsx` — the four states, the amber treatment, the
  cancel.

**Verified.** `npm run build` compiles; `npm run test:web` 221 passing (+7).
The `claimed_at`-is-the-only-honest-test claim was read off the live
`f483ee01` row, not assumed.

**Not verified.** Nothing was clicked — no `apps/web/.env.local` in this
checkout. AC1–AC4 are reasoned from the query and the existing endpoint. In
particular **the cancel path has never been executed**: the 422 content-type
bug above was caught by reading `apiFetch`, not by a failing request, so the
fix is argued rather than demonstrated. Worth pressing once in UAT against a
deliberately-dispatched refresh with no worker online.

## Still open after this story

The **general** hole remains: `requeue_expired_claims` still cannot see any
never-claimed run of any kind, and run `9f41a332` (a `plan` on Boondock Edge
Portal, queued since 2026-08-10) is still sitting there untouched. This story
fixed the card that lied about it; it did not fix the queue that forgets.
