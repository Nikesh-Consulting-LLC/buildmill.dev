# US-107.2 — Nothing sits queued forever

**Status:** New
**Phase:** 107 — Fixed is an outcome, and nothing waits forever
**Depends on:** US-3.2 (`requeue_expired_claims`), US-31.2 (stale-heartbeat sweep), us-103.1 (the same hole, one layer up), the Workbench "Factory stalled" banner

## Story

As the manager, I want a run that no worker ever claims to be surfaced and aged
out, so that a queued job cannot sit for six days while the Workbench cheerfully
reports that an agent is working on it.

**This is not hypothetical — it is why the story exists.** On 2026-08-16 an
Instructions Refresh card on the Buildmill App workbench read *"An agent is
reading the repository · 6d ago"*. Run `f483ee01` had been `queued` since
2026-08-10 15:00 and was **never claimed**: `worker_id`, `claimed_at` and
`claim_expires_at` all null, zero recommendations produced, its
`guideline_refreshes` row still `pending`. A second run, `9f41a332` (a `plan` on
Boondock Edge Portal), had been queued 6d 11h the same way. Both were cleared by
hand.

## Design

### Why nothing caught it

`requeue_expired_claims` (`apps/api/app/db.py:7828`) is the factory's only
reaper, and its `where` clause is:

```
r.status = 'running' and r.worker_id is not null and r.claim_expires_at < now()
```

Every one of those is false for a never-claimed run. **A lease can only expire
if it was ever taken.** A run that no worker picks up has no lease, so it is
invisible to the sweep — permanently. This is precisely the shape of us-103.1
(release prep had no reaper at all), one layer down, and the same lesson:
*the failure mode is not the claim going stale, it is the claim never happening.*

### The card lied, which is what made it survive

A `pending` refresh with no recommendations renders as "An agent is reading the
repository". That reads as progress, so it is not a thing to investigate — it is
a thing to wait for. Six days of waiting looked exactly like six seconds of
waiting. Whatever is built here, **the card must distinguish "queued, nobody has
picked this up" from "claimed, an agent is working"**, because the wrong words
are why nobody looked.

### Sketch, not settled

Three parts, in the order they earn their keep:

1. **Say it truthfully.** A queued-unclaimed run says so, with its age. Cheapest
   change, and on its own it would have caught this.
2. **Sweep it.** A companion to `requeue_expired_claims` — same callers, startup
   and every pool listing — that acts on `status = 'queued' and worker_id is
   null and created_at < now() - <threshold>`.
3. **Decide the action.** Auto-cancelling is destructive: a run queued
   legitimately while the operator's runner is off overnight must not be
   binned. Candidates: flag only; cancel with a reason after a long threshold;
   or cancel only when no capable worker has been online for the whole window.
   The last is the most correct and the most work.

**The threshold and the action are open and must be decided before building.**
The existing "Factory stalled" banner already detects queued-with-no-capable-
worker and was evidently not enough on its own, which is evidence for (2)/(3)
over (1) alone — but not evidence for which.

## Acceptance criteria

*Provisional — this story is `New` and its design is not settled.*

- **AC1 — a stalled run is legible.** A queued run nothing has claimed reads as
  waiting-for-a-worker, with its age, on the Workbench — never as an agent
  working.
- **AC2 — the sweep sees it.** A never-claimed queued run older than the
  threshold is picked up by a reaper that runs on the same triggers as
  `requeue_expired_claims`.
- **AC3 — nothing legitimate is binned.** A run queued while the runner is
  merely offline is not destroyed; the chosen action is justified against that
  case explicitly.
- **AC4 — a regression test.** A run with `worker_id is null` and no
  `claim_expires_at` is asserted to be reaped, since that is exactly the row the
  current sweep cannot see.

## Out of scope

- Changing why a worker did not claim the run — capability matching and pool
  routing are their own subject. This story is about the run not rotting in
  silence regardless of the cause.
- The two runs from the incident; both were cleared by hand on 2026-08-16.

## Incident record (2026-08-16)

Cleared by hand, in production:

- **`f483ee01`** (guidelines, Nikesh Consulting LLC) — run set `cancelled` with
  reason "Queued 6 days and never claimed — cancelled by the manager";
  `guideline_refreshes` `b15e9983` set `decided`. Done as a single transaction
  matching `_record_cancel`'s semantics; the run carried no `issue_id`, so no
  issue was restored and no `run-cancelled` event was owed.
- **`9f41a332`** (plan, Boondock Technologies / Boondock Edge Portal, story
  "Add landing value sections for API keys, devices, and cloud services") —
  **not touched.** It belongs to a different org than the reported card, which
  only became clear after the manager had approved treating both alike. Its
  cancel would restore the issue from `queued` to `draft` (`prev_issue_status`)
  and owe a `run-cancelled` event. **Still queued; still needs a decision.**
