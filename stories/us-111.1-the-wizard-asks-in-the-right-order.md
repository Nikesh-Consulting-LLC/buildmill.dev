# US-111.1 — The Add agent wizard asks in the right order

**Status:** New
**Phase:** 111 — The Add agent wizard asks in the right order
**Depends on:** US-77.1 (the four roles), US-77.2 (offered agent types),
US-78.3/78.5/78.6 (the interactive agent, platform-managed, pool-only),
US-66.2 (OpenCode as the current default), us-110.1 (the projects step, now
the only project question)

## Story

As the manager, I want the wizard to ask what an agent *is* and *does* before
it asks about plumbing, so that the choices that shape every later option come
first instead of last.

## Design

### What moves

| Step | Today | After |
|---|---|---|
| 1 · Who | name | name + **What this agent does** (the four roles) |
| 2 · Where | placement (pool / machine) | **Agent Type** + placement |
| 3 · What | agent type + roles + projects | **projects only** — relabelled **Projects** |
| 4 · Billing | Claude only, unchanged | unchanged |
| 5 · Done | unchanged | unchanged |

Nothing is duplicated: the roles and the type each move, they do not appear
twice. Step 3 keeps only the project list us-110.1 left it with, so its "What"
label goes with the content that earned it.

### Why step 2 is the right home for Agent Type — it fixes a real inversion

The Where step's options **already depend on the type**, which is chosen a page
later. `interactive` is `poolOnly` (US-78.6), so choosing it retracts the
owned-machine branch. The wizard copes with that backwards order twice:

- a `useEffect` snaps `placement` back to `pool` (or `null`) when a pool-only
  type is picked after a machine was already selected
  ([add-agent-wizard.tsx:195](../apps/web/src/app/(app)/team/add-agent-wizard.tsx:195));
- `chooseMachine` snaps the *module* to whatever the machine reported, when the
  manager picks a machine that never installed the chosen one
  ([add-agent-wizard.tsx:552](../apps/web/src/app/(app)/team/add-agent-wizard.tsx:552)).

Two corrections pulling in opposite directions, because the question that
constrains the answer was asked second. Putting both on one page makes the
constraint visible as it is applied — pick Interactive and the machine option
visibly is not there, rather than silently un-choosing itself a page later.

### Interactive becomes the default, and that is a pool-only default

`moduleKey` starts as `opencode` today (US-66.2). It becomes `interactive`, and
the entry moves above `grok`/`opencode` in `MODULES` so it renders first.

**The consequence has to be handled, not discovered.** Interactive is
`poolOnly`, so a wizard that opens on it offers *only* the Build Mill pool as a
placement. An org with no selectable pool would land on step 2 with nothing to
choose and a dead Next button — a worse first run than the one being fixed. So
the default is *conditional*: Interactive when a selectable pool exists,
otherwise the first offered type that can run somewhere. It is still listed
first either way.

**Ripple:** `MODULES` order is also the render order on
`servers/register-agent-dialog.tsx`, `servers/[id]/host-detail.tsx` (twice) and
the member settings page. Those lists reorder too. Cosmetic, and arguably
better — but it is a change on four screens, not one.

## Acceptance criteria

- **AC1 — step 1 asks who and what.** The Who step shows the name field and the
  four role cards (Planning, Programming, Testing, Deployment), all checked by
  default per US-77.1, with the existing "Unchecked roles are never claimed"
  note and the amber benched-agent warning when none are checked. Next requires
  a non-empty name only — a benched agent stays creatable, as today.
- **AC2 — step 2 asks type then placement, in that order on the page.** The
  Where step shows Agent Type above the placement options. Choosing a pool-only
  type removes the owned-machine option and shows the existing "runs on a Build
  Mill pool only" note **in the same interaction**, with no page change in
  between.
- **AC3 — Interactive is first and default.** Buildmill Interactive Agent is
  the first agent-type option and is pre-selected when the org has a selectable
  pool. With no selectable pool it is still listed first but not pre-selected;
  the first offered type that has a valid placement is. **Next is never dead on
  arrival at step 2.**
- **AC4 — step 3 is Projects.** The step is labelled `Projects` and contains
  only "Which projects it works on" (us-110.1). Its validity is unconditional —
  every project is checked by default and an unchecked-all agent is already
  warned about, not blocked.
- **AC5 — the two snap-backs are re-examined, not merely inherited.** With type
  and placement on one page, the placement snap-back `useEffect` is removed if
  the same-page rendering makes it unreachable; `chooseMachine`'s module snap
  stays only if picking a machine can still contradict the chosen type. Either
  way the outcome is asserted by a test, not left to reading.
- **AC6 — the billing step still follows the type.** Selecting Claude Code on
  step 2 still inserts the Billing step; selecting anything else still skips
  it. Pinned by a test over the step sequence.
- **AC7 — an agent created through the reordered wizard is identical.** Same
  `create_worker` call, same `enabled_kinds` from the roles, same
  `worker_capabilities` rows, same `enabled_modules`. This story moves
  questions between pages; it changes nothing about what is written.
- **AC8 — the reorder is proven, not eyeballed.** A web test asserts the step
  sequence and each step's contents, so a later edit cannot quietly move a
  field back. `npm run build` and `npm run lint` clean.

## Out of scope

- **Which types are offered** (US-77.2's `offered` flag) and the superadmin
  catalog that narrows them (US-57.6) — untouched.
- **`poolOnly` itself**, and the API/database enforcement behind it (US-78.6).
  This story reorders the questions; it does not change who may run where.
- **The "My own machine" (`self`) placement**, hidden as an entry point since
  2026-08-07. It stays hidden and its plumbing stays intact.
- **The roles → run-kinds mapping** (US-77.1, migration 178).
- **The projects list's all-checked default** (US-55.1) — us-110.1 already
  declined to revisit it and so does this.
- **Billing step contents** — only *when* it appears is in scope, via AC6.

## Open question for the manager

**Does Interactive-by-default match how you actually staff?** It is
platform-billed and pool-only, so every agent created without changing it
consumes a pool slot and bills the platform. That is exactly right if
Interactive is the house default now; it is an expensive accident if OpenCode
still is for most agents. AC3 as written follows the request — this note only
makes the consequence explicit.
