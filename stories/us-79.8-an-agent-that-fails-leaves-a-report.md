# US-79.8 — An agent that fails leaves a full report

**Status:** Testing
**Phase:** 79 — Production error truth
**Dependencies:** none

## Story

As the superadmin debugging agent behaviour, I want every agent failure on
every workspace — including an agent that simply dies holding its claim — to
land in a new **Agent failures** console with the full picture of the run
(which agent, what task, what instructions, how it failed), so that a dead
agent is a report I can read instead of a silence I have to reconstruct from
per-issue event feeds.

## Context

There are three ways an agent fails today, and none of them reach a console:

1. **The run reports `failed`** — `complete_run` (apps/api/app/db.py)
   keeps the error and stdout on the run row, consumes an attempt
   (`run_attempts`, reason `failed`), and appends an issue event.
2. **The lease expires without a submission** — the agent died holding the
   claim. `requeue_expired_claims` mutates the run row back to `queued`,
   nulls the worker, consumes an attempt (`lease-expired`), and appends a
   `claim-expired` issue event. Nothing is written to the run's error
   fields — the run looks like it never happened.
3. **The heartbeat goes stale** — `requeue_stale_heartbeats` does the same
   under reason `heartbeat-stale`; a run carrying a `claude_session_id`
   lands `paused` for its worker to resume (US-59.4) instead of `queued`.

The System issues inbox (US-16.8/16.9) only receives *exceptions the API
process raises*. An agent dying is not an exception anywhere — the sweep that
notices it succeeds — so the noisiest real failure mode of the factory is
invisible on the one screen built for failures. What traces do exist answer
the wrong questions: `run_attempts` is a ceiling counter (US-31.5) with no
error, no instructions, and no agent identity beyond a worker id;
`issue_events` buries the fact inside one work item's feed; and failures on
issue-less runs (deploy, release prep, test) have no feed at all.

Filing these into `app_issues` is the wrong shape: that table is
deployment-scoped and fingerprint-deduped, and dedup would collapse distinct
failures whose entire value is their individual run detail. Agent failures
get their own append-only table and their own console, sibling to System
issues.

One subtlety pins the schema: a requeue reassigns the run row (same id, new
worker later), so **agent identity must be snapshotted at failure time** —
the run row cannot answer "who failed" afterwards. The instruction bundle is
the opposite case: `input_context` is written at dispatch and never rewritten
by claim or requeue, so the console reads it *through* the run reference
rather than copying kilobytes into every failure row.

## Acceptance criteria

1. **Migration** (next free number; applied to both Supabase projects, types
   regenerated): a new `public.agent_failures` table — append-only, one row
   per failure event, no dedup — with:
   - references: `org_id`, `project_id`, `issue_id` (nullable), `run_id`;
   - the task: `kind` (the run kind: plan, code, breakdown, test, deploy,
     release…);
   - the agent, snapshotted: `worker_id`, `worker_name`, `worker_type`
     (workers.type), `preset_name`, `preset_version` (off the run row);
   - the failure: `category` check-constrained to
     `('run-failed', 'lease-expired', 'heartbeat-stale')`, `error` text,
     `detail` jsonb (held_minutes / silent_seconds / stdout tail — whatever
     the capture site knows), `resumable` boolean (true only for the
     stale-heartbeat landing that parked the run for resume);
   - triage: `status` in `('new', 'reviewed')` default `new`, `created_at`.
   - RLS: platform-admin read across all orgs (`is_platform_admin()`),
     service-role writes only, **no org-member policy** — this is a
     superadmin surface, same boundary as `/admin/system-issues`.
2. **All three paths write a row**: the `failed` branch of
   `complete_run` (including the legacy `stopped` landing),
   `requeue_expired_claims`, and `requeue_stale_heartbeats` — the last on
   *both* landings, with the parked-for-resume one marked `resumable`.
   Issue-less runs (deploy, release prep, test) are captured too — unlike
   `record_run_attempt`, which skips them by design.
3. **Recording never breaks the path that noticed the failure**: a failed
   insert is logged and swallowed — a requeue sweep or a run callback must
   commit exactly as it does today even if the failure log is unavailable
   (same posture as `self_report`).
4. **Console** at `/admin/agent-failures`, nav entry "Agent failures"
   directly beside "System issues" in the admin Settings group. The table
   shows, per row: when, workspace (org), project, work item, run kind,
   agent name, category, and the error headline; each failure is its own
   row — counts are visible as rows, not collapsed into an occurrence
   number.
5. **Expanded detail** shows: the full error text, the `detail` bag, the
   snapshotted agent identity (name, type, preset@version), and the run's
   full instruction bundle (`input_context`) fetched through `run_id` —
   rendered so the prompt/instructions are readable, not one JSON blob. A
   run that no longer exists (issue deleted, cascade) says so plainly while
   the snapshot columns still display. Where the work item still exists, it
   links to `/issues/<id>`.
6. **Copy details** produces one markdown block (agent, task, category,
   error, detail, instructions) ready to paste into an LLM for debugging —
   parity with the System issues console's copy actions.
7. **Triage**: "Mark reviewed" moves a row `new → reviewed`; the default
   view lists `new` only, with a "show reviewed" toggle — same pattern as
   System issues' fixed/ignored toggle.
8. **Tests**: `test_agent_failures_sql.py` proves each of the three sites
   writes a row with the right category and snapshot (including one
   issue-less run, and the parked/resumable landing), and proves the
   boundary — a platform admin reads rows across orgs, an ordinary org
   member reads none and cannot triage. The writers are SQL through and
   through, so the coverage lives in the `--full` SQL suite (us-80.1's
   split), not the DB-less fast suite.

## Out of scope

- Fingerprinting, dedup, or occurrence counting — every failure is a row.
- Promotion of an agent failure into a work item (System issues' US-16.6
  path). Copy-for-LLM is the v1 debugging loop.
- Realtime subscription on the console; load-time fetch is enough.
- Retention or pruning; volume is naturally bounded by the US-31.5 attempt
  ceilings.
- Notifications, digests, or dashboard cards for agent failures.
- Any change to the requeue, parking, or attempt-consumption semantics
  themselves — this story observes them, it does not alter them.
- An org-member-facing view of their own agents' failures (a later story if
  wanted; the RLS shape above deliberately leaves room for it).

## Proof required to reach Testing

Pytest green on the new unit and SQL tests, plus a page dump or screenshot of
`/admin/agent-failures` showing a real lease-expired failure from a dev-org
run with its expanded detail — agent identity, category, and the instruction
bundle visible.

## Outcome (built 2026-08-11)

`apps/api/app/db.py` wired into `complete_run`, `requeue_expired_claims`,
