# US-96.4 — The feature holds the steering wheel

**Status:** New
**Phase:** 96 — The type shapes the path
**Depends on:** nothing hard — ordered after us-96.1/96.2 because all three edit the dispatch functions

## Story

As the manager, US-22.10 already made the feature own the **build**: an
individual code dispatch of a feature child is refused ("FEAT-2.3 owns the
build — dispatch the feature to build all 5 stories") unless the story is
in trouble. But the plan phase still routes story by story — each child can
be sent to planning by hand, and each plan is hunted down and approved from
its own page. Half the batch is a batch; the other half is clicking.

The feature becomes the only steering wheel for its children, both phases:
plan and build are dispatched **from the feature**, plan approvals are
worked **from the feature**, and a child story is never routed individually
— with one standing exception that stays exactly as it is: a child at
`failed`/`needs-fixes` accepts individual dispatch, because the fix must
never be held by the thing it fixes. Underneath, nothing merges together:
every child keeps its own run, its own branch, its own PR, its own plan
approval. The feature is a control surface, not a merge unit.

## Acceptance criteria

- **AC1 — the refusal covers planning.** `issue_dispatch_refusal`
  ([235_issue_dispatch_blocks.sql](../infra/supabase/migrations/235_issue_dispatch_blocks.sql))
  extends its feature-owns-the-build guard to `p_kind = 'plan'` for a story
  with a parent feature in `feature`/`epic` build modes, wording in the
  same voice: "FEAT-2.3 owns the plan — dispatch the feature to plan all 5
  stories." The trouble exemption (`failed`/`needs-fixes`) is carried over
  verbatim and pinned by a test.
- **AC2 — the hub already knows.** `issue_dispatch_block` /
  `org_issue_dispatch_blocks` (US-74.5) surface the new refusal with no
  further change — verified: a plan-phase feature child shows the hard
  block with the message above instead of a button that errors.
- **AC3 — the feature page drives both phases.** From the feature's page,
  the existing batch actions
  ([feature-batch-action.tsx](../apps/web/src/components/feature-batch-action.tsx),
  [batch-phase-dialog.tsx](../apps/web/src/components/batch-phase-dialog.tsx),
  `dispatch_feature_batch`) cover plan and build, and the page shows
  per-child phase progress: planning / plan in review / plan approved /
  building / in review / merged.
- **AC4 — approvals walk through the feature.** The feature page lists
  every child plan awaiting review with per-child approve and send-back —
  the existing plan-gate endpoints, the existing required comment on
  send-back. No batch-approve-unread: the gate's granularity is preserved;
  what disappears is hunting child pages one by one.
- **AC5 — scheduling is untouched.** The pool holds that already sequence a
  feature (US-15.3 sibling curation, US-20.5 one-story-in-flight and
  trouble-pauses-the-feature, the plan-approval waits in
  `issue_hold_reason`) are unchanged — this story adds a refusal and a
  surface, not a scheduler.
- **AC6 — the reference stays true, the migration goes to both projects.**
  [docs/application/lifecycles.md](../docs/application/lifecycles.md)'s
  dispatch rows note the widened refusal; migration applied to prod and
  dev, types regenerated, embed sweep run.
- **AC7 — tests.** SQL tests pin the plan refusal, its build-mode scoping,
  and the trouble exemption; a web test where the progress/approval logic
  is pure.

## Out of scope

- `story` build mode keeps per-story routing. The refusal stays scoped to
  `feature`/`epic` modes, where the feature-owns rule already lives — if
  feature children should be locked in `story`-mode projects too, that is a
  mode-retirement decision to take separately, not a side effect here.
- One-click batch plan approval — reviewing stays per plan, deliberately.
- Any change to per-child runs, branches, or PRs — the feature never
  becomes the unit of execution or merge.
- The auto-complete gap for `direct`-strategy merges (documented in
  lifecycles.md) — unchanged here.
- Rolling the feature's children into one row on the Workbench and the
  Factory queue — us-96.7 (it depends on this story's controls).
