# US-96.4 — The feature holds the steering wheel

**Status:** Testing
**Phase:** 96 — The type shapes the path
**Depends on:** nothing hard — ordered after us-96.1/96.2 because all three edit the dispatch functions

## Story

As the manager, US-22.10 made the feature own the **build**, and US-86.1
(migration 247) made it the routing unit outright — `route_feature_as_one`,
"switch 2", with one feature-owned code run and `build_mode` demoted to a
derived mirror. But the plan phase still routed story by story: each child
could be sent to planning by hand. Half the batch was a batch; the other
half was clicking.

The feature becomes the steering wheel for both phases: initial planning
and the build are dispatched **from the feature**, and a child story is
never routed individually — with the exemptions that keep a batch
recoverable: a child at `failed`/`needs-fixes` (the fix must never be held
by the thing it fixes), and a child that has already been planned once
(re-planning and sent-back revision are curation, not routing). Plan
approval granularity is untouched — each child's plan is still read and
approved on its own.

*(Reworked 2026-08-14 during the build: the original text assumed the
US-22.10-era build modes and proposed a per-child approval walk US-25.2 had
already built. Corrected to the 247 reality.)*

## Acceptance criteria

- **AC1 — the refusal covers initial planning.** `issue_dispatch_refusal`
  (latest in [247](../infra/supabase/migrations/247_two_switches_serial_law.sql))
  extends its feature-owns guard to `p_kind = 'plan'` under switch 2, for a
  story that has **never been planned** — no plan artifact in any state.
  Wording in the same voice: "FEAT-2.3 owns the plan — dispatch the feature
  to plan all 5 stories." What stays individually dispatchable, pinned by
  tests: `failed`/`needs-fixes` (the trouble exemption), and any story with
  an existing plan artifact — approved (re-plan), superseded (the `/replan`
  endpoint's own path), or a sent-back draft.
- **AC2 — the batch is exempt and never wedges.** `dispatch_feature_batch`
  reuses `dispatch_issue` per child by design (US-41.1), so it sets a
  transaction-local flag (`factory.feature_batch`) the refusal honors — the
  batch IS the feature-level dispatch. The late-arrival wedge closes with
  it: a story added after its siblings were planned used to hit "not ready
  to build" at the batch while the new refusal would have blocked planning
  it individually; the batch now plans exactly the unplanned children, and
  `feature_dispatch_phase` answers `plan` for the mixed case so the
  button's label says what will actually happen.
- **AC3 — the hub and the menu already know.** `issue_dispatch_block` /
  `org_issue_dispatch_blocks` (US-74.5) surface the new refusal with no
  further change, and the story-row dispatch menu mirrors it client-side
  ("FEAT-2.3 owns the plan") from a new `hasAnyPlan` fact — no button that
  errors, no error that has no button.
- **AC4 — reviews are reachable from the feature.** Feature-level plan
  approval already exists (US-25.2's Approve-all, per-child server-side
  checks); what was missing is the walk. The feature's stories panel puts a
  direct "Review plan" link on every child sitting at `plan-review`, so
  reading-then-deciding per child never means hunting story pages.
- **AC5 — scheduling is untouched.** The pool holds that already sequence a
  feature (US-15.3 sibling curation, US-86.1's serial law and switch-gated
  ordering, the plan-approval waits in `issue_hold_reason`) are unchanged —
  this story adds a refusal, an exemption, and a link, not a scheduler.
- **AC6 — the reference stays true, the migration goes to both projects.**
  [docs/application/lifecycles.md](../docs/application/lifecycles.md)'s
  dispatch rows note the widened refusal; migration applied to prod and
  dev, types regenerated, embed sweep run.
- **AC7 — tests.** SQL tests pin the plan refusal, both exemptions, and the
  late-arrival batch behavior.

## Verified (2026-08-14, live against build-mill-dev and Software-Factory prod)

- Migration `258_the_feature_holds_the_steering_wheel.sql` applied to
  **both** projects (`dispatch_feature_batch` restated from the live body,
  hash-verified identical across prod/dev beforehand).
- Live probe on dev (switch 2 on): a never-planned draft child of a
  feature answered `issue_dispatch_refusal(child, 'plan')` =
  "FEAT-2.7 owns the plan — dispatch the feature to plan all 1 stories".
- The batch exemption held: `dispatch_feature_batch(feature)` on the same
  pair dispatched the child's plan run with an **empty** skipped list —
  the transaction-local flag lifts the refusal exactly inside the batch.
- The revision exemption held: after inserting a `superseded` plan
  artifact for the child (the `/replan` shape), the same refusal call
  returned null. Probe rows cleaned up.
- Client mirror: `story-dispatch-menu.tsx` refuses "Plan it" for a
  never-planned draft/ready feature child; `stories-panel.tsx` rows at
  `plan-review` carry a direct "Review plan" link; the child data now
  carries `hasAnyPlan` (all-state artifact read on the feature page).
  `npm run build` green.
- Two SQL tests added (Full QA; skip locally without DATABASE_URL — the
  same assertions ran live above): the refusal + both exemptions, and the
  late-arrival batch planning exactly the unplanned children.
- AC3's hub surface verified by code-read: `issue_dispatch_block` calls
  the same `issue_dispatch_refusal` this story extends; no separate
  derivation exists to disagree.
- **Not verified here, for UAT**: the workbench hub rendering the new
  hard-block message on a real feature child, and a full
  plan-batch → approve-per-child → feature build cycle in the browser.

## Out of scope

- Switch 2 **off** (`route_feature_as_one = false`) keeps per-story
  routing — that is the switch's documented meaning, not a gap.
- Changing plan approval granularity — Approve-all (US-25.2) and per-child
  review both stay exactly as they are.
- Any change to the feature-owned code run, branches, or PRs — US-86.1's
  shape is untouched.
- The auto-complete gap for `direct`-strategy merges (documented in
  lifecycles.md) — unchanged here.
- Rolling the feature's children into one row on the Workbench and the
  Factory queue — us-96.7 (it depends on this story's controls).
