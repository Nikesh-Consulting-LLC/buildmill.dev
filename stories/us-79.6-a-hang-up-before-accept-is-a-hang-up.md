# US-79.6 — A hang-up before accept is a hang-up

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-7 (`RuntimeError: Expected ASGI message 'websocket.send' or 'websocket.close', but got 'websocket.accept'.`, issue `719c1ecc-f42a-4300-a2fa-f418a8fc9bbf`)

## Story

As the superadmin, I want a websocket client that vanishes before the server
accepts to end silently, so that the single noisiest report in the inbox — 61
occurrences in 28 hours, all on `/api/v1/runner/socket` — stops burying real
crashes.

## Context

uvicorn's `websockets-sansio` implementation raises this exact `RuntimeError`
when the TCP peer is already gone by the time the route calls
`await websocket.accept()` — a race the app cannot prevent, only survive. The
runner holds a persistent control socket through the Cloudflare tunnel; every
tunnel drop or deploy restart re-runs the race, and `WebSocketErrorReporter`
(apps/api/app/errors.py) files each loss because it only exempts
`WebSocketDisconnect` and `CancelledError`. The cadence (~every 27 minutes) is
suspiciously regular, which is worth one look while in here.

## Acceptance criteria

1. A shared `safe_accept(websocket) -> bool` helper: returns `False` on this
   accept-time `RuntimeError` and on `WebSocketDisconnect`, `True` on success.
   Every `websocket.accept()` in `apps/api` uses it and returns quietly on
   `False` — runner socket, run console, session console, server terminal
   (enumerate by grep; the acceptance is *zero* bare accepts remain).
2. The hang-up path files no `app_issues` row. `WebSocketErrorReporter` also
   recognizes this `RuntimeError` shape as a hang-up (belt and braces for any
   future bare accept), still re-raising everything else.
3. The loss stays observable without inbox noise: a debug-level log line with
   the path, countable from journald.
4. Regression test: driving that `RuntimeError` through
   `WebSocketErrorReporter` files nothing; driving any other `RuntimeError`
   still files.
5. One diagnostic pass, recorded in the story's Outcome on completion: from
   runner logs (or `worker` liveness rows), say whether the ~27-minute cadence
   is the runner's own reconnect loop, the tunnel's idle timeout, or deploy
   restarts. No fix here — just the finding, so the next phase doesn't
   rediscover it.

## Already shipped — do not rebuild

**AC2 and AC4 landed in `9f9d09a` (released as PR #254, 2026-08-11)**, from the
other end: the same BUG-7 report arrived through the manager and was fixed in
`WebSocketErrorReporter` before this story was picked up.
`str(exc).startswith("Expected ASGI message")` is exempted from self-reporting,
everything else still reported and re-raised, with both regression tests AC4
asks for in `test_self_reporting.py`.

**What is left is the larger half**, and it is the half that actually stops the
flood: AC1's shared `safe_accept()` with zero bare `accept()` calls remaining
(the reporter exemption only stops the *reporting*, not the raise), AC3's debug
line, and AC5's cadence finding. Worth knowing while sizing this: the report the
manager forwarded showed **1 occurrence**, this story's own research found **61
in 28 hours** — trust the latter.

## Out of scope

- Changing the runner's reconnect/backoff behavior (finding only, per AC5).
- Cloudflare tunnel configuration.
- The HTTP-side disconnect twin (us-79.3).

## Proof required to reach Testing

Tests green for AC1/2/4; the grep output showing every accept call routed
through the helper; the AC5 finding written down.

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `6003e5b`),
on top of `9f9d09a`'s reporter exemption (AC2/AC4, already shipped).
`safe_accept()` in errors.py returns False on the accept-race RuntimeError
and on WebSocketDisconnect; all four accept sites go through it (runner
socket, run console, session console, server terminal), with a debug log
line naming the path (AC3).

**Verified:** `test_ws_accept.py` — the race answers a quiet False, any other
RuntimeError still raises, and a repo-wide sweep test asserts zero bare
`await …accept()` calls remain outside errors.py (fails by file:line if one
returns). Socket suites (console/runner/servers, 77 tests) green.

**AC5 finding:** the runner reconnects on a 1→30s capped backoff with 30s
heartbeats (`apps/runner/supervisor/connection.py`), so 61 occurrences in
28h are reconnect **bursts** during deploy restarts and tunnel drops — one
half-hour API outage alone is ~60 attempts at the 30s cap. The "~27-minute
cadence" was the dedup row's average concealing bursts; no steady clock
exists. No runner change made (out of scope, as written).

**Not verified:** the race itself against a live uvicorn (it needs a peer
vanishing mid-handshake); the exemption + helper are exercised at the
reporter and unit level.
