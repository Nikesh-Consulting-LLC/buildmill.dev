# US-79.1 — A wiring check is a confirmation, not a crash

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-1 (`WiringCheck: self-monitoring wiring verification`, issue `d3ac7c3e-4f9d-4343-8ee7-64c0ddeb5c8d`)

## Story

As a manager triaging the reports inbox, I want the self-monitoring wiring
check to read as the confirmation it is, so that a deliberate test ping can
never sit next to real crashes and get promoted into a bug.

## Context

The Phase 16 self-monitoring setup fires one verification report to prove the
report key, endpoint and deployment id are wired correctly. That ping
(`message: "self-monitoring wiring verification"`, `context.component:
"verification"`, stack `at verify (setup)`) landed in the prod inbox looking
exactly like a crash, and was promoted to BUG-1 alongside seven real defects.
The pipe worked perfectly; the presentation lied about what flowed through it.

## Acceptance criteria

1. A report whose context marks it as a verification ping renders distinctly in
   the Reports hub and the System issues inbox — a "wiring check" treatment
   (badge + neutral styling), not the error treatment. The marker is checked
   structurally (the `context.component == "verification"` key), not by
   matching message text.
2. Promote is not offered on a verification report — the action is hidden or
   disabled with the reason shown ("this is the wiring check, not a defect").
3. A verification report is auto-resolved at ingestion (lands in a
   non-`new` status such as `verified`/`dismissed`), so the inbox's unread
   count never includes it — its arrival is still visible in the deployment's
   report list, because proving the pipe is its entire job.
4. Occurrence dedup and rate limiting behave unchanged for every other report.

## Out of scope

- Changing ingestion auth, the report key model, or the wiring-check sender
  (the curl step in the setup instructions stays as documented).
- Retro-cleaning prod: BUG-1 itself is dismissed by the manager during UAT,
  not by code.

## Proof required to reach Testing

Ingest a verification-shaped report against a dev deployment; screenshot the
inbox showing the wiring-check treatment, no promote action, and an unread
count that excludes it.

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `cf96d95`).
Ingestion detects `context.component == "verification"` structurally and
lands the report as `ignored` — an existing status, so no migration: outside
the open-statuses view (the unread count never includes it), outside the
dedup index's predicate (repeat checks insert fresh visible rows, AC3/AC4).
Both surfaces render it with a neutral plug icon and a "wiring check" badge
instead of the crash treatment (AC1); the hub's detail pane replaces the
Promote button with "this is the self-monitoring wiring check — there is
nothing to promote" (AC2).

**Verified:** ingestion unit tests (verification → `ignored`, anything else →
`new`; dedup/rate-limit suites unchanged, 21 tests green); web build clean.

**Not verified:** the screenshot of the rendered treatment (no side-by-side
dev server — the standing constraint); UAT: fire the setup curl once against
a dev deployment and look. BUG-1 itself should be **dismissed** in Build
Mill, not fixed — it is the test ping.
