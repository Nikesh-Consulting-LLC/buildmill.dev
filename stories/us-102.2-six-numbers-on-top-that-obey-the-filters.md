# US-102.2 — Six numbers on top, and the filters govern them

**Status:** Testing
**Phase:** 102 — Costs leads with the numbers
**Depends on:** us-102.1 (the band takes the space the paragraph gave back),
us-95.4 (one set of controls already governs curve and table)

## Story

As the manager, Costs answers "where did the money go" and never answers
"what did it buy". The page opens on a curve and a breakdown table — both
about spend alone — so to put a dollar figure next to work delivered I have
to hold the Costs page in one tab and the Team page in another, and the Team
page's numbers are org-wide over a fixed thirty days and cannot be narrowed
to a project.

A band of KPI cards goes on top, and the point of it is the second half of
the sentence: **they obey the same filters as everything else on the page.**
Narrowing to one project, one agent, or one work-item type re-answers all six
— which is what turns "we spent $40" into "we spent $40 fixing four bugs in
Alpha".

Six numbers:

| card | what it is |
|---|---|
| Hours agents worked | `sum(runs.work_seconds)`, rendered as hours |
| Work items fixed | distinct work items an agent's run landed |
| Bugs fixed | the same count, restricted to `type = bug` |
| Lines written | `sum(runs.lines_added)`, with removed underneath |
| Tokens spent | tokens in + tokens out |
| Total cost | dollars |

The last two already exist on the page, in the table's total row. They are
**read from that same breakdown response**, not recomputed — one source of
dollars (us-91.11 AC4) is the rule that keeps two figures on one screen from
disagreeing. The first four are new and come from the runs, which is where
effort has been recorded since migration 252.

They cannot come from `agent_effort_daily`. That rollup is keyed
`(org_id, worker_id, day)` and carries no project and no work-item type, so a
card fed from it would ignore two of the three filters while sitting beside a
table that honours them — the same number meaning different things six inches
apart. The effort figures are computed from `runs` at read time, joined to
`issues` exactly the way `spend_breakdown` walks `run -> issue` for its
work-shaped dimensions.

## Acceptance criteria

- **AC1 — six cards, above the controls' effect and below the heading.** The
  band renders on `/costs` for a manager with `view_costs`, in the order
  above, each card carrying a label, the value, and one line saying what it
  counts and over what window.

- **AC2 — every filter governs every card.** Window, project, agent and
  work-item type all re-answer the band. A filtered band and a filtered table
  are the same slice: the effort endpoint takes the same four parameters as
  `/spend` and `/spend-trend`, and the client sends one set of values to all
  three.

- **AC3 — tokens and cost are not recomputed.** Those two cards read the
  breakdown response's `totals`. There is no second query for money, and no
  arithmetic on the client that could make the card and the table's Total row
  differ by a rounding.

- **AC4 — the effort figures are honest about their edges.** A new
  `GET /api/v1/llm/orgs/{org}/work-summary` returns work seconds, distinct
  items landed, bugs landed, lines added and lines removed, over runs that
  reached a terminal state inside the window.
  - "Landed" means the run carries a `merge_commit_sha` — the work reached
    the default branch. Counted `distinct issue_id`, so four attempts on one
    story are one item, and a plan run that never merged is none.
  - Time is `runs.work_seconds` as migration 252 wrote it, never recomputed
    from timestamps; **paused spans are not subtracted** (252's known gap),
    and the card says "held" rather than implying billable attention.
  - The window is anchored on when the run *ended*, so a run that finished
    before the window and merged inside it belongs to the earlier window.
    Named here, and in the code, because it is the seam where this number and
    the Team page's `issues_completed` (anchored on the merge) can differ by
    one item at a boundary.

- **AC5 — the endpoint is gated like the section, not like `/spend`.** It
  verifies `view_costs` server-side and answers 403 to a member without it,
  the way `/spend-trend` does. The shared `/spend` endpoint stays member-read.

- **AC6 — zero is a number and unknown is not zero.** Zero hours, zero items
  or zero bugs render as `0` with their note intact — a filtered-to-nothing
  slice is a fact, not an error. A window whose runs recorded no lines shows
  `0`, not a dash; only `cost_usd`'s existing null (nothing carried a price)
  keeps rendering as `—`, unchanged from the table.

- **AC7 — it survives a phone.** At 375px the band is a two-column grid, not
  six stacked cards pushing the curve off the screen.

- **AC8 — tests.** Unit tests over the new db function: the four filters are
  parameterised (never interpolated), junk values are dropped, distinct
  counting is in the SQL, and the terminal-status predicate is there. Route
  tests: 403 without the capability, filters passed through with it. api
  Essential green; `npm run build` green.

## Verified (2026-08-15)

- **AC1/AC7** — `KpiBand` in
  [costs-view.tsx](../apps/web/src/app/(app)/costs/costs-view.tsx) renders the
  six cards in the story's order, each with a label, a value, a note naming
  the window, and a hint saying what it counts. Grid is
  `grid-cols-2 sm:grid-cols-3 lg:grid-cols-6` — two across at 375px.
- **AC2** — all three requests are built from one `filterParams`
  (`days` + `project_id` + `worker_id` + `item_type`) in a single
  `Promise.all`, so the band cannot be answering a different slice than the
  table. The endpoint takes the same four parameters; a route test asserts
  they arrive.
- **AC3** — the Tokens and Total cost cards read `data.totals`. No second
  money query exists; `work_summary` deliberately returns no dollars.
- **AC4** — the SQL is pinned by test: the distinct-and-filtered count of
  landed items, the terminal-status predicate, the
  `coalesce(finished_at, last_heartbeat_at, claimed_at)` window, and the LEFT
  join that keeps a run with no work item behind it contributing its hours.
  The paused-span gap and the ended-in-window seam are stated in the docstring
  and on the card's hint, not just here.
- **AC5** — 403 without `view_costs`, asserted at the route.
- **AC6** — an all-null aggregate row returns zeroes, asserted.
- **AC8** — 13 new tests. api Essential green (**1864 passed, 545 skipped, 0
  failed**, 69s); `npm run test:web` green (181 passed); `npm run build`
  green.

### Not verified here

- **Every figure against real rows.** The db function is proven against a
  faked connection — the SQL's *shape* is pinned, not its result. Nothing in
  this checkout can run it: there is no `DATABASE_URL`, so the `*_sql.py`
  suite skips, and no `apps/web/.env.local`, so the dev server 404s every
  route from `proxy.ts` before a component renders. The band has not been
  seen in a browser and the numbers have not been read off live data.
- **The distinct-count claim on real history** — that four attempts on one
  story show as one item — follows from the SQL but has not been observed.

## Out of scope

- Changing what the Team page's KPI tiles read; they stay on the
  `agent_effort_daily` rollup, which is right for an org-wide, agent-shaped
  page.
- A pause ledger (252's gap stays open — its own change).
- Per-card drill-through, sparklines, or comparison against the previous
  window; the curve already carries the window-over-window comparison.
- Any new table, column or migration. Every figure here is a read-time query
  over rows that already exist.
