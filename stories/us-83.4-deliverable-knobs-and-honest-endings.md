# US-83.4 — Deliverable knobs and honest endings

**Status:** Testing
**Phase:** 83 — Interactive agent stability
**Dependencies:** us-83.1 (probe against a pinned CLI, not a moving one)

## Story

As the manager whose escalation ladder promises "more capability", I want the
interactive module to actually deliver effort and turn ceilings to its CLI —
and to score a truncated answer as the failure it is — so that Deep means
deeper, and "succeeded" means the answer is whole.

## Context

A live trace showed the pair that motivates this story: *"escalated from
'Balanced' to 'Deep' … more capability can plausibly answer"* immediately
followed by *"the interactive module cannot be told 'effort', so that setting
was not delivered."* Escalation is a silent no-op for exactly the module the
ladder exists to help.

Measured against the real CLI (grok 1.0.0) and pinned by probes in this
conversation:

- `--reasoning-effort <LEVEL>` (alias `--effort`) exists **on the `agent`
  subcommand itself**; the `initialize` handshake declares the vocabulary:
  `low` / `medium` / `high`, default `high`.
- `--max-turns <N>` and `--rules <TEXT>` exist top-level and parse when placed
  before the subcommand (`grok --max-turns 2 --rules "x" agent stdio` parses).
  Whether `agent stdio` *honors* them is unmeasured — parse ≠ effect.
- The module declares no effort/max_turns knobs, and its `build_argv` drops
  the `extra` argument `settings_argv` would deliver — both halves must land.
- Stop-reason handling scores any non-empty, non-cancelled answer as success
  (US-78.5's evidence-over-vocabulary rule), which lets a `max_tokens` /
  `max_turn_requests` truncation pass as a completed run — a half-written PRD
  parses as a whole one. And `AcpClient.prompt`'s docstring still teaches the
  PascalCase stop reasons that caused the original `end_turn` bug.
- `request_permission` picks the first option whose kind starts with `allow`,
  which can select `allow_always` — a standing grant persisted in the slot's
  `GROK_HOME` beyond the run.

## Acceptance criteria

1. `build_argv` splices delivered settings: `[*cmd, *extra, *ACP_ARGS, *args]`.
2. An `effort` knob (enum: `low`, `medium`, `high`; delivery argv,
   `--reasoning-effort`) is declared and verified live: one session run at
   `low` and one at `high` show the setting took effect (trace/handshake/usage
   evidence recorded in this story before it reaches Testing).
3. A `max_turns` knob (int, `--max-turns`) is declared, then probed live with
   `--max-turns 2`. If the cap holds, it ships; if `agent stdio` ignores it,
   the knob is withdrawn and this story records the measurement — the honest
   "cannot be told" trace note is the correct behavior in that world.
4. `standing_instructions` moves to `--rules` if a live probe shows agent-mode
   sessions apply it (system-prompt side); otherwise it stays prompt-delivered
   and the knob's help text names the measurement instead of guessing.
5. Stop reasons `max_tokens` and `max_turn_requests` fail the run even with
   text in hand; the error names the ceiling that ended it. The
   `AcpClient.prompt` docstring lists the real snake_case vocabulary.
6. `request_permission` prefers `allow_once` over `allow_always` when both are
   offered.
7. `test_module_declarations` reflects the new knob surface (the interactive
   "cannot be told" expectations change); runner suite and api Essential pass.

## Out of scope

- Changing preset/ladder *values* (which level Balanced or Deep names is
  manager data, not module code — the module only declares what it accepts).
- Knobs for other modules; `kind_gate` changes.
- Sandbox/tool-restriction flags (`--allow`/`--deny`/`--sandbox`) — worth a
  future story once policy wants them.

## Verification (2026-08-12, built)

**Verified:** the knobs deliver — `settings_argv({"effort": "high",
"max_turns": 4})` produces `--reasoning-effort high --max-turns 4`, and a run
with those settings spawns them BEFORE `agent stdio` (pinned by test; the
placement itself was parse-verified against the real grok 1.0.0 binary
earlier in this investigation). The effort vocabulary (`low`/`medium`/`high`,
default `high`) was read off the live `initialize` handshake, not guessed.
Truncation stops (`max_tokens`, `MaxTokens`, `max_turn_requests`) fail the
run with the partial text preserved in stdout and the ceiling named in the
trace; `max_turn_requests` maps to `end_subtype=error_max_turns` so `_failed`
speaks US-54.1's wording. `allow_once` beats `allow_always` regardless of
option order; an only-always agent still gets its grant. Whole-answer runs on
unfamiliar reasons still pass (evidence over vocabulary, unchanged).

**Not verified (UAT / AC2–AC4 live probes):** one paid session each at
`low` and `high` effort showing the setting took effect; `--max-turns 2`
actually capping an ACP session (if inert, withdraw the knob per AC3);
the `--rules` system-prompt probe (AC4's else-branch is currently in force:
standing instructions stay in-prompt and the knob's help text names the
measurement gap).
