# US-87.1 — The shell asks once, not six times

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** nothing (pure refactor of `(app)/layout.tsx` + `lib/active-org.ts`)

## Story

As anyone using the app, every page I open pays the same hidden toll before
it can render: the shell reads `principals` three times by the same key,
walks six round trips strictly in sequence, and then recomputes the entire
Things-to-Do dataset — eight org-wide queries — to print one number in the
sidebar. On `/dashboard` it does that second part **twice**, because
`loadThingsToDo` opens with `await loadWaiting(...)` too.

Measured on prod (2026-08-12): `loadWaiting`'s `issues` query is the
most-executed application statement in the database — 19,967 calls, 134 s of
execution — and it exists to render a badge. There is no `React.cache()`
anywhere in `apps/web`, so nothing dedupes inside a single request.

This is the fixed cost that makes the app feel laggy with three projects,
and it grows with every project added.

## Acceptance criteria

- **AC1 — one read per fact per request.** `auth.getUser()`, the caller's
  `principals` row, `profiles`, and `resolveActiveOrg` are each wrapped in
  `React.cache()` (or an equivalent per-request memo) so that N call sites in
  one render produce **one** query. The shell reads `principals` once, not
  three times.
- **AC2 — the independent reads run together.** Everything in the shell that
  does not depend on another read resolves in a single `Promise.all` —
  profile, principal, notifications, org resolution — rather than six
  sequential awaits.
- **AC3 — `loadWaiting` runs at most once per request.** With the shell and
  `/dashboard` both rendering, `loadWaiting` executes one time, not two. The
  badge and the page header still cannot disagree (that is why they share the
  definition — the sharing stays, the double execution goes).
- **AC4 — the gate still gates.** `must_change_password` still redirects to
  `/change-password` on every `(app)` route; caching must not let a flagged
  principal through, and must not leak one user's cached row into another
  request. A memo whose lifetime exceeds the request is a defect.
- **AC5 — proof.** The story records the before/after count of database
  round trips for one `/dashboard` navigation and one `/projects`
  navigation, taken from `api_request_log` / query counts rather than
  asserted.

## Out of scope

- Replacing `loadWaiting` with a cheap count — that is us-87.2. This story
  makes the existing call happen once; 87.2 makes it stop being expensive.
- Streaming the shell behind `Suspense` — a separate change with its own
  layout-shift questions.
- Any change to what the badge counts.

## Notes

`React.cache()` is per-request in the App Router and is the intended tool
here; a module-level `Map` would leak across requests and users, which AC4
forbids.

## Verification record

Built 2026-08-12 on `phase-87-performance`. No migration.

**Verified:** `npm run build` type-checks clean. `lib/request-cache.ts` wraps
the caller's user, principal, profile and active org in `React.cache()`, and
`(app)/layout.tsx` resolves those three in one `Promise.all`. `principals` is
read ONCE where it was read three times (the password gate, the shell's
principal id, and inside `resolveActiveOrg` -- now split into
`resolveActiveOrgFrom`, which takes the stored org its caller already holds).
`loadThingsToDo` calls the cached `getWaiting`, so the dataset cannot execute
twice in one render.

**Not verified (UAT):**

- **AC5's before/after round-trip count was not measured empirically.** The
  reduction is derived by reading the code, not from `api_request_log`. The
  measurement AC5 asks for is exactly what us-87.10 builds the fixture and the
  budget for; until then the claim is structural, not observed.
- No browser run: the password-gate redirect (AC4) and the org switcher were
  not exercised against a live session. `React.cache` is per-render-pass by
  definition, but "the flagged principal still redirects" is a UAT step, not a
  proof from the type-checker.
