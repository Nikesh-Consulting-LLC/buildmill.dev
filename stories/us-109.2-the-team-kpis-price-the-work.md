# US-109.2 — The team's KPI row prices the work

**Status:** Testing
**Phase:** 109 — The Team page answers at a glance
**Depends on:** US-91.11 (`agent_effort_daily`, the rollup every figure reads), US-91.12 (the three tiles this extends), [us-109.1](us-109.1-the-team-row-says-who-not-how-much.md) (which moved the per-agent figures off the row)

## Story

As the manager, I want the Team page's KPI row to say what the work cost and
what it produced, so that I can answer "is this worth it" from the top of the
page instead of adding up per-agent rows.

US-91.12 put three tiles on the page — completed, queued, agent hours. All
three measure *activity*. None of them says what was spent or what came out,
which are the two figures anyone asks about an AI workforce first. Those
numbers existed, per agent, on the rows — the org total existed nowhere.

And the honest comparison a manager actually wants is not agent hours at all:
agent hours are the thing being compared *to*.

## Design

### Three more tiles, off rows already loaded

`agent_effort_daily` is already read for the window to build the per-agent
figures. `lines_added`, `lines_removed` and `cost_usd` are summed in the same
loop. No new query, no new column.

The totals accumulate over **every** row in the window, while the per-principal
map skips a row whose worker no longer maps to a principal (a deleted agent).
That is deliberate: the org spent that money whether or not the agent that
spent it still exists. It also means the tiles can legitimately exceed the sum
of the rows below, which is the correct behaviour and worth knowing before it
is reported as a bug.

### The human-equivalent estimate, and why it is a guess in public

`lib/human-equivalent.ts`, with the constants named and exported so one number
governs every surface:

```
weighted = linesAdded + linesRemoved × 0.5
hours    = weighted / 25
```

- **25 reviewed lines an hour.** The widely-cited human figures (~100 lines of
  production code a day) count the whole day — design, review, meetings, the
  rewrite — not typing. 25/hour is that, per hour.
- **A removed line is half a written one.** Deletion is cheaper but not free;
  the line still has to be understood before it can go.
- **Rendered as hours, never minutes**, and with `~N days` under it. An
  approximation printed to the minute claims a precision it does not have.

This estimate says nothing about whether the change was hard. A ten-line fix
that took a week of thinking reads as 24 minutes. The tile's note says
*rough estimate from lines changed* on its face rather than letting a
confident-looking number be read as a measurement.

The layout goes from `sm:grid-cols-3` to `sm:grid-cols-2 lg:grid-cols-3` — six
tiles as two rows of three, rather than six cramped columns.

## Acceptance criteria

- **AC1 — spend has a tile.** *Spent* shows the org's `cost_usd` total over the
  window, formatted by the app's existing `money()`.
- **AC2 — output has a tile.** *Lines of code* shows `+added −removed` over the
  window, compacted (`+7.6k −621`).
- **AC3 — the human-equivalent tile is an estimate and says so.** *Human
  equivalent* shows hours from lines changed, with `~N days · rough estimate
  from lines changed` beneath.
- **AC4 — every tile states its window.** All six say *last 30 days* or
  *right now*; none is unattributed.
- **AC5 — the arithmetic is pinned.** The rate, the removed-line weight, the
  formatting and the negative-input guard are unit-tested, so changing the
  estimate is a deliberate edit to one file.
- **AC6 — six tiles lay out.** Two rows of three from `lg`, two columns from
  `sm`, one on a phone.

## Out of scope

- Making the estimate smarter — complexity, language, churn, review time. It is
  lines changed, on purpose: every other input the factory holds would make it
  look like a model while still being a guess.
- Letting the org configure the rate. The constants are exported and in one
  file; a settings surface for them is a story of its own, and pointless before
  anyone has said the default is wrong.
- Putting the estimate anywhere else — the per-agent rows, the Reports hub, the
  admin analytics. `humanEquivalentHours` is exported and ready; this is
  coverage, not design.
- Changing the window. It is US-91.12's 30 days, shared by all six tiles.

## Built (2026-08-16)

Web only; no migration, no API change, no new query.

- `lib/human-equivalent.ts` **(new)** — `HUMAN_LINES_PER_HOUR`,
  `REMOVED_LINE_WEIGHT`, `humanEquivalentHours`, `formatHumanHours`,
  `humanEquivalentDays`.
- `lib/human-equivalent.test.ts` **(new)** — 5 tests: the rate, the half-weight
  for removals, zero and negative inputs, the hours format, the days
  conversion.
- `team/page.tsx` — `linesAdded`/`linesRemoved`/`costUsd` totalled in the
  existing effort loop and carried on `TeamKpis`.
- `team/team-view.tsx` — three new tiles and the six-tile grid.

**Verified.** `npm run build` compiles and type-checks; `npm run test:web` 236
passing (+5).

**Not verified.** No tile has been seen — no `apps/web/.env.local` in this
checkout, so the page was never loaded. The six-tile layout (AC6) and the
readability of the estimate's note (AC3) are visual judgements that have not
been checked in either theme. Nor has any real total been compared against the
rows below it, which is where the deleted-agent behaviour described above would
show up.
