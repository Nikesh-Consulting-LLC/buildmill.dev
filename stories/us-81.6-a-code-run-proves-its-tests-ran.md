# US-81.6 — A code run proves its tests ran

**Status:** Testing
**Phase:** 81 — Automated release testing
**Dependencies:** none

## Story

As a manager reviewing a submission, I want evidence that the project's test
suite ran in the worker's workspace before submit — command, exit code,
counts, output tail — so "tests pass" is a recorded fact on the run, not a
sentence in a hand-back.

## Context

Today the baked `code` instruction requires *writing* tests but running them
is optional and nothing records whether it happened. Meanwhile this is
exactly the inner loop a good coding agent already lives: change, run
pytest, read the failures, fix, submit. This story makes that loop
factory-grade — declared, executed, and reported.

Phase 80's lesson applies verbatim: a slow suite is a suite that runs less
often. The declared pre-submit command must be the project's **fast** suite
(the Essential-style gate), not its full QA run — the full run belongs to the
UAT pipeline, where machine time is cheap.

## Acceptance criteria

1. The project's build config declares a pre-submit test command (per
   project, alongside the existing build-config values). The settings UI
   labels it as the fast gate and says why.
2. The baked `code` instruction requires running the declared command in the
   workspace before submitting, and the submission carries the evidence:
   the command, exit code, pass/fail/skip counts, and a bounded output tail.
   JUnit attachment is optional.
3. The evidence is stored on the run and rendered on the review page beside
   the diff — pass/fail at a glance, tail expandable.
4. `validate_submission` warns — never rejects — when a code submission
   carries no test evidence, and separately when the code changes include no
   test changes. Findings stay warnings, per the validator's standing
   design.
5. The evidence is labeled as worker-reported. Agent machines are
   operator-side: this is a review signal, not factory-observed proof — the
   UAT suite pipeline (us-81.2) is the factory's own check, and nothing in
   this story feeds the release gate.
6. A project with no declared test command behaves as today, minus a warning
   in review that the project has no declared gate.

## Out of scope

- Blocking submits or merges on test evidence — the soft-gate philosophy
  (US-2.6) stands.
- Running anything on factory infrastructure — this is the worker's
  workspace, by design.

`runs.test_evidence` (and `runs.spec_map` for 81.5). The Suites tab carries
the **Pre-submit gate** card (labeled fast-suite-only, per Phase 80's
lesson); code-run context carries the command + the report-before-submit
note (rendering-side). New MCP `report_test_evidence` (command, exit code,
counts, bounded output tail; claim-holder scoped). The review page shows the
evidence strip beside the diff — green/red with the tail expandable, labeled
**worker-reported** — and an amber "no evidence was reported" state, because
absence is information. `validate_submission` gained a non-blocking
**Advisories** section: missing evidence, and code changes touching no
test/spec files. Findings/ok are unchanged — the soft-gate philosophy stands.
