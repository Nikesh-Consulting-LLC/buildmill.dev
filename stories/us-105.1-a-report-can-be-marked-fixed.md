# US-105.1 — A report can be marked fixed

**Status:** Testing
**Phase:** 105 — The reports hub can close a report honestly
**Depends on:** US-16.6 (the Reports hub), US-16.8/16.9 (`fixed` status, migration 184), US-16.1 (`app_issues_open_fingerprint_key`)

## Story

As the manager, I want to mark a report **fixed** from the Reports hub, so that
a bug I have actually fixed is recorded as fixed — without minting a work item
for it, and without lying about it by calling it Ignored.

The hub offered exactly two outcomes: promote it to a work item, or Ignore it.
But plenty of reports get fixed on the way past — noticed, understood, and
corrected in a change already in flight — and neither outcome describes that.
Ignoring one says "this is not worth acting on" about something that was acted
on, which is the wrong record for the next person reading the inbox.

**The status already existed.** Migration 184 added `fixed` for the superadmin
System Issues console (US-16.9), and that console has had a "Mark fixed" button
since. The org-facing hub — the surface that shows *every* deployed app's
reports, including Build Mill's own — never grew one. This story closes that
gap; it is UI only.

## Design

### Nothing in the database changes

`fixed` is already a legal status on both live projects (verified 2026-08-16:
`app_issues_status_check` allows it on prod `wdudmfhhqxrqzoyhuzwx` and dev
`nncquokoblcfcqyajzmk`). The "members triage their org app issues" RLS policy
already permits the update. No migration.

### The recurrence behaviour is already correct, and is the point

`app_issues_open_fingerprint_key` is a **partial** unique index over
`(deployment_id, fingerprint)` `where fingerprint is not null and status in
('new','triaged')`. A `fixed` row sits outside that predicate, so the
`on conflict` in `ingest_report` cannot match it: the next occurrence of the
same error **inserts a fresh row** at `occurrence_count = 1` with its own
`first_seen_at`.

That is exactly the requested behaviour — fix it, and if it comes back it is a
new report counting from one — and it needed no code. What this story adds is
the button that reaches it, and a line of copy in the expanded detail saying so,
because a manager cannot be expected to infer a partial index from a green tick.

### Reopen, and the collision it can hit

Reopen was previously offered only on `ignored`. It now covers any closed report
except `promoted` — a promoted report lives as a work item and closes there.

Reopening can legitimately fail: if the error recurred after the fix, its
regression row is already open, and the index allows only one open row per
`(deployment, fingerprint)`. Postgres answers `23505`. The hub catches that code
specifically and says *"This error is already open again as a newer report"*
rather than surfacing a constraint name — the rule working, not a defect.

## Acceptance criteria

- **AC1 — the action exists on all three action sites.** An open report offers
  **Mark fixed** in the expanded detail, in the desktop table's Actions cell (a
  green check, `title`/`aria-label` "Mark fixed"), and on the phone card.
- **AC2 — it closes the report.** The row's status reads `fixed` (green pill,
  already styled), `triaged_at` is stamped, and the report leaves the default
  view — reappearing under "Show decided", exactly as an ignored one does.
- **AC3 — a recurrence is a new report.** After a report is marked fixed, the
  same error reported again produces a **second row**, `occurrence_count` 1,
  its own `first_seen_at` — not an increment on the fixed one.
- **AC4 — the hub says so.** The expanded detail of an open report states that
  marking it fixed closes it and that a recurrence opens a new report counting
  from one. Display semantics: prose, in the detail, not a tooltip.
- **AC5 — reopen is honest.** Reopen is offered on `fixed` and `ignored`, never
  on `promoted`. A reopen blocked by an already-open regression reports that in
  those words, not as a duplicate-key error.

## Out of scope

- Any migration. `fixed` is already live on both projects.
- Changing the superadmin System Issues console, which already has this button.
  Its Reopen carries the same latent `23505` (it predates this story) and is
  left alone deliberately — a separate, one-line fix.
- Linking a fix to the commit or release that made it. A `fixed` report records
  *that* it was fixed, not by what.
- Auto-marking a report fixed when a promoted work item merges.
- Re-opening a `promoted` report from the hub.

## Built (2026-08-16)

`apps/web/src/app/(app)/reports/reports-hub.tsx` only. Mark fixed added to the
detail, the desktop row and the phone card; Reopen widened from `ignored` to
any non-`promoted` closed status; `23505` given its own message.

**Verified.** The `fixed` status and the partial index were read off **both**
live projects before any code was written, which is what established that AC3
needed no work: `app_issues_status_check` allows `fixed` on both, and
`app_issues_open_fingerprint_key` is `where ... status = ANY (ARRAY['new','triaged'])`,
so a fixed row cannot be the `on conflict` target in `ingest_report`.
`npm run build` passes.

**Not verified.** AC3 was **not** exercised end-to-end — no error was reported,
fixed, and re-reported against a live deployment to watch a second row appear.
It is argued from the index predicate and the `on conflict` clause, both read
from the live database, not demonstrated. That is the one thing worth doing in
UAT rather than trusting. The `23505` reopen path (AC5) is likewise reasoned,
not reproduced.
