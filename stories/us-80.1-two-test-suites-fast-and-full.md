# US-80.1 — Two suites: the one you run, and the one you call for

**Status:** Testing
**Phase:** 80 — Tests you will actually run
**Dependencies:** none

## Story

As anyone changing this codebase, I want an **Essential** suite that finishes in
a couple of minutes and is the normal gate after coding, and a **Full QA** suite
I call explicitly when I want everything, so that verification stops costing half
an hour and stops being skipped for it.

## What is actually wrong

`apps/api`'s suite takes **~30 minutes** on the development machine. That is long
enough that it gets skipped, deferred, or run once at the end of a batch instead
of after each change — and this project has already paid for that: on 2026-08-11
a console shipped that had **never worked**, because the one test that would have
caught it faked the database call, and nobody was going to re-run half an hour to
find out.

A slow suite is not a thorough suite. It is a suite that runs less often.

There is no CI gate here by decision, so the local run *is* the gate. It has to be
one somebody will actually pull.

## Acceptance criteria

1. **Essential** is the default: `cd apps/api && python -m pytest` runs it, and it
   completes in **under three minutes** on the development machine. It is the
   gate after coding, and passing it is what "tests pass" means in a commit
   message unless the message says otherwise.
2. **Full QA** runs everything, including what Essential skips, and is invoked
   explicitly. Both are reachable from the repo root
   (`npm run test:api`, `npm run test:api:full`) and from `apps/api` directly.
3. The split is by **measured duration, not by guess** — the slow tests are
   identified with `--durations` and marked, and the story's Outcome records what
   was actually slow and why. A test is not marked slow because it feels
   peripheral.
4. **Nothing is deleted or weakened.** Every test that exists today still exists
   and still runs in Full QA; marking is the only change to slow tests. A story
   that made the suite fast by asserting less would be worse than the problem.
5. Essential keeps the checks that catch the failures this project actually has:
   the schema-derived guards (`test_embed_ambiguity`, `test_console_columns`),
   the source-scanning invariants, and the route/permission tests. Speed is
   bought from repetition and setup cost, never from coverage of a real failure
   mode.
6. `apps/runner` and `apps/web` suites are already fast (~80s and <1s) and stay in
   Essential whole.
7. Running Full QA and Essential must not disagree: if a test passes in one and
   fails in the other, that is a defect in the split, and a test asserts the two
   selections partition the suite with nothing dropped.
8. The commands are documented where somebody will find them — `CLAUDE.md`'s
   Testing section, which currently tells people to run the slow one.

## Out of scope

- Making the slow tests fast. Marking them is this story; fixing them is another,
  and the Outcome should say which ones look fixable.
- Adding a CI gate. Testing stays local by decision.
- The `*_sql.py` tests' own skip behaviour when `DATABASE_URL` is unset, which is
  unchanged and orthogonal.

## Outcome

**The suite was not slow. It was on the network.**

`--durations=40` killed the obvious theory first: the forty slowest tests sum to
~280s of ~1800s, so there was no small set of hogs to mark. The cost was ~2,000
tests at ~0.9s each — and a fake-backed route test like `test_pool_requires_token`
taking **5.23 seconds** is not a test doing work, it is a test waiting.

A probe that made `socket.connect` raise proved it: a route test whose read is not
faked calls `https://test.supabase.co` **for real**, waits on it, and turns the
failure into the refusal the test asserts on. The assertion passes either way. It
just costs seconds.

So Essential blocks outbound name resolution, and the numbers moved:

| | before | after |
|---|---|---|
| `test_worker_pool.py` (43 tests) | ~9s on its slowest alone | **1.04s** for all 43 |
| whole suite | **~30 minutes** | **~30 seconds** |

Which network layer ate the time was not isolated — the fix is the same either
way: do not go out at all.

**The split line is "needs a real Postgres", not "feels peripheral"** (AC3, AC5).
`*_sql.py` is held by convention; `test_factory_mcp.py` and
`test_git_proxy_integration.py` are marked `needs_db` because their filenames do
not say it and they failed loudly the moment the guard went in — which is exactly
how they were found. `slow` remains for anything else measured expensive; nothing
currently needs it, so nothing carries it.

Essential: **1,538 passed, 499 skipped, ~30s.** Nothing was deleted or weakened
(AC4): every held test still runs under `--full`.

## Verification

- Essential `cd apps/api && python -m pytest` — 1538 passed / 499 skipped / 29.7s,
  against the ~30 minutes it replaces.
- `test_suite_split.py` pins the rule itself rather than trusting the convention:
  the split predicate, the `*_sql.py` naming it leans on, that the guard is live
  in Essential (so the suite cannot get slow again silently), and that localhost
  still resolves for tests that bind a port. It skips its own guard assertion
  under `--full`, where the guard is lifted by design.
- The schema-derived guards that catch this project's real failures —
  `test_embed_ambiguity`, `test_console_columns` — are asserted to stay in
  Essential.

- Full QA (`--full`) confirmed the split loses nothing: every one of the 499
  held-back tests ran and passed against the real database. Its only four
  failures were `test_agent_failures_sql.py` — another session's new file for
  migration 238, which is not applied yet — so they are that feature in flight,
  not the split.

**Not verified:** the durations were measured on one Windows machine. The
network guard's benefit should hold anywhere (it removes an outbound call, not a
local cost), but the 30s figure is this machine's.
