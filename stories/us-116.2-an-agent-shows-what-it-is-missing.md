# US-116.2 — An agent shows what it is missing

**Status:** Testing
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.1 (a session resolves its model through
`run_settings.resolve` — this story asks that same question ahead of time),
US-53.1/53.2 (`BillingReadiness` — the checklist pattern: green only if it would
work now, each red naming its fix, one implementation on two surfaces),
US-77.1 (roles, and `enabled_kinds` as their storage), US-107.3 (the roster's
`Does` and `State` columns)

## Story

As the manager, I want the Team page to tell me an agent cannot do its job —
and what to set — without my having to click something and read a refusal, so
that "why did nothing happen" is answered on the page where I look at my
agents rather than after a failed action.

## Design

### What the roster shows today

Nine columns (`team-view.tsx:988`): Member, Does, Status, Seat, Worked, Done,
State, Role, actions. Three of them can turn amber:

- the `suspended` pill,
- a health pill — but **health is incident count and nothing else**
  (`page.tsx:146`): `n >= 3 ? "unhealthy" : n >= 1 ? "degraded" : "healthy"`,
  where `n` is `runner_incidents` rows in the last hour,
- the **State** column's idle reason, whose entire vocabulary is
  `working · idle · revoked · paused · no-grants · queue-held · unknown`
  (`team-view.tsx:151`).

Every one of those describes runtime or permission state. **None describes
configuration.** An agent with no roles checked, no model pinned and no
provider that offers its model renders identically to a perfectly configured
one — it says `Idle`, in muted grey, and the manager has no reason to look
closer. That is the whole of the complaint this story answers.

The knowledge exists; it is just scattered across three things that never talk
to each other:

| what it knows | where it lives | who sees it |
|---|---|---|
| will a run bill the subscription | `BillingReadiness`, client-side | settings page + wizard, **only** when billing is `subscription` |
| does any provider offer this model | `validate_model_provider_pairing` | a 422 at Save, rendered as muted grey text identical to the success message — and it exempts `interactive`, the only module with a session button |
| may this agent take work | `worker_idle_reason` | the roster's State column, the runner console |

Nothing aggregates them, and the roster consumes only the third.

### One answer, on the surface that already renders it

`worker_idle_reason` (`db.py:4791`) already answers "why is this agent doing
nothing", already feeds both the roster and the console, and the console
already turns each reason into a link to its fix (`fixForIdle`,
`runner/page.tsx:76`). It is the right place — its vocabulary is simply missing
the configuration tier.

Two reasons join it, ranked **above** the queue-state answers because a
misconfigured agent is not idle, it is stuck:

| reason | when | the fix it names |
|---|---|---|
| `no-roles` | `enabled_kinds` is `[]` — every role unchecked | Roles, on the agent's settings page |
| `no-model` | no model resolves for **any** kind the agent claims | Model per role (`…/settings#model-overrides`) |

Precedence becomes `revoked > working > paused > no-roles > no-model >
no-grants > queue-held > idle`: a dead token still beats everything, an agent
holding a run reads as working whatever its configuration (as the code has
always ordered it), and configuration is reported before queue state — before
even "nothing is queued" — because a misconfigured agent is stuck, not idle,
and it is the thing the manager can act on. (us-116.4 then puts `offline` in
front of all of these and renders `paused` as **Stopped** — this story's order
is preserved inside it.)

`no-model` is defined by us-116.1's resolver, not by a second rule — "no model
for any claimed kind" is exactly the question a session asks, asked early. An
agent that resolves a model for some roles but not others is **not** flagged:
it can work, and a warning about a role it is not currently being asked to
perform is noise. (The per-role gap is visible in the Model per role block
itself, below.)

Note `enabled_kinds: null` is *not* `no-roles` — us-53.4 makes a never-saved
agent unrestricted rather than benched, and reading it as broken would flag
every fresh agent.

### The Start session button stops being a trap

Today the button is enabled whenever a project is picked
(`start-session.tsx:95`), and every configuration problem is discovered after
the click, as an amber sentence under it. With the reason already computed, the
button is **disabled** when the agent cannot open a session, with the same
sentence shown up front and a link to the fix. The post-click error handling
stays exactly as it is — it still has to catch the races the API refuses
(offline, already holding a session, gateway fault); it just stops being the
first time the manager learns about a setting.

### "Blank inherits the org's default preset" stops being an unbacked promise

The Model per role block offers a blank option labelled **"Inherit the org
default"** and tells the manager *"Blank inherits the org's default preset"*
(`settings/page.tsx:487`). Nothing on that page shows what blank actually
resolves to — not the inherited value, not the default preset's name. The
dropdown's options come from a flat list of every model across the org's
providers, which is not the preset.

That is where the confusion is manufactured, and on prod today it is worse than
vague: the default preset in every org is **"Balanced" with `model: null`**, so
blank inherits *nothing at all*.

So each role row that is blank shows what it actually resolves to, from the
same resolver: **"Inherits Balanced — no model set"** or **"Inherits Balanced —
claude-sonnet-5"**. One extra read on a page that already loads the agent's
config, and the promise becomes checkable.

### Where the code sits

- `worker_idle_reason` gains the two reasons; the resolver call is us-116.1's
  helper, so there is one definition of "has a model".
- The roster and the console need **no new component** — both already render
  the reason and its tone; the console's `fixForIdle` gains two entries.
- `start-session.tsx` takes the reason as a prop and gates the button.
- The settings page's Model per role rows gain a resolved-value line.

## Acceptance criteria

1. On `/team`, an agent that resolves no model for any role it claims shows
   **No model configured** in the State column, in the amber tone the column
   already uses for a blocked agent — not `Idle`. On prod's current data that is
   NexDB.Programmer, Architect, NexDB.Architect, DevOps and NexDB.DevOps;
   Programmer keeps reading normally.
2. An agent with every role unchecked (`enabled_kinds: []`) shows **No roles
   checked**. An agent whose `enabled_kinds` is `null` shows neither — it is
   unrestricted, not broken (us-53.4).
3. Precedence holds: `revoked > working > paused > no-roles > no-model >
   no-grants > queue-held > idle`. A revoked agent with no model reads
   `Token revoked`; a stuck agent with an empty queue reads its configuration
   reason, not `Idle`.
4. An agent that resolves a model for some claimed roles but not others is
   **not** flagged on the roster — it can work.
5. The **Start session** button is disabled for an agent that cannot open one,
   showing the same sentence and a link to the fix, before any click. The
   existing post-click error handling is unchanged and still surfaces the API's
   other refusals.
6. On the runner console, `no-model` and `no-roles` render with a working fix
   link — `no-model` deep-links to `…/settings#model-overrides`, the anchor
   that already exists on that block.
7. In **Model per role**, each role left blank shows what it resolves to,
   naming the org default preset and either its model or that it has none.
8. `npm run test:web` covers the reason precedence and the blank-row resolution
   text; `cd apps/api && python -m pytest` covers the two new reasons, including
   that `null` `enabled_kinds` is not `no-roles` and that some-but-not-all is not
   `no-model`.

## Out of scope

- **A full readiness panel per agent** (the `BillingReadiness` treatment for
  everything: provider pairing, grants, machine, workspace). It is the obvious
  next step and probably right, but it is a bigger surface than the complaint —
  the manager wants the roster to stop lying about `Idle`. Once the reason is
  computed server-side, a panel is a rendering job.
- **Making `validate_model_provider_pairing` cover `interactive`.** It is
  exempt on purpose (us-78.5 — its model is platform-owned), and revisiting
  that is its own decision.
- **Folding configuration into the health pill.** Health means incidents; a
  misconfigured agent is not unhealthy, and overloading one word would make
  both meanings weaker.
- **Giving "Balanced" a model.** Named here because it explains what blank does
  today; setting it is the manager's call, not a code change.
- **Changing what a session resolves.** That is us-116.1 — this story only
  shows its answer early.
