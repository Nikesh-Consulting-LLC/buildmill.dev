# US-90.1 — A failed release retries; a rejected one is final

**Status:** Testing
**Phase:** 90 — Release resilience
**Depends on:** the release lifecycle (Versioning & Release), release_prep_runs (US-63.x), deployment_runs, us-74.x hold/action surfacing

## Story

As the manager, a release that **failed before anything shipped** offers
one button: **Retry**. It re-runs the failed leg — a fresh notes prep, or
a fresh UAT deploy — on the *same version and the same pinned commit*.
Release 2026.08.13.1 died because a prep agent's MCP connection hit a
transport bug; the build it pinned was never touched, yet the only path
forward was minting 2026.08.13.2 and re-explaining nothing. Retrying an
attempt is not re-versioning a build.

The immutability rule survives untouched, sharpened: **a version names
exactly one build, forever — and a failed *attempt* at describing or
deploying that build may be retried; a *rejected* build may not.** When
UAT reveals the build itself is bad, rejection stays final and a new
release supersedes it, exactly as today.

## Acceptance criteria

- **AC1 — the button.** A release at `failed` (and never promoted) shows
  **Retry** beside its failure reason, on the release detail and the
  Releases hub row. Rejected, cancelled, released, and rolled-back
  releases never show it.
- **AC2 — retry re-runs the failed leg only.** A notes-prep failure
  queues a fresh `release_prep_runs` row for the same release (any
  eligible release-capable agent claims it); a UAT-deploy failure fires a
  fresh deployment run of the pinned commit. The release returns to the
  corresponding in-flight status; completed legs (notes already written)
  are not redone.
- **AC3 — the pin never moves.** Retry re-reads `commit_sha` from the
  release row; there is no path by which a retry rebuilds, re-pins, or
  re-versions. Asserted by test.
- **AC4 — attempts are visible.** Each retry is an audited event
  (actor, leg, attempt number), and the release detail lists prior failed
  attempts with their reasons — a release that failed three times reads
  as exactly that, not as a clean first try.
- **AC5 — manager-triggered only.** No automatic retries; the button is
  the only trigger (consistent with "promotion is never automatic").
- **AC6 — supersede stays.** Cutting a new release while a failed one
  sits unretried still works and still supersedes; Retry is an option,
  never a gate.

## Out of scope

- Retrying a *rejected* release (the build is bad; supersede).
- Automatic/background retries or retry-on-transient-error detection.
- Retrying promotion to production (a failed promote is its own incident,
  handled by rollback machinery).
