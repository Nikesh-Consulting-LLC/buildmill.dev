# US-89.2 — The environment is defined once

**Status:** Testing
**Phase:** 89 — The zero-secret workspace
**Depends on:** us-89.1 (one secret, one home — the broker this rides), us-1.28 (server credentials in the private Storage bucket — the storage pattern), Phase 79 (the credential scrubber), us-34.x (tool grants — the discovery precedent)

## Story

As the manager, every project has an **Environment** section where I
define the variables an agent gets when it works that project — the
Supabase login of the app under development, a SQL connection string, a
third-party API key, a feature flag. Each entry is a name, a value
(plain or secret), a description, and an optional agent scope (default:
every agent with access to the project; scoped: only that agent). The
built-in access — worker token, factory MCP, git, the LLM gateway — is
listed right there too, read-only, so this one screen answers "what can
this agent reach on this project?" completely.

When an agent starts a run or a session on the project, the factory
delivers that environment as real process environment variables at CLI
spawn — through the supervisor, never written into workspace files
(us-89.1's rule). And the agent can *ask*: a factory MCP tool answers
"what access do I have?" with every entry's name, description, and kind —
and, for a claimed worker on that project, the secret values themselves —
so an agent never guesses at connection strings, never asks the manager
mid-run for a login that exists, and never invents credentials that don't.

## The model

- **`project_env` entries**: `name` (ENV_VAR shape), `kind`
  (`plain` | `secret`), `description` (what it is, so the MCP answer is
  self-documenting), `agent_id` (null = all agents on the project),
  timestamps + last-edited-by.
- **Secret values are write-only in the UI** (the established rule):
  stored where the API can read and the browser cannot — the private
  Storage bucket per org (`<org>/projects/<project>/env/<name>`), the
  us-1.28 pattern; the UI shows `Set · <fingerprint>` and offers replace,
  never reveal. Plain values are ordinary rows.
- **Effective environment** for (agent, project) = built-ins (managed by
  the factory, not editable here) + project-wide entries + that agent's
  scoped entries, later wins on name collision. The agent's settings page
  shows the effective set per granted project, read-only with a link to
  the project's Environment section — "manageable and editable in one
  place" means the project owns the definitions; the agent view is a lens.

## Acceptance criteria

- **AC1 — the section.** Project → Environment lists built-ins (read-only:
  factory MCP, git remote, gateway — no values shown) and the manager's
  entries with add/edit/delete. A secret entry's value is write-only:
  entered once, shown as `Set · <fingerprint>` after, replaceable, never
  readable back in the browser. RLS org-scoped like everything else.
- **AC2 — delivery.** A run or session on the project spawns its CLI with
  the effective environment present as process env vars, injected by the
  supervisor (LocalPrimitives' existing env merge), sourced from the API
  at claim/open. No value is ever written into a file under the workspace
  root, in keeping with us-89.1.
- **AC3 — discovery over MCP.** A `get_environment` factory tool answers
  for the claimed run's project: every entry's name, kind, description,
  and scope, plus the built-ins — and includes secret *values* only for a
  worker holding a claim (or open session) on that project. Unclaimed
  callers get names and descriptions, never values.
- **AC4 — changesets stay clean.** The changeset guard refuses any file
  whose content contains a currently-delivered secret value for that run
  (exact-match sweep at submit), so a login can't ride a commit the way
  the worker token once did.
- **AC5 — attribution on the row.** Every entry carries updated_by and
  updated_at; a secret's value is never in any event, row, or response.

## Out of scope

- Per-run temporary credentials or automatic secret rotation.
- Environment for human workers' IDEs (agents only; humans read the
  section).
- Injecting into deployment pipelines (deployments have their own env
  story; this is the *agent work* environment).
- Trace/notes scrubber registration for delivered values (the changeset
  sweep is the shipped anti-leak rail; wiring the Phase 79 scrubber to
  per-run dynamic values is a follow-up).
- A read-only "effective environment" lens on the agent's settings page —
  the project section plus `get_environment` are the single home; the
  lens is ergonomics for later.
