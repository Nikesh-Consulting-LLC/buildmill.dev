# US-113.1 — Release notes can be submitted

**Status:** New
**Phase:** 113 — Release notes can be submitted
**Depends on:** US-63.1 (the release-prep claim/submit contract), US-101.4
(`notes_doc`, the declaration that introduced the crash), US-21.3
(`update_release`, the service-side write), US-21.4 (the assembled test-case
set that the failed submit leaves behind)

## Story

As the manager, I want a release prep to hand its notes back successfully, so
that cutting a release produces UAT-ready notes instead of a twenty-minute
agent session, a bill, and a pile of duplicate test cases.

## Design

### Every submit has crashed since Phase 101

`submit_release_notes` has failed on every call since `6828a3b` ("Phase 101: a
release explains itself", authored 2026-08-16 03:57 UTC). The last release prep
that ever succeeded was 2026-08-16 **02:43** UTC — an hour before that commit
existed. Three releases have failed since: 2026.08.16.3 and 2026.08.16.4
(twice).

us-101.4 added the notes declaration to the update patch
([release_prep.py:203](../apps/api/app/release_prep.py:203)):

```python
"notes_doc": doc,          # a dict, straight from release_notes.as_declaration
```

`update_release` passes `patch.values()` to psycopg as `%s` parameters
([db.py:1390-1396](../apps/api/app/db.py:1390)):

```python
cols = ", ".join(f"{k} = %s" for k in patch)
row = conn.execute(f"update public.releases set {cols}, ...", (*patch.values(), release_id))
```

psycopg 3 has **no dumper for `dict`**. It raises

```
ProgrammingError: cannot adapt type 'dict' using placeholder '%s' (format: AUTO)
```

**client-side, before any SQL is sent.** Every other jsonb write in `db.py`
wraps its value in `json.dumps(...)` (lines 247, 357, 615, 626, 647, 668, 747
and on); this one path does not, and `db.py` imports no `Json` adapter at all.

### What the manager sees

The 500 reaches the agent as `tool_output_error`, which reads as "your payload
was wrong" rather than "the server is broken". So the agent rewrites the notes
and tries again — and because the failure is structural, shrinking the payload
never helps. Release 2026.08.16.4's second attempt made **61 submit attempts in
15 minutes**, including probes with a title of `t`, steps of `s` and an
expected result of `e`, before the CLI's 1200s wall-clock cap killed it. Cost:
$2.21, 43 LLM calls, no notes.

### The submit is not atomic, so each retry leaves a full set of cases behind

us-101.3 established the rule — *"a refused hand-back must never
half-complete the job"* ([release_prep.py:159](../apps/api/app/release_prep.py:159))
— and validation does run before the write. But the crash happens **after**
validation, between two writes that are not in one transaction:

| line | write | committed? |
|---|---|---|
| [189](../apps/api/app/release_prep.py:189) | `attach_release_test_cases` | **yes**, every attempt |
| [197](../apps/api/app/release_prep.py:197) | `update_release` (notes, status) | never |

So release 2026.08.16.4 carries **138 `test_cases` rows** from 61 attempts —
four near-identical 13-case batches plus ~55 single-row probes — while
`notes_summary` is empty and `notes_written_at` / `cases_attached_at` are both
null. The release page shows the junk; the release itself has no notes.

### Why no test caught it

Every existing test of this path monkeypatches `db.update_release`
([test_release_prep_lifecycle.py:218](../apps/api/tests/test_release_prep_lifecycle.py:218),
[test_releases.py:723](../apps/api/tests/test_releases.py:723),
[test_factory_mcp.py:4223](../apps/api/tests/test_factory_mcp.py:4223)), so the
parameter adaptation that fails never runs. The Essential suite fakes the
database by design, and the SQL suite skips without `DATABASE_URL` — the write
had no coverage from either side.

The fix for that is not "run more SQL tests": adaptability is checkable without
a database. psycopg's adapter registry answers `can this value be a parameter?`
in-process, so the regression test asserts every value the submit path puts in
the patch has a dumper.

## Acceptance criteria

1. A release prep submit with a `notes_doc` object **succeeds**: the release
   reaches `notes-ready`, `notes_summary`/`notes_detail`/`notes_doc` are
   stored, `notes_written_at` and `cases_attached_at` are stamped, and the UAT
   deploy fires.
2. `update_release` accepts a `dict` value for any jsonb column and stores it
   as JSON — a raw dict can never again be handed to psycopg as a parameter.
3. A regression test asserts that every value in the patch `release_prep.submit`
   builds is adaptable by psycopg, and it runs in the **Essential** suite (no
   database, no network).
4. The stored `notes_doc` round-trips: what `as_declaration` produced is what
   the release row holds, as a jsonb object rather than a quoted string.
5. Release 2026.08.16.4 can be retried and reaches UAT.

## Out of scope

- **The 138 junk test cases already written.** Cleaning existing rows is a data
  fix, done once by hand against production; this story stops new ones.
- **Making the two writes one transaction.** The real repair for the atomicity
  hole — cases and notes commit together, or neither does — is its own story
  (us-113.2). This one removes the crash that exposed it.
- **The 1200s CLI cap and the retry loop.** The agent retrying a structural
  500 sixty-one times is a supervisor concern, not this path's.
- **`tool_output_error` as an error message.** That a server 500 reaches the
  agent as if it were bad input is worth fixing, and is not this story.
