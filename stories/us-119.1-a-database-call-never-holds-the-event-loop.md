# US-119.1 — A database call never holds the event loop

**Status:** Testing
**Phase:** 119 — The API answers while the runners poll
**Depends on:** US-87.6 (the process-wide connection pool), US-62.8
(`api_request_log` — total and DB time per request), us-117.1 (the pool's
reset runs in autocommit), US-3.2 / US-59.9 (claim, resume-claim, the pool
listing — the handlers this touches), US-33.3 / us-95.x / us-102.2 (the
Costs endpoints it was measured on)

## Story

As the manager, I want a page's request to be answered in the time its own
work takes, so that opening Costs — three sub-millisecond aggregates over 153
rows — does not take four to ten seconds because a runner happened to be
polling.

## Design

### What was measured (prod, 2026-08-04 → 2026-08-18)

Every API request records its wall clock and its DB share
(`api_request_log`, US-62.8). For the Costs page's three calls:

| Route | n | p50 | p95 | DB p50 | the SQL itself |
|---|---|---|---|---|---|
| `/llm/orgs/{org_id}/spend` | 251 | **1,860 ms** | 9,435 ms | 146 ms | 0.8 ms |
| `/llm/orgs/{org_id}/spend-trend` | 51 | 1,520 ms | 3,388 ms | 196 ms | < 1 ms |
| `/llm/orgs/{org_id}/work-summary` | 31 | 1,709 ms | 3,645 ms | 194 ms | 0.7 ms |

`llm_usage` holds 153 rows; `runs` 205. `EXPLAIN ANALYZE` on the exact
statements: index scans, under a millisecond. So each call spends ~1.3 s on
nothing that belongs to it, and even its "DB" 150–200 ms is a hundred times
the query — that part is the connection lease (a `check_connection` ping on
checkout, the statement, `DISCARD ALL` on return, each a network hop to the
Supabase pooler; not this story's target).

`/auth/me` — JWT verify plus one PostgREST call, no thread pool, no database —
is a steady **170 ms** every day. That is the floor a request pays for the
network. The 1.3 s above it is contention inside the API process.

### Where the contention comes from

`db.py` is synchronous psycopg. Only 29 of its call sites in the routers go
through `asyncio.to_thread`; **178 are called directly inside `async def`
handlers**, which runs the round trip on uvicorn's event loop. While one is
in flight nothing else in the process advances — not another request's
awaited PostgREST capability check, not a response being written, not a
CORS preflight. The preflights prove it: an OPTIONS is pure in-memory
middleware, p50 2 ms, and its p95 is 200–1,750 ms.

The heaviest offenders are the runner-facing paths, because they run all
day:

| File | direct `db.*` in `async def` | via `to_thread` | traffic |
|---|---|---|---|
| `routers/worker.py` | 54 | 0 | `/worker/pool` ≈ 40k/day, p50 5.8 s (DB 1.3 s); `/worker/release-prep` ≈ 40k/day, p50 1.6 s |
| `routers/runner_socket.py` | 30 | 0 | every socket message |
| `reconcile.py` | 2 (from an `async def`) | 0 | called on every `/worker/pool` |
| `routers/mcp_catalog.py` | 25 | 0 | agent tool calls |
| `routers/presets.py` | 16 | 0 | |
| `routers/admin.py` | 10 | 0 | |

`/worker/pool` alone: ~40k requests a day, each holding the loop for its
1.3 s of database time. That is the ~1.3 s a Costs call waits.

### Why not `--workers 4`

The VM is an `n2d-standard-4` (4 vCPU, 16 GB); one uvicorn process uses one
core for its loop and the rest idle. Multiple workers look like the fix, but
the API keeps state that assumes one process: `runner_socket._LIVE` (worker
id → WebSocket), `_PENDING` (request futures), `_CONSOLES`;
`deploy._RUNNING`; `suites._SERVER_LOCKS`. `request_from_worker`
(`runner_socket.py:117`) looks the socket up in `_LIVE` and raises *"runner
is not connected"* otherwise — and it is what starting a session
(`agent_sessions.py`), the run console (`run_console.py`) and workspace prep
(`workspace_prep.py`) call. With four workers the runner's socket lives in
one of them, and three in four of those requests would fail with exactly the
class of "cannot start" fault Phases 116/117 just cleaned up. Multi-process
needs that state moved out first; that is not this story.

### The change

1. **Every `db.*` call inside a coroutine in `worker.py`, `runner_socket.py`
   and `reconcile.py` goes through `await asyncio.to_thread(...)`.**
   Mechanical, and semantically neutral for one request: each `db` function
   opens and closes its own leased connection, so no transaction spans two
   calls, and `to_thread` copies contextvars, so `_request_db_ms` (US-62.8)
   still accumulates into the right request.
2. **The executor is sized for I/O, not for cores.** `asyncio.to_thread` uses
   the loop's default executor — `min(32, cpu + 4)` = 8 threads on this box.
   The lifespan sets `loop.set_default_executor(ThreadPoolExecutor(
   max_workers=settings.db_executor_threads))`, default 32, and
   `db_pool_max_size` defaults 10 → 20 so threads do not queue on the pool
   instead. Both stay settings; the pool module's shared-budget warning is
   updated to say why 20 (Supavisor transaction pooling in front; the API is
   the only heavy dialer).
3. **A guard so it does not creep back.** An Essential test (AST, in the
   spirit of `test_suite_split.py`) fails if a direct `db.*` call appears
   inside an `async def` in the covered files. The covered list lives in the
   test and grows as files are converted; the remaining ~90 sites are named
   below as the follow-up, not silently left.
4. `GCP-setup.md:159` still says the VM is an `e2-small` with 2 GB; it is an
   `n2d-standard-4`. Corrected in passing.

### What this costs, and how the story pays for it

- **The accidental serialisation goes away.** Today the blocked loop
  serialises every database access in the process, by accident. Once 32
  threads can reach the database at once, a check-then-act that spans two
  `db.*` calls without a row lock is a real race — and the handlers this
  story touches are the ones where a race matters most: claim, resume-claim,
  submit, heartbeat. Correctness has to come from the SQL (`for update skip
  locked`, single-statement transitions), never from the loop. So the story
  **audits those handlers before wrapping them** (AC2), and the audit's
  findings are part of the verification record.
- **Some functions must stay on the loop.** Anything that touches an
  `asyncio` object or a live websocket cannot move to a thread. The guard
  cannot tell those apart; the conversion has to.
- **More connections against a shared budget.** Pool 10 → 20 is fine through
  the Supavisor transaction pooler and wrong against the direct 5432 port;
  the setting's docstring says which one it assumes. When the database is
  slow, a request now fails fast with the pool's 10 s timeout instead of
  merely being slow — bounded, and a new message operators will see; the
  message names the pool.
- **Essential proves wiring, not concurrency.** Route tests fake reads. The
  proof of the claim this story makes is prod, the day after (AC4).

## Acceptance criteria

- **AC1 — the hot paths never block the loop.** An Essential test walks the
  AST of `routers/worker.py`, `routers/runner_socket.py` and `reconcile.py`
  and finds zero direct `db.<fn>(...)` calls inside any `async def`; every
  one is the first argument of `asyncio.to_thread`. The test fails on the
  first regression.
- **AC2 — no transition depends on the loop having been single-threaded.**
  Before the wrap, `claim`, `resume-claim`, `submit`, `heartbeat`, `extend`
  and `stop` in `worker.py` are audited: every status transition is either
  one statement or runs under a row lock, and no handler reads state in one
  `db.*` call and acts on it in a second without the row being locked in
  between. The audit — each handler, the statement that guards it, and
  anything that had to change — is written into the story's verification
  record. Where a guard is missing, it is added in `db.py` in this story.
- **AC3 — nothing the runner sees changes.** `GET /worker/pool`,
  `GET /worker/release-prep`, claim, heartbeat, submit and the socket
  handlers return the same bodies as before — the existing route tests pass
  unchanged.
- **AC4 — the executor and the pool are sized by settings.**
  `db_executor_threads` (default 32) and `db_pool_max_size` (default 20) in
  `config.py`, the executor installed in the lifespan, both documented where
  the pool's sizing note is, and the note says the default assumes the
  transaction pooler.
- **AC5 — measured, on prod, the day after release.** UAT is one query on
  `api_request_log` over the first full UTC day after the deploy: p50 of
  `/llm/orgs/{org_id}/spend` under **500 ms** (from ~1.9 s) and p50 of
  `/worker/pool` under **1.5 s** (from ~5.8 s). The query is in the story's
  verification record when it flips to Testing.
- **AC6 — Essential.** Every new test runs in the ~30 s suite with reads
  faked; nothing here needs `DATABASE_URL` or the network.
- **AC7 — the machine is described correctly.** `GCP-setup.md` names the
  `n2d-standard-4`.

## Out of scope

- **`uvicorn --workers`.** Blocked by the process-local socket registry
  above; a story of its own if it is ever wanted (it needs `_LIVE`/`_PENDING`
  in shared storage first).
- **The other ~90 direct calls** in `mcp_catalog.py`, `presets.py`,
  `admin.py`, `agent_sessions.py`, `reviews.py`, `workflow.py`,
  `gitproxy.py`, `llm.py`, `agents.py`, `issues.py`. Same mechanical change,
  same guard, same audit discipline — a follow-up story extends the covered
  list once this one is measured.
- **`/agents/idle-reasons`** at p50 43 s (400 s on 2026-08-17). It holds
  threads and connections for minutes and deserves its own story.
- **What each request pays per round trip** (the checkout ping, the fresh
  TLS handshake per PostgREST call, the reconciler on every poll) — us-119.2
  takes the reconciler; the other two are deferred there.
- **The Costs page's own request shape** — us-119.3.
