# US-87.12 — A live change announces itself

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** us-87.3 (the hub's realtime handler), us-87.5 (its filtered subscription)

## Story

As the manager watching the Work Items hub while agents work, rows change
underneath me with no signal at all. A story flips from `planning` to
`in-review`, an item appears, a status moves — and unless I happened to be
looking at that exact row, nothing tells me. This is deliberate today:
`refreshSilently()` exists precisely so a page fed by realtime does not
strobe the global progress bar forever, and us-87.11 keeps that exemption.

But "do not shout" is not the same as "say nothing". The right signal for a
live change is local to the thing that changed, not global to the page.

## Acceptance criteria

- **AC1 — a changed row shows it changed.** When a realtime update arrives
  for a work item currently on screen, that row briefly tints and fades back
  over ~1.5 s. The signal is on the row, not the page.
- **AC2 — it uses the stream that already exists.** The highlight is driven
  from the realtime payloads `use-project-issues.ts` already receives — no
  second subscription, and nothing added to the publication (us-87.5 spent
  real effort shrinking it).
- **AC3 — all three lenses.** Outline, Table and Board each show it, reusing
  the `list-row` / `list-card` elements us-87.4 already put on those rows
  rather than wrapping them in something new.
- **AC4 — an insert is not a storm.** A batch dispatch that changes twenty
  rows at once must not produce twenty competing animations that make the
  list unreadable. If the changed set is large, the effect degrades (or
  stands down) rather than flashing the whole page.
- **AC5 — motion is optional.** Stands down under `prefers-reduced-motion`,
  same as us-87.11.
- **AC6 — proof.** Verified live: change an item's status from a second
  browser tab (or directly in the database) and watch the row tint in the
  first.

## Out of scope

- The global progress bar and route transitions — us-87.11.
- Any other live surface (factory queue, activity feed, run trace). Worth
  the same treatment if this lands well; the hub is where the update stream
  is already in hand.
- A "N items changed since you looked away" summary. A different feature,
  and a bigger one.

## Verification record

Built 2026-08-13 on `us-87.11-feedback`. No migration.

**Verified:** `npm run build` clean; `npm run lint` 0 errors;
`npm run test:web` 107/107, with 6 new cases in `lib/recent-changes.test.ts`.
Those cover the rule that matters — AC4's storm case: twenty simultaneous
changes stand down rather than flashing the whole list, standing down is
signalled distinctly from "nothing highlighted" (the two need different timer
handling), and marking never mutates the set it was given.

The `[data-changed]` rule and its `row-changed` keyframe are present in the
parsed stylesheet of a running build, along with the `prefers-reduced-motion`
variant that holds a static tint instead of animating.

The changed-id set is threaded from `use-project-issues.ts` — the existing
subscription, no new one and nothing added to the publication (AC2) — through
to all three lenses (AC3): `OutlineRow`, the table's `<tr>` inside
`GroupBlock`, and `BoardCard` via `PhaseColumns`.

**Not verified (UAT) — this is the whole point of the story:**

- **No live change was ever watched.** AC6 asks for an item's status to be
  changed from a second tab and the row seen to tint. That did not happen. The
  highlight is proven to be wired and its CSS proven to exist; whether it
  actually fires on a real realtime payload, and whether 1.5 s reads as a
  signal rather than a distraction, is unobserved.
- The storm rule is proven in a unit test, never against a real batch
  dispatch.
- The tint colour (`--primary` at 22%) has not been seen in dark mode.
