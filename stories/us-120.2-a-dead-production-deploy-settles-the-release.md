# US-120.2 — A dead production deploy settles the release

**Status:** New
**Phase:** 120 — A deploy that dies settles the release
**Depends on:** US-120.1 (the UAT half — its settle helper, sweep and reaper
hook are what this story extends), US-21.5 (`/promote`, `/confirm-released`),
migration 215 (`promoting` is in the in-flight set)

## Story

As the manager, I want a release whose production deploy died at `promoting`
to say so and give me a way forward, so that a lost prod run does not leave a
signed-off build stuck in-flight with only Reject — a verdict on the build —
as the exit.

## Design (to be agreed — drafted with US-120.1, not built)

`/promote` on the human rail creates a `deployment_runs` row **without**
`release_id` (it records `prod_deployment_run_id` on the release instead), and
on the agent rail dispatches a `deploy`-kind run; `/confirm-released` then
looks for a `succeeded` prod run of the pinned commit. If that run is reaped,
cancelled or times out, the release stays at `promoting`: Stop is refused
(*"let it finish, then roll it back"* — right for a run that is alive, wrong
for one that is dead), Retry refuses anything promoted, and Confirm answers
409. The manager's only move is Reject, which burns a version whose build was
signed off and may be half on the box.

Open questions the story must settle before build:

- **Where does a failed promotion land?** The candidates are back to
  `uat-signed-off` (the sign-off stands; Promote is offered again — but
  `promoted_at`/`promoted_by` then need clearing or a "last promotion
  attempt" reading) or a new `promotion-failed` status (a migration to the
  check constraint and the in-flight set, a badge, and every place that
  enumerates release states).
- **Should the prod run carry `release_id` too?** Then US-120.1's settle,
  reaper hook and sweep cover it with one more branch on outcome — but
  `_settle_release_deploy` must then know which leg it is settling.
- **What Stop means at `promoting`**, if anything: probably still refused
  while the run is live, and unnecessary once a dead run settles itself.

## Acceptance criteria

To be written with the design. The floor: a reaped, cancelled or timed-out
production deploy of a `promoting` release moves the release to an agreed
non-stuck state within one sweep tick, with a reason on the page, and the
manager has a documented next action other than Reject.

## Out of scope

- Everything US-120.1 delivers for the UAT leg.
- Rolling anything back on the box; a failed promotion's server-side state is
  the deployment page's business (US-1.35 semantics).
