# US-99.4 — An unpublished edit says so, and the manager pushes it

**Status:** New
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-99.2, us-99.3 (there is something to publish)

## Story

As the manager, editing an instruction and having it reach the repository are
now two separate things, and the gap between them is where this goes wrong.
Today the sync is automatic and invisible: `dispatch` compares
`instructions_synced_hash` ([135_instructions_sync.sql](../infra/supabase/migrations/135_instructions_sync.sql))
against the assembled content and commits if they differ, which is free when
nothing changed and silent when something did.

That was right when the factory owned a fenced block. It is wrong now that a
publish rewrites `AGENTS.md` and `CLAUDE.md` whole and writes seventeen
files: a commit that size should happen when I decide it does, with me
knowing what is in it. So publishing becomes my click.

Which means the gap needs a name. An edit saved but not published is a real
state — my agents are still running on yesterday's file — and the surface has
to say so, unprompted, until I close it. The existing hash column is exactly
the right instrument: it already survives edits that cancel out, reordering
that changes nothing, and a failed write that must be retried. It stops
gating a silent commit and starts driving a visible badge.

## Acceptance criteria

- **AC1 — saving stays a save.** Editing an instruction, or a guideline
  section, writes to the database as it does today and commits nothing.
  Edits keep landing in `content_audit`, unchanged.

- **AC2 — unpublished is a named, visible state.** The project's assembled
  instruction content is hashed the way
  [135](../infra/supabase/migrations/135_instructions_sync.sql) already
  defines; when it differs from `instructions_synced_hash` the project
  surface says so — how many files differ, and which. The state clears only
  on a successful publish, never on a page reload or a second save.

- **AC3 — publish is one commit.** Publishing writes every changed file —
  `AGENTS.md`, `CLAUDE.md`, and each `.buildmill/*.md` added, changed or
  deleted — as a **single commit to the project's default branch**, with a
  message naming what changed. It is not a pull request: instructions are
  the factory's own scaffolding, and gating them behind review would put
  every instruction fix a run-length behind the runs that need it.

- **AC4 — failure leaves the state honest.** A failed publish does **not**
  stamp `instructions_synced_hash` — the deliberate behavior
  [135](../infra/supabase/migrations/135_instructions_sync.sql) already
  documents, and the reason the next attempt retries. The manager sees the
  failure and the reason; the unpublished badge stays up.

- **AC5 — dispatch stops committing.** The pre-dispatch instruction write is
  removed. Dispatch neither commits nor blocks on unpublished content; a run
  dispatched against unpublished instructions proceeds, and us-99.5's
  fallback is what keeps it correct. A test pins that dispatch makes no
  GitHub write.

- **AC6 — the ownership line is present.** The publish surface carries the
  standing copy us-99.2 AC6 requires: Build Mill owns `AGENTS.md`,
  `CLAUDE.md` and `.buildmill/`, and rewrites them whole.

- **AC7 — publishing is audited.** Each publish records what was written and
  the commit that carried it, on the project's existing audit surface, so
  "when did this instruction reach the repo" has an answer.

- **AC8 — tests.** Essential, faked GitHub: AC2's badge across
  edit/publish/edit-again; AC3's single-commit shape including a deletion;
  AC4's no-stamp-on-failure; and AC5's assertion that dispatch writes
  nothing. `npm run build` green.

## Out of scope

- Publishing to any branch but the default one. Instructions are not
  branch-scoped in this phase.
- Reviewing instruction changes before they land (AC3 states why).
- Reconciling a `.buildmill/` file edited directly in the repository. Build
  Mill's copy wins and overwrites it on the next publish; detecting or
  merging repo-side edits is not built here.
- Automatic publishing on any trigger — a schedule, a run completing, a
  template update. Every publish is the manager's click, including the one
  us-99.7 offers.
