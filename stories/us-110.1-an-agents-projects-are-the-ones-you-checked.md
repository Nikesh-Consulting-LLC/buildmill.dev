# US-110.1 — An agent's projects are the ones you checked

**Status:** Testing
**Phase:** 110 — An agent's projects are the ones you checked
**Depends on:** US-31.3 (the fail-closed capability gate that already does this
job), US-55.1 (project access, all checked by default), migration
`216_worker_mcp_project_scope` (introduced `workers.project_id`), US-3.14 (the
retired `/mcp/<org-shortname>/<project-slug>` URL scoping this replaced)

## Story

As the manager, I want the projects I check when creating an agent to be the
only place an agent's project scope is set, so that I am not asked the same
question twice in two vocabularies and given two answers that disagree.

## Design

### The Add agent wizard asks the same question twice

Step 3 of the wizard has two project controls, stacked:

| Control | Writes | Cardinality |
|---|---|---|
| *"Which project its MCP tools connect to"* | `workers.project_id` | exactly one |
| *"Which projects it may access over git"* | `worker_capabilities` rows | many, **all checked by default** |

They are written by two independent calls in the same submit — `create_worker`
with `p_project` ([add-agent-wizard.tsx:308](../apps/web/src/app/(app)/team/add-agent-wizard.tsx:308))
and the `worker_capabilities` upsert
([add-agent-wizard.tsx:348](../apps/web/src/app/(app)/team/add-agent-wizard.tsx:348)).
Neither reads the other.

**And the two helper sentences under them contradict each other.** Under the
dropdown: *"A worker's MCP tools only ever see one project's pool."* Under the
checkboxes: *"On every project checked, the agent does whatever the roles above
allow."* Both cannot be true. The code sides with the first —
`claim_work` refuses any run outside the scoped project
([factory_mcp.py:642](../apps/api/app/factory_mcp.py:642)) — so an agent
created today with two projects checked and a scope of the first will **never**
claim the second's runs, of any kind, despite the checkbox and every role being
on. The manager is told otherwise on the same screen.

The label is wrong on its own terms too. There is one MCP endpoint for the org
(`POST /mcp`); the token is the connection, and any path segment after `/mcp`
answers 404 `unknown factory MCP url`
([factory_mcp.py:6676](../apps/api/app/factory_mcp.py:6676)). Nothing
"connects to a project".

### The access list already does the whole job

`list_worker_pool` applies the US-31.3 fail-closed capability filter *before*
any scope narrowing: with `project_id=None` it offers exactly the runs whose
project the worker is allow-listed for, and a worker with zero capability rows
is offered nothing ([db.py:4693](../apps/api/app/db.py:4693)). `claim_work`
then re-checks the same predicate through `worker_run_refusal`
([factory_mcp.py:651](../apps/api/app/factory_mcp.py:651)).

So an unscoped worker is not an ungated worker. It is a worker gated by
precisely the list the manager checked. That is the behaviour the manager
already believes they configured.

**The automated provisioning path already works this way.** The machine/pool
provisioner inserts a worker with no `project_id` at all — the column is not
in its insert ([agent_provision.py:1151](../apps/api/app/agent_provision.py:1151))
— and writes only capability grants
([agent_provision.py:1180](../apps/api/app/agent_provision.py:1180)). Every
agent Build Mill provisions for itself is unscoped. Only agents a human creates
through the wizard get pinned, because only the wizard asks.

Migration 216 itself declined to invent the value: workers with zero or several
grants were "left unscoped rather than guessed"
([216:14](../infra/supabase/migrations/216_worker_mcp_project_scope.sql:14)).
The wizard then made the guess anyway, by pre-selecting the first project in
the list ([add-agent-wizard.tsx:224](../apps/web/src/app/(app)/team/add-agent-wizard.tsx:224)).

### The decision: retire `workers.project_id`

One list, one meaning. **The projects checked on the access list are the
agent's projects** — for claiming work, for git, and for every project read
over MCP. There is no second, narrower, differently-worded scope.

This is a removal, not a rename, because a renamed field would still be a
second answer to a question already answered on the same screen. The column has
exactly **one** server-side reader
([factory_mcp.py:6681](../apps/api/app/factory_mcp.py:6681)), which makes it
cheap to take out and, left in, cheap to drift again.

### The one job that needs a replacement

Besides filtering the pool (which the capability gate already does), the scope
was serving as the **default `project_id`** for the ten tools callable without
a claim — `get_project_tree`, `read_project_file`, `get_project_workspace`,
`get_project_guidelines`, `get_project_learnings`, `list_project_documents`,
`get_environment`, `submit_learning`, and the two instruction-file proposals.
Each resolves `project_id or _scoped_project.get()` and refuses when both are
empty.

Two changes close that gap:

1. **Default to the worker's sole accessible project** when it has exactly
   one — the same unambiguous-case rule migration 216's backfill used, applied
   live instead of once.
2. **Return `project_id` from the pool listings**, which today return
   `p.name as project_name` and no id ([db.py:4713](../apps/api/app/db.py:4713)),
   so a multi-project agent always has an id to pass.

And the refusal text those tools print is stale in a way that matters: all ten
say *"connect via a project-scoped MCP url (/mcp/&lt;org-shortname&gt;/&lt;project-slug&gt;)"*,
a URL that has 404'd since migration 216 superseded it. An agent that hits this
is instructed to do the one thing the endpoint refuses.

### What we give up, deliberately

`project_id` could express one thing the access list cannot: *git access to a
project whose runs this agent may never claim*. Nothing in the product asks for
that today, the wizard cannot express it (one scope, many grants), and the
read-without-claim case is already covered by `workers.no_claim_checkout`.

If it is ever wanted, it comes back as a **per-project role** — the same
vocabulary as the roles checkboxes, on the row it applies to — never as a
second global scope with its own noun. That is the settlement: project scope is
the access list, and anything finer is a property *of a row in that list*.

## Acceptance criteria

- **AC1 — the wizard asks once.** Step 3 of Add agent has no *"Which project
  its MCP tools connect to"* control. What remains: agent type, the four roles,
  and *"Which projects it may access over git"*. Step validity no longer
  depends on a project pick, and `create_worker` is called without
  `p_project`. Creating an agent with two projects checked and no other input
  produces an agent that can claim work on both.
- **AC2 — the checkbox promise holds without qualification.** *"On every
  project checked, the agent does whatever the roles above allow"* is now true
  as written. Pinned in `test_worker_pool_sql.py` (**Full QA** — this one needs
  a real pool and real grants, and faking the read would prove nothing): a
  worker granted two projects is offered runs from both, and revoking one grant
  removes that project's run from the pool again. The Essential half is
  structural — `list_worker_pool` takes no project argument and its SQL has no
  narrowing clause left, so a second filter cannot be reintroduced by a caller.
- **AC3 — the column is gone.** Migration `279_an_agents_projects_are_its_grants.sql`
  drops `workers.project_id` and its index, drops `set_worker_project`, and
  recreates `create_worker` without `p_project` (back to its four-argument
  form). **Not the usual both-projects-same-change**: a drop is the one shape
  where code must ship first, because the deployed Team page selects the
  column. Applied to `build-mill-dev` with this branch; applied to
  `Software-Factory` as part of the release that carries this code. With
  `database.types.ts` regenerated and `test_embed_ambiguity.py` green.
- **AC4 — the scope disappears from the code, not just the UI.**
  `_scoped_project` and every branch reading it are removed from
  `factory_mcp.py`, including `claim_work`'s *"that run isn't in this
  project-scoped MCP url"* refusal — `worker_run_refusal` is the only claim
  gate left. The **MCP project** Select (with its `Unscoped` option) is removed
  from the Team page's router-token panel
  ([router-token-panel.tsx:235](../apps/web/src/app/(app)/team/[principalId]/router-token-panel.tsx:235)),
  along with `project_id` in the Team page's worker query and `WorkerRow` type.
- **AC5 — a no-claim tool still finds its project.** Each of the ten tools
  defaults `project_id` to the worker's sole accessible project when it has
  exactly one grant, through one shared `_default_project` helper rather than
  ten copies. With several grants and no argument, the refusal reads *"no
  project specified — pass project_id; list_available_work returns one for
  every claimable run"*. **No refusal in the file mentions the retired
  `/mcp/<org-shortname>/<project-slug>` form** (10 occurrences before; 0
  after). Pinned by Essential tests for the one-grant default, the
  several-grant None, the hint's content, and a file-level assertion that the
  retired URL appears nowhere in `factory_mcp.py`.
- **AC6 — the pool listing carries the id.** `list_available_work` and
  `get_factory_queue` return `project_id` alongside the existing `project`
  name, so an agent with several grants can always name a project without
  guessing. Pinned by a test asserting the key is present and is the run's
  project.
- **AC7 — no surface still describes a token scope.** The stale comments at
  [connect/page.tsx:44](<../apps/web/src/app/(app)/projects/[id]/connect/page.tsx:44>)
  ("which of the org's workers are actually scoped to *this* project" — the
  query below it never filtered by project) and
  [connect-panel.tsx:155](../apps/web/src/app/(app)/team/connect-panel.tsx:155)
  ("Scope lives on the token (`workers.project_id`)") are corrected to say the
  MCP URL is the same for every worker and access comes from the project
  grants. Neither page's behaviour changes.
- **AC8 — the reference is updated.** `docs/application/interface-catalog.md`'s
  Worker MCP section no longer says a token is scoped to at most one project
  via `workers.project_id`; it says a worker reaches every project it is
  granted access to, over the single `/mcp` endpoint.
- **AC9 — existing agents keep working.** Dropping the column widens every
  currently-scoped agent to the projects it already had grants on; no token is
  invalidated or reissued, and no agent loses access to anything. The story
  notes in its Outcome how many prod workers had a non-null `project_id` at
  migration time and which projects they widen to.
- **AC10 — the split is honest.** The structural guards
  (`test_agent_projects_are_grants.py`) run in the ~30s Essential suite: no
  database, no network. The four data-layer tests appended to
  `test_worker_pool_sql.py` are Full QA and need `DATABASE_URL`; they cover
  what a fake could only assert about itself — two granted projects both
  offered, a revoked grant offering nothing, the pool row carrying its
  `project_id`, and `sole_granted_project` refusing to guess between several.

## Out of scope

- **A per-project claim/access distinction.** Deliberately given up (see *What
  we give up*). Not rebuilt here under a new name, and if wanted later it is a
  per-project role, not a second scope.
- **The four role checkboxes** and how roles map to run kinds (US-77.1,
  migration 178) — unchanged.
- **US-55.1's all-checked default** on the access list. It stays. Whether a new
  agent should default to every project is a real question and a separate
  story; this story only makes the default mean what it says.
- **A `list_projects` MCP tool.** AC6 gives a multi-project agent project ids
  through the pool listing, which is enough. Project discovery outside the
  queue is not needed for this change.
- **`worker_capabilities`' name, shape, or the `capability = 'access'`
  vocabulary** — untouched, including the `access` row's double duty as the git
  gate and the claim gate.
- **The git proxy's 404 for an unauthorised project** (US-3.12's
  existence-leak rule) — unchanged, and us-108.1 AC5 owns its manager-facing
  half.
- **`workers.no_claim_checkout`** — the read-without-claim opt-in stays exactly
  as it is.
- The Connect pages' repo picker, snippets, or token reveal — AC7 is comment
  and copy only.
