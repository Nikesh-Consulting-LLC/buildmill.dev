# US-87.7 — A heartbeat is not a write storm

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** us-87.6 (the API keeps its connections) — same file, land in order

## Story

As the operator, worker authentication is a write. `get_worker_by_token` —
"the single auth path for every `/worker/*` call and the git remote" —
is an `UPDATE ... set last_seen_at = now()` on the `workers` row, and it has
run **940,000 times** on prod (414,305 + 525,672 across its two variants).

Every one of those produces a write-ahead log record, which feeds the
Realtime decoder that us-87.5 is trying to quiet. Every one takes a row lock
on the worker, so a single worker's concurrent requests serialize on their
own presence timestamp. A polling worker pays this on every poll.

Presence does not need write durability on the authentication path. Knowing
an agent was seen within the last few seconds is the whole requirement.

## Acceptance criteria

- **AC1 — auth reads.** The token→worker lookup on the request path is a
  `SELECT`. Authentication no longer writes.
- **AC2 — presence stays honest to the second-ish.** `last_seen_at` is
  updated at most once per worker per interval (default 15 s, configurable),
  either by throttling in the API process or by a debounced write. Every
  surface that reads liveness — the workers page, the pool listing, the
  dashboard's "no capable worker is online" stall banner, agent liveness on
  the factory tab — must still be correct within that interval, and the
  story names the interval each of them tolerates.
- **AC3 — the stall banner does not lie.** The dashboard's stalled-queue
  warning and the claim gate read the same freshness threshold, and that
  threshold is comfortably larger than the write interval. A worker that is
  alive must never be reported offline because its heartbeat was throttled.
- **AC4 — restart-safe.** In-process throttling state lost on API restart
  causes at most one extra write per worker, never a stale-forever
  timestamp.
- **AC5 — proof.** The `update public.workers set last_seen_at` call count
  is re-measured over a representative day and recorded against the ~940,000
  baseline, alongside evidence that liveness surfaces still read correctly.

## Out of scope

- `runner_sessions.last_seen_at` (the session heartbeat, US-10.1) — a
  different cadence with a different owner; measure it, and open a follow-up
  if it shows the same shape.
- Changing the worker auth token scheme.
- The git remote's own auth path beyond the shared lookup.

## Verification record

Built 2026-08-12 on `phase-87-performance`. No migration.

**Verified:** Essential suite green; the throttle is covered by seven cases in
`tests/test_pool_and_heartbeat.py`. `get_worker_by_token` is now a `SELECT` --
authentication no longer writes. Presence is recorded by
`_touch_worker_last_seen` at most once per worker per `LAST_SEEN_INTERVAL_S`
(15 s), and the tests pin: one write across five rapid auths, a second write
once the clock passes the interval, per-worker throttling (two workers do not
share a mark), and that an unknown token records nothing.

**AC3's margin was checked, not assumed.** The only reader of
`workers.last_seen_at` is the "is it online?" judgement, and that window is
`WORKER_ONLINE_MINUTES = 5` in `dashboard/data.ts`. A query against prod's
`pg_proc` confirms **no database function reads the column at all** -- so the
claim gate cannot see a live worker as offline. 15 s against 5 minutes is a 20x
margin.

**AC4 is covered:** a failed presence write forgets its mark, so the next call
retries rather than waiting out the interval on a write that never landed --
tested. A restart loses the in-memory throttle, which costs at most one extra
write per worker and never a stale-forever timestamp.

**Not verified (UAT):**

- **No real worker has authenticated through this path.** Every test fakes the
  database. The whole point of the change is what happens under a polling
  worker's traffic, and that has not been observed once.
- The stall banner ("no capable worker is online") and the workers page were not
  watched while a real agent was live. **That is the UAT step that matters**: if
  the margin reasoning above were wrong, the factory would refuse work while
  agents sat idle.
- The ~940,000-write baseline has no "after" figure yet.
