# US-103.2 — A restarted runner re-adopts the prep it was holding

**Status:** Testing
**Phase:** 103 — A release cannot get stuck
**Depends on:** us-103.1 (the reaper — the floor this story raises), US-63.3 (`release_prep_runs` claim contract), US-59.3 (worker affinity on run resume), US-207 / session resume

## Story

As the manager, when the runner restarts while it is preparing a release, I
want it to pick that release back up rather than idle next to it, so a routine
restart costs a minute instead of a dead release and a manual retry.

In the 2026.08.16.3 incident the runner was **alive and healthy** — last seen
16 seconds before I looked — while the prep it had claimed two and a half hours
earlier sat abandoned. The runner was not stuck; it simply had no idea the row
existed. `release_prep_pool` ([db.py:5387](../apps/api/app/db.py:5387)) selects
`where p.status = 'queued'`, so after a restart the workloop polls, sees an
empty queue, and idles. The job it is holding is invisible to it precisely
because it is holding it.

us-103.1 stops that from being permanent. This story stops it from happening:
a two-hour lease means the reaper's floor is *two hours late*, and a restart is
an ordinary event.

## Design

### The runner asks what it already holds

A fourth release-prep endpoint alongside the three that exist
([worker.py:1378](../apps/api/app/routers/worker.py:1378)): the held-work
question, answered for the calling worker — every `release_prep_runs` row that
is `running` with `worker_id` = me. The workloop asks it once at startup,
before its first pool poll, and re-adopts anything it finds: resume
heartbeating, and hand the job to the module exactly as `run_release_prep`
does after a fresh claim ([workloop.py:835](../apps/runner/supervisor/workloop.py:835)),
minus the claim itself — it is already claimed, by me.

Held work is asked about **at startup only**, not on every poll. A prep this
runner holds and is actively supervising must never be adopted twice; the
in-process registry of live prep tasks is the guard, and startup is the one
moment that registry is provably empty.

### The agent restarts from zero, and that is honest

There is no partial-work resume here and this story does not invent one.
Release prep writes nothing until `submit` — no notes, no test cases, no
deploy. So re-adoption re-runs the job from the beginning against the same
pinned commit, and the only cost of a restart is the tokens the dead session
already spent. `release_prep_runs` keeps one row (the same claim, still held),
so the release detail page's attempt list does not gain a phantom attempt for
work that never stopped being the same attempt.

### When re-adoption is refused

Three cases, each ending in a clean hand-back rather than a second orphan:

- the lease already expired and us-103.1 reaped it — the row is `failed`, so
  the held-work query does not return it and there is nothing to adopt;
- the manager stopped it (us-103.3) — same: not `running`, not returned;
- no module is configured for `release_prep`, or the agent has no model —
  `fail_release_prep`, the same refusal a fresh claim gets today
  ([workloop.py:860](../apps/runner/supervisor/workloop.py:860)).

The rule underneath: re-adoption is never the mechanism by which a stopped
release comes back to life. `status = 'running'` is the sole ticket.

## Acceptance criteria

- **AC1 — the endpoint exists.** `GET /worker/release-prep/held` returns the
  release-prep rows that are `running` and claimed by the calling worker
  (id, release id, version, project, claimed_at, claim_expires_at), scoped by
  the worker's own org and token. It never returns another worker's work.
- **AC2 — the runner re-adopts at startup.** Before its first pool poll the
  workloop asks for held work and supervises each row through the same path a
  fresh claim takes — heartbeat loop running, module invoked with the same
  `release_prep` run context, the same submit/fail outcomes. The claim is not
  re-issued.
- **AC3 — never twice.** A prep already being supervised in this process is
  not re-adopted; the held-work query is asked at startup only, and a test
  pins that a second call while a prep task is live adopts nothing.
- **AC4 — refusals are clean.** No module or no model on re-adoption ⇒
  `fail_release_prep` with the existing wording, so the release lands `failed`
  and Retry is available. A row that was reaped or stopped is not returned by
  the query and is never resumed.
- **AC5 — the attempt history stays true.** Re-adoption creates no new
  `release_prep_runs` row; the release detail page shows one attempt, still
  running, with its original `claimed_at`.
- **AC6 — the lease is re-armed.** The first heartbeat after re-adoption
  extends `claim_expires_at`, so a runner that restarts every hour never
  drifts into us-103.1's reaper while genuinely working.
- **AC7 — tests.** Runner: startup adopts a held prep and drives it to submit;
  adopts nothing when the pool and held sets are empty; fails cleanly with no
  module. API: the endpoint is worker-scoped, returns only `running` rows for
  that worker, and returns nothing for a reaped or stopped prep.

## Out of scope

- Resuming the *agent's session* — no transcript, context, or partial notes
  carry across a restart. The job re-runs from the top.
- Re-adopting ordinary `runs` after a restart (US-59.3 / session resume own
  that, and their machinery is not being extended here).
- Handing a held prep to a **different** worker — affinity is the point; if
  this runner never comes back, us-103.1's reaper is the answer.
- Shortening the two-hour lease.
- Any UI. What the manager sees while a prep is live is us-103.4.

## Built (2026-08-16)

`GET /worker/release-prep/held` (apps/api/app/routers/worker.py) answers with
the preps this worker holds, carrying the identical briefing a claim returns -
`release_prep.briefing` was extracted from `release_prep.claim` for exactly
that, so a re-adopted job runs with the project's Release instruction rather
than without it. The route is declared **before** `/release-prep/{prep_id}`,
since FastAPI matches in order and a literal path registered after a
parameterised one is never reached. On the runner, `run_release_prep` split
into claim + `_supervise_release_prep`, `adopt_held_release_preps` runs once
before the first poll, and `_live_preps` guards against supervising anything
twice.

**Verified.** Runner suite: 333 passed, including nine new tests - adoption
without re-claiming, the briefing arriving with it, the end-to-end drive to a
verified submit, a job that exits without submitting still being failed rather
than orphaned again, the double-supervision guard, a failing held query not
blocking startup, no-module failing cleanly, adoption preceding the first
poll, and adoption happening once per process. API essential: 1925 passed,
including five endpoint tests (worker scoping, the briefing, empty, auth, and
the route-order trap).

**Not verified.** No real runner was restarted mid-prep against a live API -
the proof is the unit path, not the field. The API-side held query
(`list_held_release_preps`) is covered only in the Full QA file that could not
run here.
