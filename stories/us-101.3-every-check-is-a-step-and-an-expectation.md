# US-101.3 — Every check is a step and an expectation

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** us-101.2 (a case must have a section before one can be required)

## Story

As the manager, the reason UAT costs me an afternoon is that a test case
reads "Merge chore dispatch" and I have to reconstruct what to do and what
should happen. The case I want reads:

> Tick two branches, then reload the page.
> **Expect** — both still ticked, and the count line reads "2 branches will
> land onto *main*, all of them or none."

Two sentences. One is an instruction, one is an observation. A tester who has
never seen the story can execute it, and — this is the part that matters —
I can confirm it without a conversation.

Nothing today asks for that. `test_cases` on hand-back is **optional and
completely unvalidated**: `attach_release_test_cases`
([db.py](../apps/api/app/db.py) L1437–1482) requires a title, truncates it to
500 characters, **silently drops** any case whose title is blank, and accepts
`steps` and `expected_result` as free text with no format, no length, and no
requirement that they exist at all. A release can ship with zero cases, or
with fifteen titles and nothing behind them, and every layer above will treat
it as a finished job.

The refusal is the fix, but it has to be a careful one, and Phase 100 sharpened
that. us-100.6 added versioning to this same hand-back and named the risk in
its own AC4: *"`release` already carries several responsibilities, and this
adds a fourth. If the hand-back starts refusing for reasons that have nothing
to do with each other, that is the signal the split was wrong after all."*
This story adds a fifth reason to refuse. So the rule must be one a re-read
genuinely fixes — "this case has no expected result" is that; "this expected
result is not specific enough" is not — and the refusals must be legible as a
set rather than arriving one at a time across successive re-runs.

## Acceptance criteria

- **AC1 — a case without both halves is refused.** Every submitted case needs
  a non-empty `steps` and a non-empty `expected_result`. Neither may be a
  restatement of the title. A blank title stops being silently dropped and
  becomes a named refusal.

- **AC2 — a release needs checks at all.** Handing back zero cases is
  refused. The floor is a real number, stated in the refusal, and it scales
  with the release rather than being a flat constant an agent can satisfy with
  one case for a fifteen-story release — every included work item is either
  covered by at least one case the agent authored, or already covered by a
  case it will inherit (which us-101.1 lets it see), or explicitly named as
  deliberately uncovered.

- **AC3 — the refusal teaches the shape, and arrives all at once.** A rejected
  hand-back names every offending case in one response, says which half each
  is missing, and shows the two-part form. It does not stop at the first
  problem: a re-run costs a whole agent session, and discovering the second
  rule after fixing the first costs two. This is the house style set by
  `report_merge_failure`, where the text that comes back is the whole of what
  the next attempt knows.

- **AC4 — the rule lives at the choke point, alongside the others.**
  [release_prep.py](../apps/api/app/release_prep.py) `submit` (L32–183)
  validates, so both transports are governed by construction rather than by
  two copies of the same check. It runs with the existing checks — notes
  present, then the version-in-first-line rule (L65–71) — and before any case
  is written or any deploy fires, so a refused hand-back never half-completes
  the job. That ordering is the property us-100.6 established for the version
  proposal and it must hold for this too.

- **AC5 — steps render as written.** Case steps are rendered as markdown, not
  as preformatted text
  ([release-test-cases.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/release-test-cases.tsx)
  L258–265), so a numbered list is a numbered list. This is the one place in
  the product that already asks for "numbered markdown steps"
  ([llm.py](../apps/api/app/llm.py) L113) and then displays the markers raw.

- **AC6 — existing releases still open.** Cases already attached, from before
  this rule, are not retro-validated and their pages do not change behavior.
  The rule governs hand-back, not storage.

- **AC7 — the accumulating hand-back is watched, not ignored.** With this
  story `submit_release_notes` can refuse for five unrelated reasons: notes
  missing, version not in the title line, a bad version proposal, a case
  without its halves, and coverage below the floor. That is us-100.6's warning
  sign arriving. This story does not split the run — but it records the count,
  and the first time a real release bounces twice for two unrelated reasons,
  the split is the next story rather than a surprise.

## Out of scope

- Judging whether an expected result is *good*. The gate is structural. A
  vague expectation is a manager's send-back, not a 422.
- The notes themselves — us-101.4.
- Splitting the release run into separate versioning / notes / cases phases.
  Named as a watch item in AC7, deliberately not done here.
- Automated cases, suites, and `always_on_uat` inheritance (migration 242);
  those arrive already-shaped and are not what the agent authors.
- Raising the bar on inherited cases written before this story.
