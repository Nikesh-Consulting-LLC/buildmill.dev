# US-118.6 — The catalog carries the five CRE demo templates

**Status:** Testing
**Phase:** 118 — A template shows its face
**Depends on:** US-118.1 (a template carries a markdown description, a
category and a `builtin/<name>` cover; the `BUILTIN_COVERS` registry in
`lib/template-cover.ts`), migration 227 (`project_templates` /
`project_template_sections`, the Default template), 265–267 (a template
carries `agent_instructions`; a copy carries it too), US-114.1 (the admin
page's Duplicate, and its rule that a copy takes only the
`worker_instruction` sections), the five demo docs under
[docs/demos/cre/](../docs/demos/cre/README.md) (their §4 *Agent Instructions*
blocks are the documents this story seeds)

## Story

As the platform admin preparing the commercial-real-estate demos, I want
the catalog to hold one template per demo — the Default template's shape,
with the Agent Instructions document and every per-task file rewritten for
that project — so that a manager creating a demo project picks the card,
gets AGENTS.md and the sixteen `.buildmill/*.md` files already speaking dbt,
TMDL, rent rolls, waterfalls or evals, and no one pastes twenty kilobytes of
markdown out of a doc.

## Design

### Five copies of Default

A data migration inserts five `project_templates` rows, each built the way
the admin page's **Duplicate** builds one (`duplicate_project_template` in
`apps/api/app/routers/admin.py`): the row's face, its `agent_instructions`,
and its `worker_instruction` sections — never the retired guideline and
prompt rows.

| key | name | category | cover | doc |
|---|---|---|---|---|
| `cre-report-conversion` | CRE · Legacy report conversion (dbt) | Data platform | `builtin/data-pipeline` | [01](../docs/demos/cre/01-legacy-report-conversion.md) |
| `cre-power-bi-model` | CRE · Power BI semantic model as code | Data platform | `builtin/bi-model` | [02](../docs/demos/cre/02-power-bi-as-code.md) |
| `cre-rent-roll-normalizer` | CRE · Rent roll & T-12 normalizer | Data platform | `builtin/spreadsheet` | [03](../docs/demos/cre/03-rent-roll-normalizer.md) |
| `cre-waterfall-calculator` | CRE · Waterfall & promote calculator | CRE applications | `builtin/finance-model` | [04](../docs/demos/cre/04-waterfall-calculator.md) |
| `cre-text-to-sql-evals` | CRE · Text-to-SQL agent with evals | AI systems | `builtin/assistant` | [05](../docs/demos/cre/05-text-to-sql-evals.md) |

The **description** is the doc's template card (short markdown, bold on the
one thing that distinguishes it). The **document** (`agent_instructions`,
what a project created from the template gets as AGENTS.md) is the doc's
§4 block verbatim — Project overview, Tech stack, Commands, Run commands,
Testing expectations, Environment setup, Things to avoid, Permissions or
boundaries — followed by the Default template's own document (Working with
Build Mill, Versioning & Release), so the project still knows how the
factory works. Each of the ten **per-task files** (prd, plan, code, release,
breakdown, test, deploy, guidelines, elaborate, wireframe) is the Default's
text with one project-specific paragraph in front: what a feature is in
this repo, what a plan must name, what a code run must and must not touch,
which command proves the work, and — for the four projects with no UI —
that a wireframe run hands back `no_ui_surface`.

`sort_order` 10–14 puts them after the three general templates. The
migration is idempotent and conservative: a key already present is left
alone (an admin who edited one keeps it); sections are copied only for a
row the migration created; nothing touches an org's copies — a manager adds
a catalog template to their org from Settings → Project templates, exactly
as for Generic Web App today.

### Five covers

Five built-in covers join the registry so each demo has its own face
without a Storage upload: `data-pipeline` (a document flowing into a
checked table), `bi-model` (a bar chart beside a code tag), `spreadsheet` (a
grid with a highlighted total row), `finance-model` (a waterfall chart),
`assistant` (a question bubble and a reply carrying SQL). Same 320×160
palette and geometry as the six from US-118.1. A new test pins every
registered name to a shipped `public/template-covers/<name>.svg`, so a
registry entry with no file behind it — a broken image on every card that
picked it — fails `npm run test:web` instead of shipping.

### What is not built

The templates are catalog rows; nothing seeds them into an org, registers
a pre-submit gate, project environment, suite or deployment — those are
project settings a manager applies after creating the project (each doc's
§5 lists them). No demo repository is created; the documents describe the
scaffold each doc's §3 lays out, and the guidelines-refresh run adjusts the
files once a real repo exists.

## Acceptance criteria

1. **Admin → Project templates** lists five new cards after Default,
   Generic Web App and Python + Next.JS: *CRE · Legacy report conversion
   (dbt)*, *CRE · Power BI semantic model as code*, *CRE · Rent roll & T-12
   normalizer*, *CRE · Waterfall & promote calculator*, *CRE · Text-to-SQL
   agent with evals* — each with its own cover (not a monogram), its
   category chip, and a one-line markdown description that names what
   distinguishes it.
2. Opening a card's files shows **AGENTS.md** beginning `## Project
   overview` for that project and ending with the Default's *Working with
   Build Mill* and *Versioning & Release* sections, and **10 of 16** files
   with content: `PRD.md`, `Plan.md`, `Code.md`, `Release_Prep.md`,
   `Breakdown.md`, `Test.md`, `Deploy.md`, `Guidelines_Refresh.md`,
   `Elaborate.md`, `Wireframe.md` — each opening with a paragraph about this
   project and continuing with the Default's text.
3. **Settings → Project templates → Add from catalog** offers the five; a
   copy made from one carries the same face and files, and a project created
   from that copy starts with that AGENTS.md and those files (US-114 /
   migration 266 behavior, unchanged).
4. The five covers appear in the details dialog's built-in picker with a
   label each, and `npm run test:web` fails if a registered cover has no SVG.
5. Re-running the migration changes nothing (every key already present is
   left alone, and no section is duplicated).
6. Both Supabase projects hold the five rows with 10 `worker_instruction`
   sections each and no `guideline` or `prompt` sections.

## Out of scope

- Seeding the templates into any org, or into existing projects.
- Creating the demo repositories, or any project setting (gate, env, suite,
  deployment) the docs' §5 describe.
- New instruction kinds: only the ten kinds the Default template carries
  are seeded; the other six files stay blank and fall back to the factory
  default, as for every template today.
- Changing the three general templates' content (US-118.5 handles the wider
  cover set; migration 285 handled their faces).
