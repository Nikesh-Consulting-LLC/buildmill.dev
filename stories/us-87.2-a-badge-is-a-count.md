# US-87.2 — A badge is a count, not a dataset

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** us-87.1 (the shell asks once)

## Story

As anyone using the app, the sidebar badge showing how many things need me
costs eight org-wide queries to produce — the full Things-to-Do dataset:
every waiting issue with its epic and project joins, every UAT release,
every active PRD run, every open clarification, every pending
recommendation, every refresh, every parked run, every dispatch block —
fetched, mapped, grouped, and then reduced to a single integer.

It is the most-executed application query in the database (19,967 calls,
134 s measured on prod over six weeks), and it is unbounded: it scales with
the size of the workspace, not with the size of the answer. At 100s of
projects the badge alone is a heavier query than any page.

A count should cost a count.

## Acceptance criteria

- **AC1 — one cheap call.** The shell badge is produced by a single
  `security definer` RPC (`org_pending_count(p_org uuid)`) that returns an
  integer, or by count-only queries that fetch no rows. No issue bodies, no
  joins for display, no grouping.
- **AC2 — the number is identical.** For any workspace state, the RPC
  returns exactly what `loadWaiting(...).pendingCount` returns today. The
  story ships a test that asserts the two agree across the fixture states
  (waiting issues, UAT releases, clarifications, recommendations, refreshes)
  — the badge and the Things to Do page header disagreeing is the failure
  this replaces, and the shared definition must survive the optimization.
- **AC3 — the definition stays single.** `loadWaiting` remains the one
  definition for the *page*; the RPC is derived from it and lives beside it,
  with a comment naming the other as its twin. Two drifting definitions of
  "pending" is a worse outcome than a slow badge.
- **AC4 — org-scoped and RLS-safe.** The RPC is `security definer` with a
  membership check on `p_org` (the `is_org_member` helper), so it cannot
  count another workspace's work.
- **AC5 — proof.** Measured execution time of the badge path before and
  after, recorded in the story, on a workspace with at least 20 projects
  (seed if prod does not have them).
- **AC6 — applied to both projects.** The migration lands in
  `infra/supabase/migrations/`, is applied to **prod and dev**, and
  `database.types.ts` is regenerated.

## Out of scope

- Changing what counts as "pending".
- The Things to Do page's own loading — it still needs the full dataset and
  keeps `loadWaiting`.
- Caching the count across requests (a stale badge is a bug report).

## Verification record

Built 2026-08-12 on `phase-87-performance`. Migration 249, applied to **both**
prod and dev; `database.types.ts` regenerated.

**Verified:** `org_pending_count` mirrors `loadWaiting`'s `pendingCount` group
for group -- Reviews, QA sign-offs, Fix & retry, Dispatch (including US-22.10's
feature-owns-build exclusion and US-14.6's ready-feature guard), Triage, ad-hoc
recommendations, ready refreshes, open clarifications. Its per-group counts
were run against prod's live data for all nine organizations before wiring, and
returned plausible non-zero numbers (Kaushleshchandel's Workspace: 4 reviews,
1 fix, 3 dispatch). `security definer` with an `is_org_member` gate.
`npm run build` clean.

**Not verified (UAT):**

- **AC2's equality test does not exist.** The story asked for a test asserting
  the RPC and `loadWaiting().pendingCount` agree across fixture states. What
  shipped is a structural mirror plus a live spot-check, with both sides
  carrying a comment naming the other. That is weaker than what AC2 demanded,
  and the drift it was meant to catch is now caught only by review. A follow-up
  story should add that test -- it is the one guard that makes keeping two
  definitions in step verifiable rather than hoped for.
- The badge has not been compared against the Things to Do header in a browser.
  That is the highest-value UAT step here: they must show the same number.
