# US-100.5 — The refresh run proposes a document, not sections

**Status:** Completed
**Phase:** 100 — One document, not twenty-two sections
**Depends on:** us-100.1 (sections are gone)

## Story

As the manager, an agent can propose changes to my project's conventions —
that is the `guidelines` run kind, and two MCP tools behind it:
`submit_guidelines_refresh(run_id, summary, sections)` and
`recommend_guideline_change(proposed_text, rationale, severity, section_key)`
([factory_mcp.py](../apps/api/app/factory_mcp.py) L3724, L3242). Both are
**section-addressed**: an agent names a `section_key` and proposes text for
it.

With one document there is no key to name. Left alone, the refresh run keeps
writing to a table nothing reads, and the learning loop this factory has —
agents noticing that the conventions are wrong and saying so — quietly stops
working while still appearing to run.

So it is reworked to the shape the content now has: an agent proposes a
**revised document**, with a summary of what it changed and why, and the
manager accepts or rejects it whole.

## Acceptance criteria

- **AC0 — the refresh keeps existing, and studies the repository.** Confirmed
  by the manager, 2026-08-15, when it would have been reasonable to retire it
  instead: the run reads the actual repository and recommends changes to the
  `.md` files so they fit what the project really is. That is the point of
  the loop — instructions drift from the code they describe, and an agent
  working in the repo is the participant best placed to notice.

- **AC1 — the proposal covers the whole published set.**
  `submit_guidelines_refresh` takes the proposed **Agent Instructions** in
  full *and* proposed replacements for any of the per-task instructions —
  the same set that publishes to `.buildmill/*.md` (us-99.1). The refresh run
  exists to improve what agents are told, and after Phase 99 that is more
  than one document: an agent that keeps tripping over a vague `Code.md`
  should be able to propose a better `Code.md`, not only a note in the
  conventions. The `sections` parameter retires; each proposed instruction is
  addressed by its **kind**, which is a real key with a file behind it.
  A proposal identical to what is already there is refused rather than
  creating an empty one.

- **AC1b — one refresh, many files, one decision.** A refresh is accepted or
  rejected whole, not file by file. It is one agent's coherent read of what
  is wrong with this project's instructions; splitting it into per-file votes
  would let a manager accept a change that only makes sense alongside another.

- **AC2 — the recommendation follows.** `recommend_guideline_change` loses
  `section_key`; a recommendation is a proposed change to the document with
  its rationale and severity, and still reaches the manager the way it does
  today.

- **AC3 — the manager sees a diff per file, not a wall.** The review surface
  shows what the proposal changes against each current file — the Agent
  Instructions and every per-task instruction it touches. Accepting writes
  them all and leaves the project **unpublished** (us-99.4) — a refresh must
  not put a commit in the repository on its own, which matters more here
  because it can now change many files at once.

- **AC4 — the run kind keeps its name and its file.** `guidelines` stays a
  run kind and `Guidelines_Refresh.md` stays its instruction file (us-99.1);
  only the shape of what it submits changes. Its default instruction text is
  rewritten to describe proposing a document.

- **AC5 — nothing silently no-ops.** If any part of this is deferred, the run
  kind is disabled rather than left dispatchable against a shape it can no
  longer produce. A kind that runs, succeeds, and changes nothing is worse
  than one that refuses.

- **AC6 — the surface is pinned and documented.** Changed tools go into
  `test_all_tools_listed`, the server `instructions` blob, and
  [interface-catalog.md](../docs/application/interface-catalog.md) — which is
  also still claiming 36 tools when there are 53 (us-99.5's uncorrected AC7).

- **AC7 — tests.** Essential: AC1's full-document submission and its
  no-change refusal; AC2's reshaped recommendation; AC3's
  accept-leaves-unpublished.

## Partially built (2026-08-15) — AC5 only, deliberately

**AC5 is done; AC1, AC1b, AC2, AC3, AC4, AC6 and AC7 are not.** The story
anticipated exactly this and said what to do about it: *"If any part of this
is deferred, the run kind is disabled rather than left dispatchable against a
shape it can no longer produce."*

- **The refresh is disabled at both ends.** `POST
  /projects/{id}/guidelines/refresh` answers **409** with a reason and a
  next step, and `submit_guidelines_refresh` refuses any run queued before
  that landed. Pinned by a test asserting the refusal names Agent
  Instructions, because a refusal that does not say what to do instead is
  just a dead button.
- **Why disabling was the correct partial step.** The tool is
  section-addressed and us-100.1 retired sections. Left dispatchable, a
  refresh would run, succeed, and write proposals into
  `project_guidelines` — a table nothing has read since migration 263. The
  manager would see a completed refresh that changed nothing an agent reads.
  That is the same silent-dead-write hazard us-100.1 opened and closed
  earlier the same day; recreating it knowingly would have been worse than
  the first time.
- **Reshaping the tool alone would not have been safe.** The signature is the
  small part; the storage (`record_guidelines_refresh`) and the accept path
  are both section-shaped too, and changing only the front would have left
  proposals landing in the dead table with the API *looking* correct.
- api Essential green (**1797 passed, 545 skipped, 0 failed**).

**Picked up the same day (below).**

## Built (2026-08-15, second pass) — the reshape

**AC0/AC1 — whole files, keyed by file.** `submit_guidelines_refresh(run_id,
summary, files)` — `files` is `[{key, proposed_text, rationale, severity}]`,
`key` = `agents` (AGENTS.md) or a run kind (its `.buildmill/*.md`; a path is
accepted and normalised). The `sections` parameter is gone. Refused: a key
that names no file (the old catalog keys included), the same file twice, a
file **identical** to what the project holds, a per-task file when the
run's scope is `document`, a file with no rationale. `[]` remains the legal
"nothing to propose". The brief (`get_work_context`) carries the current
Agent Instructions and every per-task file **read live at claim time**, not
snapshotted at dispatch — the pending prod refresh from 2026-08-10, queued
under the old shape, therefore proposes against today's files when claimed.

**AC1b — one decision.** Migration **268**: `decide_guidelines_refresh(
p_refresh, p_accept, p_note)` applies or rejects every pending row in one
transaction through the per-row `decide_guideline_recommendation`, which now
writes by file — `agents` → `projects.agent_instructions`, a kind →
`worker_instructions` (upsert, attributed to the deciding manager). Legacy
section rows (`section_id` set) still write `project_guidelines`, so nothing
already queued becomes undecidable (prod has none pending). Storage is the
same two tables; `section_key`/`section_title` now mean file key / repo path,
recorded as column comments.

**AC2 — the recommendation follows.** `recommend_guideline_change(
proposed_text, rationale, severity)` — no `section_key`; it proposes the
full Agent Instructions document, refuses an identical one, records under
`agents`. Ad-hoc cards decide through the same RPC as the bundle.

**AC3 — a diff per file, one button, unpublished.** The review page
(`/projects/[id]/guidelines/refresh/[refreshId]`) shows each proposed file
against what the project holds now — `AGENTS.md` first, then the per-task
files in the project's group order — as a unified diff (`+n −m` in the
header) with **Apply all** / **Reject pass**. Proposed text is editable
before applying (the edit is what is written). Accept writes the factory's
text and **publishes nothing**; the closed pass offers "Review and publish"
which lands on the Agent Instructions tab. Diffs come from
[line-diff.ts](../apps/web/src/lib/line-diff.ts) (LCS, no dependency)
rendered by the existing `DiffView`.

**AC4 — name and file kept; the default text speaks files.** `guidelines`
stays the kind, `Guidelines_Refresh.md` its file. Migration **269** rewrites
the baked default (and, for us-100.6's gap, the `release` default: propose a
version from the Agent Instructions' rules with a rationale) with the same
hash-guarded splice as 261, and backfills every project row and template
section that still held the old text verbatim — prod: **10/10** projects for
both kinds, 2 platform + 16 org template sections. Edited rows untouched.

**AC5 — the refusals are gone.** `POST /projects/{id}/guidelines/refresh`
dispatches again (scope `all` | `document`; `existing` reads as `document`);
`submit_guidelines_refresh` no longer refuses. Dialog copy: "Refresh
instructions", scopes "Agent Instructions and the per-task files" /
"Agent Instructions only".

**AC6 — pinned and documented.** Interface catalog: both tools rewritten,
the `refresh` route added, and the tool count corrected **36 → 53** (us-99.5
AC7's uncorrected number). Help copy (web + api mirrors) now says Agent
Instructions / Task Instructions and describes the refresh — us-100.3's
open gap. Agent role label: "Instructions refresh".

### UAT

1. Project → Agent Instructions tab → **Refresh instructions** → pick a
   scope, dispatch → a `guidelines` run appears queued (rank −1).
2. Let an agent claim it: `get_work_context` shows the current AGENTS.md
   body and every per-task file; `submit_guidelines_refresh` with two files
   (one `agents`, one `code`) succeeds; with `deployment` as a key → refused
   naming the file list; with text identical to the current → refused.
3. Things to Do → "Instructions refresh" card → "N files proposed — one
   decision" → open: a diff card per file, `+n −m`, Apply all / Reject pass.
4. Apply all → toast "Instructions updated … Publish when ready"; the Agent
   Instructions tab shows the new text and reads **unpublished**; the repo
   is unchanged until Save instructions.
5. Agent settings → Planning role lists "Instructions refresh".

## Out of scope

- Auto-accepting a proposal under any condition.
- `project_learnings` and `submit_learning`, which are a different loop and
  unchanged.
- Retiring the `guidelines` run kind — considered and rejected: the loop is
  worth keeping, it just needs the right shape.
