# US-116.7 — The org's default model counts

**Status:** New
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.1 (sessions resolve through `run_settings.resolve`, so
one floor serves both), US-32.7 (the one resolver), US-32.8 (a run whose model
no provider offers is failed at claim, naming the model), US-66.1 (per-kind
pins), US-78.5 (no model, no run — never a CLI's own default), Settings → LLM
providers (a default provider with a `default_model`, and the gateway's
existing fallback to it, US-27.8)

## Story

As the manager, I want the default model I set on the org's default LLM
provider to be the model an agent uses when nobody pinned one — for runs and
for sessions — so that "no model to reason with" is only ever true when I
have genuinely chosen nothing, and so that a wizard-created agent runs on the
first dispatch instead of failing it.

## Design

### The org already has a default model; the resolver does not look at it

`run_settings.resolve` (`run_settings.py:114-182`) climbs: the agent's route
preset → the org's default preset → the agent's per-kind pin → the legacy
`model_routes[kind]`. On prod today every org's default preset is **"Balanced"
with `model: null`**, `platform_run_config.model_routes` is `{}` (the us-78.5
AC3 gap APPLICATION.md records at 319–323), and a wizard-created agent has no
pin. So the chain yields nothing for five of six live agents, and:

- a run is **claimed anyway** — `stamp_run_settings` only checks routability
  *if* a model resolved (`worker.py:226-242`) — the runner spawns, refuses
  with *"this agent has no model to reason with … nothing was spent"*, and the
  run fails (`agent_failures`: NexDB.Architect, `guidelines`, 2026-08-17 10:00,
  "Repair exhausted after 1 attempt");
- a session is refused (us-116.1 fixes which kinds are asked; the answer is
  still nothing).

Meanwhile the manager *did* choose a model. Settings → LLM providers has a
default provider with a `default_model` — on prod, Sandy's Workspace's default
is xAI with `grok-4.6`; Nikesh Consulting's is Groq with `llama-3.3-70b`. The
gateway already honours it: a key that carries no model is answered by the
org's default provider and its model, and traced as such
(`llm_gateway.py:347-358`). Two layers, two rules: the resolver says *no model
→ refuse*, the gateway says *no model → the org's default*. The manager sees
only the first.

### The floor is the org's default provider's model

`resolve()` gains a last tier below the legacy `model_routes` value:

```
… > agent pin > legacy model_routes[kind] > org default provider's default_model
```

recorded in `settings_sources` as `org-default-provider` — so a finished run
still says who decided — and read by the same caller-built arguments us-116.1
introduces, so runs and sessions get it identically. It is a *floor*, never a
ceiling: anything above it that named a model still wins, and an explicit
named-preset route keeps its preset's model exactly as US-66.1 says.

**Why this is not what US-78.5 forbade.** US-78.5's rule was written against
the CLI's *own* built-in default — a model nobody in the org chose, on a bill
nobody agreed to. The org's default provider model is chosen, by the manager,
on the page whose whole purpose is choosing it, and it is already the model
the gateway would use for that org's brain calls. The refusal stays for the
case US-78.5 meant: no pin, no preset model, **and no default provider model**.
That message names the third place too:

> **NexDB.DevOps** has no model for any of the roles it claims (Release,
> Deploy). Set one under Model per role, give the org's default preset a
> model, or set a default model on the org's default LLM provider (Settings →
> LLM providers).

### Refuse at claim, not on the machine

When even the floor is empty, `stamp_run_settings` refuses the way US-32.8's
unroutable-model case already does: `fail_run_minimal` with the sentence
above, a 409 to the runner, no spawn. The runner's own refusal
(`interactive.py:483-500`, us-116.3's shared routine) stays as the last line
of defence, but a manager should learn "no model" from the roster
(us-116.2), then at claim, and never from a run that occupied an agent to say
nothing was spent.

### The known gap closes

APPLICATION.md's Phase 78 gap — *"an interactive agent created by the wizard
resolves a model from nowhere … choosing a fleet-wide default is a superadmin
decision about which model and whose money"* — closes without a platform-wide
model: each org's own default provider model is that org's fleet default,
chosen by that org, billed to that org's key. `platform_run_config.model_routes`
stays empty and stops mattering.

## Acceptance criteria

1. An agent with no route preset, no pin and an org default preset with
   `model: null`, in an org whose default LLM provider has a `default_model`,
   claims a run that resolves to that model; `settings_sources.model` reads
   `org-default-provider`; the run executes. On prod's data: **DevOps** and
   **NexDB.DevOps** dispatch and run without any per-agent change.
2. The same agent opens a session on that model (through us-116.1's path).
3. Any tier above the floor that names a model still wins: an agent pin, a
   preset model, a manager override — pinned by resolver tests for each,
   including that a named-preset route beats the floor and the pin.
4. In an org with **no** default provider model, the run is failed at claim
   with the three-place message and a 409 to the runner; the runner never
   spawns a CLI (no `agent_failures` row of the runner's making, no
   `run_trace` from the machine). The session refusal carries the same
   sentence.
5. `worker_idle_reason`'s `no-model` (us-116.2) and the wizard's warning
   (us-116.6) use the same floor — one definition of "no model", pinned by a
   test that fails if the roster and the resolver can disagree.
6. APPLICATION.md's Phase 78 gap paragraph is updated to say how it closed.
7. `cd apps/api && python -m pytest` covers the floor, its source label, the
   precedence above it, the claim-time refusal, and the session path.

## Out of scope

- **Giving "Balanced" a model.** Still the manager's call — us-116.1/116.2 say
  why; with the floor in place it stops being urgent.
- **A platform-wide default model** (`platform_run_config.model_routes`). Not
  needed once each org's own default counts; leaving it empty is the point.
- **The CLI's own default.** Still refused, still US-78.5.
- **Provider routability.** US-32.8's check runs on the floored model too; if
  the org's default model is offered by no provider, that existing refusal
  fires — this story adds no new case there.
