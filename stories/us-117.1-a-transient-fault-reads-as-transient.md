# US-117.1 — A transient fault reads as transient

**Status:** Testing
**Phase:** 117 — A transient fault reads as transient
**Depends on:** US-79.5 (`SupabaseUnreachable` and its 504 handler), US-10.8
(the self-repair loop), US-54.2 (destructive repairs fire only on genuine
failure phrasings), US-3.12 (the git proxy's auth gate), us-108.1 BUG-12
(written, retired unbuilt 2026-08-17 — this story carries its live half)

## Story

As the manager, I want a passing infrastructure fault to say it is one, so
that a two-minute network blip does not read as a permissions problem, an
unexplained 500, and a fleet that gives up without retrying.

## Design

### One fault, three wrong answers

On 2026-08-17 the prod API intermittently could not reach Supabase — 13
recorded transport failures between 23:37 and 23:49 UTC (`ReadError` ×7,
`SupabaseUnreachable … during RPC has_org_capability (ConnectTimeout)` ×3,
`ConnectTimeout` ×1, `RemoteProtocolError` ×2). Supabase itself was healthy:
its REST endpoint answered from a third machine in ~0.1s throughout.

That single fault reached the manager as three unrelated-looking problems:

| Surface | What it said | Why |
|---|---|---|
| Agent run | `git ls-remote failed: … returned error: 500` | `gitproxy.py` has **no** `except httpx.*` at all — an unreachable upstream is an unhandled exception |
| Start a session | **"You cannot run work in this workspace."** | `agent_sessions._require_develop` wraps the capability RPC in `except Exception: ok = False` |
| Self-repair | `unrecoverable — nothing to change → not attempted` | `repair.classify` matches no needle for an HTTP 5xx, so it falls to the catch-all |

The middle one is the worst: the manager is an active **owner** of that
workspace, `is_approved_user()` is true, and `owner → develop` is
`allowed = true`. Every input to the check said yes. The refusal claimed a
permission verdict it had never actually reached.

### Why the repair loop sat still

`classify()` checks `_RECLONE`, then `_REINSTALL`, then `_WAIT`, then defaults
to `unrecoverable`. Run the real error text through them and nothing matches:
`_RECLONE` names `git clone/fetch/checkout/reset/pull failed` but not
`ls-remote`; `_WAIT` names `timeout`, `connection`, `network` — while git's
phrasing for a server error is `The requested URL returned error: 500`.

`_WAIT` exists for exactly this class; its own comment cites "a factory-api
restart during a deploy". It simply cannot see an HTTP status.

**The 5xx test runs before `_RECLONE`, not after.** A server-side 5xx is never
fixed by deleting the workspace, and US-54.2 is on record about what a
destructive repair firing on the wrong needle costs — 41 turns of written code,
2026-07-30. Ordering it first is the whole safety argument.

### Two transport errors nobody was catching

`supabase._TRANSPORT_FAILURES` lists `ConnectTimeout`, `ConnectError`,
`ReadTimeout`, `PoolTimeout` — but **not** `ReadError` or
`RemoteProtocolError`, which were 9 of last night's 13. That is why some
reports are titled `SupabaseUnreachable: … (ConnectTimeout)` with the operation
attached, and others are a bare `ReadError` traceback: the same outage, half of
it legible and half of it not.

## Acceptance criteria

- **AC1 — a server error is waited out, not given up on.** `repair.classify`
  returns `wait` for an HTTP 5xx failure (git's `returned error: 5xx`, and the
  bare status names — bad gateway, service unavailable, gateway timeout,
  internal server error). Pinned by a test using the **verbatim** production
  error string from 2026-08-17.
- **AC2 — a 5xx never triggers a destructive repair.** The 5xx test runs before
  the `_RECLONE` scan, so a message containing both a git verb and a server
  error waits instead of wiping the workspace. Pinned by a test with
  `git fetch failed … returned error: 502`.
- **AC3 — `ls-remote` is a recognised git failure.** `git ls-remote failed` is
  matched, so a genuinely broken remote is classified rather than defaulting to
  `unrecoverable`. It is **not** added to `_RECLONE`: recloning does not fix a
  remote that will not answer.
- **AC4 — a refusal never claims a verdict it did not reach.**
  `_require_develop` no longer catches the RPC's failure. A `False` answer is
  still **403 "You cannot run work in this workspace."**; an *unanswered* check
  raises and is served by the existing US-79.5 handler as **504** naming the
  operation. Pinned by two tests — one where the RPC returns `False`, one where
  it raises.
- **AC5 — the git proxy says which upstream did not answer.** A transport
  failure reaching out of `gitproxy` answers **504** with a detail naming the
  upstream, instead of an unhandled 500. The US-3.12 existence-leak rule is
  untouched: an unauthorised project still answers 404.
- **AC6 — the two missing transport errors are caught.** `ReadError` and
  `RemoteProtocolError` join `_TRANSPORT_FAILURES`, so they become
  `SupabaseUnreachable` with the operation attached rather than a raw
  traceback. Pinned by a test per class.
- **AC7 — Essential.** Every test above runs in the ~30s Essential suite with
  reads faked; none needs `DATABASE_URL` or the network. The repair tests run
  in the runner's own suite.

## Out of scope

- **The connectivity fault itself.** Whatever makes the GCP VM's link to
  Supabase stall is not addressed here; this story stops one blip from
  producing three misleading answers. If it recurs the box needs looking at.
- **Retrying writes.** US-79.5's rule stands: reads retry once, writes never —
  a timeout does not prove the write failed.
- **`llm_gateway`'s half of BUG-12.** Same shape, separate surface, and it did
  not fire last night. Worth its own story rather than a speculative edit here.
- **The `_WAIT` time budget** (60s retry, 600s ceiling) — inherited unchanged.
- **Anything about `has_org_capability`'s own definition** or the role matrix.
