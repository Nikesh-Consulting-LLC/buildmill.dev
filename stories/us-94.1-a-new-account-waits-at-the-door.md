# US-94.1 — A new account waits at the door

**Status:** Testing
**Phase:** 94 — The beta gate
**Depends on:** nothing (touches the surfaces us-91.10 gave SuperAdmin)

## Story

As the manager, buildmill.dev now invites people in — and the app will let
anyone who signs up straight through. The factory is in beta and runs on
real capacity: every account that gets in dispatches real agents on real
machines. I want the door to open only when I nod.

A new signup should be able to create their account and log in — and then
wait. Not at an error, not at a broken dashboard: at a gate that says
plainly what is happening. Build Mill is in beta; due to capacity, every
account goes through approval; you'll be let in when a seat opens. The
superadmin sees the queue of waiting accounts and approves each one
deliberately. Until that happens, a pending account gets nothing — no
workspace, no data, no API surface — and that must be enforced where
enforcement is real, not painted on the client.

## Acceptance criteria

- **AC1 — a new account starts pending.** Every signup after this ships
  lands in a pending state. Pending users can authenticate (their login
  works, their session is real) but every app surface routes them to the
  gate page — deep links included.
- **AC2 — the gate says what's happening, kindly.** One screen, brand on
  it: Build Mill is in **beta**; due to capacity, **every account goes
  through approval**; you'll get an email address to reach us and a way to
  **log out**. No countdown promises, no support-ticket theater. The copy
  is part of this story's UAT — pin it before build in the plan.
- **AC3 — enforcement is server-side.** A pending user who skips the UI
  and calls Supabase directly reads at most their own profile and their
  own pending status; org data, projects, and the API's orchestration
  surfaces refuse. If it is only a redirect in the web app, this story is
  not done.
- **AC4 — SuperAdmin sees the queue.** The us-91.10 **Accounts** menu
  gains the pending list: email, name if given, signup time, ordered
  oldest first, with an **Approve** action per row. An empty queue says
  so. Approval takes effect on the user's next page load — no re-login
  required.
- **AC5 — everyone already inside is grandfathered.** The migration marks
  every existing account approved in the same change that adds the state.
  Nobody working today ever sees the gate.
- **AC6 — the decision is recorded.** Who approved which account, and
  when, lands in the audit surface the app already writes gate decisions
  to. The pending row shows nothing about *why* — there is no deny flow in
  this story.

## Verification (2026-08-14, pre-UAT)

Built as migration `253_beta_gate.sql` (applied to **both** live projects
via MCP; `scripts/.migrate.env` is absent on this machine, so migrate.py's
own path wasn't used — types were regenerated from prod and the embed
sweep passed), plus `/gate` + a redirect in the `(app)` layout and both
chrome-less pop-outs, plus the pending queue on `/admin/users` backed by
`POST /api/v1/admin/users/{id}/approve`.

- **Enforcement design (AC3):** one choke point. `is_approved_user()` was
  added to `is_org_member` / `is_org_owner` / `has_org_capability` — the
  helpers every RLS policy evaluates and every FastAPI capability check
  RPCs **under the caller's own JWT** — so browser CRUD and API
  orchestration are gated by the same predicate. The three live bodies
  were md5-pinned (verified byte-identical across prod and dev) and the
  migration raises on drift, per the 193 precedent.
- **Proven against the real dev database**, as the `authenticated` role in
  rolled-back transactions: an approved user keeps everything (member ✓,
  capability ✓, sees their 2 projects); the same user with `approved_at`
  nulled loses everything (member ✗, capability ✗, **0** projects visible)
  while still reading exactly their own profile row; `display_name`
  updates still work; setting one's own `approved_at` fails with
  `permission denied` (column-level grant — profiles had a row-level
  "update own profile" policy that would otherwise have allowed
  self-approval).
- **Grandfather (AC5):** verified on both projects after apply: 7 profiles,
  0 pending.
- **Suites:** web `npm run build` clean (route `/gate` registered); api
  essential suite exit 0 (run with dummy env — this machine has no
  `apps/api/.env`).
- **Deviations to note at UAT:**
  - **AC2's contact address is not on the gate page** — no real mailbox
    exists to name, and inventing one fails AC4 of the front-door story.
    Copy says "nothing you need to do / sign back in later". Supply a
    mailbox and it's a one-line add.
  - **AC6:** the record is `approved_by` + `approved_at` on the profile
    row, plus the API request log capturing the approve call. There is no
    platform-level audit table to write to (content_audit is
    project-scoped); the profile columns are the durable record.
- **Not verified (needs UAT):** the end-to-end browser flow — sign up
  fresh, see the gate, approve from a second superadmin session, next
  load passes — this machine has no test credentials. The gate page and
  queue render from the same components verified by the build, but nobody
  has walked the full loop yet.

## Out of scope

- Deny / reject / revoke — approval only; removing an account stays a
  manual superadmin act outside this story.
- Email notifications in either direction (the applicant learns by
  logging in; the superadmin learns from the Accounts queue).
- Invite codes, waitlist positions, or capacity counters.
- Any change to the public site's Sign up buttons — the front door still
  invites; the gate is inside.
