# US-79.4 — A network failure in the browser reports as one

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-5 (`TypeError: Load failed`, issue `78cea3d5-5d9b-4ad3-89e2-bd1822b84b2f`)

## Story

As the superadmin triaging browser-side reports, I want a network failure to
arrive labeled as one and naming what failed to load, so that "TypeError: Load
failed" with no URL stops being a report nobody can act on — and as a user on
a flaky connection, I want a stale-deploy chunk failure to heal itself with
one reload instead of showing me the jam screen.

## Context

The one prod occurrence came from an iPad (Chrome on iOS) on
`/servers/<id>`, through the **global** boundary — the root layout itself came
down. "Load failed" is WebKit's message for *any* failed fetch: the user's
network dropping, or a hashed JS chunk that no longer exists because a deploy
replaced it mid-session (Build Mill deploys many times a day, so the
stale-chunk case is a certainty over time). The report
(`apps/web/src/lib/self-report.ts`) currently forwards `error.message`
verbatim: no failing URL, no classification, indistinguishable from an app
defect.

## Acceptance criteria

1. `apiCall` (apps/web/src/lib/api.ts) throws a typed error carrying the
   request path and method when `fetch` itself rejects; boundary reports
   include that (`context.request`), so a failed API call names its endpoint.
2. The reporter classifies known network signatures — WebKit "Load failed",
   Chromium "Failed to fetch", Firefox "NetworkError when attempting to fetch
   resource", and dynamic-import/chunk-load failures — as
   `context.kind: "network"`. The Reports/System issues inbox displays the
   kind, so these group visibly apart from app defects.
3. On a network/chunk-load signature, the error boundaries reload the page
   once per session (a sessionStorage guard) before rendering the jam screen —
   the standard stale-deploy cure. A second failure in the same session shows
   the screen as today, and still reports.
4. The reporting loop guard and dedup behavior are unchanged; the reload path
   must not double-report the same error.

## Out of scope

- Per-page offline/retry UX beyond the one guarded reload.
- Service workers, precaching, or keeping old chunk hashes serveable across
  deploys.
- Classifying anything server-side (the API's reports are other stories).

## Proof required to reach Testing

A simulated fetch failure in dev showing: the report payload with
`kind: "network"` and the failing request path, and the one-reload-then-screen
behavior (screen recording or stepped screenshots).

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `cf96d95`).
`apiCall`/`apiFetch`/`apiFetchText` throw a typed `NetworkError` carrying
`METHOD /path` when fetch itself rejects (AC1) — its message ("could not
reach the API (POST /…)") also replaces the browser's unactionable one in
every existing toast. `classifyError` (own zero-import module) recognizes the
WebKit/Chromium/Firefox network signatures plus the stale-chunk shapes;
the reporter stamps `context.kind = "network"` and `context.request` (AC2).
Both boundaries call `reloadOnceForNetworkError` after reporting — one
sessionStorage-guarded reload, then the jam screen; the report rides
`keepalive` so the navigation cannot drop it, and a recurrence dedupes
server-side into the same row (AC3/AC4). Both report surfaces show the kind
as a badge.

**Verified:** `error-classify.test.ts` (6 node:test cases: every signature +
the not-network case); web build clean (type-checks all call sites), lint 0
errors, web tests 79/79.

**Not verified:** the live one-reload-then-screen behavior in a browser (a
dev-server preview cannot run beside the user's own — the standing
constraint), and a real report payload landing in the inbox; both are the
UAT walk.
