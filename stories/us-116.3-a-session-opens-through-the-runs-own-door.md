# US-116.3 — A session opens through the run's own door

**Status:** Testing
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-78.10 (sessions with no work item), US-83.2 (a session's CLI
gets the same env a run gets), US-89.1 (the worker token lives in the process
env, read by the git credential helper), US-115.1 (the interactive agent's tools
come from its own `config.toml`)

## Story

As the manager, I want "Open session" to open a session on any agent the API
lets it through for, so that the CLI window is not a button that has silently
failed on the machine since 2026-08-14 while the API's own checks all pass.

## Design

### What happens today

Every session that gets past `POST /agent-sessions` — the module check, the
liveness check, the model gate — dies on the machine. `session_host._open`
(`apps/runner/supervisor/session_host.py:191-193`) still reads:

```python
mcp_written = mcpconfig.write(
    workdir, os.environ.get("FACTORY_API_URL", ""), token, project_id, []
)
```

There is no `token` in that function. US-89.1 moved the worker token into the
process environment for the git credential helper and rewrote the two run-path
call sites to `os.environ.get("FACTORY_WORKER_TOKEN", "")`
(`modules/cli_base.py:692`, `:768`); this third site kept the bare name. Python
raises `NameError`, `handle()` catches it and answers
`{"ok": False, "error": "name 'token' is not defined"}`, the API turns that
into a 502 and marks the session row `failed`. On prod: `agent_sessions` shows
`name 'token' is not defined` on 2026-08-14 20:27 and 2026-08-17 20:56 — both
on **Programmer**, the one agent whose session passes the model gate today
(us-116.1's table). The last session that opened was 2026-08-13 13:20. The
`app_issues` inbox has the 502 as `HTTPException: 502: name 'token' is not
defined`, one row, status `new`.

`tests/test_session_host.py` never gets there: its `_open` cases stop at the
`session.open needs session_id and git_remote_url` refusal, so the line was
never executed under test.

### The bug under the bug: two doors

Fixing the name is one line. The reason it broke — and will break again — is
that a run and a session open the CLI through **two different code paths**
that have to be kept in step by hand:

| step | run (`modules/interactive.py`) | session (`session_host.py`) |
|---|---|---|
| model config | `write_model_config($GROK_HOME, env)` | same |
| tools | us-115.1: `[mcp_servers.*]` in `$GROK_HOME/config.toml`, `MCP_INIT_STRATEGY=blocking`, `session/new` gets an empty list | still `mcpconfig.write()` → `.factory-mcp.json`, passed as `mcp_config=` into `open_session` |
| spawn | `DEFAULT_CMD` + `ACP_ARGS` | same, re-derived |
| worker token | from env | the missing name |

us-115.1 landed this week and moved the run path off `.factory-mcp.json` for a
measured reason (the CLI reads its tools from its own config and starts the
first turn before a `session/new` server has handshaken). It did not touch
`session_host`, so once the `NameError` is fixed a session still opens the CLI
the *old* way — with tools it will read too late — while a run opens it the new
way. That is the second drift in a week; the file invites it.

### One door

The interactive module owns "open this agent's CLI on this checkout":

- one routine that takes the checkout, the model env, an optional resume id and
  the narration callbacks; writes `config.toml` (model **and** tools, us-115.1's
  shape) into the slot's `$GROK_HOME`; builds the argv and the child env
  (`MCP_INIT_STRATEGY=blocking`, the bearer variable); and calls `open_session`
  with an empty `session/new` list.
- the run path (`_run_cli`) and `session_host._open` both call it. `session_host`
  stops importing `mcpconfig` at all — no `.factory-mcp.json` is written for a
  session, exactly as us-115.1 keeps it out of a run's workspace.
- `write_model_config` stays where it is; the routine calls it.

The refusal for a run with no model (`interactive.py:483-500`) and for a
session with none (`session_host.py:185-190`) become one refusal in the shared
routine, with the same sentence.

### Shipping it

The runner bundle reaches Pod-001 only through an **Update** job
(`agent_server_jobs`, kind `update`), which restarts each agent one at a time.
This story is not verified until a session has actually opened on prod after
that update — the API-side tests cannot see this bug, which is how it survived
three days.

Order in the phase: **first**. The one-line `os.environ.get(...)` fix may go to
`main` immediately as a hotfix ahead of the consolidation, per the branching
rules; the rest of this story follows on the phase branch.

## Acceptance criteria

1. On prod, after the runner Update: **Programmer** opens a session from
   `/team/{id}/console`, the narration reaches "session opened", and a typed
   line gets a reply. The `agent_sessions` row is `open`, not `failed`.
2. `session_host` writes no token-bearing config file and defines no spawn of
   its own: a run and a session obtain the CLI through one function in the
   interactive module (the tools description is `mcpconfig.build`, the same
   dict `execute()` writes for a run — built for a session, never written). A
   test pins that both callers reach the same routine and that the routine
   writes `[mcp_servers.*]` into `config.toml` and passes an empty list to
   `session/new` — the us-115.1 shape — for a session as well as a run.
3. `apps/runner/tests/test_session_host.py` drives `_open` past checkout
   preparation with fakes for `prepare_checkout` and `open_session`, and asserts
   the CLI is spawned with the worker token taken from `FACTORY_WORKER_TOKEN`
   and no other source. Run against the pre-fix `session_host.py`, that test
   fails with the `NameError`.
4. A session on an agent with no model is refused on the machine with the same
   sentence a run gets — one string, defined once.
5. `cd apps/runner && python -m pytest` passes; the story records the Update
   job id on Pod-001 and the session id that opened.

## Out of scope

- **Which model a session resolves to.** That is us-116.1; this story makes the
  session survive the machine once the API has said yes.
- **Sessions on the four one-shot modules.** Still no session to open (US-78.10).
- **A runner-side test that spawns a real CLI.** The runner suite has no CLI
  binary; the pin is at the seam (one routine, both callers), not end-to-end.
