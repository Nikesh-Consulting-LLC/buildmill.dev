# US-120.1 — A dead UAT deploy settles the release

**Status:** Testing
**Phase:** 120 — A deploy that dies settles the release
**Depends on:** US-63.2 (the UAT deploy is `deploy.py`'s pipeline, reporting
back through `_settle_release_deploy`), US-1.32 (`reap_orphaned_runs`),
US-1.35 (`request_cancel`), US-103.3 (Stop vs Reject; `STOPPABLE`), US-90.1
(Retry of the deploy leg), migration 215 (`releases_one_in_flight_per_project`),
migration 275 (a release in flight freezes `plan`/`code` dispatch)

## Story

As the manager, I want a release whose UAT deploy died to say so and offer me
the next action, so that a deploy that ended without its pipeline — an API
restart, a lost task, a hang — cannot hold the project's only release slot
and its dispatch queue for the rest of the day.

## Design

### The 2026.08.18.2 incident

Release `2026.08.18.2` (demo project) was cut at 12:22 UTC. The prep agent
wrote notes and attached cases at 12:26:22; `release_prep.submit` fired the
UAT deploy at 12:26:27 and moved the release to `deploying`. Eight seconds
later the API process (re)started — no prod deploy ran at that hour; the cause
is unknown and out of scope — and `deploy.reap_orphaned_runs` did what US-1.32
built it to do: it flipped the `deployment_runs` row to `failed` with
`[interrupted by API server restart]`.

It did **not** flip the release. `_settle_release_deploy` (US-63.2) is called
from exactly four places, all inside `run_pipeline`'s terminal branches, and a
restart skips every one of them. The release sat at `deploying` for nine and
a half hours, and from `deploying` there was no legal move:

| Action | Answer at `deploying` |
|---|---|
| Stop (`POST /releases/{id}/cancel`) | 409 — *"the UAT deploy is running — let it finish, then stop or reject"* |
| Retry (`POST /releases/{id}/retry`) | 409 — only `failed` / `uat-deploy-failed` |
| Release page | badge `deploying`, masthead *"UAT deploy: failed"*, **no button at all** |
| Workbench card | the raw word `deploying`, no Stop |
| Reject | allowed — but burns the version for a build nothing was learned about |

Meanwhile `deploying` is in migration 215's in-flight set, so
`releases_one_in_flight_per_project` refused every new cut for the project,
and migration 275 refused every `plan`/`code` dispatch on it. One reaped run,
one project frozen.

### What already times out, and what does not

The manager's first reading — *"there is no mechanism to time out
deployments"* — is half right. `run_pipeline` wraps the whole deploy in
`asyncio.wait_for(…, timeout=run_timeout_minutes * 60)` (default **30
minutes**, per deployment); a timeout fails the run **and** settles the
release. So a deploy that is genuinely running slowly is already bounded.

What has no bound is a deploy that has *no pipeline*: the task died with the
process. Two writers move such a run to a terminal status and neither tells
the release — `reap_orphaned_runs` at startup, and `request_cancel`'s
"marked" branch (cancel requested when no live task exists in this process).
And nothing looks from the release's side at all: a release at `deploying`
whose run is terminal, missing, or long past the deployment's own timeout is
never noticed.

### The rule this story installs

**Every writer that ends a release-linked deployment run settles the
release, and a release at `deploying` is re-read from its run on a timer.**
Concretely:

1. `_settle_release_deploy(settings, run_id, outcome, reason=None)` gains a
   reason. `failed`/`cancelled` land the release at `uat-deploy-failed` (as
   today) and — new — write `failure_reason`, which the release page already
   renders and which `retry` already clears. `succeeded` is unchanged.
2. `reap_orphaned_runs` returns `release_id` alongside `id, org_id` and
   settles each reaped run that has one: outcome `failed`, reason *"the UAT
   deploy was interrupted by an API server restart"*.
3. `request_cancel`'s "marked" branch settles: outcome `cancelled`, reason
   naming who cancelled and that no pipeline was running. The "signalled"
   branch already settles through the pipeline's `CancelledError` handler.
4. **`settle_stranded_release_deploys`** — a sweep in `deploy.py`, run from
   us-119.2's lease sweep (`sweeps.lease_sweep_tick`: first tick at startup,
   right after the lifespan's `reap_orphaned_runs`, then every 30 s) as the
   deploy-leg twin of the release-prep reaper. For each release at `deploying`, read its `uat_deployment_run_id`
   run and:
   - run row missing (null id, or deleted) → `uat-deploy-failed`, reason
     *"the UAT deploy run no longer exists"*;
   - run `failed` / `cancelled` → `uat-deploy-failed`, reason from the run's
     last log line;
   - run `succeeded` → `uat-deployed` with `uat_deployed_at` = the run's
     `finished_at` (a success whose settle was swallowed by a DB hiccup);
   - run `queued` / `running`, **not** live in this process's `_RUNNING`
     table, and older than the deployment's `run_timeout_minutes` (default
     30) plus a five-minute grace → the run is failed
     (`[timed out: no pipeline reported for N minutes]`, an `error` event)
     and the release settles to `uat-deploy-failed`. A run that *is* live
     here is left to its own `wait_for`.
   The sweep is the belt to the reaper's braces: it also repairs a release
   the old code already stranded (2026.08.18.2 on prod, at the first restart
   after this ships), and covers a startup where the reaper itself was
   skipped because the database was unreachable.
5. **Stop at `deploying`.** `STOPPABLE` (API and `release-states.ts`) gains
   `deploying`; `_STOP_REFUSALS` loses it. `POST /releases/{id}/cancel` at
   `deploying` first cancels the UAT deployment run through
   `deploy.request_cancel` (signalled if live — cooperative, US-1.35's rule
   that work already done on the server is not undone — or marked if not),
   then marks the release `cancelled` as everywhere else. The response
   carries `deploy_run: signalled | marked | not-active`. `/reject` at
   `deploying` cancels the run the same way — the US-103.3 AC5 argument: a
   verdict on the release ends its job, or a zombie deploy keeps writing to
   UAT after the release is gone. The dialog copy for `deploying` says what
   happens on the server.

   Stop keeps its one meaning — the release is stopped, the project freed,
   the version not reused. The manager who wants to **retry the deploy on
   the same version** instead cancels the *deployment run* (the existing
   Cancel on the deployment page), which — by rule 3 — now lands the release
   at `uat-deploy-failed`, where Retry lives.
6. **The workbench card** names the phase in words (`notes-ready`,
   `deploying`, `uat-deploy-failed` had none and printed the raw status) and
   shows Stop at `deploying`.

No migration: `uat-deploy-failed`, `failure_reason` and the in-flight set are
all in place. No new status.

## Acceptance criteria

- **AC1 — the reaper settles the release.** With a `deploying` release whose
  linked run is `running`, an API startup lands the run at `failed` **and**
  the release at `uat-deploy-failed` with a `failure_reason` naming the API
  restart. A run with no `release_id` is reaped exactly as before and touches
  no release. Pinned by a test driving `reap_orphaned_runs` against a fake
  connection.
- **AC2 — cancel-without-a-pipeline settles the release.** `request_cancel`
  on a `running` run that is not in `_RUNNING` returns `marked` and the
  linked release lands at `uat-deploy-failed`. Pinned by a test.
- **AC3 — the sweep re-reads a stranded release.** `settle_stranded_release_deploys`
  moves a `deploying` release to `uat-deploy-failed` when its run is
  `failed`, `cancelled` or missing; to `uat-deployed` when its run
  `succeeded`; fails-and-settles a `running` run older than
  `run_timeout_minutes` + 5 that is not live in `_RUNNING`; and leaves a
  young or live run alone. It returns what it changed (release id, version,
  from-run-status, landed-status). Pinned by tests for each branch.
- **AC4 — the sweep runs at startup and on the loop.** `sweeps.lease_sweep_tick`
  calls it (first tick immediately at startup, then every 30 s) and logs
  each settled release at warning; the tick's own guard means a DB failure
  in the sweep is logged and never stops the next tick or startup.
- **AC5 — Stop works at `deploying`.** `POST /releases/{id}/cancel` on a
  `deploying` release answers 200 `{status: "cancelled", deploy_run: …}`,
  having called `deploy.request_cancel` with the release's
  `uat_deployment_run_id`; the release row is patched to `cancelled` with
  the reason. A release at `deploying` with no run id still cancels
  (`deploy_run: "not-active"`). Pinned by route tests; the existing
  "refused elsewhere" test drops `deploying`.
- **AC6 — Reject at `deploying` ends the deploy too.** `POST /releases/{id}/reject`
  on a `deploying` release calls `deploy.request_cancel` on the linked run
  before marking the release `rejected`. Pinned by a route test.
- **AC7 — the pipeline's own failure carries its reason.** `run_pipeline`'s
  `failed` and timeout branches pass their note through to
  `_settle_release_deploy`, so a release that failed on health-check reads
  the health-check line on its page rather than only *"UAT deploy: failed"*.
- **AC8 — the web offers Stop at `deploying`.** `STOPPABLE` in
  `release-states.ts` includes `deploying`; the release page, `/releases`
  and the workbench card render the Stop button there; the Stop dialog for a
  `deploying` release states that the UAT deploy is cancelled and that files
  already transferred and script steps already run are not undone. The
  workbench line under the version reads in words for `notes-ready`,
  `deploying` and `uat-deploy-failed`.
- **AC9 — Essential.** Every API test above runs in the Essential suite with
  the database faked; `npm run build` and `npm run test:web` pass.
- **AC10 — the stranded prod release is repaired by the code, not by hand.**
  After this ships, the first API start on prod moves `2026.08.18.2` from
  `deploying` to `uat-deploy-failed` with a reason, and the release page
  offers Retry and Stop. Recorded in the verification record.

## Out of scope

- **`promoting`.** A production deploy that dies leaves the release at
  `promoting` with the same shape of hole — the prod run is not linked by
  `release_id`, so nothing settles it, and Stop is (rightly) refused there.
  It needs its own landing state or a return to `uat-signed-off`, which is a
  design decision, not a settle call: **US-120.2** carries it.
- **Why the API restarted at 12:26:35 UTC on 2026-08-18.** No prod deploy ran
  then; `journalctl -u factory-api` on the VM around that minute is the
  place to look. If `factory-api-uat` shares prod's database, its restart
  would reap prod's live runs — worth confirming on the box, and a reason the
  sweep is written to be safe when it happens again.
- **A lease or heartbeat on `deployment_runs`.** The reaper's premise — a
  live run cannot predate this process — is what a shared database breaks.
  Fixing that means the pipeline writing a heartbeat and the reaper reading
  it; a bigger change than this incident justifies.
- **A second button at `deploying`** ("stop the deploy, keep the release").
  One Stop, one meaning; the retry path exists through the deployment run's
  own Cancel and is named in the dialog.
- **The interface catalog's missing `releases.py` section.** The router has
  no rows in `docs/application/interface-catalog.md` today; the lifecycle
  doc's deployment-state table is updated for the rows this story changes,
  and the catalog gap is left as found.
- **Changing `run_timeout_minutes`'s default** or making the grace
  configurable.
