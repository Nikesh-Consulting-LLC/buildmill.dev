# US-81.4 — Suite results reach the cases and the gate

**Status:** Testing
**Phase:** 81 — Automated release testing
**Dependencies:** us-81.3

## Story

As a manager, I want automated results to land on the release's test cases
and — for suites I've flagged — to gate sign-off, so the release page stays
the one place where "is this release tested" is answered, and machine results
carry exactly the weight I've assigned them.

## Acceptance criteria

1. After a release-scoped run, `suite_run_tests` rows are matched to that
   release's copied cases by `(suite_id, spec_ref)`; matches set
   `test_case_id`.
2. `release_test_results` gains `suite_run_id`. The pipeline machine-upserts
   `pass`/`fail` for each matched automated case (`noted_by` null — machine
   rows are visibly machine rows in the UI). Manual cases are never touched
   by the pipeline; `blocked` stays human vocabulary.
3. `release_signoff_blocker` v2, same shape and grants: the existing checks
   are unchanged, **plus** — for each active `run_on_uat` suite with
   `blocks_signoff = true` — the latest run for this release must be
   `succeeded` or waived. Distinct messages: has not run yet / still
   running / failed — re-run or waive / could not run (error). Suites with
   `blocks_signoff = false` (the default) never block; their results are
   advisory display only.
4. Waiver: `POST /api/v1/releases/{release_id}/suites/{suite_id}/waive`
   `{reason}` stamps the latest run (`waived_at/by/reason`, audited). A
   waiver waives *that verdict*: a re-run produces a fresh run with no
   waiver.
5. Stale-UAT hardening: the blocker also refuses when the UAT deployment's
   latest succeeded deploy commit differs from `releases.commit_sha` —
   closing the "someone redeployed UAT mid-testing" hole manual testing has
   today.
6. JUnit tests with no matching case appear in the run view as **untracked**
   (adoption is us-82.4). An automated case whose spec never produced a
   result gets no result row — it blocks through the existing
   every-case-has-a-result rule, and the manager's escape hatches are the
   ones that already exist: hand-mark it, flip it to manual, or abandon it.

## Out of scope

- Any new release status. Suites run and gate entirely within
  `uat-deployed`.
- Blanket per-release waivers — the waiver is per suite run, deliberately.
- Untracked-test adoption (us-82.4).

## Outcome

Built 2026-08-11. Migration `241_suite_results_gate.sql` (both DBs; the live
function bodies were md5-verified identical across prod/dev before being
replaced — no drift introduced). The pipeline maps `(suite_id, spec_ref)` to
the release's copied cases, machine-upserts `release_test_results` with
`suite_run_id` + null `noted_by` (skipped tests answer nothing, deliberately);
the release page marks machine verdicts with a bot "auto" chip. Blocker v2
keeps 132's checks verbatim and adds the stale-UAT commit check plus the
gating-suites loop (only `blocks_signoff=true`, distinct messages for
not-run / running / failed / could-not-run). The waive endpoint stamps the
run (who/when/why); the release page offers Waive only on a non-passing
gating suite; the page now asks the real `release_signoff_blocker` RPC
instead of re-deriving a narrower version.

**Verified:** waive endpoint tests (404 no run / 409 running / 409 succeeded /
stamps reason); schema pins for the blocker's new clauses; Essential green.
**Not verified:** a machine verdict landing on a real release.
