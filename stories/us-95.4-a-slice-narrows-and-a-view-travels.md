# US-95.4 — A slice narrows, and a view travels

**Status:** Testing
**Phase:** 95 — Cost management
**Depends on:** [us-95.1](us-95.1-cost-gets-its-own-room.md), [us-95.2](us-95.2-spend-is-a-curve-not-a-number.md), [us-95.3](us-95.3-every-dollar-names-the-work.md) — the section, the curve, and the type dimension this filters

## Story

As the manager, a group-by answers one question across the whole org, and my
follow-up is always narrower: *this project's* spend, by epic. *Bugs only*,
by agent. The API has accepted `project_id` and `worker_id` filters on the
breakdown since US-33.3 ([db.py](../apps/api/app/db.py),
`spend_breakdown`) — nothing in the UI has ever exposed them.

Filters that compose with the grouping and the window — and a URL that
carries the whole slice, so a view I built can be bookmarked or pasted to
the other admin instead of described in words.

## Acceptance criteria

- **AC1 — three filters, freely combinable.** `/costs` gains Project, Agent,
  and Type filters, each optional, composing with any group-by and any
  window. Filtering by the dimension currently grouped by is legal and just
  narrows the rows — never an error, never a silent reset of the grouping.
- **AC2 — the server does the narrowing.** `spend_breakdown` gains a `type`
  filter beside the existing `project_id`/`worker_id` (resolved through the
  same run → issue join us-95.3 builds), and the trend endpoint accepts the
  same three. Filtering is never the client subsetting an unfiltered
  payload — the unfiltered payload is exactly what us-87.10 forbids
  shipping.
- **AC3 — one set of controls governs the page.** The table and the curve
  obey the same filters, and their totals agree under every combination —
  the us-95.2 AC6 reconciliation holds filtered, not just bare.
- **AC4 — the view lives in the URL.** Group-by, window, and active filters
  are query params on `/costs`; landing on such a URL restores the exact
  view (behind the us-95.1 gate as always). No saved-view table, no state
  outside the address bar.
- **AC5 — active filters are visible and removable.** Each active filter
  shows as a removable chip with one Clear-all beside them, and the empty
  state names the slice — "nothing metered for bugs in Alpha in the last
  7 days" — rather than the generic nothing-metered copy, which would read
  as a metering fault.
- **AC6 — tests.** Route tests (Essential, faked reads) cover each filter
  alone and combined with a grouping, and a web test covers URL state
  restore where the logic is pure.

## Out of scope

- An epic filter — reach that slice by filtering to a project and grouping
  by epic; a dependent two-step picker (project first, then its epics) is
  not worth its UI until someone asks for it.
- Saved or named views, and sharing to anyone who does not hold
  `view_costs` — a pasted URL still meets the gate.
- Row click-through drill-down (click a project row to filter to it) —
  pleasant, but the chips already make every slice reachable; add it the
  day the chips feel slow.
- CSV export of a filtered slice.

## Verified (2026-08-14, localhost:3000 against build-mill-dev)

- In the browser: choosing "By type" and the Bugs filter rewrote the URL to
  `/costs?group=type&type=bug`; a removable "Bugs ×" chip appeared with
  Clear beside it; a **fresh navigation to that URL restored the exact
  view** (the By type button active, the type select on Bugs, the chip
  re-rendered) — the server page parses the params, the view writes them
  back with `history.replaceState`, defaults omitted so bare `/costs`
  stays bare.
- The wire filter param is `item_type` (avoids shadowing on the API side);
  the URL param stays the friendlier `type`.
- Unit tests (Essential): `item_type` parameterised and forcing the walk,
  junk dropped rather than interpolated, filters composing with a work
  grouping (`epic` × project × story in one query), and the trend accepting
  the same three filters. Web tests (6, `costs-url.test.ts`): round-trip,
  junk-to-defaults, bare-URL defaults, repeated params.
- The filter dropdowns populated from live projects (2) and workers (16)
  under RLS.
- **Not verified here, for UAT**: filtered *data* in the table/curve and
  the named empty state with real requests (local API cannot start without
  `apps/api/.env`).
