# US-91.15 — A notification says what happened, and goes there

**Status:** Testing
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** nothing

## Story

As the manager, the bell shows me seven rows reading **"runner_fault: a work
item"** and clicking one does nothing. Every word of that row is either
machine text or false, and it is not a rendering accident — the renderer and
the producers were written for different vocabularies and never reconciled:

- [notification-bell.tsx](../apps/web/src/components/notification-bell.tsx)
  knows three types — `assigned`, `review_requested`, `blocked` — and
  **nothing in the API writes any of them**.
- The API writes exactly two: `runner_fault` (from
  `routers/runner_socket.py`, `routers/worker.py`, `agent_provision.py`) and
  `deploy_unhealthy` (from `factory_mcp.py`). Neither has a renderer.
- So the label falls through to the raw type string, and the title falls
  through to the literal `"a work item"` — which a runner fault is not.
- The deep link needs `payload.issue_id`; these payloads carry `run_id`. So
  `deepLink` returns null, and the click silently marks the row read and goes
  nowhere.

Meanwhile the payload already holds everything worth showing: `worker`,
`run_id`, and a `message` truncated to 200 characters. The information is in
the database. The bell just doesn't render it.

## Acceptance criteria

- **AC1 — every produced type has a renderer, written from its own payload.**
  At minimum:
  - `runner_fault` → names the agent and what happened: *"**Chip** hit a
    runner fault"* with the stored `message` on a second line.
  - `deploy_unhealthy` → names the deployment: *"**app-uat** failed its
    health check"*, with the message beneath.
- **AC2 — the message is shown.** The `message` field is the whole point of
  the notification and is currently never displayed. Two lines maximum in
  the dropdown, truncated with the full text in a `title`.
- **AC3 — no row ever renders a raw type or a wrong noun.** The literal
  fallback `"a work item"` is deleted. An unrecognised future type renders
  its type humanised (`runner_fault` → "Runner fault") plus whatever
  message the payload carries — degraded, but never machine text and never a
  claim about an object the notification isn't about.
- **AC4 — every row goes somewhere.** `runner_fault` with a `run_id` opens
  `/runs/{run_id}`; without one, the agent's page. `deploy_unhealthy` opens
  the deployment's run. A row whose payload genuinely names no destination
  must **not** be a dead button — it expands in place to show its detail
  instead. Clicking must never be a no-op that silently marks the row read.
- **AC5 — repeats collapse.** Faults from one agent are one row with a count
  (`×7`) and the newest timestamp, expandable to the individual events. The
  bell's job is to tell me something is wrong once, not seven times.
  **Amended during implementation:** grouping is by (type, subject) across the
  whole loaded window, not consecutive runs only. The sweep notifies once per
  agent per round, so no two neighbouring rows are alike and consecutive-only
  grouping collapsed nothing at all.
- **AC6 — the dead vocabulary goes.** `assigned`, `review_requested` and
  `blocked` have no producer. Remove them, or keep them only alongside a
  comment naming the code that will write them — a map that describes
  nothing is what let this ship.
- **AC7 — a test pins the set.** The known types live in one exported
  constant with a `.test.ts` covering each renderer, the unknown-type
  fallback, and the destination each type resolves to. `db.notify_org_managers`
  gains a docstring line: a new `notif_type` needs a renderer here, or the
  bell will show its raw name.
- **AC8 — the rest of the bell is unchanged.** Unread dot, the `9+` badge,
  Mark all read, the realtime INSERT subscription and the 40-row cap all
  behave exactly as they do today.

## Out of scope

- Adding new notification producers, or notifying on anything not notified
  on today. If work-item assignment should notify, that is its own story —
  this one makes the existing notifications legible.
- A full notifications page or history beyond the dropdown's 40 rows.
- Outbound delivery (`notification_endpoints`, `notify.py`) — a different
  channel with its own formatting.
- Per-type mute or preference settings.

## Verified (2026-08-14, localhost against build-mill-dev)

The bell that read **"runner_fault: a work item"** now reads
**"pod-001-5 hit a runner fault"** with the stored message beneath it and the
age below that. Thirty rows collapsed to five, each carrying **×6**.

**AC5 amended — grouping is by (type, subject) across the whole loaded window,
not consecutive runs only.** Consecutive-only was the first cut and it collapsed
*nothing* against real data: the fault sweep notifies once per agent per round,
so the feed reads pod-001-5, Architect.001, Build.001, … and then repeats — no
two neighbours alike, thirty rows saying five things. The head keeps the newest
timestamp and the row shows how far back the run goes, so merging distant events
never hides when they happened.

- Real payloads carry `{worker, message, run_id: null}`, so these rows resolve
  to no destination and **expand in place** rather than being dead buttons
  (AC4's second half). The run-id path is unit-tested.
- The dead vocabulary (`assigned`, `review_requested`, `blocked`) is gone, and
  `db.notify_org_managers` now says in its docstring that a new type needs a
  renderer.
- 12 unit tests in `notification-copy.test.ts`, including the interleaved-sweep
  case that motivated the amendment.
