# US-96.6 — A failed breakdown gets another try

**Status:** Completed
**Phase:** 96 — The type shapes the path
**Depends on:** nothing

## Story

As the manager, a feature whose breakdown run fails is stranded — and the
application reference has documented it as a known gap since 2026-07-19
([lifecycles.md](../docs/application/lifecycles.md)): the failed submit
moves the feature `ready` → `failed`, but `dispatch_breakdown` only accepts
`ready`, the breakdown panel
([stories-panel.tsx](../apps/web/src/app/(app)/issues/%5Bid%5D/stories-panel.tsx))
only renders for `ready`, and `dispatch_issue` can't help because a feature
is never planned directly. One transient worker error and the feature needs
a database edit to move again.

The fix follows the pattern the `prd` kind already proved: a think-phase
run's failure is the **run's** failure, not the work item's. A failed
breakdown leaves the feature standing at `ready` — visibly failed on the
run row, the events, and the workbench — and the manager just dispatches
the breakdown again.

## Acceptance criteria

- **AC1 — failure keeps the feature dispatchable.** A `breakdown`-kind run
  failing (runner `POST /worker/runs/{run_id}/submit` with `error` set)
  leaves the feature's status untouched at `ready` — the same exemption
  `prd`-kind runs already have. The failure stays fully visible: run row
  `failed`, event recorded, workbench shows it.
- **AC2 — the reaper agrees.** `reap_orphaned_provider_runs` stops forcing
  the issue to `failed` for `prd`- and `breakdown`-kind runs — closing, in
  the same move, the second documented gap (the reaper never exempted `prd`
  the way a failed submit does).
- **AC3 — stranded features recover.** The migration returns to `ready`
  every feature currently at `failed` that has an approved PRD, no
  non-abandoned children, and a most-recent run that is a failed
  `breakdown` run — writing an `issue_events` row naming the repair. Any
  such feature then shows its breakdown panel again with no further change.
- **AC4 — the retry is informed.** The breakdown panel shows the prior
  failed breakdown run's error beside the retry action, so the manager
  redispatches knowing what went wrong last time — not a mystery button.
- **AC5 — the reference stays true.** The two entries this story fixes are
  removed from lifecycles.md's Known gaps and the transition table updated,
  in the same commit.
- **AC6 — both projects, tests.** Migration applied to prod and dev, types
  regenerated, embed sweep run. An Essential route test (faked reads) pins
  the failed-submit exemption for `breakdown`; a test pins the reaper's
  exemption; the recovery migration's predicate is pinned by a SQL test or
  verified against both live projects and recorded here.

## Verified (2026-08-15)

- **AC1**: `perform_submit`'s failure path ([db.py](../apps/api/app/db.py))
  now exempts `breakdown` alongside `prd`/`test`/`elaborate` — the run
  fails, the event is recorded, the feature's status is untouched. Pinned
  by a new Essential test (`test_db_complete_run.py`,
  FakeConn: a failed breakdown submit writes **no** `issues.status`
  update and still writes the event).
- **AC2**: `reap_orphaned_provider_runs` exempts the same four kinds from
  its unconditional issue → `failed` — closing the second documented gap
  (the reaper never exempted even `prd`) in the same move.
- **AC3**: migration `260_a_failed_breakdown_gets_another_try.sql` applied
  to **both** projects; the repair predicate found **zero** stranded
  features on either live project (the dead end was documented before it
  claimed a live feature) — the migration stands as the safety net for
  any environment where it did.
- **AC4**: the feature page now carries the last failed breakdown run's
  error in an amber note directly above the breakdown panel's retry
  (`page.tsx` reads it off the runs it already fetches;
  `stories-panel.tsx` renders it only when no fresh run is pending).
- **AC5**: both lifecycles.md entries updated — the `ready → failed`
  breakdown row replaced by the exemption note, the known-gap bullet
  struck through with the fix recorded.
- Essential suite green (1673 passed, 539 skipped); `npm run build` green.
- **Not verified here, for UAT**: a real failed breakdown round-trip on
  dev (fail a split → panel shows the error → redispatch succeeds) — the
  failure path needs a live worker to exercise end-to-end.

## Out of scope

- Auto-retry or retry limits — redispatch stays a manager's deliberate
  click.
- The `direct`-strategy parent-completion gap (the other lifecycles.md
  known gap) — a different mechanism, not touched here.
- Any change to the breakdown submit contract (`submit_stories`) or to how
  child stories are created.
