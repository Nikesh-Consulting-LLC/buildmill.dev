# US-116.5 — Start means start

**Status:** New
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-116.4 (one status; "live" is a fresh heartbeat), US-26.5
(pause is not stop), US-26.9 (the restart job drains first), US-55.2 /
migration 232 (suspend cascades to token revocation; reactivate restores),
US-57.3 (a tenant's agent on a platform pool), US-109.1 (Remove left the
roster's action cluster)

## Story

As the manager, I want one **Start** on the Team page that leaves the agent
running and ready — and one **Stop** that leaves it stopped — so that starting
an agent is never a trip to the superadmin's machine page, never a button that
does half the job, and never a button that silently does something else.

## Design

### Three buttons called start, none of which starts

1. **The Team roster's ▶ / ⏸ on an agent row is not the agent's.**
   `team-view.tsx:796-808` renders Play/Pause titled *Reactivate* / *Suspend*
   for every row, agents included, and it writes
   `organization_members.status`. For an agent that cascades — migration 089's
   `cascade_membership_to_tokens` **revokes its worker token**. The socket
   survives (the handshake already happened), so Team keeps saying `online`
   while the machine page says `Token revoked`. Migration 232's header records
   this "killed Architect.001 twice (2026-07-29/30) and the whole Sandy fleet
   on 2026-08-09"; `runner_incidents` holds 429 `agent-token` rows in the last
   14 days. A manager who wants to pause an agent from Team has one button in
   reach, and it is this one.
2. **Enable does not start.** `PATCH /agent-servers/{host}/slots/{slot}`
   (`agent_servers.py:735-783`) flips `runner_config.paused`, pushes
   `config.update`, writes `desired_state` — and touches nothing on the
   machine ("Pause is not stop", `:745`). If the systemd unit is `inactive` or
   `failed`, Enable changes a flag and the agent stays down until the probe
   notices (≤5 min) and the auto-repair ladder's first rung fires (≥15 min
   cooldown, `agent_provision.py:2456`).
3. **Restart is not reachable from Team for a pool tenant, and failures are
   swallowed.** `POST …/restart` authorizes on the **host's** org
   (`agent_servers.py:794-795`, `_get_host` under the caller's JWT). A shared
   pool's host row belongs to the platform org, whose `agent_servers` select
   policy is member-only (`142_agent_servers.sql:82-84`), and `agent_pools.py`
   has no restart twin (only `/place` and `PATCH /slots/{id}`). A tenant's
   click answers 404 — and the runner page wraps both buttons in `catch {}`
   (`runner/page.tsx:164, 184`), so the click looks like nothing happened. It
   works for the platform admin, which is why "I have to go to superadmin".

### One Start, one Stop, on the agent

Two endpoints on the agent router, keyed the way the roster is:

```
POST /api/v1/agents/{principal_id}/start
POST /api/v1/agents/{principal_id}/stop
```

Both authorize on the **slot's org** (`manage_org`, exactly as the PATCH does
and for the same reason its docstring gives) and resolve the agent's autonomous
worker and its active slot. An agent with no slot (installed by hand) gets a
409 that says so.

**Start** does everything the word implies, in order, and reports what it did:

1. `runner_config.paused = false`, `agent_slots.desired_state = 'enabled'`,
   push `config.update` — today's Enable.
2. If the agent is **live** (us-116.4's presence) — done; the answer is
   `{enabled: true, restarted: null}` and the roster reads Ready or Working
   within a heartbeat.
3. If it is not live, or the last probe recorded the unit as anything but
   `active` — queue the existing restart job for the slot (`_job_restart`),
   reading the host row with the service role because the slot's org has
   already authorized the caller. The answer is
   `{enabled: true, restarted: <job_id>}`; the roster shows **Starting…** until
   presence returns. `_job_restart` restores whatever `desired_state` it read
   at the top (`agent_provision.py:2104,2124`); because step 1 ran first, that
   is `enabled` — no code change there.
4. Refusals come back as sentences and are shown: a job already running on the
   host (409, naming it), a revoked token (409, "re-issue its token" — the
   repair is a different button and the manager should be told which).

**Stop** is today's Pause, unchanged in meaning: the service keeps running,
the socket stays up, the agent claims nothing, a run it holds finishes. It
reads **Stopped** (us-116.4). It is deliberately not `systemctl stop`: a
stopped process cannot tell you it is stopped, and the whole phase is about
agents that say what they are.

### Where the buttons are

- **Team roster, agent rows:** Start / Stop in the action cluster (▶ / ⏹),
  gated on `manage_org` like the machine page's controls. The membership
  ▶ / ⏸ is **removed from agent rows** — humans keep it. Suspending an agent's
  membership remains possible from its expanded detail panel, behind
  `ConfirmDialog`, worded as what it does: *"Suspend — revokes this agent's
  worker token. Reactivate restores it."*
- **Runner page** (`/team/{id}/runner`): Enable/Pause become Start/Stop
  calling the same two endpoints; Restart stays as the explicit machine
  action, and every failure surfaces as a toast — the `catch {}` goes.
- **Machine page slot card:** Enable/Pause become Start/Stop on the same
  endpoints; Restart, Re-issue token and Remove stay as they are.
- **Wizard Done step:** its Enable button (`add-agent-wizard.tsx:1348`) calls
  Start.

## Acceptance criteria

1. On Team, Start on a stopped agent whose service is running: the row reads
   Ready (or Working) within 5 s, no other page involved. The API answered
   `{enabled: true, restarted: null}`.
2. On Team, Start on an agent whose unit is `inactive`/`failed` (or that is
   simply not live): the API answers with a `restarted` job id, the row reads
   Starting… and then Ready within 90 s of the job finishing; the job appears
   in the machine's job list as `restart` by the caller's email.
3. A user who is a member of a tenant org and **not** of the platform org can
   Start and Stop that org's pool-placed agent from Team and from the runner
   page. Pinned by an API test that runs `start` as a tenant against a slot on a
   platform-owned host and gets 200 — today's 404.
4. A refusal (job already running; revoked token) is a toast with the API's
   sentence on the roster, the runner page and the machine page. No handler
   swallows it.
5. Agent rows on the Team roster no longer show the membership ▶ / ⏸.
   Suspending an agent requires the confirm that names token revocation.
   Human rows are unchanged.
6. Stop leaves a running run to finish and reads Stopped once idle; a stopped
   agent claims nothing (unchanged enforcement, `db.py` `worker_is_paused`).
7. `cd apps/api && python -m pytest` covers: authorization on the slot's org;
   restart queued only when not live or unit not active; no restart when live;
   the restart restoring `enabled`; both refusals; the hand-installed 409.
   `npm run test:web` covers the roster action cluster: Start/Stop present on
   agent rows, membership control absent, present on human rows.

## Out of scope

- **`systemctl stop` as Stop.** Rejected above: a stopped process cannot report
  itself. Removing an agent's service entirely stays the machine page's Remove.
- **Restart from the Team roster.** Start does the restart when needed; an
  explicit Restart button on the roster is a knob for a case the manager should
  not have to diagnose. It stays on the runner and machine pages.
- **The auto-repair ladder.** Unchanged; Start is the manual rung, taken
  immediately.
- **Deciding whether agents should ever be suspendable.** Kept, moved, and
  labelled honestly.
