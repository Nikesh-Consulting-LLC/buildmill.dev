# US-96.8 — The hand-back speaks with one voice

**Status:** New
**Phase:** 96 — The type shapes the path
**Depends on:** nothing (runner + factory MCP; no schema change expected)

## Story

As the manager, I watched a fifteen-minute code run spend its last eight
minutes arguing with itself about how to hand the work back — and the trace
says the factory started the argument. Run `51cd4fd3` (2026-08-14, the
transcribe-button bug): the module's task section told the agent "Leave your
changes uncommitted — the harness commits and pushes … Write test cases a
human should run to `.factory-out/test_cases.json`"
([cli_base.py](../apps/runner/supervisor/modules/cli_base.py),
`HANDBACK_WORKTREE`), while `get_work_context` on the same run named
`submit_changeset` as the hand-back. The agent deliberated for four minutes
over which master to obey, chose `submit_changeset`, dutifully included the
`.factory-out/test_cases.json` the prompt had told it to write — and the
factory **rejected the whole changeset** for containing factory scratch
([changesets.py](../apps/api/app/changesets.py), `FACTORY_SCRATCH`). Worse:
that first submit carried only 2 of the 5 changed files, and nothing in the
pipeline noticed — the agent caught its own omission, re-read everything,
and resubmitted. Had it not, the PR would have been broken in a way review
might have missed.

Three fixes, one story: the run prompt speaks with one voice about hand-back;
scratch in a changeset is filtered, not fatal; and a submit answers with
exactly what it received, so a partial hand-back is visible the moment it
happens instead of by luck.

## Acceptance criteria

- **AC1 — one voice per run.** The task section a module composes and the
  hand-back that `get_work_context` returns name the same path. A code run
  handing back over MCP (`submit_changeset`) never receives the worktree
  wording ("leave uncommitted, the harness commits") or the
  `.factory-out/test_cases.json` instruction — the module resolves the
  hand-back shape from the transport actually in play, not from run kind
  alone. Pinned in
  [test_handback_shapes.py](../apps/runner/tests/test_handback_shapes.py):
  for an MCP-transport code run, "uncommitted" and `.factory-out` do not
  appear in the task and the submit tool is named once.
- **AC2 — test cases have exactly one route per transport.** Whichever
  transport a run uses, the instructions name a single destination for test
  cases (the worktree collection file, or the submit's own structured
  field), and it is the one the factory actually reads. No run is told to
  write a file its own hand-back will refuse.
- **AC3 — scratch is filtered, not fatal.** A changeset that mixes
  `FACTORY_SCRATCH` paths with real files is accepted: the scratch paths are
  dropped and the tool response names each dropped path and why
  ("factory scratch never lands"). A changeset that is *only* scratch is
  still refused — there is nothing to commit. The security property is
  unchanged (the scratch never reaches the repo either way — the 2026-08-13
  token-in-history incident stays impossible); what changes is that the real
  files no longer fail with it. Pinned in
  [test_factory_mcp.py](../apps/api/tests/test_factory_mcp.py).
- **AC4 — the submit echoes what it received.** `submit_changeset` and
  `validate_submission` responses list the paths received (op, add/update/
  delete) and the paths dropped, and state the count plainly ("received 5
  files"). The worker instruction for MCP hand-back tells the agent to check
  that echo against its own list of changed files before reporting done.
- **AC5 — the harness sweeps for the files left behind.** On the MCP
  transport the bench holds the served manifest
  ([workspace_deliveries](../apps/api/app/db.py), us-31.6 — sha and path
  manifest per worker/project). After a code-run module finishes, the
  harness hash-compares the workspace against that manifest; files modified
  in the workspace but absent from every accepted changeset of the run are
  named in a `progress` trace line and in the hand-back notes ("modified but
  never submitted: …"), so a partial submit is a named fact on the run, not
  a silent gap in the PR.
- **AC6 — tests.** Runner tests for AC1/AC5 (no database), api Essential
  tests for AC3/AC4 (faked reads).

## Out of scope

- The git-native transport (humans in IDEs) — its hand-back is a push, and
  nothing here changes it.
- Any change to review, approval, or the PR pipeline downstream of submit.
- Re-litigating `FACTORY_SCRATCH`'s contents — the list stays as it is.
- Blocking a submit outright when the sweep finds leftovers — AC5 names the
  gap; refusing the hand-back on it is a policy decision for a later story
  if the warning proves insufficient.
