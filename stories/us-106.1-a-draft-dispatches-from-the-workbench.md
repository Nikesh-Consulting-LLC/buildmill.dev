# US-106.1 — A draft dispatches from the Workbench

**Status:** Testing
**Phase:** 106 — The Workbench acts on a draft
**Depends on:** US-6.2 (the "Waiting on you" list), US-74.5 (`org_issue_dispatch_blocks` and the held row), us-96.1 (a chore is one-shot), us-96.5 (a bug's think-first phase is an RCA), US-12.1 (`draft-prd` as an action a surface can take)

## Story

As the manager, I want a draft work item's one click on the Workbench to **send
it to the factory**, so that a freshly written backlog moves without a detour
through each item's own page.

Every other group on this tab acts: Reviews approve, Fix & retry re-dispatches,
Dispatch dispatches. Triage — the group holding every `draft` item — navigates.
A bug reads "Open draft" where the item page reads "Dispatch RCA", so the row
that exists to say *this is waiting on you* hands the decision to a second
screen that then offers the real button. The manager pays a page load per item
to press a button the row could have carried.

## Design

### The row says what the factory would do with it

The label is not a guess. `dispatch_kind_for` (migration 255) already decides
what a plain dispatch of a `draft` item means, and the row names that:

| type | what dispatch runs | label |
|---|---|---|
| story | `plan` | Dispatch planning |
| bug | `plan` — an RCA (us-96.5) | Dispatch RCA |
| chore | `code` — no planning phase (us-96.1) | Dispatch build |
| feature | *not dispatchable* — a PRD first | Draft PRD |

A **feature is the one type that cannot be dispatched from `draft` at all**:
`dispatch_kind_for` infers `plan` and the us-11.2 guard refuses it — "a feature
is not planned directly". Its real next run is the PRD draft, so its one click
posts `/api/v1/issues/{id}/prd/draft` — the same call the item page's **Draft
PRD** button makes. That is a new action mode on this list (`draft-prd`), not a
dispatch wearing a different word.

### Held drafts show the hourglass instead of erroring

Triage rows now pass `org_issue_dispatch_blocks` through like the Dispatch and
Fix & retry groups do, so a draft the build rules will not let through — a
story whose feature owns the initial plan (us-96.4), a project frozen behind a
release in flight (us-103.5), siblings still being curated — reads **Waiting**
with the database's own reason rather than offering a button that errors.

Features are unaffected by that: `issue_dispatch_block` returns no row when
`dispatch_kind_for` raises, which is exactly the feature case, and `heldReason`
only ever holds `dispatch`/`redispatch` modes. A PRD draft is authoring work and
us-103.5 deliberately leaves authoring open during a freeze.

### The draft is still one click from the row

The title is a link, and the row keeps a secondary **Open draft** button (the
existing `inspectHref` slot, with the label now settable — it read "Inspect",
which is the honest word for a run log and the wrong one for a description
waiting to be written). Nothing is lost; the primary slot is simply no longer
spent on navigation.

### Not batched, and not green

Triage rows are **not** selectable and do not count toward "Dispatch selected"
or "Dispatch all". Those act on items the manager has already fleshed out and
marked ready; sweeping half-written drafts into the same click is a different
decision, and a louder one. For the same reason the row loses its green
`emphasis` and renders like every other dispatch row — green on this page means
"approve", and these are not approvals.

## Acceptance criteria

- **AC1 — a draft story dispatches from the row.** A `draft` story shows
  **Dispatch planning**; one click creates the plan run, toasts "Dispatched",
  and the row leaves Triage on the refresh. No navigation.
- **AC2 — the words match the run.** A `draft` bug shows **Dispatch RCA**, a
  `draft` chore shows **Dispatch build**, and each dispatches the kind
  `dispatch_kind_for` picks for it (`plan`, `plan`, `code`).
- **AC3 — a feature drafts its PRD.** A `draft` feature shows **Draft PRD**;
  one click posts `/api/v1/issues/{id}/prd/draft` and the row leaves Triage
  (an active PRD run already removes it from the list).
- **AC4 — a blocked draft says so.** A draft the build rules hold shows
  **Waiting** with the reason from `org_issue_dispatch_blocks`, disabled, the
  same hourglass treatment the Dispatch group gives — not a button that errors.
- **AC5 — the draft is still reachable.** Every Triage row keeps a secondary
  **Open draft** link to `/issues/{id}`, on both the table and the phone card,
  and the title stays a link.
- **AC6 — batch is unchanged.** Triage rows carry no checkbox, and the
  Dispatch group's "Dispatch selected (n)" / "Dispatch all (n)" counts do not
  include them.
- **AC7 — failure is legible.** A refusal surfaces its message in an error
  toast and the row returns to its normal state.

## Out of scope

- Batch-dispatching drafts (see Design).
- Any change to what the factory accepts — no migration. `dispatch_kind_for`
  and `issue_dispatch_refusal` already allow every action this story offers.
- The item page's stage tracker, which already offered these actions.
- Confirming before dispatch. The Dispatch group does not, and a run is
  stoppable.

## Built (2026-08-16)

Web only; no migration, no API change.

- `apps/web/src/app/(app)/workbench/triage-action.ts` **(new)** — the
  type → {reason, action, mode} mapping, in its own module so it can be tested
  without dragging `data.ts` (and Supabase) into the node test runner.
- `apps/web/src/app/(app)/workbench/triage-action.test.ts` **(new)** — six
  tests pinning the mapping, including the unknown-type fallback.
- `apps/web/src/app/(app)/workbench/data.ts` — `TodoActionMode` gains
  `draft-prd`; `TodoItem` gains `inspectLabel`; the Triage group now builds its
  rows from `triageAction`, passes `blockByIssue`, and sets `inspectHref` +
  "Open draft" instead of spending the primary slot on navigation. Its
  `emphasis: "success"` is gone.
- `apps/web/src/app/(app)/workbench/waiting-list.tsx` — `draftPrd()` posting
  `/api/v1/issues/{id}/prd/draft`; `runInline` routes `draft-prd` to it with
  its own toasts ("Drafting the PRD" / "Couldn't draft the PRD");
  `ActionGlyph` gives `draft-prd` the FileText icon; both Inspect buttons
  render `inspectLabel ?? "Inspect"`.

Batch selection was not touched: the checkbox and both "Dispatch selected" /
"Dispatch all" controls are still gated on `g.title === "Dispatch"`, so AC6
holds by construction.

**Verified.** `npm run build` (type-checks) and `npm run test:web` (206 tests)
pass. The mapping was read out of migration 255's `dispatch_kind_for` and
migration 235's `issue_dispatch_block` rather than assumed — in particular that
a feature yields no block row (`dispatch_kind_for` raises, and the block
function's `exception when others then return` swallows it), which is what
keeps AC4's hourglass off the Draft PRD button.

**Not verified.** Nothing was clicked against a running app: this machine has
no `apps/web/.env.local`, so the dev server 500s in `proxy.ts` before any page
renders. AC1–AC5 and AC7 are reasoned from the endpoints the item page already
calls successfully, not demonstrated. UAT should press one of each: a draft
bug, a draft chore, a draft story, a draft feature, and one held draft.
