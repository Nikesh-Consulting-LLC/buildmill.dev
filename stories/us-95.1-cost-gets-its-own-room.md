# US-95.1 — Cost gets its own room, and managers hold the key

**Status:** Completed
**Phase:** 95 — Cost management
**Depends on:** nothing (us-95.2–95.4 render inside the section this creates)

## Story

As the manager, what the factory costs is a settings page. `/settings/spend`
mixes a report (the breakdown) with a configuration form (the model rates),
sits behind a submenu nobody visits to *learn* anything, and is visible to
every member of the org — us-91.14 noted the gap and deliberately left it:
"cost is already visible to any member via `/settings/spend`".

Money deserves its own room, and the room needs a door. A **Costs** section,
top-level in the navigation, that holds reporting and only reporting — and
that only an org's owner and admin can enter. The rates form is configuration,
not reporting; it stays behind in Settings where configuration lives.

The gate goes through the capability layer, not a hard-coded role pair.
US-9.2 built authorization as capabilities resolved through the
`role_capabilities` grid precisely so a new gate is a new row, not a new
`if (role === "owner")` scattered through pages
([permissions.ts](../apps/web/src/lib/permissions.ts)).

## Acceptance criteria

- **AC1 — a top-level Costs entry.** A new `/costs` route with its own entry
  in [nav-items.ts](../apps/web/src/components/nav-items.ts), grouped with
  Activity and Bug Reports (the other "what happened" surfaces). The entry
  renders only for members whose role grants the new capability; everyone
  else never sees it.
- **AC2 — the gate is server-side.** Hiding the nav entry is courtesy, not
  enforcement: a member without the capability who navigates to `/costs`
  directly is turned away by the page's own server-side check (the same
  pattern the superadmin pages use), with one plain sentence — "Costs is
  visible to owners and admins" — not an error page and not a blank.
- **AC3 — `view_costs` is a capability, seeded for owner and admin.** A
  migration adds `view_costs` to the `role_capabilities` grid: allowed for
  `owner` and `admin`, denied for `lead`, `developer`, `reviewer`, `viewer`.
  The superadmin can retune it like any other cell (US-9.3). The client gate
  and any server check resolve through the same grid so they cannot disagree.
- **AC4 — the breakdown moves whole.** Everything Settings → Spend *reports*
  today renders on `/costs` unchanged: the four dimensions
  (project/agent/provider/model), the four windows, tokens in/out kept
  separate, the cache share, the unmeasured-calls badge (US-33.3), and the
  subscription-runs off-meter line (US-52.4). Same
  `spend_breakdown` query underneath
  ([db.py](../apps/api/app/db.py), `SPEND_DIMENSIONS`) — this story moves the
  report, it does not re-derive a number.
- **AC5 — rates stay in Settings.** The Rates block (model prices, the
  US-36.4 edit flow, the US-38.1 cache rates) moves to
  [/settings/llm-providers](../apps/web/src/app/(app)/settings/llm-providers)
  — rates are the provider's published pricing, and that is the page about
  providers. The Settings submenu drops its Spend entry; `/settings/spend`
  redirects to `/costs` so bookmarks survive.
- **AC6 — no link leads a member to a locked door.** The in-app links that
  point at `/settings/spend` today —
  [spend-summary.tsx](../apps/web/src/components/spend-summary.tsx) on
  project and agent pages,
  [budget-card.tsx](../apps/web/src/app/(app)/projects/%5Bid%5D/budget-card.tsx)
  — follow the move, and render as links only for viewers who hold
  `view_costs`; for everyone else the same text renders without the link.
  The facts those surfaces show stay visible to every member (see out of
  scope); only the door to the section is gated.
- **AC7 — the migration goes to both projects.** Written in
  `infra/supabase/migrations/`, applied to prod and dev, types regenerated,
  embed sweep run.
- **AC8 — tests.** A web test on the nav/gate logic where it is pure, and an
  api route test (Essential, faked reads) if any endpoint gains a capability
  check here.

## Out of scope

- Tightening `llm_usage` RLS or removing spend facts other surfaces already
  show every member — the project card's spend line, us-91.14's item costs,
  the agent page's summary. This story gates the *section*, not the ledger;
  the shared spend endpoint stays member-accessible because member-visible
  surfaces read it.
- Any new reporting — trends (us-95.2), work-shaped dimensions (us-95.3),
  filters (us-95.4).
- The superadmin's cross-org view — `/admin/usage` (US-60.2) is unchanged.
- Budgets, ceilings, and alerts — the US-37.1 project budget machinery is a
  different concern and already has its home.

## Verified (2026-08-14, localhost:3000 against build-mill-dev)

- Migration `254_view_costs_capability.sql` applied to **both** Supabase
  projects; the seed confirmed identical on each (owner+admin true, the other
  five roles false). No table shape changed, so `database.types.ts` is
  untouched by it; the embed sweep ran green inside the Essential suite.
- `/costs` renders for the owner: header, four windows, all seven dimension
  buttons, filters populated from live projects/workers under RLS.
- The sidebar shows **Costs** directly after Bug Reports; `/settings/spend`
  redirects to `/costs` (checked in the browser); the Settings submenu no
  longer lists Spend.
- **Model rates** card renders on `/settings/llm-providers` with the real
  five-model rate table.
- AC6 was implemented as a client-side capability hook
  (`use-can-view-costs.ts`) rather than threaded server props — the agent
  runner page is a client route with no server parent to thread from. Same
  outcome: the breakdown link renders only for key-holders.
- **Not verified here, for UAT**: the turn-away page as seen by a non-admin
  (only an owner account was available — the server-side check is code-read
  plus the API-side 403 route test); the mobile drawer's gated entry.
