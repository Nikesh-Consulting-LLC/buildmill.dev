# US-105.2 — A report is promoted in one click

**Status:** Testing
**Phase:** 105 — The reports hub can close a report honestly
**Depends on:** US-16.6 (the Reports hub), US-16.7 (`promote_app_issue`, migration 183), [us-105.1](us-105.1-a-report-can-be-marked-fixed.md)

## Story

As the manager, I want to promote a report to a work item **from the list**, so
that the common case — a bug that belongs to no epic — costs one click instead
of expand, open a dialog, accept the default, confirm.

Promotion was reachable only from the expanded detail, through `PromoteDialog`.
That dialog exists to ask the single thing a report cannot answer: which epic.
For a `bug` the honest answer is usually "none" — the dialog's own copy says a
standalone bug does not need one — so the manager's most frequent path through
it was to open it and change nothing.

## Design

### One click means the default, not a different transaction

The list action calls the same `promote_app_issue` RPC with `p_epic_id` omitted
(it defaults to `null`). Everything else is unchanged: one transaction, the
description pre-filled with the message, stack trace and provenance, the report
flipped to `promoted` and linked. The epic is an ordinary field on the work item
afterwards, so taking the default costs nothing that cannot be set later.

**The dialog stays.** It is the right surface when the epic matters, and it now
sits beside the one-click action rather than in front of it.

### No confirmation step

Promotion is additive and reversible in the ordinary way — it creates a work
item the manager can delete. `promote_app_issue` already refuses a second
promotion, so a double click cannot mint two work items; the client does not
need to guard that.

### Where it is offered, and where it is not

`canPromote` — open status, no `promoted_issue_id`, not the self-monitoring
wiring check (US-79.1) — gates the row action, the phone card and, newly, the
dialog inside the detail.

That last one fixes a real inconsistency this story exposed: the detail offered
`PromoteDialog` on an **ignored** report, and `promote_app_issue` refuses one
(`status in ('promoted','ignored')`). The button could only ever fail. It is now
not offered.

The RPC's guard does **not** list `fixed` — migration 184 added the status
without revisiting migration 183's check. Nothing in the UI reaches it, because
`canPromote` requires an open status. Left as-is rather than widened: changing
that guard is a migration, and no surface can currently trigger it. Noted here
so the next person finds it on purpose rather than by surprise.

## Acceptance criteria

- **AC1 — one click from the list.** An open, promotable report shows a promote
  action (↗, `title`/`aria-label` "Promote to a work item") in the desktop
  Actions cell and a **Promote** button on the phone card. One click creates the
  work item — no dialog, no confirmation.
- **AC2 — same result as the dialog.** The created item is a `bug` with the
  report's title and the pre-filled description; the report flips to `promoted`
  and links to it. The row updates in place; "Open the work item this became"
  appears in its detail.
- **AC3 — it is not offered where it cannot work.** No promote action on a
  wiring check, an already-promoted report, or any decided report — in the row,
  the card, or the detail.
- **AC4 — the dialog survives.** An open report still offers **Promote to work
  item** in its expanded detail, with the epic picker, unchanged.
- **AC5 — failure is legible.** An RPC refusal surfaces its message in an error
  toast; the row's status does not change.

## Out of scope

- Choosing an epic from the list. That is what the dialog is for.
- Bulk promotion, or any multi-select on the hub.
- Widening `promote_app_issue`'s guard to refuse `fixed` (see Design) — a
  migration, for a path no surface reaches.
- Undo. A wrongly promoted report is corrected by deleting the work item.

## Built (2026-08-16)

`apps/web/src/app/(app)/reports/reports-hub.tsx` only, alongside us-105.1. A
`promote()` helper calling `promote_app_issue` with no epic, a shared
`canPromote` predicate, and the action wired into the desktop row and the phone
card. The Actions column widened `w-20` → `w-40` to hold four actions.

**Verified.** `npm run build` passes. `promote_app_issue`'s signature
(`p_epic_id uuid default null`) and its double-promotion guard were read from
migration 183 before relying on either.

**Not verified.** No report was actually promoted from the list against a live
database — AC1 and AC2 are reasoned from the RPC the dialog already uses
successfully, not demonstrated. Worth one click in UAT.
