# US-79.5 — The database not answering is a 504 in words

**Status:** Completed
**Phase:** 79 — Production error truth
**Dependencies:** none
**Fixes:** prod BUG-6 (`ConnectTimeout`, issue `9b6ec5a5-c860-4158-853d-f7dd9a0c7309`)

## Story

As a manager recording a test-case result (or hitting any endpoint), I want a
moment where Supabase does not answer to come back as "the database did not
answer — nothing was recorded; try again", so that a transient network fault
is a retry, not a naked 500 and a raw `httpcore.ConnectTimeout` in the crash
inbox.

## Context

Twice in prod (both on `POST /releases/…/test-cases/…/result`,
apps/api/app/routers/releases.py:119 → `rpc("release_signoff_blocker")`), the
VM could not open a TCP connection to Supabase inside the timeout. The
exception climbed out of `httpx` unhandled: the manager saw "Internal Server
Error", and the inbox got a 200-line traceback titled `ConnectTimeout` with no
hint of *what* timed out. Every `postgrest_get`/`postgrest_patch`/`rpc` call in
`apps/api/app/supabase.py` shares this hole — the fix belongs there, once, not
in each of the ~40 call sites.

## Acceptance criteria

1. `supabase.py` maps httpx transport failures (`ConnectTimeout`,
   `ConnectError`, `ReadTimeout`, `PoolTimeout`) to a typed
   `SupabaseUnreachable` error carrying the operation (table or RPC name, verb)
   — never the URL's query values.
2. An exception handler answers it with **504** and a detail the UI already
   renders: "the database did not answer (<cause>) — nothing was recorded; try
   again". Display semantics: the manager sees that sentence in the toast, not
   "API error 500".
3. Idempotent reads (`postgrest_get`) retry once after a short backoff before
   surfacing the error; writes and RPCs are **never** blind-retried — a
   timeout does not prove the write failed.
4. It is still self-reported (an unreachable database is an incident), titled
   `SupabaseUnreachable` with the operation in context, so five different
   endpoints failing the same way dedupe into one legible report instead of
   five tracebacks.
5. Tests: a fake transport raising `httpx.ConnectTimeout` proves the 504 body,
   the single-retry-on-GET, the no-retry-on-POST/RPC, and the report row.

## Out of scope

- Circuit breakers, health probes, or connection pooling changes.
- Retry budgets beyond the single GET retry.
- The websocket data paths (`db.py`'s direct Postgres connections have their
  own error shapes and are untouched).

## Proof required to reach Testing

The tests above green; a captured 504 response body from a dev run with an
unroutable Supabase URL.

## Outcome

Built 2026-08-11 on `phase-79-production-error-truth` (commit `98d1b0c`).
Every PostgREST call in supabase.py (user-token, admin, and RPC paths) leaves
through one `_send()` door mapping ConnectTimeout/ConnectError/ReadTimeout/
PoolTimeout to a typed `SupabaseUnreachable` carrying "VERB table" (never
query values). Reads retry once after 0.5s; writes and RPCs never. The new
handler answers 504 with the exact sentence the AC pins and self-reports
titled `SupabaseUnreachable` with the operation in context.

**Verified:** `test_supabase_unreachable.py` — retry-once-then-raise on GET
(exactly 2 attempts), recovery on the retry, exactly 1 attempt for POST/RPC,
and the on-the-wire 504 body + report row via a faked transport. The handler
is registered in us-79.7's websocket-safety sweep.

**Not verified:** the captured 504 from a dev run with an unroutable Supabase
URL (the fake-transport test asserts the identical body); a real network
outage window.
