# US-107.1 — A work item can be marked fixed

**Status:** Testing
**Phase:** 107 — Fixed is an outcome, and nothing waits forever
**Depends on:** [us-105.1](us-105.1-a-report-can-be-marked-fixed.md) (`app_issues.fixed`), US-16.7 (`promote_app_issue`), migration 168 (`approve_run`'s parent rollup), US-6.2 (the Workbench waiting list)

## Story

As the manager, I want to mark a work item **fixed** without running it through
plan → code → review → merge, so that a defect I already fixed is recorded as
done — and the report it came from closes with it.

Until now the only way to clear one was **Abandon**, which records the opposite
of what happened. Abandoned means "we decided not to do this"; the whole point
here is that it *was* done. us-105.1 gave the Reports hub this outcome; the work
item it promotes into did not have it, so a bug fixed in passing left a
completed-in-reality item sitting open, or an abandoned one lying about why.

## Design

### `done`, not a new status

`issues.status` already has `done` — "complete, with no PR of its own" — set
today by the feature rollup in 033/126/140/168. Reusing it means every existing
consumer counts it correctly with no changes: `TERMINAL_STATUSES` in
`lib/epics.ts`, `HIDDEN_BY_DEFAULT` in the hub's filter, the stage tracker, and
the rollup itself. A new status would have needed all of them taught a new word.

### One transaction, three effects

`mark_issue_fixed` (migration 278) does the whole transition at once, for the
same reason `promote_app_issue` does:

1. the item → `done`, with a `marked-fixed` issue event recording what it came
   from and who did it;
2. the `app_issues` row promoted into it → `fixed` (us-105.1's status), so the
   Reports hub stops asking about something that is finished. Terminal there
   too — a recurrence opens a fresh report counting from one;
3. the parent feature → `done` **if this was its last open child**, mirroring
   `approve_run` exactly. Without this, marking the last story of a feature
   fixed would leave that feature open forever: the only other place that
   closes a parent is the approval path this item never travels.

A half-applied version of this is a completed bug whose report is still in the
inbox, which is precisely the inconsistency the RPC exists to prevent.

### What it refuses, and why the client knows the same rules

| refused | because |
|---|---|
| `type = 'feature'` | it completes when its last story does; marking it by hand strands its open stories under a completed parent |
| `merged` / `done` | already complete |
| `queued` / `running` | a worker is mid-flight — the same rule Abandon already applies |
| `abandoned_at` set | abandoned and fixed are different claims; restore first |

`lib/mark-fixed.ts` restates these for the client so no surface renders a button
the RPC would refuse — the shown-vs-enforced divergence us-14.6 fixed for
dispatch and us-106.1 avoided for held drafts. The RPC stays the authority; the
predicate only decides what to draw, and a test asserts the predicate and its
reason string can never disagree.

## Acceptance criteria

- **AC1 — the item completes.** Marking a `bug`, `chore` or `story` fixed sets
  it to `done`, stamps a `marked-fixed` event, and it leaves the Workbench.
- **AC2 — the report closes with it.** An item promoted from an app report
  moves that report to `fixed`; the Reports hub shows it under "Show decided",
  and a recurrence opens a **new** report at count 1.
- **AC3 — the feature follows.** Marking the last open child of a feature fixed
  completes the feature, with a `feature-completed` event carrying
  `via: marked-fixed`. A feature with other open children is untouched.
- **AC4 — a feature is never marked directly.** No surface offers it, and the
  RPC refuses it with the "mark the stories instead" message.
- **AC5 — an in-flight run blocks it.** A `queued`/`running` item offers no
  button, and the RPC refuses one with the stop-it-first message.
- **AC6 — it is offered on the Workbench and the item page.** A secondary
  action on the waiting-list row (table and phone card) and a button beside
  Abandon on `/issues/{id}`.
- **AC7 — the toast says what else closed.** The RPC returns `report_id` and
  `feature_completed`, and the toast names them rather than leaving the manager
  to go and check.

## Out of scope

- **The Issues hub.** Asked for, and **not built** — neither hub view
  (`issue-table-view`, `issue-outline-view`) has a per-row actions column at
  all; they are pure navigation lists. Adding one is a real change to both, not
  a button drop, and it is the least valuable of the three surfaces.
- Confirming before marking. Abandon does not, and Dispatch does not (us-106.1).
- Un-marking. `reset-stage-button` already exists for moving a status back.
- Recording *what* fixed it — a commit or release link. `done` records that it
  is finished, not by what.

## Built (2026-08-16)

- `infra/supabase/migrations/278_mark_issue_fixed.sql` **(new)** — the RPC.
  **Applied to both live projects** and verified present with
  `authenticated` execute and `anon` denied on each.
- `apps/web/src/lib/mark-fixed.ts` + `.test.ts` **(new)** — the shared
  predicate and its reason string, 8 tests including one that sweeps every
  type × status pair asserting the two agree.
- `apps/web/src/components/mark-fixed-button.tsx` **(new)** — one component for
  every surface, so they cannot drift on what the click does to the report.
- `apps/web/src/app/(app)/workbench/data.ts` — `TodoItem.markFixable`, computed
  once in `toItem` so no group can forget it.
- `apps/web/src/app/(app)/workbench/waiting-list.tsx` — the secondary action on
  both the table row and the phone card.
- `apps/web/src/app/(app)/issues/issue-actions.tsx` + `[id]/page.tsx` — the
  button beside Abandon; `IssueActions` now takes `type`.

**Verified.** `npm run build` compiles and type-checks; `npm run test:web` — 214
tests, 0 failures. The RPC's guards were written against the live
`issues_status_check` and the real `approve_run` rollup, both read from the
production database rather than recalled.

**Not verified.** Nothing was clicked: this checkout has no `apps/web/.env.local`
(the dev server 500s in `proxy.ts`) and no `apps/api/.env`, so the api pytest
suite — including `test_embed_ambiguity.py`, which CLAUDE.md asks for after a
types change — could not run either. The types edit adds a *function* signature
only and introduces no foreign key, so the embed graph is unchanged by
construction, but that is an argument rather than a green test. **AC1–AC3 and
AC7 are the ones to actually press in UAT** — especially AC2 end-to-end, and
AC3, which is the only path that writes to a row the manager did not select.
