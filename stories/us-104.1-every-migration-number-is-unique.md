# US-104.1 — Every migration number is unique

**Status:** Testing
**Phase:** 104 — The tree can be trusted
**Depends on:** CLAUDE.md's "applied in numeric order" rule, `scripts/migrate.py`, US-87.2 (`249_org_pending_count`), US-89.2 (`249_project_env`), us-100.5 / us-101.2 (the two 271s)

## Story

As the manager, I want a migration number to identify exactly one file, so
that "applied in numeric order" is a fact rather than a coin toss, and a fresh
replay of the tree produces the schema that is actually live.

`main` carries **five** duplicated numbers today: 014, 015, 205, 249 and 271.
Each pair came from the same cause — two branches numbering their migration
from the same starting point, neither able to see the other's choice, both
merged. At a duplicated number the apply order is whatever the filesystem
happens to return.

There is a second, sharper reason this story exists now. The fix for the 249
collision **was written on 2026-08-13 and then lost**. It sat on an unpushed
local branch (`claude/sad-noyce-e5ec95`, commit `1a5ebcb`) for three days,
went stale while it waited — it renumbered `249_project_env` to 252, and
`252_agent_effort_ledger.sql` landed on `main` on 2026-08-14 — and the branch
was deleted on 2026-08-16 during a cleanup. The work was recovered from the
object store. A guard that only exists on somebody's laptop is not a guard.

## Design

### Which file moves

The later arrival, always. The earlier migration's number is settled fact the
moment it is applied anywhere, and renumbering it would orphan ledger rows
that name it for no gain.

| number | keeps it | moves to |
|---|---|---|
| 249 | `249_org_pending_count` (phase 87) | `project_env` → **276** |
| 271 | `271_the_pass_is_decided_by_a_manager` (us-100.5, 20:41) | `a_release_case_knows_its_section` (us-101.2, 22:57) → **277** |

Both moved files are **already applied to both projects**. Renaming a file
does not re-apply it, and must not appear to.

### Why renaming is safe: identity is the stem, not the number

The recovered commit found the bug that makes this work at all. `migrate.py`
looked up the ledger by the file's prefix-stripped name, but rows applied
through Supabase's own migration path store the name verbatim — so the two
never matched, the skip-if-applied guard was dead for every prefixed row
(92 of 258 on prod, 44 of 247 on dev), and `migrate.py` would have offered to
re-run migrations that were already live. `strip_prefix` normalizes both sides.

Re-checked on 2026-08-16, the two ledgers do not agree with each other about
this very row: **dev** records `249_project_env`, **prod** records plain
`project_env`. Under the normalization all three of `276_project_env`,
`249_project_env` and `project_env` reduce to `project_env`, so the rename
cannot orphan a row or re-apply anything — on either project, despite them
disagreeing.

### The guard

`test_migration_numbering.py` fails in Essential the moment two files share a
number. 014, 015 and 205 are grandfathered — all long applied to both
projects, so their relative order is settled and renumbering them would only
orphan ledger rows. A paired test asserts each grandfathered pair **still
collides**, so a stale exemption cannot silently mask a fresh collision on the
same number.

## Acceptance criteria

- **AC1 — the live collisions are gone.** `249_project_env.sql` →
  `276_project_env.sql`; `271_a_release_case_knows_its_section.sql` →
  `277_a_release_case_knows_its_section.sql`. No number outside the
  grandfathered set has two files.
- **AC2 — nothing is re-applied.** Neither renamed migration is run against
  either project. `migrate.py` matches both to their existing ledger rows
  through `strip_prefix`, verified against the live ledgers on both projects
  including their disagreement about `project_env`.
- **AC3 — the guard runs in Essential.** `test_migration_numbering.py` fails
  on any new duplicate, asserts the grandfathered pairs still exist, and
  checks every migration is numbered at all.
- **AC4 — references follow the files.** `project_env.py`'s docstring,
  `migrate.py`'s `strip_prefix` example, and both migrations' own header
  comments name their new numbers and say why they moved.
- **AC5 — the ledger disagreement is recorded, not invented.** The prod/dev
  ledgers differ on 27 rows and are left alone; the header comment on
  `276_project_env.sql` states what is true of each rather than claiming they
  match.

## Out of scope

- Renumbering 014, 015 or 205, or reconciling the 27 disagreeing ledger rows —
  both would rewrite applied history to make a report look tidy.
- Any schema change. This story moves files and adds a test; it applies
  nothing.
- Enforcing numbering at dispatch time (a story could be told its number when
  it is planned) — worth considering if collisions recur despite the guard.
- The other half of Phase 104, us-104.2.

## Built (2026-08-16)

The 2026-08-13 fix was recovered from the object store (`git cat-file` on
`1a5ebcb`, still reachable after the branch delete) and cherry-picked rather
than rewritten, so its reasoning and its `migrate.py` bug fix survive intact.
Its one conflict was the us-89.2 story file, deleted from the tree when Phase
89 closed. It was then brought current: 252 was no longer free, so
`project_env` went to **276**, and the 271 collision it never saw was resolved
by moving the later arrival to **277**.

**Verified.** `test_migration_numbering.py` passes: no duplicate outside
014/015/205, each grandfathered pair still collides, every file numbered. Full
api essential suite 1931 passed (up 6 — the new guard). `story.py check` OK
across 15 stories.

Checked live before renaming, on both projects: the ledger rows for both moved
migrations exist and reduce to the same stem after `strip_prefix`, so neither
is orphaned and neither can be offered for re-application. That check turned
up something the recovered commit had recorded wrongly — the two ledgers do
not agree with each other on this row. **dev** stores `249_project_env`;
**prod** stores plain `project_env`. Both reduce to `project_env`, so the
rename is safe on each, but the file's header comment claimed they matched. It
now states what is actually true of each.

**Not verified.** No migration was applied or replayed — the story renames
files and adds a test, and a real replay of the tree from 001 has not been
done here, so "numeric order now yields the live schema" is argued from the
ledger rather than demonstrated. The 27 disagreeing ledger rows are untouched
by design.
