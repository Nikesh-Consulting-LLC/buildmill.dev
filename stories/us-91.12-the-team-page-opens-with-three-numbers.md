# US-91.12 — The team page opens with three numbers

**Status:** Completed
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** [us-91.11](us-91.11-an-agents-work-is-measured-in-seconds.md) (records what this shows)

## Story

As the manager, the Team page is a roster: who exists, what they can reach,
what they are doing this minute. It never answers the question I actually
bring to it — **is this team producing anything?** Which agent has done the
most work, which one has been idle all week, what did the workspace get for
the money.

Put three numbers across the top, and give every agent in the roster a row of
its own totals. The facts are recorded by us-91.11; this story is where they
become visible.

## Acceptance criteria

- **AC1 — three KPI tiles above the roster.** Full width, in this order:
  - **Work items completed** — merged in the last 30 days.
  - **Work items queued** — dispatched and not yet finished, **right now**.
  - **Agent work** — hours worked in the last 30 days, summed across every
    agent.
- **AC2 — every tile says what window it covers.** Two of these are 30-day
  windows and one is a live count; a tile that does not say which is a
  number nobody can act on. The window is stated on the tile itself, not in
  a tooltip.
- **AC3 — each agent row carries its own totals.** In the roster, for every
  agent: **hours worked**, **work items completed**, **lines of code**
  (`+added −removed`), **tokens**, and **dollars** — over the same 30-day
  window, with the all-time figures available on the agent's own page or on
  hover. A person's row shows no agent metrics rather than zeros.
- **AC4 — hours are rendered, seconds are stored.** Display follows the
  existing `formatDuration`/`formatMinutes` conventions (`3h 40m`, not
  `3.6667`). Nothing in the UI recomputes a duration from timestamps —
  everything reads `work_seconds` (us-91.11 AC1), so this page and the run
  pages can never disagree.
- **AC5 — the work item shows the effort it cost.** On the work-item page,
  beside the existing `Work item total: +X −Y lines · N files across R runs`
  line ([work-item-sections.tsx](../apps/web/src/app/(app)/issues/[id]/work-item-sections.tsx)),
  add the time and the money: hours worked and cost, attributed to the
  agent(s) whose runs did it. This is the same data the Team totals sum, read
  at the other end.
- **AC6 — one query for the tiles, one for the rows.** Both read
  `agent_effort_daily`, filtered by day range — not `runs`, and never one
  query per agent. The Team page's load must not grow with the number of
  runs the workspace has ever done (us-87.1, us-87.10).
- **AC7 — an empty workspace reads as empty, not broken.** With no agents,
  or with agents that have never run, the tiles show `0` with a line saying
  what would make them non-zero. No spinner that never resolves and no
  em-dash grid.
- **AC8 — the numbers reconcile with the surfaces that already exist.**
  Spot-check against `/admin/analytics/runs` and `/settings/spend` for the
  same window; if they disagree, the disagreement is the bug, and this story
  fixes it rather than shipping a fourth number.

## Out of scope

- Charts, sparklines or trends over time. Three numbers and a column of
  totals; a graph is a later story if the numbers prove worth watching.
- A selectable date range. 30 days is the window; making it adjustable is a
  follow-on.
- Ranking, leaderboards, or any per-agent quality judgement — lines of code
  is a volume measure and must not be presented as a merit one.
- Human productivity metrics. `user_activity_sessions` exists and this story
  deliberately does not surface it (us-91.11 AC6).
- Changing the roster's existing rows, actions, or live "working on" line.

## Verified (2026-08-14, localhost against build-mill-dev)

- The three tiles render above the roster, each stating its window:
  **Work items completed 8** (merged · last 30 days), **Work items queued 38**
  (dispatched, not finished · right now), **Agent work 8h 8m** (across every
  agent · last 30 days).
- `effortByPrincipal` reaches the client with real values — e.g. Tech.LEAD.002:
  11,342s, 1 completed, +982/−31 lines, 15.3M tokens, $71.73 — from one
  `agent_effort_daily` read over the window.
- Durations render through `formatWorkSeconds` (`3h 40m`), reading stored
  seconds; nothing recomputes a duration from timestamps.

**Not visible on dev**: the per-agent line on a roster row. The agents that have
effort in this workspace (Tech.LEAD.002, Architect.001, Programmer.001) have no
`organization_members` row — they were removed from the roster while their
workers and history remain — so the roster does not list them. The data reaches
the client correctly; the line renders for roster members with effort.
