# US-109.3 — Nobody wrote node_modules

**Status:** Testing
**Phase:** 109 — The Team page answers at a glance
**Depends on:** US-1.17 (`compute_diff_metrics`, the parser this changes), US-91.11 (`agent_effort_daily`, migration 252's accumulator), [us-109.2](us-109.2-the-team-kpis-price-the-work.md) (the tile that surfaced it)

## Story

As the manager, I want a run's change metrics to count only lines somebody
actually wrote, so that every figure derived from them — an agent's output, the
team's lines of code, the human-equivalent estimate, the cost-per-line in
reports — means what it says.

us-109.2 put a **Human equivalent** tile on the Team page. It read
**72,841 hours — about 9,105 days, 35 person-years**, over a 30-day window in
which 35 work items merged. The tile was arithmetically perfect. Its input was
not.

## What was actually wrong

One run:

| run | item | files | +lines | −lines | lines/file |
|---|---|---|---|---|---|
| `60af1e2a` | Recording status and detail APIs | **7,999** | **1,788,138** | 30 | 224 |

Every other run in the same 30-day window changed **fewer than 200 files**;
that day's others were 6–19 files and 200–2,900 lines. 7,999 files at 224 lines
each is not authorship, it is a dependency tree — `node_modules`, a `.venv`, or
a build output directory that the project's ignore rules did not catch — swept
into the changeset and counted as somebody's work.

That single run was **98.3%** of the workspace's reported 30-day output:

| | reported | authored |
|---|---|---|
| Lines added | 1,819,320 | **31,182** |
| Lines removed | 3,405 | **3,375** |
| Human equivalent | 72,841h (9,105 days) | **~1,315h (164 days)** |

164 person-days across 35 merged items — about 4.7 days an item — is a number
a manager can reason about. The other one is noise wearing a number's clothes.

It also came from **Sandy's X Developer**, a revoked worker no longer in the
org, so it inflated the org tile while no roster row could show it.

## Design

### The fix is at the ingest, not the tile

`compute_diff_metrics` counted every file in the stored diff. It now classifies
each path first, and the three totals — `lines_added`, `lines_removed`,
`files_changed` — count **authored files only**. Every consumer inherits the
fix: the Team KPIs, an agent's Output panel, the Costs page, the issue and
review pages, `agent_effort_daily` and everything rolled up from it.

### Vendored files stay in the record

They are **not** dropped from `change_breakdown`. They were genuinely in the
changeset, and hiding them would conceal the thing that went wrong — the run
page still lists them, now marked `area: "vendored"`, and the file-area summary
names the count ("12 frontend, 3 backend, 7981 vendored") rather than omitting
it. The totals exclude them; the record does not.

### Whole segments, never substrings

`dist` as a substring also matches `redistribute/`; `build` matches
`buildings.py`. Silently discounting real work is the one failure mode worse
than the bug being fixed, so matching is on whole path segments, and the
directory segments are judged separately from the filename. A file *named*
`docs/node_modules.md` is authored.

`vendored` is checked **before** the frontend/backend heuristic, because
`apps/web/node_modules/react/index.js` matches the frontend marker too — and
whichever check wins decides whether 1.8M lines count as somebody's work.

What counts as vendored: the dependency and output directories
(`node_modules`, `.venv`, `venv`, `vendor`, `.next`, `.nuxt`, `.turbo`, `dist`,
`build`, `target`, `coverage`, `__pycache__`, `site-packages`,
`bower_components`, `.git`), the nine common lockfiles by exact filename, and
`.min.js` / `.min.css` / `.map`.

### The rollup cannot fix itself

`agent_effort_daily` is an incremental accumulator — migration 252's trigger
adds each run's delta on its way to a terminal state. Nothing recomputes it, so
correcting `runs` alone leaves the rollup wrong forever. `recompute_run_metrics`
reparses every succeeded run that still holds its diff, then rewrites the three
line/file columns for **only** the `(org, worker, day)` keys whose runs moved.

`work_seconds`, `runs_finished`, `tokens_*` and `cost_usd` are deliberately
untouched: this change cannot affect them, and rewriting them from `runs` would
silently discard any correction made by hand.

It is dry by default. `--apply` writes.

### Why not just fix the one row

Because the next dependency-tree commit does it again, and because six other
surfaces read the same columns. Correcting the data without correcting the
parser fixes one number for one workspace until the next time.

## Acceptance criteria

- **AC1 — vendored lines are not output.** A changeset carrying
  `node_modules/`, a lockfile or a minified bundle reports only the authored
  files in `lines_added`, `lines_removed` and `files_changed`.
- **AC2 — the record still shows them.** Those files remain in
  `change_breakdown` with `area: "vendored"`, and the run's area summary names
  the count.
- **AC3 — authored work is never discounted.** `redistribute/`, `buildings.py`,
  `src/vendors/stripe-client.ts`, `distance.ts`, `package.json` and
  `target-picker.tsx` all still count. Pinned by test.
- **AC4 — vendored outranks the area heuristic.**
  `apps/web/node_modules/react/index.js` classifies as `vendored`, not
  `frontend`.
- **AC5 — all-vendored is zero, not unknown.** A changeset that is entirely a
  dependency tree returns `0`, not `None` — "parsed, produced nothing" and "no
  diff to parse" are different facts and must not collapse into a null column.
- **AC6 — the backfill corrects both tables.** `recompute_run_metrics --apply`
  fixes `runs` and the affected `agent_effort_daily` keys, and leaves
  work_seconds/tokens/cost alone.
- **AC7 — the Team page reads true afterwards.** Lines of code ≈ +31k −3.4k and
  Human equivalent ≈ 1,315h for the 30-day window.

## Out of scope

- **Stopping the vendored tree entering the changeset in the first place.**
  This makes the *metrics* honest; the submit path still accepts the files, and
  the run's diff still carries them. That is the deeper fix and it is a
  different story — it needs a decision about whether the factory refuses such
  a changeset, strips it, or warns.
- Backfilling runs whose diff was dropped by retention (us-87.8). No diff, no
  recompute; their metrics stay as recorded.
- The `.gitignore` of the affected project, which is the actual root cause of
  this instance and is not this repository's file.
- Any change to what `agent_effort_daily` stores, or to the trigger.
- Re-estimating the human-equivalent rate. us-109.2's 25 lines/hour is
  unchanged — it was never the problem.

**Verified.** api Essential suite 1936 passed / 586 skipped (no `DATABASE_URL`
in this checkout, so the SQL layer is untested here as usual); `npm run build`
compiles and type-checks; `npm run test:web` 236 passing. The 1.8M-line run and
its shape were confirmed by direct query against production before any code was
written.

**Not verified — and this is the important part.** The backfill has **not been
run**. `recompute_run_metrics` has never executed against a database: it needs
`apps/api/.env`, which is not in this checkout, and the run in question is large
enough that reading its `diff`/`change_breakdown` through the Supabase MCP
connector times out. So:

- the parser fix is tested but has not processed the real 1.8M-line diff;
- production still reports +1.8M lines and 72,841 hours;
- AC6 and AC7 are **unmet** until someone runs the script with a database
  credential — dry first, then `--apply`.
