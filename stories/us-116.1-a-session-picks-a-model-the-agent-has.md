# US-116.1 — A session picks a model the agent actually has

**Status:** New
**Phase:** 116 — An agent says what it is missing, and starts when told
**Depends on:** US-32.7 (`run_settings.resolve` — the one resolver for a run's
effective settings), US-66.1 (`model_overrides[kind]`, the agent's own per-kind
model pin), US-78.5 (no model, no run — never a CLI falling back to a default
nobody chose), US-83.2 (the session's CLI gets the same env a run gets),
US-116.3 (the session survives the machine — since 2026-08-14 every session
that passes this gate dies on a `NameError` in `session_host`; AC1 below
cannot be observed on prod until that lands). US-116.7 later adds a floor
below this resolver (the org's default provider model); this story changes
nothing about that and gets it for free.

## Story

As the manager, I want opening a CLI session with an agent to resolve a model
the same way dispatching work to that agent does, so that an agent which
happily runs plans all day does not refuse a conversation with a message
pointing me at a setting its own settings page will not show me.

## Design

### What happens today

`POST /agent-sessions` reads `db.session_model(worker)`
(`apps/api/app/db.py:10233`), which is two lines:

```python
overrides = (row or {}).get("model_overrides") or {}
routes    = (row or {}).get("model_routes") or {}
return str(overrides.get("code") or routes.get("code") or "")
```

Empty means refuse — `agent_sessions.py:129`, *"This agent has no model to
reason with — set one on its settings page under Model per role, then open the
session again."*

A **run** resolves nothing like that. `stamp_run_settings`
(`apps/api/app/routers/worker.py:120`) calls `run_settings.resolve()` with the
agent's run routes, the org's presets, the org default preset, the legacy
`model_routes` value, the agent's per-kind pin, and the supervisor and manager
layers — precedence **manager > supervisor > agent model pin > agent route/org
default**. That resolver's own docstring is the indictment:

> Resolution happens ONCE, here, server-side — never in the runner. A runner
> that resolved its own settings would be a second implementation of these
> rules, and the two would disagree.

`session_model` is that second implementation. It lives in the API rather than
the runner, which is the only reason the sentence did not already name it. It
skips the preset chain, the org default, the routes, and every layer above the
pin — and it hard-codes one kind.

### The kind is the actual bug

A session is a conversation, not a code run, so `session_model` picked the kind
closest to "free-form work" and hard-coded `code`. On the six active
interactive agents on prod today:

| agent | roles it claims | `code` pinned | session opens? |
|---|---|---|---|
| Programmer | code | `grok-4.5` | **yes** |
| NexDB.Programmer | code, merge, test | — | no |
| Architect | prd, breakdown, plan, guidelines, elaborate, wireframe | — | no |
| NexDB.Architect | same six | — | no |
| DevOps | test, release, deploy | — | no |
| NexDB.DevOps | release, deploy | — | no |

The Architect is the case that makes the point. Every one of its six roles is
pinned to `grok-4.5`. It has a model. It reasons with that model all day. It is
refused a session because it has no model for a kind **it is configured never
to do** — and the settings page renders a model picker only for roles the agent
claims (*"Only roles checked above are shown — a role this agent never claims
has no model to route"*), so the Code dropdown the error tells the manager to
set **is not on the page**. The only way to follow the instruction is to check
the Programming role, which also makes the Architect claimable for real code
runs. The message asks for something that cannot be done, to fix something that
is not wrong.

### A session resolves like a run, for a kind the agent has

The session asks the same resolver the same question, and asks it about a kind
the agent actually claims:

1. Read the agent's `enabled_kinds`. Try `code` first when it is among them —
   it stays the best proxy for free-form work — then the rest in `ROUTE_KINDS`
   order (`runner_socket.py:771`, the API's own list, which
   `agent-roles.test.ts` already pins the web roster against), so the choice is
   stable and explainable rather than dictionary order.
2. For each candidate, call `run_settings.resolve(kind=…)` with exactly the
   arguments `stamp_run_settings` passes. The first that yields a `model` wins.
3. That model is what the session mints its gateway key with and what the CLI
   is told to use — unchanged from today past this point.

A `null` `enabled_kinds` claims **every** kind (us-53.4 — a never-saved agent is
unrestricted rather than benched), so `code` is tried first for it exactly as
today. Nothing that works now stops working.

The session records **which kind it resolved through**, on the session row, so
"why is this conversation using Sonnet" has an answer that is not a guess.

### When there genuinely is no model, say what is missing

The refusal stays — US-78.5's rule is right, and a CLI falling back to a model
nobody chose is worse than a refusal. What changes is that it stops naming a
control that may not exist:

> **Architect** has no model for any of the roles it claims (Planning). Set one
> under Model per role on its settings page, or give the org's default preset a
> model.

It names the agent, the roles actually tried, and both places a model can come
from. Today's default preset is worth naming for a reason: **"Balanced" is the
default preset in every org on prod and its `model` column is `null`**, so the
org-default tier currently supplies nothing to anybody. An agent with no pin of
its own has no second chance, and the message should say so rather than imply
the preset will cover it.

The refusal stays a `409` with the same shape — only the text and the reasoning
behind it change.

### Where the code sits

`session_model` is replaced by a resolver call. The natural home is beside
`stamp_run_settings` — the two want the same six arguments, and a helper that
builds them once means the session cannot drift from the run again. The session
router keeps its gate; it just asks a better question.

## Acceptance criteria

1. Opening a session with an agent that pins a model for any role it claims
   succeeds, and the CLI reasons with that model. Specifically: **Architect**
   (six planning roles, all `grok-4.5`, no `code`) opens a session on
   `grok-4.5`.
2. The model a session resolves is produced by `run_settings.resolve()` with
   the same arguments `stamp_run_settings` passes — the preset chain, the org
   default, the legacy `model_routes` value and the agent's per-kind pin all
   apply, in the documented precedence. There is no second copy of the
   precedence rules anywhere in the session path.
3. The kind resolved through is `code` when the agent claims it, otherwise the
   first claimed kind in `ROUTE_KINDS` order that yields a model; it is
   recorded on the session row and readable afterwards. An agent whose
   `enabled_kinds` is `null` claims every kind and so resolves through `code`,
   as today.
4. An agent that pins nothing and whose org default preset names no model is
   still refused `409`, and the message names the agent, the roles it tried,
   and both places a model can be set — it does not tell the manager to set a
   role the agent does not claim.
5. **Programmer** (pins `code: grok-4.5`) resolves exactly as it does today —
   this story changes no working case.
6. A session opened on an agent whose only model comes from the org default
   preset uses that model, and says so via the recorded kind and the run
   settings' existing `sources` record.
7. `cd apps/api && python -m pytest` covers: resolution through a claimed
   non-`code` kind, `code` preferred when claimed, the org-default tier
   reaching a session, the refusal text naming the tried roles, and a `null`
   `enabled_kinds` behaving as today.
8. The API suite pins that the session path and `stamp_run_settings` build the
   resolver's arguments from one helper — a test that fails if a second copy of
   the precedence rules reappears.

## Out of scope

- **A dedicated "session model" setting.** It is the obvious alternative and it
  may still be right, but it adds a control to a page the manager already finds
  confusing, and it cannot explain the Architect case — an agent that has a
  model should not need a second one declared before it can be spoken to. If
  the resolved kind turns out to be the wrong answer often enough to notice,
  that is the story to write next, and this one makes it cheap.
- **Giving the default preset a model.** "Balanced" having `model: null` in
  every org is worth fixing and is not this story's business — a preset's model
  is the manager's choice, and this story only stops pretending the tier is
  populated.
- **Showing any of this on the Team page.** That is us-116.2, which is where
  the manager finds out *before* clicking.
- **The `code`-role gating on the settings page.** Whether a picker should
  render for a role the agent does not claim is a real question; this story
  removes the need to answer it by not requiring that picker.
- **Run dispatch.** Untouched. Runs already resolve correctly; this story only
  makes sessions agree with them.
