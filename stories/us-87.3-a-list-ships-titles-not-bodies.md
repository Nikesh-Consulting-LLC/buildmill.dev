# US-87.3 — A list ships titles, not bodies

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** nothing (`issues/page.tsx` + `issue-view-types.ts` + `lib/issue-search.ts`)

## Story

As the manager opening Work Items, the hub loads **every work item in the
workspace**, with each item's **full markdown body and acceptance criteria**,
regardless of which projects I have selected — and then narrows it in the
browser. `issues/page.tsx` says so out loud: "The hub always loads every
project in the active org so any stored/typed selection has its data ready;
the client narrows further to the selection."

There is no `.limit()`. No list view renders `body` or `acceptance_criteria`
— they are fetched only so the *client-side* realtime filter can re-run a
search the server already applied.

Measured on prod: 63 items carry 55 kB of body and 17 kB of acceptance
criteria; average body 902 B, largest 12,015 B. At 5,000 work items that is
~4.5 MB of markdown serialized into the RSC payload, shipped, parsed, and
held in React state on every load — to render titles.

## Acceptance criteria

- **AC1 — the list select carries no prose.** `VIEW_ISSUE_SELECT` drops
  `body` and `acceptance_criteria`. Any view that genuinely needs them
  fetches them for the one item it is showing.
- **AC2 — the query is scoped to the selection.** The server query filters
  to the globally-selected project ids (plus a deep-link seed), not to every
  project in the org. Changing the selection re-queries; it does not rely on
  everything already being in memory.
- **AC3 — the list is bounded.** The active-items query carries an explicit
  page size (default 200) ordered by `updated_at DESC`, with an honest
  "showing N of M" affordance and a way to load more. A workspace with 5,000
  items must not produce a 5,000-row payload.
- **AC4 — search stays correct.** Server-side search
  (`applyIssueSearch`) keeps matching title, body, acceptance criteria and
  GitHub number — the columns stay searchable in Postgres even though they
  stop being shipped. The client-side `issueMatchesQuery` filter on realtime
  payloads degrades gracefully when the row it receives has no `body`: it
  must not silently drop a matching item. If it cannot decide, it refetches
  that row rather than guessing.
- **AC5 — an index backs the order.** A migration adds
  `issues (project_id, updated_at DESC) WHERE abandoned_at IS NULL`, applied
  to **prod and dev**, with `database.types.ts` regenerated if the shape
  changes.
- **AC6 — proof.** The story records the measured RSC payload size for
  `/issues` before and after, on a workspace seeded with at least 1,000 work
  items.

## Out of scope

- Row virtualization — us-87.4 covers rendering cost; this story is about
  what crosses the wire.
- The Outline's grouping and nesting behavior, which is unchanged.
- Abandoned-items view pagination beyond the same default page size.

## Verification record

Built 2026-08-12 on `phase-87-performance`. Index shipped in migration 249
(`issues (project_id, updated_at desc) WHERE abandoned_at IS NULL`), applied to
both prod and dev.

**Verified:** `npm run build` type-checks clean; `npm run test:web` 93/93 with
8 new cases in `lib/issue-search.test.ts`. `VIEW_ISSUE_SELECT` no longer
carries `body` or `acceptance_criteria`. `hub-query.ts` is one definition of
the filter/order/select triple used by both the server's first page and the
browser's `Load more`, ordered `(updated_at desc, id desc)` so a timestamp tie
across a page boundary cannot repeat one row and lose another.

The realtime hazard was closed rather than accepted: `use-project-issues.ts`
DROPS a row when `issueMatchesQuery` returns false, so a false negative would
make an item vanish while the manager was looking at it. `search_text` -- the
generated column (migration 036) the server's own `applyIssueSearch` filters
on, and always present on a `postgres_changes` payload, which carries the whole
row regardless of this select -- is now checked first, and the new tests pin
that every field can only ADD a match, never veto one.

Scoping is safe because `GlobalProjectFilter` calls `router.refresh()` after
writing its cookie; that was checked in the source, so changing the selection
re-runs the server query rather than re-slicing memory.

**Not verified (UAT):**

- **AC6's payload measurement was not taken.** No workspace with 1,000+ items
  exists to measure against; that fixture is us-87.10's job.
- `Load more`, the "Showing N of M" footer, and the abandoned tab's paging were
  not exercised in a browser. Prod's largest workspace is far under the 200-row
  page, so **the paging path has never actually run** -- the most important UAT
  step in this story.
