# US-99.7 — A template edit offers itself to the projects using it

**Status:** Testing
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-99.6 (templates carry the whole file set)

## Story

As the superadmin, a template today is a starting pistol and nothing more. It
seeds a project at creation and is never read again — `seed_worker_instructions`
consults `org_project_template_sections` on project insert and that is the
last time the two ever speak. So when I find a real mistake in a template's
`Code.md` — an instruction that has been sending every agent down the same
wrong path — fixing the template fixes it for projects that do not exist yet,
and for nobody else. Ten existing projects keep the bad text, and my only
recourse is to open each one and paste.

But pushing the fix automatically is worse. A project whose manager
deliberately rewrote that instruction for their own repository would have
their work silently reverted by an edit made somewhere they cannot see.

So the template **offers**. When a template section changes, every project
bound to it is told, and its manager decides. And the offer can be honest
about the risk, because the database already records who last wrote each
instruction: a row still stamped `updated_by NULL` is one the project has
never touched, and taking the update costs nothing.

## Acceptance criteria

- **AC1 — a changed section is noticed.** Editing an
  `org_project_template_sections` row marks the projects bound to that
  template (via `projects.org_template_id`) as having a template update
  available, per section. Editing a **platform** template does not reach
  projects directly — it reaches orgs through the existing
  `copy_project_template_into_org` step, and only then does this apply.

- **AC2 — the offer names the risk.** The project surface shows which
  instructions its template has changed, and for each one whether the
  project has ever edited it — using `worker_instructions.updated_by`,
  which the `stamp_worker_instructions_editor` trigger
  ([052_worker_instructions.sql](../infra/supabase/migrations/052_worker_instructions.sql)
  L41) already maintains, with `NULL` meaning never edited. A never-edited
  instruction is offered as safe; an edited one shows a diff of what would
  be lost.

- **AC3 — the manager decides, per instruction.** Accepting applies the
  template's text to that instruction; declining dismisses the offer for
  that section at that version and does not ask again until the template
  changes again. Accepting all and declining all are available, and neither
  is the default action.

- **AC4 — accepting does not publish.** An accepted update writes to
  `worker_instructions` and leaves the project in the unpublished state
  us-99.4 defines, with its badge up. The commit is still the manager's
  click — a template edit made by somebody else must not put a commit in a
  project's repository.

- **AC5 — a declined offer stays declined.** Declining is recorded against
  the template section's current content, so a page reload, a re-seed, or an
  unrelated template edit does not resurrect it.

- **AC6 — org scoping holds.** All of this is org-scoped under existing RLS;
  a superadmin editing a platform template learns nothing about which orgs
  or projects accepted it beyond what they can already see. New tables, if
  any, are `is_org_member`-scoped and cross-org isolation is verified.

- **AC7 — both projects, types, sweep, tests.** Any migration applied to
  prod and dev, `database.types.ts` regenerated, embed sweep run. Essential
  tests: AC1's marking; AC2's edited-vs-never-edited classification against
  real `updated_by` values; AC3's per-section accept and decline; AC4's
  unpublished-but-uncommitted state; AC5's persistence. `npm run build`
  green.

## Verified (2026-08-15)

- **AC2 — the offer names the risk, and needed no new storage.**
  `GET /projects/{id}/instructions/template-offers` compares the project's
  `worker_instructions` against its bound `org_project_template_sections` and
  returns each differing kind with **both** texts and `safe_to_accept`.
  Safety is read from `updated_by`: null means the seeding trigger wrote it
  and nobody has touched it since (migration 052's
  `stamp_worker_instructions_editor` maintains that), so accepting reverts
  nothing. A non-null editor means a local edit would be lost, and the
  manager is shown exactly what.
- Counts split the set (`safe_count` / `conflicting_count`) so a surface can
  say "3 safe, 1 would overwrite your edit" without walking the list.
- **AC6** — org scoping holds: the project row is read under the caller's own
  JWT, so a project they cannot see answers 404 rather than leaking that it
  exists. No new table, therefore no new RLS.
- **AC4** — reading offers writes nothing, pinned by a test that fails if the
  endpoint ever touches a write path. Were that to regress, a superadmin's
  edit would reach every project the moment anyone opened a page.
- **8 tests**; api Essential green (**1780 passed, 545 skipped, 0 failed**),
  `npm run build` green, runner **323 passed**.

### Gaps — this is the read half only

- **AC1 (marking projects when a template changes)** is not built; the
  comparison is computed on read instead. That is honest and needs no
  migration, but it means nothing *notifies* a manager — they see it when
  they look.
- **AC3 (accept / decline, per instruction)** is **not built**. There is no
  apply endpoint and no decline record, so nothing can be actioned from the
  offer yet.
- **AC5 (a declined offer stays declined)** therefore does not exist either;
  it needs the storage AC3 would have added.
- **AC7** — no migration was needed, so nothing was applied to either
  database.

## Out of scope

- Applying template updates automatically, under any condition — including
  to never-edited instructions. AC2 makes that case *look* safe; it still
  waits for the click.
- Guideline and prompt sections. This story covers `worker_instruction`
  sections only; the other two section types keep their seed-once behavior.
- Propagating platform-template edits into org copies without the existing
  copy step (AC1 states the boundary).
- Any notion of a template *version* or history. The offer is against the
  template's current content, and declining is recorded against that content
  rather than against a version number.
