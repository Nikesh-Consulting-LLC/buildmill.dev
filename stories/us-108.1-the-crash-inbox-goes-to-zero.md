# US-108.1 — The crash inbox goes to zero

**Status:** New
**Phase:** 108 — The crash inbox goes to zero
**Depends on:** US-79.2–79.5 (the prod BUG-2/4/5/6 taxonomy), us-97.1 (owns the
301 root cause — see *Not this story*), us-105.1 (**Mark fixed** on a report),
us-107.1 (marked fixed on a work item), US-21.3 (`db.update_release`),
US-78.10 (`session.open`), US-3.12/3.13 (git-proxy addressing)

## Story

As the manager, I want every live crash in the production Reports hub either
fixed or closed, so that the inbox is a list of things that are wrong **now** —
not an archive where six already-fixed defects and six unfixed ones look
identical.

**The inbox does not currently say which is which, and that is half the
problem.** On 2026-08-16 `app_issues` on prod held 23 reports: 14 `new`, 8
`promoted`, 1 `ignored`. All eight promoted ones had been turned into work
items — and **all eight are still `draft`**, never planned, never coded. Yet
six of them were fixed in code weeks ago, by hand, under US-79.2–79.5 and
commit `f8d488e`. The `promoted` status recorded that somebody looked; it
recorded nothing about whether the code changed. So an audit of the eight had
to be done by reading every crash site in the tree against every stack trace.

That audit found **six real, unfixed defects**, two of them breaking live
paths today. This story closes those six and empties the inbox behind them.

## Design

### What the audit found

Read against the tree at `f8d488e`, the 23 reports fall into four groups.

**Already fixed — nothing to build, work items to close** (8 promoted + 1 new):

**The six this story fixes** are below, worst first.

### BUG-9 — a `jsonb` column is handed a `dict`

**4 occurrences, most recent 2026-08-16 16:45 UTC. Release-notes submission is
broken in production right now.**

```
psycopg.ProgrammingError: cannot adapt type 'dict' using placeholder '%s'
  release_prep.py:167 → db.py:1392
```

`db.update_release` ([db.py:1383](../apps/api/app/db.py:1383)) builds
`set {col} = %s` from the patch keys and passes `*patch.values()` raw.
`release_prep.submit` sends `notes_doc` — the coerced notes declaration, a
**dict** — into a `jsonb` column ([release_prep.py:203](../apps/api/app/release_prep.py:203)).
psycopg v3 will not adapt a bare `dict`; it needs `Jsonb(...)`.

This is a *generic* hole, not a `notes_doc` one: `update_release` accepts any
patch, and the next jsonb column added to `releases` fails the same way. Fix it
in the helper, not at the call site.

### BUG-10 — an interactive session dies on an undefined name

**1 occurrence; every session that reaches this line dies.**

[session_host.py:192](../apps/runner/supervisor/session_host.py:192):

```python
mcp_written = mcpconfig.write(
    workdir, os.environ.get("FACTORY_API_URL", ""), token, project_id, []
)
```

`token` is never bound in `_open`. It is a plain `NameError`, caught by the
`handle` wrapper and relayed to the API as the session's `error`, where
`agent_sessions.py:182` re-raises it as a 502 — so a **runner** bug arrives in
the inbox wearing an API path (`POST /api/v1/agent-sessions`) and a FastAPI
traceback. The value wanted is the worker token the credential helper already
reads from this process's environment (US-89.1).

Two things are wrong here, and the second is why it survived: nothing in the
runner suite executes `_open` far enough to bind that name, and a NameError in
a rarely-taken branch is invisible until a manager opens a session.

### BUG-11 — a NUL byte kills the runner socket dispatch

**3 occurrences.** [db.py:4601](../apps/api/app/db.py:4601):

```python
(exit_code, (output or "")[:20000], audit_id)
```

Command output is truncated but never sanitised, and Postgres `text` cannot
hold `\x00`. A runner command that emits one NUL — any binary on stdout —
raises `psycopg.DataError` out of `_dispatch`
([runner_socket.py:608](../apps/api/app/routers/runner_socket.py:608)), killing
the dispatch rather than the command's audit row.

The audit is a record of what ran, not a transport for the bytes. Strip and
say so.

### BUG-12 — an upstream that does not answer becomes a bare 500

**2 reports, 5 occurrences** — `httpx.ConnectTimeout` on `/git/…/info/refs`
and `httpx.ReadError` on `/api/v1/llm-gateway/v1/chat/completions`.

Neither [gitproxy.py](../apps/api/app/routers/gitproxy.py) nor
[llm_gateway.py](../apps/api/app/routers/llm_gateway.py) catches a single
`httpx` transport error — `grep` finds no `except httpx.` in either file. So
GitHub or the model provider being briefly unreachable produces an unhandled
exception, a naked 500, and a crash report titled with the httpx class name
and nothing else.

**US-79.5 solved exactly this shape, for Supabase only.** `supabase._send`
names its `_TRANSPORT_FAILURES` and raises `SupabaseUnreachable` carrying the
operation. The two remaining outbound edges in the app never got the same
treatment. This story does not invent a mechanism; it extends the one that
already exists to the other two upstreams.

### BUG-13 — "repository not found" when the repo is right there

**1 occurrence.** A session open on the *Power BI Project* answered:

```
502: git clone failed: fatal: repository
'https://api.buildmill.dev/git/kaushlesh-s-workspace/power-bi-project.git/' not found
```

The project exists, with that exact slug, that exact org shortname, and
`repo_full_name = kaushlesh-nikesh/demo`. It had been created **two minutes
earlier**. The 404 comes from the second branch of
[gitproxy.py:127](../apps/api/app/routers/gitproxy.py:127) — the worker is not
allow-listed for the new project — and answering 404 there is **deliberate**
(US-3.12: an unauthorised project must be indistinguishable from a
non-existent one, or the proxy leaks existence to an untrusted worker).

The 404 is right. What is wrong is that it reaches a **manager** as
"repository not found", which is a lie about the state of their project and
sends them to look at GitHub. The git wire is the wrong place to fix that; the
right place is the authenticated, manager-facing `POST /agent-sessions`, which
knows both the project and the worker and can check before it ever asks the
runner to clone.

### BUG-14 — a transient GitHub write is not retried

**1 occurrence.** `502: GitHub commit failed: could not build tree:
GitRPC::BadObjectState` on save-instructions
([projects.py:441](../apps/api/app/routers/projects.py:441)).
`BadObjectState` is GitHub-side and transient. `commit_files` is
blob → tree → commit → ref with no retry anywhere, so a moment of GitHub
indigestion costs the manager their Save. Lowest severity of the six, and the
cheapest.

### Not this story: the three redirect reports belong to us-97.1

Three reports — `AttributeError: 'str' object has no attribute 'get'` (15
occurrences, `ignored`), `TypeError: string indices must be integers` (2), and
`KeyError: 'object'` (1) — are the **same root cause**, and it is already
written up and unbuilt.

`github.list_open_pulls` ([github.py:652](../apps/api/app/github.py:652))
builds a bare `httpx.AsyncClient`, does not follow redirects, and only raises
on `>= 400`. GitHub answers a **renamed** repo with `301`, so `resp.json()`
returns the redirect body — a dict — and iterating it yields *strings* to
`worker.py:1211` (`p.get(...)` → AttributeError) and
`routers/github.py:328` (`p["number"]` → TypeError). `get_ref` has the same
gap, which is how `repo_docs.py:712` reaches `ref["object"]` on a payload
without one.

That is precisely us-97.1 AC1 ("no call site constructs a bare
`httpx.AsyncClient` for the REST API anymore") and AC2 (`get_ref` and friends
validate before indexing). Duplicating it here would produce two competing
fixes for one bug. **This story does not touch them** — it only requires that
when us-97.1 lands, those three reports are confirmed closed against it.

The 15-occurrence one is currently `ignored`, which is wrong: it is a live
crash on the submit path, ignored because it was unreadable. It should be
`promoted` to us-97.1's work item, or marked fixed when 97.1 ships.

## Acceptance criteria

- **AC1 — a jsonb patch value survives `update_release`.** `db.update_release`
  adapts `dict`/`list` values for `jsonb` columns (psycopg `Jsonb`), so a
  release-notes submit carrying `notes_doc` completes. Pinned by an Essential
  test that patches a dict-valued column and asserts the adapted parameter,
  and by a `release_prep.submit` test that would have failed before this
  change. The fix is in the helper: no call site pre-serialises.
- **AC2 — an interactive session opens.** `session_host._open` passes the
  worker token from the process environment to `mcpconfig.write` — no
  unbound name. A runner test drives `_open` far enough to execute that line
  with the surrounding calls faked, so the `NameError` cannot return
  unnoticed.
- **AC3 — a NUL byte does not kill the socket.** `finish_command_audit`
  strips `\x00` from output before writing (after truncation), and a runner
  command emitting binary output records its audit row and leaves the
  dispatch loop alive. Pinned by a test passing `"a\x00b"`.
- **AC4 — an unreachable upstream is said in words.** A transport failure
  (`ConnectTimeout`, `ConnectError`, `ReadTimeout`, `ReadError`, `PoolTimeout`)
  reaching out from the git proxy or the llm gateway answers **504** with a
  detail naming which upstream did not answer and during what — the shape
  US-79.5 established for Supabase — instead of an unhandled 500. The report
  is titled by that named condition, not by the httpx class, so five endpoints
  failing the same way dedupe into one incident. Pinned by tests that make the
  faked outbound call raise each class.
- **AC5 — a session refused for authorisation says so.** `POST
  /api/v1/agent-sessions` checks, before dispatching `session.open`, that the
  chosen worker is allowed for the project, and refuses with **409** and *"this
  agent is not authorised for <project> — add the project to its access list"*.
  It never reaches the clone, so the manager never sees "repository not found"
  for a project that exists. `gitproxy.py`'s 404 is **unchanged** — the
  existence-leak rule stands, and a worker hitting the wire directly still gets
  404. Pinned by a route test with a worker lacking the capability.
- **AC6 — a transient GitHub write is retried once.** `repo_docs.commit_files`
  retries the tree/commit step once, after a short backoff, on GitHub's
  retryable server-side conditions (`GitRPC::BadObjectState` and 5xx) — and
  only those; a 401, 403, 404 or a genuine conflict still fails immediately.
  A second failure answers exactly as it does today. Pinned by a test that
  fails once then succeeds, and one that asserts a 404 is not retried.
- **AC7 — the inbox reflects reality.** Every report in the *Already fixed*
  and *Not a code defect* tables above is closed on prod through the existing
  outcomes — **Mark fixed** (us-105.1) for the eight fixed ones, with the
  eight promoted work items closed through us-107.1's marked-fixed outcome;
  the two GitHub-credential reports resolved as configuration. The three
  us-97.1 reports are re-pointed at us-97.1 (the `ignored` one included) and
  left open. After this story the hub's open list is the six fixed here plus
  us-97.1's three, and nothing else.
- **AC8 — tests are Essential.** Every test above runs in the ~30s Essential
  suite with reads faked; none needs `DATABASE_URL` or the network. The runner
  test (AC2) runs in `apps/runner`'s own suite.

## Out of scope

- **The 301 redirect root cause and its three reports** — us-97.1 owns it, is
  written, and is unbuilt. See *Not this story*. This story must not add a
  competing fix at the two call sites.
- **Re-fixing the eight already-fixed reports.** They are closed as records
  (AC7), not rebuilt. If UAT shows any of them still reproducing, that is a new
  report, not this story.
- **The GitHub App credentials mismatch.** Configuration; the message already
  names the cure. Reconnecting the installation is a manager action.
- **Retrying anything other than the tree/commit step of `commit_files`** — no
  general GitHub retry policy, no retry on reads, no backoff ladder. AC6 is one
  retry on one named condition.
- **Auto-authorising a worker for a new project** (AC5 refuses honestly; it does
  not grant), and any change to how capabilities are assigned.
- **Reporting volume** — network-classified web reports (`kind: network`) still
  file. Whether a classified network failure should reach the inbox at all is a
  real question and a separate story.
- **`releases.notes_doc`'s shape**, the notes declaration itself, and
  `release_notes.as_declaration` — BUG-9 is a persistence bug, not a schema one.
- Indexing, retention, or performance on `app_issues` — us-87.8/87.9.
