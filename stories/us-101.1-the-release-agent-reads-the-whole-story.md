# US-101.1 — The release agent reads the whole story, not just its title

**Status:** New
**Phase:** 101 — A release explains itself
**Depends on:** nothing — this story is independently shippable and independently useful

## Story

As the manager, I want release notes and UAT instructions I can hand to a
tester without rewriting them. What I get is two paragraphs of prose and a
handful of test cases that read like their titles, because the agent that
writes them has almost nothing to write from.

Here is everything a release-prep agent receives today, in full: a version
string, the list `[{issue_id, title, type, display_id}]` snapshotted at cut,
the **first line** of each commit message, and a list of changed file paths
with `+`/`-` counts. That is the entire input to `get_release_changes`
([factory_mcp.py](../apps/api/app/factory_mcp.py) L2341).

From that you cannot write "tick two branches, then reload — both still
ticked". You can only write "us-98.2 was included". The gap between those two
sentences is the whole of this phase, and no amount of prompt-writing closes
it: the acceptance criteria that say what the story promised are not in the
payload, the plan that says how it was built is not in the payload, and the
test cases the story already carries are not in the payload either.

That last one has a sharp edge. `attach_release_inherited_cases` copies every
included story's own active test cases onto the release **at submit time**,
server-side, seconds after the agent hands back
([release_prep.py](../apps/api/app/release_prep.py) L74). So the agent authors
"regression cases for the release as a whole" while blind to the twenty cases
that are about to land beside them. Duplication is not a risk here, it is the
default.

Three things in the payload are also simply wrong or missing, and they are
cheap:

1. `message` is built with `.strip().splitlines()[:1]` — a **list**, not a
   string. Every commit reaches the agent as `["subject"]`.
2. `commit_count` is `len(commits)`, but GitHub's compare API caps `commits`
   at 250 and reports the truth in `total_commits`, which is never read. A
   large release silently understates its own size.
3. `touched_modules` is computed at cut by matching changed files against
   `project_modules.path_globs`, stored on the release, and **never shown to
   the agent** — the one piece of "what area of the product moved" the system
   already knows.

And `path_prefix` filters the file list *after* the 300-file cap, so
`get_release_changes(path_prefix="infra/supabase/migrations/")` on a big
release can answer with an empty list that looks authoritative.

## Acceptance criteria

- **AC1 — every included work item arrives with its requirement.** Each entry
  in `work_items` carries, in addition to today's four fields, the item's
  description and its acceptance criteria. Text is capped per item, and the
  cap is stated in the payload rather than applied silently — a truncated
  requirement must be visibly truncated.

- **AC2 — the agent sees the cases it is about to be given.** Each work item
  carries the **titles** of the active test cases it already owns — the exact
  set `attach_release_inherited_cases` will copy onto this release. Titles
  only, not steps: enough to not duplicate, not so much that the payload
  doubles.

- **AC3 — the release's own facts arrive with it.** The response carries
  `touched_modules` (already stored on the release) and `migrations` — the
  migration files in the range, derived **server-side from the full file list
  before any cap or prefix filter**, so the answer does not depend on the
  agent guessing this project's migration folder.

- **AC4 — a commit message is a string.** `message` is the commit's subject
  line as a string. Pinned by a test, because this shipped once.

- **AC5 — the range says how big it really is.** `commit_count` reports
  GitHub's `total_commits`, not the length of the returned page, and a range
  that exceeds what was returned says so in `note` in a sentence naming what
  was withheld.

- **AC6 — `path_prefix` filters before the cap, not after.** Narrowing by
  prefix returns the first N matching files, never the matching subset of an
  arbitrary first 300. A prefix that matches nothing is distinguishable from a
  prefix whose matches fell off the end.

- **AC7 — the first release is honest about the difference.** A first release
  has no compare range and therefore no file list; `migrations` is empty
  *because the range is unknown*, not because there are none, and the payload
  says which of the two it means.

- **AC8 — one tool, one round trip.** All of this rides on
  `get_release_changes`. No second tool: a second tool is a second thing an
  agent forgets to call, and this one is already the first call the prompt
  demands.

## Out of scope

- Anything the agent writes. This story only changes what it can read —
  us-101.3 and us-101.6 govern the output.
- The `section`/`critical` columns on a case (us-101.2) and the notes
  declaration (us-101.4).
- Full diff text. Paths, counts, requirements and prior cases are the
  material for acceptance-level testing; hunks are not, and they would blow
  the payload apart.
- Env var values. `get_environment` withholds them without a run, and a
  release prep is not a run.
- The unrelated `NameError` at [repo_docs.py](../apps/api/app/repo_docs.py)
  L798 (`digest` is never assigned in `_sync_tree_locked`), found while
  reading this area. It deserves its own story.
