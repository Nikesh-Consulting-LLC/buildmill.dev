# US-101.2 — A release case knows its section, its story, and whether it is critical

**Status:** Testing
**Phase:** 101 — A release explains itself
**Depends on:** us-101.1 (the agent must be able to see the stories before it can tag them)

## Story

As the manager running UAT, I want the release's checklist to have a running
order — pre-flight first, the happy path next, then the refusals, then
regression — because the order is the instruction. "Work top to bottom, the
happy path first, because every refusal below assumes a merge chore exists to
refuse" is a sentence that only means anything if the list is actually in that
order.

Today a release's cases are a flat list ordered by `issue_id` then `title`
([page.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/page.tsx) L65–71),
which is to say: ordered by a UUID. `test_cases` has nineteen columns and none
of them is a section, a position, or a priority — the last DDL to touch the
table was migration 243's `module_id`. So there is no way to say that the two
or three checks tests genuinely cannot do for you — "open the diff and confirm
both branches' changes are actually present" — are different from the twenty
that are routine.

`test_cases` already carries `issue_id`, and the release page already renders
its provenance
([release-test-cases.tsx](../apps/web/src/app/\(app\)/releases/[releaseId]/release-test-cases.tsx)
L241–257). The gap is one-directional: `attach_release_test_cases`
([db.py](../apps/api/app/db.py) L1437–1482) inserts exactly seven columns —
`org_id, project_id, release_id, title, steps, expected_result, source` — and
`issue_id` is not among them, while `attach_release_inherited_cases`
([242_inherit_automated_cases.sql](../infra/supabase/migrations/242_inherit_automated_cases.sql)
L19–66) copies fifteen columns including `issue_id`. An agent-authored case is
therefore permanently unattributable: it renders as "Regression case for this
release" and can never link back to the story it exists for.

This story gives a case the three properties the running order needs, and lets
the agent set the one that already exists.

## Acceptance criteria

- **AC1 — a case has a section, a position, and a criticality.** `test_cases`
  gains `section` (free text), `sort` (integer), and `critical` (boolean,
  default false), in the next free migration. A case with no section is not an
  error — it lands in a default section rather than being refused, because a
  refused hand-back costs a whole re-run.

- **AC2 — the sections have a canonical order, and an invented one still
  works.** The factory names the sections it expects — pre-flight, the happy
  path, the refusals, regression, and a catch-all — and orders them. A section
  the agent invents is appended after the known ones rather than rejected: a
  release that genuinely needs "Data migration" as a section should get it.

- **AC3 — an agent can tag its own case with the story it tests.** The
  `test_cases` element accepted by `submit_release_notes` carries the work
  item's display id, and the server resolves it to `issue_id`. The element
  type widens from `dict[str, str]` to carry the new fields.

- **AC4 — a tag that is not in this release is refused.** An id outside the
  release's `included_items` is rejected at hand-back, naming it. Without
  this, an agent can tag a case with an issue the release does not contain,
  and the page's display-id map silently renders no provenance at all — a
  wrong answer that looks like a missing feature.

- **AC5 — inherited cases land in the running order too.**
  `attach_release_inherited_cases` carries the new columns, so the cases
  copied from included stories arrive with a section rather than as an
  unsorted tail. The function is replaced whole, forward from migration 242's
  body, the way 242 replaced 132's. Its `(issue_id, title)` dedup key, which
  compares with `is not distinct from` so null-issue `always_on_uat` cases
  dedup correctly, is preserved exactly.

- **AC6 — `critical` is a badge and nothing more, for now.**
  `release_signoff_blocker` — now at
  [241_suite_results_gate.sql](../infra/supabase/migrations/241_suite_results_gate.sql)
  L22–121, which also gates on a stale UAT build and on suites marked
  `blocks_signoff` — is not touched. Every active case still needs a verdict,
  and none may fail or block. Whether a critical failure should block *harder*,
  or a non-critical one block at all, is a product decision the manager has not
  made, and that function gates the entire release lifecycle.

- **AC7 — the test library does not change shape.** `test_types` stays the
  curated `unit` / `regression` / `pre-release` taxonomy that drives the
  library's filters. Section and criticality are properties of *this
  release's running order*, not of the project's permanent test library, and
  must not be smuggled into that field.

- **AC8 — the widened element lands on both transports, and the existing
  divergence is closed while we are here.** The MCP tool
  ([factory_mcp.py](../apps/api/app/factory_mcp.py) L5541) and the HTTP twin
  (`ReleasePrepSubmit`, [worker.py](../apps/api/app/routers/worker.py)
  L1426–1435) must accept the same case shape.

  Note what is true today, because it changes this AC from a formality into a
  fix: us-100.6 added `proposed_version` and `version_rationale` to the MCP
  tool and **not** to the HTTP model, so the two transports have already
  diverged — a git-native worker submitting over HTTP cannot propose a
  version at all. `release_prep.submit` accepts both parameters and is still
  the single validation choke point, which is what kept this from becoming a
  correctness bug; the module exists precisely because these two diverged once
  before.

## Verified (2026-08-15)

- **AC1** — migration **271**, applied to **both** databases: `test_cases`
  gains `section text`, `sort integer`, `critical boolean not null default
  false`. Confirmed on dev and prod via `information_schema`.
- **AC2** — `release_notes.SECTIONS` names five and orders them;
  `normalize_section` maps what agents actually write ("Happy Path",
  "preflight", "regressions") and keeps an invented one as a slug;
  `section_rank` puts invented sections after every known one.
- **AC3/AC4** — `attach_release_test_cases` now inserts `issue_id`, `section`,
  `sort` and `critical`; `check_cases` resolves a `story` display id against
  `included_items` and refuses one outside the release, naming it and listing
  what is included.
- **AC5** — `attach_release_inherited_cases` v3 carries the three columns,
  defaulting a source case with no section to `regression`. 242's
  `is not distinct from` dedup and its `project_id` filter are preserved
  verbatim.
- **AC6** — `release_signoff_blocker` untouched; `critical` renders as a
  badge only.
- **AC7** — `test_types` untouched; section and criticality are their own
  columns.
- **AC8 — and the divergence us-100.6 left is closed.** `ReleasePrepSubmit`
  gains `proposed_version`, `version_rationale`, `notes_doc` and `uncovered`,
  and its `test_cases` element widens to `dict[str, Any]` (it was
  `dict[str, str]`, which could not have carried `critical` or `sort` at all).
  The version-proposal check **moved into `release_prep.submit`** so both
  transports are governed by construction rather than by two copies.
- **34 pure tests** in `test_release_notes_vocabulary.py`; **4** in
  `test_release_section_map.py` pinning the web mirror against the Python in
  both directions, with the parsers asserted non-vacuous.
- api Essential green; `npm run build` green; `npm run test:web` 188 passed.

### Not verified

No live release. The migration is proved applied and the rules are proved by
tests; nothing has yet written a sectioned case through a real agent.

## Out of scope

- Validating that a case *has* steps and an expectation — us-101.3.
- Rendering any of this — us-101.5.
- Editing section or criticality by hand in the UI. The agent writes the
  running order; the manager's lever is sending the release back, not
  re-sorting it.
- Giving `critical` teeth in the sign-off gate.
- The suite-gating and stale-UAT-build rules migration 241 added to
  `release_signoff_blocker`. They are untouched.
