# US-99.1 — Every instruction kind has a file, and one map says which

**Status:** New
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-98.1 (`merge` exists, so the file set is complete on arrival)

## Story

As the manager, my workers' instructions live in a database and are handed
to them as prose inside a context payload. That means the repository — the
thing an agent actually works in, the thing a human opens to understand a
project — says nothing about how work is done in it. It also means the
instructions are invisible to every tool that reads repositories, unversioned
against the code they describe, and impossible to review as a diff.

They move into the repository. One markdown file per instruction kind, under
`.buildmill/`, referenced from `AGENTS.md`. An agent fetching its workspace
gets them for free, because they are files in the tree it already has.

This story establishes the map and nothing else — which kind writes which
file — because that map is the thing every later story in this phase reads,
and the one thing that must not exist in two places. Phase 96 spent three
migrations establishing that the type-to-instruction mapping lives in exactly
one function so its two call sites cannot disagree; the kind-to-file mapping
gets the same treatment for the same reason.

Sixteen kinds get files. Three instruction kinds do **not**:
`story_breakdown`, `test_case_elaborate` and `deploy_script_generate` are
server-side LLM prompts driven by `LLM_FUNCTIONS`
([llm.py](../apps/api/app/llm.py) L46) — no agent ever reads them, and they
are platform-global rather than per-project. They stay where they are.

## Acceptance criteria

- **AC1 — the map exists, once.** A single declaration maps instruction kind
  to filename, readable by both the api and the web app without either
  restating it. It covers exactly:

  | kind | file | | kind | file |
  |---|---|---|---|---|
  | `prd` | `PRD.md` | | `chore` | `Chore.md` |
  | `breakdown` | `Breakdown.md` | | `merge` | `Merge.md` |
  | `plan` | `Plan.md` | | `test` | `Test.md` |
  | `standalone_plan` | `Plan_Standalone.md` | | `wireframe` | `Wireframe.md` |
  | `bug_rca` | `RCA.md` | | `elaborate` | `Elaborate.md` |
  | `code` | `Code.md` | | `deploy` | `Deploy.md` |
  | `standalone_code` | `Code_Standalone.md` | | `release` | `Release_Prep.md` |
  | `bug_fix` | `Fix.md` | | `guidelines` | `Guidelines_Refresh.md` |

  All files sit under `.buildmill/`. `Guidelines.md` is reserved for the
  project's conventions and belongs to no kind — us-99.3 owns it.

- **AC2 — the map is total, and proved to be.** A test asserts that every
  value in `worker_instructions_run_kind_check` is either in the map or in
  the named LLM-function exclusion list — so a future kind added without a
  file fails a test rather than silently producing an instruction nobody can
  read. The exclusion list is written down with its reason, not implied.

- **AC3 — the mapping is reversible and unambiguous.** Filename to kind is a
  function too: no two kinds share a file, and a file not in the map is not
  treated as an instruction file. Pinned by a test.

- **AC4 — nothing changes yet.** This story adds no writes to any
  repository and no change to how any instruction is served. It is the map
  alone, so that us-99.2 through us-99.7 can each be read and reviewed
  against a fixed vocabulary.

- **AC5 — documented.** The file set and the three exclusions are recorded
  in [docs/application/domain-objects.md](../docs/application/domain-objects.md)
  alongside the existing instruction-kind notes.

## Out of scope

- Writing any file to any repository — us-99.2.
- `AGENTS.md`'s content or ownership — us-99.2.
- Project conventions and `Guidelines.md` — us-99.3.
- Publishing, and the uncommitted-changes warning — us-99.4.
- What an agent reads at run time — us-99.5.
- Templates — us-99.6, us-99.7.
- Rewording any instruction's default text. Kinds keep the text Phase 96 and
  us-98.1 gave them; only their destination changes.
