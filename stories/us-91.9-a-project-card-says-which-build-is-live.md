# US-91.9 — A project card says which build is live

**Status:** Testing
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** nothing

## Story

As the manager, the Projects page shows each project's deployments as small
cards — name, environment, URL, and a dot reading `succeeded` or `failed`.
That answers "did the last deploy work", which is not the question I open
this page with. The question is **which build is on UAT, and which is on
production** — because that is what tells me whether the release I signed off
this morning actually went out, and whether UAT is ahead of production or
behind it.

Today the answer takes three clicks per environment: project → deployment →
read the current run. On a page whose whole purpose is the at-a-glance view,
the one fact worth glancing at is missing.

Every deployment already records the build it is running:
`deployments.current_run_id` points at the `deployment_runs` row that is
live, and that row carries `release_id`. So the version is one hop from data
the page already loads — no new bookkeeping, and it cannot disagree with the
deployment page, because it is the same row.

## Acceptance criteria

- **AC1 — each deployment card names its live build.** Under the deployment
  name, a line reading the release version currently deployed (e.g.
  `2026.08.13.1`), in the mono/tabular style versions use elsewhere. This
  applies to every deployment on the card — which is how UAT and production
  each get answered — not only to the two named environments.
- **AC2 — the version comes from the live run, not the newest release.**
  Resolved as `deployments.current_run_id` → `deployment_runs.release_id` →
  `releases.version`, the same chain the deployment page reads. A release
  that was cut, or signed off, but never deployed here must **not** appear
  on this card. What is live is a fact about the deployment, not about the
  release list.
- **AC3 — a rollback tells the truth.** After a rollback, `current_run_id`
  points at the restored run, so the card shows the version that is actually
  serving — not the rolled-back one. Verify this against a real rolled-back
  deployment (`rollback_to_run_id` set) before claiming the criterion.
- **AC4 — an off-release deploy says so.** A live run with no `release_id` —
  a branch deploy, an uploaded zip, a manual override — shows the short
  commit sha (or the zip filename when there is no sha) with a plain marker
  that it is not a release build. Borrowing the last release's version here
  would be the worst possible lie on this card.
- **AC5 — never deployed reads as never deployed.** A deployment with no
  `current_run_id` keeps today's `Never deployed` line and gains nothing
  else. A deployment whose last run failed still shows the version that is
  live *plus* the existing failed indicator — a failed deploy does not
  change what is serving.
- **AC6 — the version links to its release.** Clicking it opens
  `/projects/{projectId}/releases/{releaseId}`; the rest of the card still
  links to the deployment, and the two targets must be visibly distinct
  enough not to be clicked by accident.
- **AC7 — two queries, not two per project.** The existing deployments load
  in [projects/page.tsx](../apps/web/src/app/(app)/projects/page.tsx) gains
  `current_run_id`, plus one batched `deployment_runs` read over those ids
  and one batched `releases` read over the release ids found. No per-project
  and no per-deployment query (us-87.1, us-87.10).
- **AC8 — the compact card stays compact.** One extra line per deployment,
  truncating rather than wrapping. Ten projects with four deployments each
  must still read as a grid of cards.

## Out of scope

- The project **detail** page's deployment tab, which already shows the
  live run's commit and message — this story is the Projects list card.
- Showing release *status* (signed off, promoted, rejected) on the card, or
  a UAT-vs-production drift indicator ("UAT is 2 releases ahead"). Worth
  having; a separate story once the version itself is on screen.
- Any change to how `current_run_id` is maintained, to the release
  lifecycle, or to the deployments list on the dashboard's Releases tab.

## Verified (2026-08-14, localhost against build-mill-dev)

- A deployment serving a run with no `release_id` reads **`off-release ·
  8c5d3e3`** — named as a commit, never dressed up as a version (AC4).
- A deployment with no live run still reads `Never deployed` (AC5).
- Two batched reads for the whole page (the live runs, then their releases).

**Not exercised on dev**: the version + release link (AC1/AC6). No deployment
in the dev workspace is serving a release build. Production has one — its UAT
deployment is serving `2026.08.13.1` — so that path shows up in the prod UAT.
