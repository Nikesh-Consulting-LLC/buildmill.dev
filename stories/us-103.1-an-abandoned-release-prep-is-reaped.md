# US-103.1 — An abandoned release prep is reaped

**Status:** Testing
**Phase:** 103 — A release cannot get stuck
**Depends on:** migration 215 (`release_prep_runs`, US-63.3), `db.fail_release_prep`, US-3.2 (`requeue_expired_claims`), US-13.6 (the 60-second liveness sweep), US-90.1 (release retry)

## Story

As the manager, when the agent preparing a release stops existing — the runner
restarted, the machine died, the process was killed — I want the release to
land on `failed` by itself within a minute or two, so the Retry button that
already exists becomes reachable and the project is not locked out of cutting
releases by a job nobody is doing.

The defining incident: release **2026.08.16.3** (Demo, prep
`e755bd82-c99e-4be1-b1ac-aff912e2e931`, worker Architect). The prep was claimed
at 13:36 UTC. The runner restarted around 13:46, ten minutes in, taking its
supervising task with it. The lease expired at 15:46. At 16:12 the row was
still `running`, the release was still `running`, the worker was online and
healthy — and nothing anywhere was going to change that. It was failed by hand
against the production database.

Every other kind of claimed work in this factory has a reaper.
`requeue_expired_claims` ([db.py:7720](../apps/api/app/db.py:7720)) sweeps
`runs` on startup, on every pool listing, and every 60 seconds from the
liveness loop in [main.py:126](../apps/api/app/main.py:126). Release prep has
its own claim, its own heartbeat (`heartbeat_release_prep`, a two-hour lease)
and its own submit — and no sweep at all. Grep every use of
`release_prep_runs` across the API: claim, heartbeat, complete, fail, the
queued-pool listing, the retry dispatch. Nothing reads `claim_expires_at`.

That omission is not merely untidy. `releases_one_in_flight_per_project`
(migration 215) counts `running` as in flight, so one orphaned prep blocks
**every future cut for that project**, permanently, with no UI able to clear
it.

## Design

### The reaper is small because the landing is already built

`fail_release_prep` ([db.py:5475](../apps/api/app/db.py:5475)) already does
exactly the right thing, and its docstring already names the 2026-08-01
incident it was written for: it moves the prep to `failed`, stamps the error,
and moves the release to `failed` with a `failure_reason`. A release at
`failed` with `notes_written_at` null is precisely the state `/releases/{id}/retry`
([releases.py:293](../apps/api/app/routers/releases.py:293)) accepts, and the
Retry button already renders for it
([releases/page.tsx:271](../apps/web/src/app/(app)/releases/page.tsx:271)).

So this story adds the one missing step: find expired running preps, and put
them down the path that already exists. `reap_expired_release_preps` selects
`status = 'running' and claim_expires_at < now()` `for update skip locked`,
and routes each through the same failure path with a lease-expiry reason
naming how long it was held and which worker held it.

### Where it runs

The three places `requeue_expired_claims` runs, for the same three reasons
US-13.6 gave: at startup (the restart that orphaned the row is often the same
restart that boots the API), on the 60-second liveness sweep (so it surfaces
with no worker polling), and before the release-prep pool listing (so a runner
asking for work also clears the corpse blocking it). Cadence matters less than
it does for runs — a two-hour lease means the reaper fires hours after the
agent died — which is exactly why us-103.3's manual Stop is the companion
story, not an alternative to this one.

### Not a requeue

An expired `runs` claim goes back to `queued` and another worker takes it.
Release prep deliberately does not: it goes to `failed` and waits for the
manager. Retry is a manager decision here because a prep that died may have
burned a paid session, and because `dispatch_release_prep_for`
([db.py:1316](../apps/api/app/db.py:1316)) refuses while any prep for the
release is `queued` or `running` — an auto-requeue would silently re-enter a
loop the manager cannot see. `releases.failure_reason` says what happened in
plain words, the failed `release_prep_runs` row keeps the attempt history the
detail page already renders, and the manager clicks Retry.

## Acceptance criteria

- **AC1 — the sweep exists.** `db.reap_expired_release_preps(settings)` fails
  every `release_prep_runs` row that is `running` with `claim_expires_at <
  now()`, through the existing `fail_release_prep` path (prep `failed` +
  release `failed` + `failure_reason`), and returns how many it reaped. It
  uses `for update skip locked` and is safe to run concurrently with a live
  claim, heartbeat, or submit.
- **AC2 — it runs on the same three triggers as the run reaper.** API startup,
  the 60-second liveness loop in `main.py`, and the release-prep pool listing.
  A non-zero reap logs at warning level, naming the release version and how
  long the prep was held.
- **AC3 — the wording is honest.** The prep's `error` and the release's
  `failure_reason` say the lease expired without the agent reporting, name the
  worker and the hold duration, and state that no notes were written — not a
  fabricated agent failure. A reaped release shows Retry, and clicking it
  dispatches a fresh prep against the same pinned `commit_sha` and `version`.
- **AC4 — a live prep is never reaped.** A prep whose heartbeat is current
  survives every sweep. Pinned by a test that heartbeats, sweeps, and asserts
  the row is untouched.
- **AC5 — the project is unblocked.** After a reap, the in-flight uniqueness
  index no longer counts the release, so `POST /projects/{id}/releases`
  succeeds and `build_preview` reports no in-flight blocker.
- **AC6 — a late zombie cannot resurrect it.** If the original agent comes
  back after the reap and calls submit, it is refused: `release_prep.submit`
  already requires `status == 'running'`
  ([release_prep.py:84](../apps/api/app/release_prep.py:84)), and the test
  pins that the refusal is a plain sentence naming the expiry, with nothing
  written to the release.
- **AC7 — tests.** API: expired prep is reaped and the release lands `failed`;
  a current prep is not; the reaped release passes `/retry`'s guards; a submit
  after reap is refused and writes nothing; concurrent sweep and heartbeat do
  not deadlock.

## Out of scope

- The manager's Stop button for a prep whose lease has **not** yet expired —
  that is us-103.3, and it is what covers the two-hour window this story
  cannot.
- The runner re-adopting a prep it was holding before a restart — us-103.2.
- Any Workbench surface — us-103.4.
- Shortening the two-hour lease or making release prep heartbeat faster: the
  lease length is not the defect, the missing sweep is.
- Auto-retrying a reaped release. The manager clicks Retry.
- Reaping stuck `deploying` releases (the UAT deploy pipeline has its own
  terminal branches in `deploy.py`); if that proves to strand releases too, it
  is its own story with its own evidence.
- Backfilling historical stuck rows — 2026.08.16.3 was already cleared by
  hand.

## Built (2026-08-16)

`db.reap_expired_release_preps` (apps/api/app/db.py) fails every `running`
prep whose `claim_expires_at` has passed, through the same
`_fail_release_prep` body `fail_release_prep` uses - refactored to run on a
caller's transaction so the sweep holds its row locks (`for update of p skip
locked`) across both writes. Wired to all three triggers: API startup and the
60-second liveness loop (apps/api/app/main.py), and `list_release_prep_pool`,
which now sweeps before listing.

**Verified.** The SQL was run end to end against the dev database with a prep
built to the incident's own shape (claimed 156 minutes ago, lease 26 minutes
expired):

- the select found it and reported `held_minutes 156`, `lapsed_minutes 26`;
- the prep landed `failed` with "the agent stopped reporting: the claim on
  this release prep expired 26 minute(s) ago...";
- the release landed `failed` carrying the same sentence;
- in-flight releases for the project went to **0**, so a fresh cut is possible;
- `notes_written_at` stayed null and no prep remained queued or running - both
  of `/retry`'s guards satisfied, so Retry is the one-click way out;
- the us-103.5 freeze lifted in the same instant (`issue_dispatch_refusal`
  returned null), which is AC6 of that story proven from this side.

The dev rows were then removed and the release restored to `queued` exactly as
found. Essential API suite: 1925 passed.

**Not verified.** `tests/test_release_prep_reaper_sql.py` (10 tests: the reap,
the live prep it must not touch, the heartbeat rescue, the four non-running
statuses, the in-flight release, retry's guards, idempotency, and held-prep
visibility) is Full QA and **was not run** - this machine has no
`DATABASE_URL`, so `--full` and Essential cover the same ground here. The
concurrency claim in AC1 (safe alongside a live claim/heartbeat/submit) rests
on `skip locked` and is untested. Startup and 60-second-loop wiring is
verified by reading, not by running the API.
