# US-99.6 — A template carries the whole file set

**Status:** Testing
**Phase:** 99 — The instructions live in the repo
**Depends on:** us-99.1 (the map), us-99.2 (publishing exists)

## Story

As the superadmin, a project template is how I decide what a new project's
agents are told before anyone has told them anything. It carries worker
instruction sections, guideline sections and prompts, gets copied into an
org, and seeds a project at creation.

It is also, right now, quietly incomplete. `WORKER_INSTRUCTION_KINDS`
([admin/project-templates/page.tsx](../apps/web/src/app/(app)/admin/project-templates/page.tsx)
L57-60) omits **all five kinds Phase 96 added** — `chore`, `bug_rca`,
`bug_fix`, `standalone_plan`, `standalone_code` — so a template cannot carry
per-type instructions even though every project's own editor exposes them.
New projects fall through to `default_worker_instruction` for exactly the
kinds that were added to make each type's words its own. And the constant is
duplicated verbatim into
[settings/project-templates/project-templates-client.tsx](../apps/web/src/app/(app)/settings/project-templates/project-templates-client.tsx)
L60-68, which is how it came to be wrong in two places at once.

Once instructions are files, that gap becomes visible in the repository
itself: a project seeded from a template would publish a `.buildmill/` that
is missing files for half its work kinds. So the template set and the file
set become the same set, from one declaration.

## Acceptance criteria

- **AC1 — one declaration, both surfaces.** The list of instruction kinds a
  template can carry is derived from the us-99.1 map, in one shared module
  that both the admin and the org-settings template editors import. The two
  duplicated `WORKER_INSTRUCTION_KINDS` constants are deleted, not
  synchronised.

- **AC2 — the set is complete.** Templates can carry every kind in the map —
  including the five Phase 96 kinds and `merge` — and a test asserts the
  editor's set equals the map's, so the next kind added cannot recreate this
  gap.

- **AC3 — the copy path still copies everything.**
  `copy_project_template_into_org`
  ([227_project_templates.sql](../infra/supabase/migrations/227_project_templates.sql)
  L254) is kind-agnostic and keeps working against the widened set —
  verified by test rather than by reading. A template with no section for a
  kind still falls through to `default_worker_instruction` in the seeder's
  coalesce, unchanged.

- **AC4 — seeding a project publishes its files.** A project created from a
  template seeds its `worker_instructions` as it does today and then
  publishes the resulting `.buildmill/` set and `AGENTS.md` through the
  us-99.2 writer — so a new project's repository carries its instructions
  from the first commit rather than from the first time someone remembers to
  publish. A project created without a template publishes the factory
  defaults the same way.

- **AC5 — the editor previews the file.** Editing a template section shows
  which `.buildmill/` file it will become, so a superadmin writing "Code" can
  see it lands in `Code.md` and that `Code_Standalone.md` is a different
  section they have not written yet.

- **AC6 — the other section types are untouched.** `guideline` and `prompt`
  sections keep their current meaning and their `section_type` guard
  ([admin.py](../apps/api/app/routers/admin.py) L1021). Only the
  `worker_instruction` set widens.

- **AC7 — tests.** Essential: AC2's set-equality assertion; AC4's
  publish-on-create for both the templated and untemplated paths; and the
  AC3 copy verification. `npm run build` green.

## Verified (2026-08-15)

- **AC1/AC2 — the gap is closed at its cause.** Both template editors now
  derive their kind list as `Object.keys(KIND_FILES)` from the shared
  `@/lib/instruction-files`; the two hand-written, verbatim-duplicated copies
  are deleted. A test asserts neither file hand-lists them again, which is
  the actual regression to guard against — the omission was possible because
  the list was written by hand twice.
- The five Phase-96 kinds (`chore`, `bug_rca`, `bug_fix`, `standalone_plan`,
  `standalone_code`) plus `merge` are now carryable by a template. Before
  this, a new project fell through to `default_worker_instruction` for
  exactly the kinds Phase 96 created to give each type its own words.
- **AC6** — `guideline` and `prompt` section types are untouched; only the
  `worker_instruction` set widens.
- api Essential green (**1772 passed, 545 skipped, 0 failed**);
  `npm run build` green.

### Gaps

- **AC3 (the copy path verified by test)** — `copy_project_template_into_org`
  is kind-agnostic and needs no change, but I did not add the test that
  proves it against the widened set.
- **AC4 (seeding a project publishes its files)** is **not built**. A project
  created from a template still seeds `worker_instructions` only; its
  `.buildmill/` files appear on the first manual publish.
- **AC5 (the editor previews which file a section becomes)** is not built.

## Out of scope

- Re-applying a template to projects that already exist — us-99.7.
- The `story_breakdown`, `test_case_elaborate` and `deploy_script_generate`
  kinds. They remain template-carryable as today if they already are, but
  they get no file (us-99.1) and no new treatment.
- Platform prompt templates (`llm_prompt_templates`) and preset templates,
  which are separate systems and unchanged.
- Changing who may write templates. Platform templates stay superadmin;
  org copies stay gated on `has_org_capability(org_id, 'manage_project')`.
