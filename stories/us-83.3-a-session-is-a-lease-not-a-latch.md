# US-83.3 — A session is a lease, not a latch

**Status:** Testing
**Phase:** 83 — Interactive agent stability
**Dependencies:** us-83.2 (the watchdog lives in the shared session engine)

## Story

As the operator, I want a session that goes quiet or whose CLI dies to release
its agent on its own, so that an abandoned conversation is a closed row —
never an agent silently held forever.

## Context

Two liveness promises are currently unkept:

1. **The 30-minute idle close does not exist.** The UI states "closes itself
   after 30 minutes of silence" (`IDLE_TIMEOUT_MINUTES` in
   apps/api/app/routers/agent_sessions.py), and `db.idle_agent_sessions` is
   written to find the victims — but it has **zero callers**. Nothing sweeps.
   A forgotten session holds its agent indefinitely, the one-live-session
   unique index then refuses every new session on that worker, and
   `session_host.is_busy()` keeps the work loop from claiming runs.
2. **A dead CLI is a zombie host.** Nothing watches the session's child
   process. If it crashes, `HOSTS`/`LIVE` keep their entries, `is_busy()`
   stays true, and (per 1) not even a sweep would ever clean it up. Runs have
   the opposite discipline — lease headroom guarantees a dead run reports
   with time to spare.

The live handshake (grok 1.0.0) additionally declares a session `close`
capability the host never uses — today's close is a bare process kill.

## Acceptance criteria

1. The api liveness sweep (apps/api/app/main.py `_liveness_sweep`, 60s
   cadence) closes sessions idle past `IDLE_TIMEOUT_MINUTES`, through the
   same path the Close button uses: `session.close` to a live worker, then
   `finish_agent_session`. Idle means the *agent* went quiet
   (`last_active_at`), matching the existing UI copy.
2. Runner watchdog: when the session's ACP read loop ends or the child exits,
   the host closes itself — `HOSTS`/`LIVE` popped, the server notified so the
   row finishes as `failed` with the stderr tail, `is_busy()` false — without
   waiting for anyone to ask. Test: kill the child; the agent claims runs
   again and a new `session.open` on the same worker succeeds.
3. Graceful close first: when the agent declared a close capability in
   `initialize`, `session.close` asks the agent to close the ACP session
   before terminating the process; measured against the real CLI, with a
   fall-back to the current kill when the capability is absent or the close
   times out.
4. The sweep and the watchdog are both idempotent against each other and
   against a manager's own Close click (closing a closed session stays the
   success case).

## Out of scope

- Changing the timeout value or making it configurable.
- Multiple concurrent sessions per agent (the unique index stands).
- Transcript retention/cleanup policy for `agent_session_events`.

## Verification (2026-08-12, built)

**Verified:** the sweep closes idle sessions through the button's own path
(live worker asked, dead worker skipped, row closed either way — including
when the socket call throws), pinned by api tests; the watchdog fires
`on_disconnect` exactly once on an unrequested stream end and never on a
deliberate close (client tests), and `_reap` frees HOSTS/LIVE, reports
`session.failed` with the stderr tail, and is idempotent against a close
that won the race (host tests). **Graceful close measured live** against
grok 1.0.0 in this session: `session/close {sessionId}` answered
`{"_meta": {"x.ai/closeOutcome": "closed"}}`, and the capability is declared
as `sessionCapabilities.close = {}` — an empty object, so the check is
presence, not truthiness (pinned by test).

**Not verified (UAT):** the sweep firing inside a live API process on its
60-second cadence, and a real kill of a session CLI on a pool machine
freeing the agent (watch `is_busy` release and the row flip to failed).
