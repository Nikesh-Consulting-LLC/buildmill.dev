# US-87.6 — The API keeps its connections

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** nothing (`apps/api/app/db.py`)

## Story

As anyone waiting on the API, every database helper opens a brand-new
Postgres connection, runs one statement, commits, and closes it.
`_connect(settings)` appears at **214 call sites** in `db.py` and there is
no pool. A request handler that calls three helpers pays three connection
handshakes to Supabase before it does any work.

The evidence is in the database: `SELECT * FROM pgbouncer.get_auth($1)` at
**143,388 calls**. That statement exists only because connections keep being
established.

`record_api_request` is its own instance of this — a fresh connection per
request for a single insert, **584,613 times**. It is correctly off the
response path (`asyncio.create_task` + `to_thread`), so it adds no latency,
but it doubles connection count and takes a threadpool slot per request,
which under load starves every other synchronous database call in the
process.

## Acceptance criteria

- **AC1 — one pool, shared.** `db.py` acquires connections from a single
  `psycopg_pool.ConnectionPool` sized from settings, created at startup and
  closed at shutdown. `_connect` becomes a context manager that leases from
  the pool; the 214 call sites keep their current shape.
- **AC2 — the guarantees survive.** The 15 s `statement_timeout`, the 5 s
  connect timeout, `dict_row`, and the `_TimedConnection` wrapper that feeds
  `db_ms` are all preserved. Per-request timing must still be attributable.
- **AC3 — transactions are not leaked between requests.** A connection
  returning to the pool is rolled back / reset; no request may observe
  another's session state (`search_path`, `role`, temp settings). This is
  the defect a pool most easily introduces.
- **AC4 — request logging batches.** `api_request_log` rows are buffered and
  written in batches (or on a small interval) on one pooled connection
  rather than one connection per request. Losing the tail of the buffer on
  process exit is acceptable for a diagnostic table; blocking a request is
  not.
- **AC5 — the pool is sized for the pooler.** The pool size is set against
  Supabase's connection limits with the runner, the web app, and the API all
  counted; the story records the arithmetic. Exhausting the database's
  connections is a worse outage than the churn it replaces.
- **AC6 — proof.** Essential suite green (`cd apps/api && python -m pytest`,
  ~30 s, zero failures is the baseline). `pgbouncer.get_auth` call rate
  re-measured after a representative day and recorded.

## Out of scope

- Making the API's database calls async — the pool is the win; `asyncio`
  conversion is a much larger change with its own story.
- The runner's own connections.
- Changing what `api_request_log` records (us-87.8 covers its retention).

## Verification record

Built 2026-08-12 on `phase-87-performance`. No migration. Adds
`psycopg-pool>=3.2` to `apps/api/requirements.txt` -- the deploy's
`pip install -r` picks it up.

**Verified:** Essential suite green (exit 0, zero failures, two full runs).
18 new cases in `tests/test_pool_and_heartbeat.py`, and
`tests/test_request_timing.py` updated to the new contracts -- it pinned the
two things this story deliberately changed. `app/pool.py` is one pool per
`DATABASE_URL`, and all five `_connect` definitions -- `db.py`, `deploy.py`,
`notify.py`, `agent_provision.py`, `workspace_prep.py` -- now lease from it, so
the whole API has a single bounded budget instead of five independent sources
of new connections.

Three things are load-bearing and tested:

- **`prepare_threshold=None`.** psycopg3 auto-PREPAREs a query after a few
  executions on one connection. Short-lived connections never reached that;
  pooled ones do -- and this API reaches Postgres through Supabase's pooler
  (143,388 `pgbouncer.get_auth` calls is the proof). Behind a transaction-mode
  pooler that surfaces as "prepared statement already exists" at random under
  load. A test asserts the setting.
- **`DISCARD ALL` on return to the pool** (AC3), so no `search_path`, `role`,
  temp table or cursor crosses between requests. A test asserts the reset hook
  runs it. This one would be a security bug, not a performance one.
- The 15 s statement timeout, 5 s connect timeout and `dict_row` all survive;
  a test asserts each.

**Pool sizing (AC5):** `max_size=10` per API process. The web app talks to
Supabase over PostgREST (HTTP), not Postgres, so it consumes no direct
connections; the runner reaches the database only through this API. One
`factory-api` process therefore accounts for the whole direct-connection
budget, and 10 is deliberately well under Supabase's pooler limit. Configurable
via `db_pool_max_size` -- raise it with the whole fleet counted, never because
a graph looked busy.

**Not verified -- read this before releasing:**

- **The pool has never opened a real connection.** Essential blocks outbound
  network by design, so every test here exercises the pool's logic with the
  database faked. Nothing has proven it works against Postgres, let alone
  through Supabase's pooler, let alone under concurrency.
- **Which pooling mode prod uses was not confirmed.** `prepare_threshold=None`
  makes the answer not matter, which is why it is set -- but the assumption is
  untested.
- Pool saturation behavior (a caller waiting `db_pool_timeout_s`, then erroring)
  has not been observed.
- The first Essential run after this change **hung past 600 s**: the pool waits
  for a slot where a direct connect used to fail instantly, so every reaper in
  the app's lifespan blocked on each TestClient construction. Fixed by giving
  the test settings a 0.1 s acquire timeout and `min_size=0`. Worth carrying
  forward -- the same shape in production is a database that is unreachable
  rather than saturated, and it will wait `db_pool_timeout_s` before saying so.
