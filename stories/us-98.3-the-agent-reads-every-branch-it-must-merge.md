# US-98.3 — The agent reads every branch it must merge

**Status:** New
**Phase:** 98 — Many branches, one landing
**Depends on:** us-98.2 (the branch list exists and rides `input_context`)

## Story

As an agent holding a merge run, every repo-reading tool I have serves **one
ref**. `get_workspace` resolves the run's own working branch or the default
branch and gives me that; `get_repo_tree` and `read_repo_file` take a `ref`
but are scoped to the claimed run's repository at whatever ref the tool
decides is legitimate. A merge is the first kind of work that is inherently
about several refs at once, and I cannot do it by reading one.

The obvious shortcut — `get_project_workspace(project_id, ref)`, which
already takes an arbitrary ref — is the wrong door: it is gated on the
worker's `no_claim_checkout` capability, which is a *standing* permission
granted for browsing, not something a merge run should require. A worker
that can be trusted to land a merge should not also have to be trusted to
read any ref of any project it can see.

So the claim itself becomes the authority. A merge run declares its branches
at dispatch (us-98.2); the reading tools accept any ref **in that declared
set**, plus the base, and refuse everything else. The permission is exactly
as wide as the job and no wider, and it expires with the claim.

## Acceptance criteria

- **AC1 — the brief says what to merge.** `get_work_context` for a `merge`
  run renders a markdown section naming the base branch and its head, then
  each branch to land with its head sha, in the order the manager listed
  them. The structured mirror carries the same as data. The instruction text
  resolved for the run is the `merge` instruction from us-98.1.

- **AC2 — the claim licenses the declared refs, and only those.**
  `get_workspace` accepts an optional `ref`. For a merge run it is honoured
  when — and only when — the ref names a branch in the run's declared list
  or the base branch; anything else refuses with a message naming what the
  run is allowed to read. For every other run kind the parameter is either
  absent or refused, so no existing run gains reach it did not have.
  `get_repo_tree` and `read_repo_file` take the same restriction on the same
  set.

- **AC3 — the delta cache is not corrupted by multi-ref reads.** The
  workspace delta machinery records the last delivery per run
  (`record_workspace_delivery` / `get_workspace_delivery`) and computes the
  next one by comparing against it. Fetching branch B after branch A must
  not make the factory believe the worker holds a tree it does not. Either
  deliveries are tracked per `(run, ref)`, or merge-run fetches bypass the
  delta path and always answer full — whichever is chosen is stated in the
  code and pinned by a test, because the failure it prevents is a silently
  wrong tree rather than an error.

- **AC4 — the ceiling is honest per branch.** Each branch's zip is subject
  to the same `workspace_zip_max_bytes` ceiling
  ([config.py](../apps/api/app/config.py) L52) and, over it, answers the
  same message pointing at the git remote. A merge whose branches exceed the
  ceiling is a git-native job, and the refusal says so rather than
  half-serving it.

- **AC5 — the tool surface stays pinned.** Any new or changed tool is added
  to `test_all_tools_listed` and, if read-only, to `_READ_ONLY_TOOLS`
  ([test_factory_mcp.py](../apps/api/tests/test_factory_mcp.py) L82, L117) —
  the annotation test asserts that set exactly. The server `instructions`
  blob ([factory_mcp.py](../apps/api/app/factory_mcp.py) L95-183) and
  [interface-catalog.md](../docs/application/interface-catalog.md) are
  updated together.

- **AC6 — tests.** Essential, with faked GitHub reads: the AC2 refusal for
  an undeclared ref, on all three tools; the AC2 refusal for a non-merge run
  passing a ref; the AC1 brief shape; and the AC3 delta decision. No test
  reaches the network.

## Out of scope

- Anything the agent hands back — us-98.4 and us-98.5.
- Changing `get_project_workspace` / `get_project_tree` /
  `read_project_file` or the `no_claim_checkout` capability. They keep their
  current meaning; this story deliberately does not route merge reads
  through them.
- Doing any merging server-side. The factory serves trees; the agent
  decides. There is still no three-way merge anywhere in the api.
- Repositories above the snapshot ceiling. AC4 refuses them by name; the
  git-native transport for merge runs is not built here.
