# US-107.3 — An agent capability has an icon

**Status:** Testing
**Phase:** 107 — Fixed is an outcome, and nothing waits forever
**Depends on:** US-77.1 (`AGENT_ROLES` — the four roles), us-61.2 (the grouped checkboxes), US-68.4 (`ActionGlyph`), [us-107.2](us-107.2-nothing-sits-queued-forever.md) (the `NoCapableWorker` treatment this sits beside)

## Story

As the manager, I want each agent capability to have one icon used everywhere,
so that I can see what an agent can do without opening it, and see what an
action will need before I click it.

Two concrete complaints, one cause:

- **"Right now I have to go inside to see what they are capable of."** The team
  roster showed a name, an `agent` pill and a module — never what the agent
  actually claims. That lives in `runner_config.enabled_kinds`, two pages away.
- **Every routing button was a rocket.** `ActionGlyph` gave `Rocket` to every
  dispatch, so "send it for planning" and "ship it" looked like the same act,
  and the row hinted nothing about which kind of agent has to be in the pool
  for the click to go anywhere.

## Design

### The vocabulary is the four roles, which already existed

US-77.1 settled that what an agent does is **four roles, not ten run kinds** —
`AGENT_ROLES`, the four checkboxes on its settings page. That is already the
manager's vocabulary; it simply had no picture.

| role | icon | why |
|---|---|---|
| Planning | `ClipboardList` | a plan is a checklist written before building |
| Programming | `Code` | the literal thing |
| Testing | `Bug` | what a test run is hunting |
| Deployment | `Rocket` | ship it |

### Where the icons live, and why not on `AGENT_ROLES`

`components/role-icon.tsx`, not `lib/agent-roles.ts`. That module is pure and
unit-tested by the node runner, which cannot parse JSX and should not be
resolving `lucide-react` to check a mapping. The test file pins the *contract*
the mapping depends on instead — exactly four roles, and every routed run kind
resolving to one — because `iconForKind` goes through `roleOfKind`, and a kind
belonging to no role silently renders no icon and falls back to a rocket.

### A run kind gets its icon from its role, never its own

`iconForKind("plan")` resolves through `roleOfKind`, so a kind cannot grow a
glyph that disagrees with its role's. Ten kinds, four icons, one source.

### The action button says which capability it needs

`TodoItem` gains `runKind`, and `ActionGlyph` prefers its icon over the generic
rocket. The kind is not guessed:

- **Triage rows** — `triageAction` already encodes what `dispatch_kind_for`
  (migration 255) picks: story→`plan`, bug→`plan` (an RCA, us-96.5),
  chore→`code` (no planning phase, us-96.1), feature→`prd`. It now returns that
  kind rather than only the label.
- **Dispatch, `planned`** — always `code`. An approved plan codes next
  whatever the type.
- **Dispatch, `ready`** — reuses `triageAction(type).kind`, because it is
  **not** always `plan`: a chore dispatches straight to code.
- **`failed` re-dispatch** — deliberately left unset. It replays whatever kind
  failed, which the row does not know, and a wrong glyph is worse than a
  generic one. It keeps `RotateCcw`.

### All four, always, on the roster

The team row draws every capability and greys the ones the agent lacks, rather
than listing only what it has. "What can it *not* do" is usually the thing
being looked for, and a filtered list silently answers half the question.

`null` `enabled_kinds` means **every** role (the us-53.4 rule: a never-saved
agent is unrestricted, not benched) and must not collapse to `[]` on the way
through, which would grey out all four for an agent that does everything. A
test pins that.

People and headless MCP workers have no `runner_config`, so they get no icons
at all rather than four grey ones implying they are a benched agent.

## Acceptance criteria

- **AC1 — one icon per capability, everywhere.** Planning/Programming/Testing/
  Deployment render as clipboard/code/bug/rocket on every surface below.
- **AC2 — the roster answers it without a click.** Each agent row shows all
  four, the ones it lacks greyed, each with a tooltip and an accessible label
  saying enabled or not enabled.
- **AC3 — a routing button wears what it needs.** A Dispatch/Triage row's
  action button shows the capability icon of the run it would create — planning
  for a story, code for a chore, code for an approved plan, PRD for a feature.
- **AC4 — an unknowable kind is not guessed.** A `failed` re-dispatch keeps its
  generic glyph rather than showing a possibly-wrong capability.
- **AC5 — the checkboxes match.** The role checkboxes on the settings page and
  in the Add Agent wizard carry the same glyph, greyed when unchecked.
- **AC6 — an unrestricted agent reads as capable.** `enabled_kinds` null shows
  all four lit, not all four greyed.

## Out of scope

- Adopting the icons on every surface that names a run kind. The Workbench
  routing buttons, the team roster, the settings page and the wizard have them;
  **the factory queue, the runs page, the activity feed, the parked-runs card
  and the in-progress section still show text alone.** `iconForKind` is
  exported and ready for them — this is coverage, not design.
- Changing what any role grants. Pure presentation; no migration, no API.
- Replacing the `TypeBadge` (work-item type: feature/bug/chore/story). That is
  a different axis — what the *work* is, not what an *agent* does — and
  conflating them would make `Bug`-the-work-type and `Bug`-the-testing-capability
  the same glyph in the same row. **They are already both `Bug`**, which is a
  real collision worth watching, though they do not currently co-occur.

## Built (2026-08-16)

Web only; no migration, no API change.

- `components/role-icon.tsx` **(new)** — `ROLE_ICONS`, `iconForKind`,
  `RoleIcon`, `RoleCapabilities`.
- `lib/agent-role-icons.test.ts` **(new)** — 6 tests pinning the contract:
  four roles, every routed kind has one, plan/code/test/deploy map where the
  manager expects, and null-means-all.
- `workbench/triage-action.ts` — returns the run `kind` it dispatches.
- `workbench/data.ts` — `TodoItem.runKind`, set on Triage and both Dispatch
  branches.
- `workbench/waiting-list.tsx` — `ActionGlyph` prefers the capability icon.
- `team/page.tsx` + `team-view.tsx` — `enabled_kinds` loaded per agent and
  rendered as four icons on the row.
- `team/[principalId]/settings/page.tsx`, `team/add-agent-wizard.tsx` — the
  glyph beside each role checkbox.

**Verified.** `npm run build` compiles and type-checks; `npm run test:web` 231
passing (+6). The role↔kind mapping was read out of `AGENT_ROLES` rather than
restated, and the dispatch-kind rules out of `triageAction`, which itself
derives from migration 255.

**Not verified.** Nothing was rendered — no `apps/web/.env.local` in this
checkout, so no page was loaded and **no icon has been seen**. Every acceptance
criterion here is visual, which makes this the story in Phase 107 least served
by a passing type-check: AC2 and AC3 in particular need eyes on a real roster
and a real Dispatch row. Contrast is a specific risk — the greyed state is
`text-muted-foreground/30`, chosen to read as absence rather than as a
rendering fault, and that judgement has not been checked against either theme.
