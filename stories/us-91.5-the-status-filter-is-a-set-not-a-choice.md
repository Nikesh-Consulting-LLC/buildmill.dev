# US-91.5 — The status filter is a set, not a single choice

**Status:** Completed
**Phase:** 91 — Usability: the dashboard reads like the job
**Depends on:** nothing

## Story

As the manager, Work Items opens showing everything ever created — including
every merged and done item, which is most of them and none of what I am
about to act on. The Status filter cannot help: it is a radio group, so it
answers "show me exactly one status" when the question is "show me
everything except the finished ones".

Make it a checkbox set, and open with **merged** and **done** unchecked. The
first screen becomes live work; finished work is one checkbox away and its
absence is stated, not silent.

## Acceptance criteria

- **AC1 — the filter is multi-select.** `StatusFilter` in
  [issue-views.tsx](../apps/web/src/app/(app)/issues/issue-views.tsx)
  becomes a checkbox menu (`DropdownMenuCheckboxItem`, already in
  [dropdown-menu.tsx](../apps/web/src/components/ui/dropdown-menu.tsx)) over
  `ISSUE_STATUS_ORDER`. Checking and unchecking each status filters
  independently; the menu stays open while I check several.
- **AC2 — merged and done start unchecked.** Every other status starts
  checked. This is the default on a first visit and after any reset.
- **AC3 — the trigger says what is hidden.** The closed pill never lies by
  omission: with the default set it reads something like `All but merged,
  done`; with everything checked, `All statuses`; with a small selection,
  the selection. A manager who cannot find an item must be able to see why
  from the toolbar without opening the menu.
- **AC4 — two one-click escapes.** The menu offers `Select all` and `Clear`
  (or equivalent), because reaching "everything" by ticking eleven boxes is
  how a filter becomes an obstacle.
- **AC5 — the choice sticks.** The selection persists across navigation and
  reload the same way the layout preference does
  (`localStorage`, beside `ISSUES_LAYOUT_KEY`), so the manager sets it once.
- **AC6 — every lens obeys it.** Outline, table and board all filter on the
  same set — the board's Done column simply empties under the default rather
  than showing rows the toolbar claims are hidden.
- **AC7b — an epic with nothing left is not shown.** *(added after UAT.)*
  The outline groups project → epic → items; with merged and done unchecked,
  a finished epic rendered as a header over nothing. An epic whose items the
  filter hid is dropped entirely, so the page shortens the way the filter
  implies. A project left with no bucket at all says "Nothing matches these
  filters" rather than "No work items in this project", which would be false.
- **AC7 — the type filter is untouched.** It stays single-select, and the
  two filters still compose (type AND status).
- **AC8 — the filter logic has a test.** A `.test.ts` beside the pure
  filtering helper covers: default hides merged and done, an empty set shows
  nothing (or is prevented — pick one and pin it in the test), all-checked
  equals no filtering.

## Out of scope

- Changing what the hub *loads* — this filters the already-fetched set, and
  `HUB_PAGE_SIZE` paging is unchanged. (If the default filter makes "Load
  200 more" feel wrong because most of what it loads is hidden, that is a
  follow-on story, not this one.)
- The abandoned-items view, which has its own list.
- Filtering by status anywhere else (dashboard, releases, tests).

## Verified (2026-08-14, localhost against build-mill-dev)

**UAT round 2:** Demo's "Epic 1 · Basic App Setup" — eight items, all merged —
no longer renders under the default filter; it survives only in the payload
that feeds the epic picker, which is where it belongs. The four epics with
open work still show, with their counts.


- Work Items opens with the pill reading **"All but merged, done"** and no
  merged or done rows in the list.
- The selection persists under `sf-issues-status-filter`, beside the layout
  preference.
- Eight unit tests (`issue-status-filter.test.ts`) pin the default, the
  all-checked case, the empty-set rule (shows nothing, says "No statuses"), the
  trigger's wording, and stored-value parsing.

**Not exercised**: opening the menu and ticking boxes by hand — the browser
pane would not composite, so Base UI's popover could not be driven with real
pointer events. The logic behind it is what the unit tests cover.
