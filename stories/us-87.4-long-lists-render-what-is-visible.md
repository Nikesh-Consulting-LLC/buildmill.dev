# US-87.4 — Long lists render what is on screen

**Status:** Testing
**Phase:** 87 — The app gets fast
**Depends on:** us-87.3 (the list ships titles, not bodies)

## Story

As the manager with a workspace of thousands of work items, the Outline,
Board and Table lenses each build a DOM node for every row they are given.
There is no virtualization anywhere in `apps/web` — no `react-window`, no
`@tanstack/react-virtual` in `package.json` — so the browser lays out and
paints the entire set, and every realtime update re-reconciles all of it.
Typing in the search box does this on each keystroke.

Even with the payload trimmed and paginated, a 200-row Table with per-row
badges and menus is a slow first paint and a janky scroll. Past ~500 rows
the tab stops being usable.

## Acceptance criteria

- **AC1 — the three lenses skip what is off screen.** Outline, Board and
  Table lay out and paint only the rows in (and near) the viewport, and the
  initial paint does not grow with the row count.

  *Amended during implementation (2026-08-12).* This originally said
  "virtualize", meaning JS windowing. Reading the Outline showed why that is
  the wrong tool: it is a nested tree (project → epic → feature → story) with
  per-tier collapse state and inline actions, and flattening it into a
  virtualizer's row model is precisely where grouping, keyboard navigation
  and deep-link scrolling break — on the DEFAULT lens. CSS containment
  (`content-visibility: auto` + `contain-intrinsic-size`) removes the same
  cost, keeps every row a real DOM node, and therefore cannot break any of
  those things; it also keeps in-page find working, which AC4 below had
  conceded as an acceptable loss. What it does not remove is React's
  per-row reconciliation — bounded instead by us-87.3's 200-row page. If a
  future measurement shows reconciliation is the bottleneck, windowing the
  flat Table lens alone is the follow-up, and the tree stays as it is.
- **AC2 — grouping survives.** The Outline's epic → feature → story nesting
  and the Board's columns still group correctly under virtualization;
  collapsed groups cost nothing.
- **AC3 — search is not a re-render storm.** Typing in the hub search
  debounces and does not re-render the whole list per keystroke.
  *Already true:* `IssueSearchInput` has debounced at 300 ms since US-2.11
  and only navigates when the trimmed query actually changes. Verified, not
  rebuilt.
- **AC4 — nothing regresses in behavior.** Selection, keyboard navigation,
  deep links to an item, and the "showing N of M" affordance from us-87.3
  all still work. Ctrl+F within the page keeps working too — the containment
  approach in AC1 leaves every row in the DOM, so the loss this AC was
  prepared to accept does not happen.
- **AC5 — proof.** Measured time-to-interactive and scroll frame timing for
  `/issues` at 1,000+ items, before and after, recorded in the story.

## Out of scope

- The work-item detail page.
- Any other long list in the app (Runs, Activity, Reports) — worth the same
  treatment later, but this story proves the pattern on the hub first.
- Server-driven infinite scroll; page-size + load-more from us-87.3 is the
  fetching model.

## Verification record

Built 2026-08-12 on `phase-87-performance`. No migration.

**Verified:** `npm run build` compiles clean, and both utilities are present in
the emitted CSS -- `.list-row{content-visibility:auto;contain-intrinsic-size:auto 36px}`
and `.list-card{...}`. That check matters: a Tailwind v4 `@utility` that
silently fails to generate looks identical in the source. Applied to
`OutlineRow`, the table body rows, and `BoardCard`. AC3 needed no work and was
verified rather than rebuilt: `IssueSearchInput` has debounced at 300 ms since
US-2.11 and only navigates when the trimmed query changes.

AC1 was amended during implementation -- see the AC itself for why windowing
was the wrong tool for a nested, collapsible tree.

**Not verified (UAT):**

- **AC5's frame timing and time-to-interactive were not measured.** No
  1,000-item workspace exists yet (us-87.10).
- Not observed in a browser at all, in any lens, light or dark.
  `content-visibility` is well supported, but the `contain-intrinsic-size`
  placeholder heights (36 px rows, 84 px cards) are estimates -- if they are
  far off, the scrollbar will jump as rows are realized. **That is the specific
  thing to watch in UAT**, and it is a one-line fix if it looks wrong.
